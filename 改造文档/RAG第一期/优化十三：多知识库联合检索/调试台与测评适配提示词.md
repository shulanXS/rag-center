# 调试台与测评适配提示词

点击此处可复制本篇提示词

后端多库检索上线后，调试台仍是单库选择框，eval 脚本也只认 `kb_id`，意味着多库能力只能靠 curl 验证。这篇补上两个缺口：前端检索页改成 Checkbox 多选，eval 脚本支持 `kb_ids` 格式，让多库检索能融入现有的调试和测评流程。

## 使用场景

这份提示词用于后端多库并行召回和 RRF 融合完成后，接入调试台和离线测评两个界面。前端只改检索页，其他页面不动；eval 脚本小改兼容 `kb_ids`，增加几条跨库 golden case。

### 一、调试台检索页改造

**检索范围区**，原来是一个 `kb_id` 文本输入框，改为从 `GET /knowledge-bases/tree` 拉取当前 tenant 的知识库列表并展示为 Checkbox 多选：

```
┌─ 检索范围 ─────────────────────────────────────┐
│  ☑ 电商规则库       kb_ecommerce               │
│  ☑ 客服知识库       kb_customer_service         │
│  ☐ 商品合规库       kb_compliance               │
└────────────────────────────────────────────────┘
```

- 至少勾选一个库才允许提交，否则提示「请选择至少一个知识库」
- 从列表页「去检索」跳转时，URL 携带的 `kb_id` 对应的库默认勾选，用户可在此基础上再勾选其他库
- 勾选一个库时传 `kb_id`（兼容旧格式）或 `kb_ids: [one]`；勾选多个时传 `kb_ids: [...]`

**召回结果展示**：每条 chunk Card 增加 Badge 显示来源库，取 `kb_name` 或 `kb_id` 前 8 位。Badge 建议用不同底色区分不同库，便于目视判断多库结果分布。

**运行摘要区**只读展示多库相关字段：

```
mode=hybrid | top_k=5 | 联查 2 个库 | 融合方式: rrf | 服务端耗时 320ms
```

**plan 提示**：若 retrieve 返回 `20013`，在选择框旁展示「当前套餐最多支持 N 个库联合检索」，引导用户减少勾选数量。

### 二、离线测评脚本适配

**eval dataset 格式扩展**，`cases` 里的每条记录支持 `kb_ids` 字段，兼容旧的 `kb_id`：

```json
{
  "name": "multi_kb_retrieval",
  "cases": [
    {
      "id": "cross_kb_refund_vip",
      "question": "退款时限和会员补偿标准各是什么？",
      "kb_ids": ["<ecommerce_kb_id>", "<customer_service_kb_id>"],
      "ground_truth": "用户可在订单完成后 7 天内申请退款；会员等级不同补偿积分比例不同，具体见会员权益说明。"
    }
  ]
}
```

`scripts/run_retrieval_eval.py` 小改：读 case 时 `kb_ids = case.get("kb_ids") or [case["kb_id"]]`，请求 body 传 `kb_ids`；report 里每条 case 记录 `multi_kb: true/false`。

### 三、新增跨库 golden case

在 `eval/datasets/` 新增 `multi_kb_cases.json`，或合并进 `ecommerce_retrieval.json`，增加 2～3 条必须跨库才能答全的测例：

| question | kb_ids | ground_truth 要点 |
|----------|--------|-------------------|
| 退款时限和会员补偿标准各是什么？ | ecommerce + customer_service | 各库各覆盖一个关键事实 |
| 满减规则和客服工单处理时效？ | ecommerce + customer_service | 跨域信息互补 |

这类 case 的价值在于：单库 retrieve 只能答对一半，多库 retrieve 的 `context_recall` 应明显更高，用数字验证多库的效果增益。

### 四、Langfuse 导出脚本适配

`scripts/export_eval_cases_from_langfuse.py` 读取 trace metadata 时：优先取 `kb_ids`，回退取 `kb_id`，转为列表写入导出 case。字段名改动量极小，确认与第一篇提示词里 Langfuse metadata 的字段名一致即可。

### 五、文档

- `README` retrieve 小节增加 `kb_ids` curl 示例
- `docs/tenant-onboarding.md` 增加各 plan 对 `max_kb_per_retrieve` 的说明，并提示 free 租户只支持单库

### 六、边界说明

- 不改 `RagService` 核心，后端逻辑在上一篇完成
- 列表页树形结构、上传页不为本篇修改
- URL 不写入多库参数，多库选择只在页内维护状态

### 七、验收标准

- 调试台检索页展示当前 tenant 的知识库 Checkbox 列表
- 勾选两个库提交后，召回结果 chunk 带来源库 Badge，运行摘要有联查库数和融合方式
- 返回 `20013` 时页面有套餐提示，不崩溃
- 从列表页「去检索」跳转后，对应库默认勾选
- `run_retrieval_eval.py` 跑 `multi_kb_cases.json` 成功，report 有 `multi_kb: true` 标记
- 原 `ecommerce_retrieval.json` 单库 eval 回归，分数与改前基线无明显下降
- `export_eval_cases_from_langfuse.py` 导出的 case 含 `kb_ids` 字段
