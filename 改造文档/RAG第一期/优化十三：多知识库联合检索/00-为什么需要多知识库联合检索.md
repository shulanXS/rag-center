# 为什么需要多知识库联合检索

前面已经把单库内的索引质量做得比较扎实——结构化切块、Word/PDF 解析、混合检索、rerank。但真实业务里，一次问答往往不只涉及一个知识库。

## 当前的痛点

`/rag/retrieve` 接口目前只接受一个 `kb_id`。当用户的问题横跨多个知识库时，业务方只有两条路：

**自己调两次接口再合并**。先查一个库，再查另一个库，手动去重排序后交给 LLM。这意味着 Embedding 计算和检索执行都要做两遍，延迟和配额翻倍；融合逻辑各接入方写各的，无法在中台统一优化；Langfuse trace 也会分散成两条，遇到 bad case 难以复盘。

**把所有文档塞进同一个大库**。看起来简单，但词表、权限、文档运维的边界都变模糊——本来属于不同业务线的内容混在一起，更新其中一部分时也容易牵连其他内容。

这两条路都是把本该由中台解决的问题，推回给了接入方。

## 在中台支持多库联合检索

解决思路是让 `/rag/retrieve` 原生支持传入多个 `kb_ids`，中台并行查询各库，跨库融合排序后统一返回。调用方感知到的仍然是一次检索调用，只是返回的 chunk 里会带上来源库信息。

整个流程在已有管道里只在"召回"这一环节扩展：

```
用户 query
    ↓
query 处理（词表扩展 / LLM 改写）—— 与单库相同，不变
    ↓
【多库并行召回】—— 各库同时执行向量检索 + BM25
    ↓
跨库 RRF 融合排序
    ↓
rerank（可选）
    ↓
统一返回 chunks（每条带 kb_id / kb_name）
```

并行召回意味着查三个库的延迟和查一个库接近，而不是串行叠加。跨库用 RRF 融合，和单库内的 RRF 逻辑一致，不引入额外复杂度。

同时，多库能力也需要纳入套餐管控——一次检索最多可以查几个库，由租户的 Plan 决定，避免资源被无限消耗。

## 和单库检索的关系

多库联合检索和单库检索是正交的能力——**切块质量决定每个库的召回上限，多库联合决定检索范围**。两者一起具备，才能在复杂问答场景里给出完整的结果。

接口上也保持向后兼容：原有的单 `kb_id` 用法仍然支持，已有接入方不需要改代码。
