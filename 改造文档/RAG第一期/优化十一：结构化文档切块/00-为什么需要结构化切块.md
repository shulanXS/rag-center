# 为什么需要结构化切块

前面已经在检索侧做了不少工作——调试台、词表、query 改写、profile、RAGAS 离线测评已经比较完整。但这些都在检索侧发力，**索引侧还停在一个很初级的阶段**：无论上传什么文档，都按固定字符数滑动切块。

这一根基如果不对，检索侧再怎么调也有上限。

## 固定字符切块的问题

当前入库链路是这样的：

```
文档上传 → 把 content 当普通字符串 → 每 800 字切一块 → Embedding → 索引
```

这意味着文档里的标题、表格、段落对系统来说只是普通字符，系统完全不理解文档结构。这会产生几类典型问题：

**标题被切断**。切块边界落在 `## 退` 和 `款时效` 之间，这个 chunk 既不是完整的标题行，也没有对应的内容，检索到它等于检索到残片。

**跨节混入**。一个 chunk 从上一节末尾开始，延伸到下一节开头，内容本身就是两件不相关的事情混在一起，语义向量也因此变得模糊。用户问"退款时效是多少天"，召回的 chunk 里混着"特殊商品不支持退款"的内容，回答质量自然不稳定。

**表格被拦腰切断**。表格第一行是表头，第二行开始是数据。如果切块边界恰好落在第三行，后面那个 chunk 只有若干数据行，没有表头——语义完全丢失。用户问"满减和优惠券能否叠加"，答案在表格的某一行里，但那一行脱离了表头就读不懂。

这些问题在跑 RAGAS 时会有体现：`context_recall` 长期卡在某个水平，调 `top_k`、换 profile 都没用——根因在块本身就不完整，不是检索参数的问题。

## 结构化切块的思路

解决思路直接：**让切块边界跟着文档结构走，而不是跟着字符数走**。

文档有自己的逻辑结构——Markdown 有 `#`/`##` 标题层级，Word 有标题样式，PDF 有版面章节。这些结构本质上已经划定了"哪里该是一个完整语义单元"的边界，切块时直接复用这些边界，就能保证每个 chunk 对应一段完整的、语义独立的内容。

具体来说，结构化切块做两件事：

1. **按结构边界分节**：遇到 `#` 或 `##` 标题才 flush，保证 chunk 不跨章节；表格整体作为一个单元，不从中间切开
2. **在 metadata 里记录来源路径**：每个 chunk 带上 `heading_path`（如 `平台交易规则/退款时效`），让检索结果可溯源，也方便后续过滤

单节内容超过 `CHUNK_SIZE` 时，在节内做二次切，但绝不跨 `#`/`##` 边界。

## 做了之后有什么变化

切块质量提升会直接反映在检索效果上：

- **单个 chunk 语义更完整**：每个 chunk 对应一节或一张表，不再混入无关内容，embedding 向量更准确地代表这段内容的语义
- **表格类问题召回改善**：表格整体成块并保留表头，"叠加规则""收费标准"等问答场景 recall 明显提升
- **RAGAS 分数可归因**：reindex 之后重跑测评，精确率和召回率的变化能直接归因到切块改善，而不是和其他参数混在一起

同时，每个 chunk 的 `metadata` 里新增了 `heading_path` 和 `chunk_type`，调试台里能直接看到每条召回结果属于哪个章节，排查问题更直接。

## 适用范围

结构化切块不只对 Markdown 有效——**所有格式都需要按结构边界切，而不是按固定字符数硬切**。本质上这是两层独立的事情：

| 层 | 做什么 | 因格式而异？ |
|----|--------|-------------|
| **解析层** | 从原始文件提取文本和结构信息 | 是。Markdown 扫描语法轻量；Word 读标题样式；PDF 需要版面分析，重 |
| **切块层** | 按结构边界分节、表格保护、metadata 注入 | **否**。规则对所有格式一样 |

本期先用 Markdown 实现：样例数据（`data/ecommerce` 等）都是 Markdown，解析层几乎无需额外工作，改完可以立刻上传、检索、跑 RAGAS 验证效果。后续接入 Word/PDF 时，主要是**换解析层**——切块层的逻辑、metadata 结构、reindex 流程不需要重来。
