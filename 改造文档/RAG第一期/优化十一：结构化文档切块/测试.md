# 结构化切块与全量 reindex 测试验收

## 测试准备

PostgreSQL、Redis、Celery Worker、后端均已启动。准备两类测试文档：一份含多个 `##` 小节和三级标题的 Markdown，一份含 Markdown 表格的 Markdown。

## Markdown 标题切块测试

### 1. 准备测试文档

```markdown
# 测试知识库

## 第一节

这是第一节的内容，用于验证 heading_path。

### 1.1 子内容

这段三级标题下的内容应归入第一节。

---

## 第二节

这是第二节的内容，应与第一节分开切块。
```

### 2. 上传并等待索引完成

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/documents/upload \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{
    "kb_id": "<kb_id>",
    "title": "heading_test.md",
    "content": "# 测试知识库\n\n## 第一节\n\n这是第一节的内容。\n\n### 1.1 子内容\n\n三级标题下的内容。\n\n---\n\n## 第二节\n\n这是第二节的内容。"
  }'
```

轮询 `GET /documents/{document_id}` 直到 `status=SUCCESS`。

### 3. 查 chunk metadata

在 PostgreSQL 中查询，或通过调试台 retrieve 查看召回结果：

```sql
SELECT metadata->>'heading_path', metadata->>'chunk_type', LEFT(content, 80)
FROM chunks
WHERE document_id = '<document_id>'
ORDER BY metadata->>'chunk_index';
```

预期：

1. 至少 2 个 chunk，「第一节」和「第二节」分开，不在 `## 第` 中间截断
2. `heading_path` 分别为 `测试知识库/第一节`、`测试知识库/第二节`
3. `### 1.1 子内容` 下的内容在「第一节」的 chunk 里，没有单独成块
4. 无任何 chunk 的 content 只含 `---`

### 4. 检索验证

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/rag/retrieve \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{
    "kb_id": "<kb_id>",
    "user_id": "test",
    "query": "第一节内容",
    "profile": "balanced"
  }'
```

预期：Top 结果 content 来自第一节，不与第二节内容明显混杂。

## 表格专项切块测试

### 1. 上传含表格的文档

使用 `data/ecommerce/促销活动与优惠券使用规则.md` 或以下精简内容：

```markdown
## 叠加规则

以下为各场景叠加情况：

| 场景 | 是否可叠加 | 说明 |
|------|-----------|------|
| 满减 + 优惠券 | 否 | 同一订单只能选一种 |
| 会员折扣 + 券 | 是 | 需满足会员等级 |
| 积分 + 券 | 是 | 无额外限制 |
```

上传到测试知识库，等待 `status=SUCCESS`。

### 2. 检查表格 chunk

```sql
SELECT metadata->>'chunk_type', metadata->>'table_part', LEFT(content, 120)
FROM chunks
WHERE document_id = '<document_id>'
  AND metadata->>'chunk_type' = 'table';
```

预期：

1. 存在 `chunk_type=table` 的记录
2. content 含完整表头行和至少一行数据，不出现只有半行数据的残片
3. 大表场景下 `table_part` 从 1 开始递增，每个 chunk 都有表头行

### 3. 检索验证

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/rag/retrieve \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{
    "kb_id": "<kb_id>",
    "user_id": "test",
    "query": "满减和优惠券能否叠加",
    "profile": "balanced"
  }'
```

预期：Top chunk 包含完整的「满减 + 优惠券」那行，且表头可见；不出现只有 `| 否 | 同一订单` 这样的不完整行。

## 全量 reindex 测试

前置：01、02 切块已完成，测试知识库里有用旧字符切法索引过的文档。

### 1. 对整个知识库跑 reindex

```bash
python scripts/reindex_knowledge_base.py --kb-id <ecommerce_kb_id>
```

观察 Celery Worker 日志，确认各文档依次出现 `index_existing_document_success`。

脚本结束后预期终端输出类似：

```
已完成：8 篇    失败：0 篇    跳过：0 篇
```

### 2. 抽查 chunk metadata

任选一篇之前用旧切块索引的文档，reindex 后查库：

预期：

1. 含 `#` / `##` 的 Markdown 文档有 `heading_path`，`###` 内容随所属 `##` 节
2. 含表格的文档有 `chunk_type=table`，content 带表头行
3. 无仅含 `---` 的无意义 chunk

### 3. 调试台目视确认

打开 `/retrieve`，对「满减和优惠券能否叠加」或「第一节内容」检索：

预期：Top chunk 为完整小节或带表头的表格行，召回结果卡片上显示「所属章节」和「块类型」。

### 4. 单文档强制 reindex

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/documents/<document_id>/reindex \
  -H "Authorization: Bearer rk_live_你的key"
```

预期：`status=SUCCESS` 的文档接受重建，旧 chunk 被清除，新 chunk 按新切法生成；`PROCESSING` 中的文档返回错误拒绝重入。

### 5. 异常场景

| 场景 | 预期 |
|------|------|
| `--kb-id` 不存在 | 脚本友好报错，不崩溃 |
| 某篇文档 Worker 索引失败 | 记录 document_id，其余文档继续执行，统计进失败数 |
| `PROCESSING` 中的文档 | 脚本计入 skipped，不重复触发任务 |
| 纯文本 `.txt` 文档 reindex | 仍可成功索引，无报错 |
