# 多格式文档解析提示词

点击此处可复制本篇提示词

插件层和具体 Parser 实现是一体的：01 把 `DocumentParser` 接口、registry、upload 双模式、入库编排搭好；02 在同一套结构里填入 Word 和 PDF 两种实现，前端上传页随之接入。两步代码高度连续，合为一篇可以让 AI 在同一个上下文里把整条链路跑通，不需要中间交接。

## 使用场景

这份提示词用于在 rag-center 工程基础上，完成多格式文档解析。

当前 `POST /documents/upload` 只收 JSON 纯文本，`source_type` 写死 `text`。改完后：上传接口同时支持 `multipart/form-data`，`.docx` 和文字版 `.pdf` 可直接上传；Worker 里用插件化的 Parser 转成 Markdown 风格字符串，写入 `documents.content`，然后完全走现有的切块和索引流程；检索层、多库、配额一律不动。

改造完成后的链路：

```
upload（JSON 或 multipart）
  → 建 Document（multipart 时暂存原文件路径）
  → Celery index_document_task
       → prepare_document_content()   ← 唯一解析入口
       → 现有：split → embed → pgvector + ES
```

### 一、Parser 插件层

新建 `app/providers/parsers/` 目录，结构与现有 Embedding/LLM Provider 风格一致，方便后续新增 HTML 等格式：

```
app/providers/parsers/
  base.py       # DocumentParser ABC
  registry.py   # get_document_parser(filename) 按扩展名选择
  markdown.py   # 处理 .md / .txt
  docx.py       # Word 解析，用 mammoth
  pdf.py        # PDF 解析，用 PyMuPDF
  noop.py       # 不支持的扩展名，明确报错
```

**`DocumentParser` ABC**，每种 Parser 实现两个方法：

```python
class DocumentParser(ABC):
    def supports(self, filename: str, mime_type: str | None = None) -> bool: ...
    async def parse(self, file_bytes: bytes, *, filename: str) -> ParsedDocument: ...
```

**`ParsedDocument` 数据结构**，所有 Parser 的统一输出：

```python
@dataclass
class ParsedDocument:
    content: str       # Markdown 风格纯文本，splitter 的唯一输入
    source_type: str   # text | markdown | docx | pdf
    metadata: dict     # page_count、parser_name、warnings 等，写入 chunk metadata
```

**registry** 按扩展名选 Parser，注册顺序：DocxParser、PdfParser、MarkdownParser（`.md`/`.txt`）。未匹配的扩展名走 NoopParser，抛 `PARAM_ERROR`。

### 二、Word 解析（DocxParser）

`app/providers/parsers/docx.py`，使用 **mammoth** 将 `.docx` 转成 Markdown：

```python
import mammoth

async def parse(self, file_bytes: bytes, *, filename: str) -> ParsedDocument:
    result = mammoth.convert_to_markdown(io.BytesIO(file_bytes))
    warnings = [w.message for w in result.messages]
    return ParsedDocument(
        content=result.value.strip(),
        source_type="docx",
        metadata={"parser": "mammoth", "warnings": warnings},
    )
```

Word 里用「标题 1/2」样式的段落会输出 `#` / `##`，表格输出为 `| |`，转换效果对多数制度文档够用。老式 `.doc`、嵌入 OLE 对象、复杂文本框遇到时置 `FAILED` 并提示「请另存为 docx」。

### 三、PDF 解析（PdfParser）

`app/providers/parsers/pdf.py`，使用 **PyMuPDF（fitz）** 抽取文字，不需要 OCR：

```python
import fitz

async def parse(self, file_bytes: bytes, *, filename: str) -> ParsedDocument:
    doc = fitz.open(stream=file_bytes, filetype="pdf")
    parts = []
    for i, page in enumerate(doc):
        text = page.get_text("text").strip()
        if text:
            parts.append(f"## 第 {i + 1} 页\n\n{text}")
    content = "\n\n".join(parts)
    return ParsedDocument(
        content=content,
        source_type="pdf",
        metadata={"parser": "pymupdf", "page_count": len(doc)},
    )
```

按页加 `## 第 N 页` 的原因：PDF 往往没有可靠的标题结构，按页分节能让优化十一的 `MarkdownStructuredSplitter` 至少按页切节，避免整篇粘成一块。

抽出的纯文本为空时（疑似扫描件），置 `FAILED`，`error_message` 提示「疑似扫描件，本期不支持 OCR」。本期不做 OCR，不保证多栏学术论文的阅读顺序。

```python
    # 有 file_path → 读 bytes → registry 选 Parser → parse
    # 两者都没有或 parse 结果为空 → 抛 DOCUMENT_CONTENT_EMPTY 或 DOCUMENT_PARSE_FAILED
```

`IndexingService.index_existing_document` 在切块前插入调用：若 `document.source_file_path` 存在且 `content` 为空（或 `reparse` 标志），调 `prepare_document_content`，把结果写入 `document.content` 和 `source_type` 后 commit，再继续现有的 `_index_document_content`。

JSON 文本 upload 时 `content` 已有值，不读文件、不进 Parser，行为与优化十二之前完全一致。

### 五、upload API 双模式

`POST /api/v1/documents/upload` 保留原 path，同时支持两种 Content-Type：

| Content-Type | 请求体 | 行为 |
|---|---|---|
| `application/json` | `{ kb_id, title, content }` | 与改前完全一致，零破坏 |
| `multipart/form-data` | `file` + `kb_id` + 可选 `title` | 存原文件，content 先空，Worker 里 parse |

multipart 时：
- `title` 默认取文件名去掉扩展名
- 校验扩展名（`.pdf`/`.docx`/`.md`/`.txt`），不支持的格式返回 `PARAM_ERROR`
- 校验文件大小不超过 `DOCUMENT_MAX_SIZE_MB`
- 存文件到 `DOCUMENT_STORAGE_PATH/{tenant_id}/{document_id}/{filename}`
- `Document.source_file_path` 填写存盘路径，`content` 先空，触发 `index_document_task.delay`
- 配额仍走 `QuotaService.check_upload_document`

### 六、数据库扩展

新 Alembic 迁移，给 `documents` 表增加：

| 字段 | 说明 |
|------|------|
| `source_file_path` | 原文件存盘路径，可空；JSON 文本 upload 为 null |
| `source_filename` | 原始文件名，便于调试台展示和 reparse 时溯源 |

已有 `source_type` 字段：从写死 `text` 改为按来源赋值，取值为 `text`、`markdown`、`docx`、`pdf`。

### 八、reparse 支持

Parser 逻辑升级时需要从原文件重新解析，不只是重新切块：

- `POST /documents/{id}/reindex?reparse=true`：当 `source_file_path` 存在时，从原文件重新 parse 再 index；JSON 纯文本 upload 的文档忽略该参数
- `scripts/reindex_knowledge_base.py` 增加 `--reparse` 选项，与单篇语义一致

默认 `reindex`（不带 `reparse`）仍只读 `documents.content` 重新切块，不重新 parse。

### 十、错误处理

| 场景 | 行为 |
|------|------|
| 不支持的扩展名 | upload 阶段拒绝，`PARAM_ERROR` |
| 文件超过大小限制 | upload 阶段拒绝 |
| parse 抛错或结果为空 | 文档置 `FAILED`，`error_message` 含解析失败原因 |
| PDF 抽文本为空 | `FAILED`，提示「疑似扫描件，本期不支持 OCR」 |
| parse 成功但切块失败 | 沿用现有索引失败逻辑 |

`exceptions.py` 新增 `DOCUMENT_PARSE_FAILED`，建议错误码 `20023`。

### 十一、验收脚本

新增 `scripts/verify_parser_12.py`：

- 准备 `sample.docx` 和 `sample.pdf`（文字版），可放在 `data/` 或文档里说明如何生成
- 依次：multipart upload docx → 等 SUCCESS → retrieve 抽关键词
- multipart upload pdf → 等 SUCCESS → retrieve 抽关键词
- JSON `.md` 回归一条
- 打印所有场景通过，exit 0

### 十二、边界说明

- 不改 `MarkdownStructuredSplitter`、`RagService`、retrieve、多库逻辑
- 扫描件 PDF 本期不支持，应 `FAILED` 而非静默空库
- HTML、Excel 等格式留待后续新 Parser 插件，本篇不涉及

### 十三、验收标准

- JSON upload `.md` 内容与优化十二前完全一致（回归）
- multipart upload `.txt` → Worker parse → `SUCCESS` → retrieve 能召回
- multipart upload `.docx` → `SUCCESS` → retrieve 有 chunk，若 Word 有标题样式则 `heading_path` 存在
- multipart upload 文字版 `.pdf` → `SUCCESS` → retrieve 有 chunk
- 上传扫描件 PDF → `FAILED`，`error_message` 含提示信息
- 不支持扩展名 `.zip` → `PARAM_ERROR`
- 调试台上传页支持选择 `.pdf`、`.docx`，上传流程与 curl 效果一致
- `scripts/verify_parser_12.py` exit 0
- `reparse=true` 重建后，chunk 来自重新 parse 的内容
