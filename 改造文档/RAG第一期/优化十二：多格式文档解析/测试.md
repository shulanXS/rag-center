# 多格式文档解析测试验收

## 测试准备

PostgreSQL、Redis、Celery Worker 已启动，`alembic upgrade head` 已跑新迁移，`pip install -e ".[parsers]"` 已完成。准备三类测试文件：

- `sample.md`：含 `##` 小节的 Markdown
- `sample.docx`：含「标题 1/2」样式和表格的 Word 文档
- `sample.pdf`：文字版 PDF（非扫描），版式简单的制度文档最佳

## JSON 文本 upload 回归

改造后最先验这条，确认旧路径零破坏。

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/documents/upload \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{
    "kb_id": "<kb_id>",
    "title": "回归测试",
    "content": "## 测试节\n\n用于验证 JSON upload 未破坏。"
  }'
```

轮询 `GET /documents/{id}` 至 `status=SUCCESS`。

预期：行为与优化十二改造前完全一致，`source_file_path` 为 null，retrieve 能命中「测试节」。

## multipart 上传 .txt 文件

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/documents/upload \
  -H "Authorization: Bearer rk_live_你的key" \
  -F "kb_id=<kb_id>" \
  -F "title=txt测试" \
  -F "file=@./sample.txt"
```

预期：`code=0`，等待 `SUCCESS`；`GET /documents/{id}` 可见 `source_filename`；retrieve 能召回文件内容。

## Word 文档上传与检索

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/documents/upload \
  -H "Authorization: Bearer rk_live_你的key" \
  -F "kb_id=<kb_id>" \
  -F "file=@./sample.docx"
```

轮询至 `SUCCESS`，再检索 Word 里的某段关键词：

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/rag/retrieve \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{"kb_id":"<kb_id>","user_id":"demo","query":"<docx里某关键词>","profile":"speed"}'
```

预期：有召回 chunk；若 Word 里使用了「标题 1/2」样式，chunk metadata 含 `heading_path`。

## PDF 上传与检索

curl -s -X POST http://127.0.0.1:8000/api/v1/documents/upload \

轮询至 `SUCCESS`，再 retrieve 确认有 chunk，chunk content 含「## 第 N 页」结构。

## 调试台验证

### 1. 上传 .docx 和 .md

打开上传页，文件选择器应支持 `.pdf`、`.docx`（和原有 `.md`、`.txt`）：

1. 选择 `sample.docx` 上传，等待列表页状态变 SUCCESS
2. 选择 `sample.md` 上传（确认旧路径），等待 SUCCESS

### 2. 检索结果展示

打开检索页，对 docx 里的关键词检索：

- 有召回结果
- 若启用了调试台 chunk 元信息展示，可见「所属章节」和「块类型」

## 验收脚本

```bash
python scripts/verify_parser_12.py \
  --api-key rk_live_你的key \
  --kb-id <kb_id>
```

预期：脚本依次跑 docx、pdf、md 三种上传，各自等待 SUCCESS 并检索，全部通过后打印「通过」并 exit 0。

## reparse 测试（可选）

先用旧 Parser 上传一份 `.docx`，记录 document_id。更新 Parser 逻辑后：

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/documents/<document_id>/reindex?reparse=true \
  -H "Authorization: Bearer rk_live_你的key"
```

预期：从 `source_file_path` 重新 parse，新 chunk 替换旧 chunk；不带 `reparse` 的 reindex 仍只读已有 `content`。

## 异常场景

| 场景 | 预期 |
|------|------|
| 上传 `.zip` 等不支持格式 | `PARAM_ERROR`，msg 提示不支持该格式 |
| 上传超过 `DOCUMENT_MAX_SIZE_MB` 的文件 | upload 阶段拒绝，返回参数错误 |
| Celery Worker 未启动时上传 | 文档停在 `PROCESSING`，与优化八行为一致 |
| `.docx` 包含不支持的 OLE 对象 | `FAILED`，`error_message` 提示请另存为 docx |
| `reparse=true` 但文档无 `source_file_path` | 参数被忽略，正常 reindex |
