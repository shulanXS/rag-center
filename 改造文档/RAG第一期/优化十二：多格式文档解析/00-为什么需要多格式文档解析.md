# 为什么需要多格式文档解析

前面的结构化切块把索引质量提升了一大步——按章节边界分块、表格整体成块、chunk 携带 `heading_path`。但入库入口还停在"前端把 `.md` 读成字符串，后端当普通文本收进来"这个阶段。

真实业务里，文档不都是 Markdown。

## 当前的痛点

接入中台的业务方，手里更多是 Word 制度文件、HR 手册、PDF 合同和对外规范。这些格式都是二进制文件，不能直接当文本读取。

当前只接受 JSON 里的 `content` 字符串，这意味着业务方得**自己先把 Word/PDF 转成纯文本再 upload**——等于把解析成本推回每个接入方。中台如果无法直接接收原始文件，"文档入库"这个能力就不完整。

## 增加解析层

解决思路是在切块之前加一层 DocumentParser：接收原始文件，输出 Markdown 风格的纯文本，后面的切块、Embedding、双路索引、检索**一行不改**。

```
┌─ 解析层（新增）─────────────────────────────────────────┐
│  Word：读取标题样式和表格，转成 Markdown 风格文本           │
│  PDF：按页抽取文字，尽量保留标题和段落结构                  │
│  MD/txt：归一化或直接透传                                  │
└──────────────────────────┬──────────────────────────────┘
                           ↓ 统一的 Markdown 风格文本
┌─ 切块层（不改）──────────────────────────────────────────┐
│  按 #/## 分节，表格整体成块，Embedding → pgvector + ES     │
└──────────────────────────┬──────────────────────────────┘
                           ↓
                    检索 / rerank / 多库……（都不改）
```

Parser 的输出不是保存一个 `.md` 文件，而是一段 Markdown 风格的字符串写入 `documents.content`，供现有切块逻辑消费。Word 里的"标题 1"转成 `#`，表格转成 `| |`，这样结构化切块的标题和表格规则就能直接复用。

这一设计让格式支持变成了**可插拔**的能力：Parser 按扩展名选实现，后续新增格式只需写一个新的 Parser 并注册，切块层之后的所有逻辑完全不感知。

## 本期支持的格式

优先支持两种最常见的业务格式：

- **Word（`.docx`）**：制度文件、HR 手册、产品说明，用 mammoth 转换，能保留标题层级和表格结构
- **PDF（文字版）**：合同、对外规范、电子版文档，用 PyMuPDF 按页抽取文字

这两种格式覆盖了大多数业务场景，且不依赖 OCR，实现成本可控。

## 解析效果的预期

不同格式的解析质量存在差异，需要提前了解：

| 格式 | 解析效果 | 局限 |
|------|---------|------|
| Word `.docx` | 标题和表格大多可正确识别，结构还原较好 | 复杂嵌套对象、老版 `.doc` 格式不支持 |
| PDF 文字版 | 能提取文字内容，按页加标题 | 多栏排版、扫描件无法处理；排版复杂时结构可能丢失 |
| `.md` / `.txt` | 与之前行为一致，完全兼容 | — |

PDF 的解析效果受原始文档版式影响较大。排版简单的 PDF（如纯文字合同）通常效果不错；复杂排版或扫描件暂不支持，后续可针对性地增加专用 Parser。

解析不完美时，仍比"业务方无法传 PDF/Word"好得多。效果问题可以通过调试台看召回、用 RAGAS 跑测评来定位，再决定是否需要优化解析策略。
