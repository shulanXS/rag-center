# 00 - 为什么需要效果调优与工具选型

优化五做完检索调试台，你能对着一条 query 看召回了哪些 chunk、分数怎么来的。优化七加了词表和 query 改写，优化九加了 profile 和套餐——**配置能改了，但还缺一条闭环：改完有没有变好、线上哪里还不行、怎么持续改。**

调试台解决的是「此刻这一次搜得怎么样」。生产里每天成百上千次 retrieve，你不可能每次都蹲在前端点检索。运营想知道「退款相关的问题最近是不是老搜偏」；研发想对比「开了 quality profile 之后 recall 有没有上去」——这些都需要**把检索效果当成可度量、可复盘、可迭代的事**来做。

这就是优化十要补上的那一块。

## 能搜，不等于搜得对

rag-center 是检索中台：`POST /rag/retrieve` 返回 chunk，答案生成在业务方。中台不负责「答得像不像人话」，但要负责**捞回来的片段是不是用户真正需要的那几段**。

典型挫败感往往长这样：

- 库里明明有《促销活动与优惠券使用规则》，用户问「满减和券能叠加吗」，排第一的却是另一篇里顺带提了一句「优惠券」的段落
- 优化七加了词表、优化九切了 `quality` profile，体感好像好了一点，但**说不清好多少**，也不敢放心上线
- 客服同事反馈「这条检索没用」，你却找不到当时到底召回了什么、用的什么 profile

根因不是某一次 bug，而是：**我们一直没有把「检索效果」从主观感受，变成可记录、可量化、可对比的工程对象。**

## 效果调优需要三角闭环

把「检索效果」拆开，其实对应三件不同的事：

```
        可观测（01）
       /    每次 retrieve 发生了什么
      /     问句怎么变的、召回了什么、哪步降级了
     /
效果调优 ─── 可反馈（02）
     \      线上哪里不准、用户觉得有没有用
      \
       \    离线测评（03）
            改配置之前，批量量化「变好了还是变差了」
```

| 能力 | 回答什么问题 | 没有它会怎样 |
|------|--------------|--------------|
| **可观测** | 这次检索的完整现场是什么？ | bad case 无法复盘，只能猜 |
| **可反馈** | 用户/运营觉得哪次结果不好？ | 线上问题沉淀不下来 |
| **离线测评** | 改词表、改 profile 前后效果差多少？ | 调参靠感觉，不敢发版 |

三者串起来，才是完整的调优闭环：

```
离线测评发现系统性问题
    → 改词表 / profile / 参数
    → 再跑测评验证
    → 上线
    → 线上反馈发现长尾问题
    → 查可观测记录复盘
    → 补充进测评集
    → 继续改……
```

优化五的调试台是这条链路的**起点**，优化十把它**延伸成可沉淀、可量化、可回流**的体系。

## 为什么引入工具，而不是全自建

三角闭环里的能力，理论上都可以自建：日志表、反馈表、评测脚本、历史查询 API、运营后台……

但对中小型中台来说，全自建有几个现实问题：

| 自建项 | 工作量 |
|--------|--------|
| 检索链路 trace，改写→检索→重排各步 | 大 |
| 按 query / 时间翻历史的 UI | 中 |
| 反馈与 trace 关联 | 中 |
| RAG 检索向评测指标 | 中～大 |

**能用成熟框架的环节就用框架**，把精力放在 rag-center 自己的检索链路和业务契约上。

## 我们选哪两个工具

优化十引入两个框架，各管闭环里的一块，分工不重叠：

| 工具 | 负责哪一块 | 为什么是它 |
|------|-----------|------------|
| **Langfuse** | 01 可观测 + 02 反馈 | 开源可自托管；一次接入同时有 trace 面板和 score 反馈；和现有 FastAPI 栈兼容 |
| **RAGAS** | 03 离线测评 | RAG 领域常用评测框架；提供 context precision、context recall 等检索向指标 |

### Langfuse 做什么

每次 retrieve 记一条 **trace**，下面挂子 span：query 处理、vector/bm25/hybrid、rerank。Web 面板按时间、query、metadata 过滤，查看历史检索。对某条 trace 打 **score**，供反馈闭环使用。

Langfuse 不替代 `POST /rag/retrieve` 接口，不负责批量算检索指标，也不管 faithfulness / answer relevancy 这些需要完整 RAG 链路才能算的指标。

### RAGAS 做什么

读入一批测例，对 rag-center 批量调 retrieve，把召回 chunks 组装成评测数据集，输出 context precision、context recall 等分数和失败 case。它不做生产 trace，不替代 Langfuse 的可观测面板。

### 和其他工具的对比

| 工具 | 和本方案的关系 |
|------|----------------|
| **LangSmith** | 能力类似 Langfuse，但是 SaaS；数据出域，不作为本项目依赖 |
| **Arize Phoenix** | RAG 检索可视化很强；若更强调 embedding 空间分析可考虑，本篇以 Langfuse 为主 |
| **DeepEval / PromptFoo** | 偏端到端 RAG 或 prompt 回归；已有 RAGAS 覆盖离线测评，不必再堆 |

## 和现有优化的关系

```
优化五  调试台         → 单次即时调试（保留，不替代）
优化七  词表 / 改写    → 可调配置之一
优化九  profile / plan → 可调配置之一
优化十  观测+反馈+测评  → 衡量配置改动的效果，沉淀 bad case
```

调优动作仍然落在**词表、profile、检索参数**上，优化十提供的是**度量尺和复盘手段**。

## 中台仍要保留什么

框架是旁路接入，不替代中台核心契约：

| 保留在中台 | 原因 |
|------------|------|
| `retrieve` API 本身 | 业务方对接面不变 |
| 响应里的 `log_id` | 业务方挂反馈、对账、关联自家业务流水，不绑死 Langfuse |
| 响应里的 `trace_id` | 关联 Langfuse trace，调试与反馈用，从 01 起回传 |
| `retrieval_logs` 表 | 关键字段本地留底，Langfuse 不可用时仍有最小记录 |

```
业务方调用 retrieve
    → 返回 chunks + log_id + trace_id
    → 旁路写 Langfuse trace（01）
    → 精简写 retrieval_logs（01）
    → 业务方 / 运营用 trace_id 打反馈（02）
    → 研发用 RAGAS 批量测评（03）
```

## 三篇实施路线

| 篇章 | 主题 | 依赖 |
|------|------|------|
| **01 检索可观测** | docker 起 Langfuse；retrieve 埋 trace；响应回传 `trace_id` / `log_id` | 无 |
| **02 检索反馈** | 反馈 API；Langfuse score 挂在 trace 上 | 01 的 `trace_id` |
| **03 离线测评** | golden set + RAGAS 脚本；对比 profile / 词表前后 | 01 可选，测评直接调 API |

建议按 01 → 02 → 03 顺序做。01 是地基；02 依赖 trace_id；03 可与 02 并行，但放在最后便于串起「观测 → 反馈 → 量化」完整闭环。

## 小结

优化十解决的不是「再做一个调试台」，而是检索效果的三角闭环：可观测、可反馈、可量化。Langfuse 管 01+02，RAGAS 管 03，各管一块，不重复造轮子。中台仍保留 `log_id` 契约，框架是增强，不是替换 retrieve API。下一篇 **01** 落地检索可观测：接入 Langfuse，让每次 retrieve 在面板里留下完整现场。
