# 03 - 离线测评

01 能复盘每一次 retrieve，02 能沉淀线上的 👍/👎。但上线改词表、改 profile 之前，你需要回答一个更硬的问题：**这批改动手把手变好多少？**

这就是 **离线测评**：拿一套固定的测例（golden set），批量调 `retrieve`，用 **RAGAS** 算检索向指标，出报告、找失败 case。改配置前后各跑一遍，用数字说话，而不是凭体感。

## 现状与目标

改词表或切换 profile 之后，效果靠体感，说不清好多少；测例手工维护、和线上反馈脱节；也没有批量跑的入口。本篇把这三块补上：测例主要从 02 低分反馈拉取，一条命令对比改配置前后的 context recall / precision，输出失败 case 列表，用数字说话。

## 测评在闭环里站哪

```
02 低分反馈（user_feedback < 3）
       │
       ▼
  export 脚本拉 Langfuse → 生成/追加 golden set 候选
       │
       ▼  人工补 ground_truth（必做）
  eval/datasets/*.json
       │
       ▼
  run_retrieval_eval.py + RAGAS → 发现某类 query recall 偏低
       │
       ▼
  改 kb 词表 / 换 quality profile / …
       │
       ▼
  再跑 03 → context_recall 从 0.55 升到 0.82 → 放心上线
       │
       ▼
  02 持续产生新的 <3 分 case → 再 export → 测评集越跑越贴近真实业务
```

离线测评负责 **批量、可重复、可对比**；02 负责 **供给 bad case 候选**；01 负责 **单条复盘**。三者互补。

## 测例从哪来（数据来源）

### 主路径：02 低分反馈 → Langfuse 导出

02 把 1～5 分写入 Langfuse score（`name=user_feedback`），**不建本地 feedbacks 表**。03 的测例 **主要** 从 Langfuse 筛：

| 条件 | 说明 |
|------|------|
| score 名 | `user_feedback` |
| 分数 | **低于 3 分**（即 1 或 2；默认阈值，脚本可 `--max-score 2` 收紧） |
| trace | `rag_retrieve`，且 metadata 含 `kb_id` |

脚本 `scripts/export_eval_cases_from_langfuse.py` 通过 **Langfuse Public API** 拉取上述 score + 关联 trace，输出 golden set 片段或独立 JSON，例如：

```json
{
  "id": "lf_a1b2c3d4",
  "question": "满减和优惠券能叠加吗？",
  "ground_truth": "",
  "source": {
    "trace_id": "2a86e534-...",
    "log_id": "b7f57ae1-...",
    "feedback_score": 2,
    "feedback_comment": "排第一的不是优惠券规则文档",
    "exported_at": "2025-06-25T10:00:00Z"
  }
}
```

| 字段 | 脚本能否自动填 | 说明 |
|------|----------------|------|
| `question` | ✅ | 来自 trace input |
| `feedback_score` / `comment` / `trace_id` | ✅ | 来自 score |
| `ground_truth` | ❌ 默认空 | **必须人工补**：打开对应文档摘 1～2 句关键话；RAGAS 无法从 comment 可靠推断 |

导出后两种用法：

1. **单独文件** `--output eval/datasets/imported_from_feedback.json` → 补 ground_truth → 先单独跑评测，见下节详述
2. **`--merge`** 追加到 `ecommerce_retrieval.json` → 全量回归时一起评

**跳过规则**（脚本默认）：`ground_truth` 仍为空的 case **不参与** `run_retrieval_eval.py`（或计入 `--skipped` 列表），避免无标准答案硬跑。

### 辅路径：冷启动种子集（可选）

项目初次还没有足够线上反馈时，可保留少量 **手工种子**（5～10 条），对齐 `data/ecommerce/` 等文档，保证第一天就能跑通 RAGAS。上线后有 02 数据后，**新增测例以 export 为主**，种子集只增不删、作回归基线。

## 用什么指标

rag-center 只返回 chunk，不生成答案。RAGAS 里和本篇相关的主要是 **检索向** 指标：

| 指标 | 通俗理解 | 需要什么标注 |
|------|----------|--------------|
| **Context Precision** | 召回来的 chunk 里，有多少真的相关 | question + 召回 contexts + ground_truth |
| **Context Recall** | 该召的内容，有没有被召回来 | question + 召回 contexts + **ground_truth** |

RAGAS 用 LLM 做语义判断：**ground_truth 是短句、召回是长 chunk 也可以**，不要求字面一致；但 ground_truth 必须准确，一般从知识库原文摘关键事实。

> faithfulness、answer_relevancy 等需要 `answer` 字段，在业务方「检索 + 生成」链路里使用，不纳入本篇默认指标。

## Golden set 长什么样

建议目录：

```
eval/
  datasets/
    ecommerce_retrieval.json          # 主集（export merge + 已补 ground_truth）
    imported_from_feedback.json       # export 原始输出（可选，待审）
    _seed_ecommerce.json              # 冷启动种子（可选）
  reports/                            # 评测报告，gitignore
```

单文件示例 `eval/datasets/ecommerce_retrieval.json`：

```json
{
  "name": "ecommerce_retrieval",
  "kb_id": "939a5baf-xxxx",
  "default_profile": "balanced",
  "cases": [
    {
      "id": "lf_coupon_stack",
      "question": "满减和优惠券能叠加吗？",
      "ground_truth": "同一订单不可同时使用满减活动与店铺优惠券，二者择一适用。",
      "source": {
        "trace_id": "2a86e534-...",
        "feedback_score": 2,
        "feedback_comment": "排第一的不是优惠券规则文档"
      }
    }
  ]
}
```

字段说明：

| 字段 | 必填 | 说明 |
|------|------|------|
| `kb_id` | 是 | 测哪个库；export 时可从 trace metadata 带出，merge 前需统一 |
| `default_profile` | 否 | 未在命令行覆盖时用 |
| `cases[].question` | 是 | 调 retrieve 的 query |
| `cases[].ground_truth` | **跑 RAGAS 前必填** | 从文档摘的关键句；export 阶段可为空 |
| `cases[].id` | 否 | 建议用 `lf_<trace_id 短码>` 或业务 id |
| `cases[].source` | 否 | 追溯 Langfuse trace、原始反馈分，便于和 01/02 对照 |

## 两个脚本分工

### 1. 从 Langfuse 导出低分 case

`scripts/export_eval_cases_from_langfuse.py`：

```
1. 读 .env：LANGFUSE_HOST、LANGFUSE_PUBLIC_KEY、LANGFUSE_SECRET_KEY
2. 调 Langfuse API 拉 score（name=user_feedback, value < max_score，默认 max_score=3）
3. 按 trace_id 取 trace：input.query、metadata.kb_id、log_id
4. 输出 JSON cases（ground_truth 留空，comment/score/trace_id 写入 source）
5. 可选 --merge 到已有 dataset（question 去重）
6. 打印：导出 N 条，其中 M 条待补 ground_truth
```

命令行示例：

```bash
python scripts/export_eval_cases_from_langfuse.py \
  --max-score 3 \
  --days 30 \
  --kb-id 939a5baf-xxxx \
  --output eval/datasets/imported_from_feedback.json

# 审完 ground_truth 后合并进主集
python scripts/export_eval_cases_from_langfuse.py \
  --max-score 3 \
  --merge eval/datasets/ecommerce_retrieval.json \
  --output eval/datasets/ecommerce_retrieval.json
```

在 Langfuse UI 直接筛 `user_feedback < 3` 与脚本等价；脚本适合定期跑或 CI 前自动更新测例。

### 2. 批量评测（RAGAS 打分）

`scripts/run_retrieval_eval.py`：

```
1. 读 golden set JSON，跳过 ground_truth 为空的 case
2. 对每条 case POST /rag/retrieve（带 API Key、profile）
3. contexts = [chunk.content for chunk in retrieved_chunks]
4. ragas.evaluate(metrics=[context_precision, context_recall])
5. 打印汇总分 + 每条 case 得分；recall 低的单独列出
6. 可选 --output eval/reports/20250625_balanced.json
```

```bash
python scripts/run_retrieval_eval.py \
  --dataset eval/datasets/ecommerce_retrieval.json \
  --api-key rk_live_xxx \
  --base-url http://127.0.0.1:8000 \
  --profile balanced \
  --output eval/reports/balanced.json
```

对比改词表前后：

```bash
# 改词表前
python scripts/run_retrieval_eval.py --dataset ... --profile balanced \
  --output eval/reports/before_synonyms.json

# 改词表后
python scripts/run_retrieval_eval.py --dataset ... --profile balanced \
  --output eval/reports/after_synonyms.json
```

**为何 export 后还要再 retrieve？** 反馈/trace 里是**当时**的召回摘要；RAGAS 需要**当前配置下**的完整 chunk 正文，且改词表/profile 后必须用同一 question **重跑** retrieve 才能对比前后分数。ground_truth 不变，retrieve 每次重跑。

评测脚本里 `user_id` 固定 `eval_runner`；可走 01 的 Langfuse trace（可选关 Langfuse 减少噪音）。

## 两种跑法：单独测反馈 vs 全量回归

`run_retrieval_eval.py` 的 `--dataset` 指向**任意** golden set JSON，脚本只跑该文件里的 cases，**没有「必须一次跑完全部测例」的限制**。

| 跑法 | `--dataset` | 什么时候用 | 报告建议路径 |
|------|-------------|------------|--------------|
| **单独跑反馈集** | `eval/datasets/imported_from_feedback.json` | export 后刚补完 ground_truth，先验证这几条低分 case 当前检索如何 | `eval/reports/imported_balanced.json` |
| **全量回归** | `eval/datasets/ecommerce_retrieval.json` | 种子 + 已 merge 的反馈 case，改词表/profile 前后对比 | `eval/reports/balanced.json` |

典型顺序：

```
export → 补 ground_truth（imported_from_feedback.json）
    │
    ├─ ① 单独跑 imported_from_feedback.json   ← 快，只看低分题
    │      recall 低 → 改词表 / profile / 查文档
    │
    ├─ ② 确认没问题后 merge 进 ecommerce_retrieval.json（可选）
    │
    └─ ③ 全量跑 ecommerce_retrieval.json       ← 回归基线 + 新 case 一起评
```

### 单独跑反馈集（推荐 export 后第一步）

补完 `imported_from_feedback.json` 的 `ground_truth` 后，**不必等 merge**，直接：

```bash
python scripts/run_retrieval_eval.py \
  --dataset eval/datasets/imported_from_feedback.json \
  --api-key rk_live_你的key \
  --profile balanced \
  --output eval/reports/imported_balanced.json
```

- 只评 export 出来的几条（如 3 条低分），RAGAS 阶段更快
- 终端与报告里可对照 `source.feedback_score`、`feedback_comment`，和 Langfuse 原 trace 复盘
- 若某条 recall 仍低，针对性改配置后再 **对同一文件重跑**，对比 `imported_balanced.json` 前后

### 全量跑主集（merge 后或冷启动种子）

```bash
python scripts/run_retrieval_eval.py \
  --dataset eval/datasets/ecommerce_retrieval.json \
  --api-key rk_live_你的key \
  --profile balanced \
  --output eval/reports/balanced.json
```

- 含种子测例 + 已 merge 的反馈 case，作**回归基线**
- 改词表 / 换 profile 前后，对**同一 dataset** 各跑一遍，对比 `before.json` / `after.json`

### merge 进主集（可选，单独跑满意后再做）

手动把 `imported_from_feedback.json` 里已审 case **复制**进 `ecommerce_retrieval.json`，或：

```bash
python scripts/export_eval_cases_from_langfuse.py \
  --max-score 3 \
  --merge eval/datasets/ecommerce_retrieval.json \
  --output eval/datasets/ecommerce_retrieval.json
```

`--merge` 按 `question` 去重；**已手写 ground_truth 的 case 不会被覆盖**，仅追加新 question。

### 依赖

```toml
# pyproject.toml optional-dependencies
eval = [
  "ragas>=0.2.0",
  "datasets>=2.0.0",
]
```

安装：`pip install -e ".[eval]"`

RAGAS 评测阶段会调 LLM，需在 `.env` 配置 `MODEL_BASE_URL`、`MODEL_API_KEY`（与 rag-center 共用即可）。

## 和 retrieve 的衔接

```json
{
  "kb_id": "...",
  "user_id": "eval_runner",
  "query": "...",
  "profile": "balanced"
}
```

pro 租户还可对同一 dataset 分别跑 `speed`、`balanced`、`quality`，对比套餐策略：

```bash
for p in speed balanced quality; do
  python scripts/run_retrieval_eval.py --dataset ... --profile $p \
    --output eval/reports/profile_${p}.json
done
```

RAGAS 只负责**打分**；能提升检索的手段包括词表、profile、hybrid/rerank/rewrite 等——改完再用同一 golden set 重跑验证。

## 做完怎么验

前置：02 已有若干低于 3 分的反馈（或先用种子集）；知识库已索引；`.env` 配好 `LANGFUSE_*` 与 `MODEL_*`；`pip install -e ".[eval]"`。

### 1. 从 Langfuse 导出低分 case

```bash
python scripts/export_eval_cases_from_langfuse.py \
  --max-score 3 \
  --days 30 \
  --kb-id <你的kb_id> \
  --output eval/datasets/imported_from_feedback.json
```

预期：JSON 含 `question`、`source.feedback_score`；`ground_truth` 为空。

### 2. 人工补 ground_truth

打开 `data/ecommerce/*.md`（或对应 kb 文档），为 `imported_from_feedback.json` 每条 case 摘 1～2 句关键话。

### 3. 单独跑反馈集（export 后建议先做）

```bash
python scripts/run_retrieval_eval.py \
  --dataset eval/datasets/imported_from_feedback.json \
  --api-key rk_live_你的key \
  --profile balanced \
  --output eval/reports/imported_balanced.json
```

预期：只评 export 的几条低分 case；终端有中文汇总；`ground_truth` 为空的 case 被 skip。

### 4. （可选）merge 后进主集

满意后再把 case 并入 `ecommerce_retrieval.json`（复制或 `--merge`）。

### 5. 全量 RAGAS 评测

```bash
python scripts/run_retrieval_eval.py \
  --dataset eval/datasets/ecommerce_retrieval.json \
  --api-key rk_live_你的key \
  --profile balanced \
  --output eval/reports/balanced.json
```

预期：种子 + 已 merge 的 case 一起评；`eval/reports/balanced.json` 已生成。

### 6. 对比改配置前后

1. 记录当前报告分数（单独集或全量集均可，**对比时用同一 `--dataset`**）  
2. `scripts/update_kb_settings.py` 加 synonyms，或换 `--profile quality`  
3. 再跑同一命令  
4. 对比 `context_recall` 是否提升  

### 7. 与 Langfuse 对照（可选）

- 低分来源：Langfuse 筛 `user_feedback < 3`  
- 评测 trace：`user_id=eval_runner`  

---

优化十至此闭环：

- **01** 单次检索可观测  
- **02** 线上反馈挂 trace，**低于 3 分是 03 测例的主来源**  
- **03** export 候选 → 补 ground_truth → RAGAS 量化 → 改配置再跑  

测评集随 02 低分反馈持续长大，越跑越贴近真实业务。
