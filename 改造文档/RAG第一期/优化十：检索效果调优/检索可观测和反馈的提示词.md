# 检索可观测与反馈提示词

点击此处可复制本篇提示词

可观测和反馈是一条流水线：可观测先把 trace 打通，让响应带回 `trace_id`；反馈再把 score 挂到这个 `trace_id` 上。两步关系紧密，放在一篇里给 AI，可以确保 `log_id` 和 `trace_id` 的返回规范与反馈 API 的设计保持一致，不需要来回对接两份文档。

## 使用场景

这份提示词用于在当前 rag-center 工程基础上，完成检索可观测和检索反馈两步。

**可观测完成后**：每次 retrieve 在 Langfuse 留下一条 trace，记录 query 改写、召回、rerank 各阶段细节；响应 metadata 带回 `log_id` 和 `trace_id`；本地 `retrieval_logs` 精简留底。

**反馈完成后**：调用方和运营可对某次检索提交 1～5 分和备注，score 写入 Langfuse 并挂在对应 trace 上；调试台检索结果区出现五星反馈条。

### 一、依赖与配置

`pyproject.toml` 增加 `langfuse>=2.0.0,<3.0.0`。

`app/core/config.py` 增加以下配置项：

```env
LANGFUSE_ENABLED=false
LANGFUSE_HOST=http://localhost:3000
LANGFUSE_PUBLIC_KEY=
LANGFUSE_SECRET_KEY=
```

`.env.example` 补充上述变量说明。

### 二、Langfuse 基础设施

**docker-compose**：在项目根目录 `docker-compose.yml` 增加两个 service。`langfuse-db` 使用独立的 Postgres，库名 `langfuse`；`langfuse` 使用镜像 `langfuse/langfuse:2`，对外暴露 3000 端口，须配置 `NEXTAUTH_URL=http://localhost:3000` 和 `ENCRYPTION_KEY`。两个 service 与现有 postgres、redis、es 并列：

```bash
docker compose up -d langfuse
```

**封装**：新增 `app/observability/langfuse_client.py`，提供统一的 trace 操作接口。`LANGFUSE_ENABLED=false` 时所有 helper 静默无操作，`get_langfuse()` 返回 `None`，调用方无需判空。提供 `RetrieveObservability`，封装 trace 开启、三个子 span 记录、结束时 flush 的全流程。Langfuse client 使用 `httpx.Client(trust_env=False)` 访问，避免本地代理干扰。

### 三、RagService 埋点

`retrieve` 全程包在 Langfuse trace 内，trace 名称为 `rag_retrieve`，metadata 携带 tenant_id、kb_id、user_id、profile、plan，便于在 Langfuse 面板按租户或检索策略筛选历史记录。

三个子 span 分别对应检索链路的三个阶段：

- `query_processing`：记录原始 query、改写后的 effective_query、同义词扩展情况
- `retrieval`：记录检索 mode、vector 和 bm25 各自的命中数、是否发生 hybrid 降级
- `rerank`：记录是否启用、候选数量、是否降级

trace output 只存最终返回的 chunk_id 和 score 摘要列表，不塞全文，避免 Langfuse 面板体积过大。

Langfuse 写入失败时只打 warning 日志，不影响 retrieve 正常返回。

响应 `metadata` 新增两个字段：`log_id` 是本次检索的唯一标识，与 `retrieval_logs` 表主键一致，业务方可用来关联自己的流水；`trace_id` 是 Langfuse 生成的标识，用于在面板里直接定位这条记录。

### 四、retrieval_logs 表扩展

Alembic 迁移 `0006_retrieval_log_observability`，新增字段均可空，不影响旧数据：

| 字段 | 类型 | 说明 |
|------|------|------|
| trace_id | VARCHAR(64) | Langfuse trace 标识，与响应里的 trace_id 一致，方便本地和 Langfuse 双向查找 |
| profile | VARCHAR(32) | 本次使用的检索策略，如 balanced、quality，留底便于分析不同策略的表现 |
| search_query | TEXT | 实际送入向量和全文搜索引擎的 query，词表扩展后的版本 |
| effective_query | TEXT | LLM 改写后的 query，没有改写则与原始 query 相同 |

写入时填充新字段，保留现有 `retrieved_chunks` 等字段不动。

### 五、Schema 更新

`RetrieveMetadata` 新增：

```python
log_id: str
trace_id: str | None = None   # Langfuse 未启用时为 null
```

`frontend/src/types/api.ts` 同步 `log_id` 和 `trace_id`。

### 六、反馈 API

`POST /api/v1/rag/feedback`，需鉴权，通过 `Depends(get_current_tenant)` 接入，挂到 `api/v1/router.py`。

**Schema** — 新增 `app/schemas/feedback.py`：

| 字段 | 必填 | 说明 |
|------|------|------|
| trace_id | 是 | 可观测阶段响应里的 Langfuse trace 标识，反馈挂在这条 trace 上 |
| log_id | 建议传 | 本地 retrieval_logs 的记录 ID，用于校验当前租户有权操作这条记录 |
| score | 是 | 整数 1～5，`Field(ge=1, le=5)` |
| comment | 否 | 可选备注，比如「排第一的 chunk 不是对的文档」 |

响应 `FeedbackData` 含 `feedback_id`、`trace_id`、`log_id`、`score`。

**Service** — 新增 `app/services/feedback_service.py`，处理逻辑分三步：

1. 若传 `log_id`：查 `retrieval_logs`，校验 `tenant_id` 匹配且 `trace_id` 一致，不通过则返回错误码 20021
2. 调 Langfuse SDK 在 `trace_id` 上创建 score，`name=user_feedback`，`value=score`，`comment` 透传
3. 复用 `app/observability/langfuse_client.get_langfuse_client()`，不重复创建 client

`LANGFUSE_ENABLED=false` 或 Langfuse 写入异常时，返回 `AppError 20020`，retrieve 接口不受影响。

**错误码**，在 `exceptions.py` 新增：

| code | 含义 |
|------|------|
| 20020 | 反馈失败，Langfuse 不可用或写入异常 |
| 20021 | log_id 与 trace_id 不匹配，或当前租户无权操作 |
| 20022 | score 超出 1～5 范围 |

### 七、调试台反馈条

在「检索与召回」Card 内、chunk 列表上方加反馈区，不要弹窗：

```
┌─ 检索与召回 ─────────────────────────────────────┐
│ query …                          [检索]          │
│ ── 反馈（有结果且 trace_id 存在时显示）───────── │
│  ★ ★ ★ ★ ☆   点亮黄色，未点亮灰色，点击选 1～5   │
│  ┌ 备注（可选）──────────────────────────────┐  │
│  │ 排第三的 chunk 才是对的…                    │  │
│  └────────────────────────────────────────────┘  │
│                              [提交反馈]           │
│ ── 召回结果 ─────────────────────────────────── │
│ #1 chunk …                                      │
└────────────────────────────────────────────────┘
```

交互规则：

| 规则 | 说明 |
|------|------|
| 何时显示 | 本次 retrieve 成功且 metadata.trace_id 非空；无 trace_id 时隐藏，并提示「Langfuse 未启用」 |
| 星级 | 5 颗星，点击选 1～5；已选及左侧显示黄色，未选灰色；提交前必选 |
| 备注 | 多行输入框，可选填 |
| 提交 | 调 `POST /rag/feedback`，带当前次的 trace_id、log_id、score、comment |
| 提交成功 | 简短提示「已提交」，可附显示「已评 N 分」 |
| 再次检索 | 清空星级与备注，避免挂到新 trace 上 |

新增 `ragService.submitFeedback()`，`types/api.ts` 补 `FeedbackRequest` 和 `FeedbackData`，样式对齐现有 RetrievePage，使用 shadcn 的 Card、Button、Textarea 组件。

### 八、文档

`docs/tenant-onboarding.md` 增加「检索反馈」小节：retrieve 后业务方保存 `trace_id`；score 为 1～5 分；运营可在 Langfuse 按 `user_feedback` 筛选低分 trace 复盘。

### 九、边界说明

- 不建 `feedbacks` 表，反馈数据由 Langfuse 持久化
- 不做 RAGAS 离线测评，该部分见独立提示词
- 不做历史查询 API，查历史检索记录直接用 Langfuse UI
- 不做 Langfuse 统计大盘
- body 多传字段由 Pydantic 忽略

### 十、验收标准

- `LANGFUSE_ENABLED=true`，调 retrieve 成功，响应含非空 `log_id` 和 `trace_id`
- Langfuse UI 能看到对应 trace，metadata 含 tenant_id、kb_id、profile，子 span 含 query_processing、retrieval、rerank
- `LANGFUSE_ENABLED=false`，retrieve 正常，`trace_id` 为 null，`log_id` 仍有值
- `retrieval_logs` 新增字段有值，`id` 与响应 `log_id` 一致
- 调试台：检索 → 选 4 星加备注 → 提交 → Langfuse 该 trace Scores 为 4
- curl feedback：`score=2` → Langfuse `user_feedback=2`，comment 一致
- 传错误 `log_id` → 20021
- `score=0` 或 6 → 20022
- `LANGFUSE_ENABLED=false` 时调 feedback → 20020，调试台反馈条不可用
- 再次检索后，反馈条星级与备注已清空
