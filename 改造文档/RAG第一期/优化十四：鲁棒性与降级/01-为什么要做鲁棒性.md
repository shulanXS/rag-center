# 为什么要做鲁棒性

前面在效果侧做了不少工作——结构化切块、多格式解析、混合检索、多库联合检索。在调试台里、在离线测评里，happy path 往往很漂亮：该召回的 chunk 能上来，多库的来源标注也对得上。

但一旦像生产那样跑，或者真的接进业务系统，会遇到另一类问题——**不是搜不准，而是根本搜不了**。Elasticsearch 重启了一下，整个 retrieve 直接 500；多库联合检索时，其中一个库还没索引好，两个库的结果一起没了；BM25 偶尔挂了有时能返回、有时整单报错，业务方很难预期。

这不是偶发 bug。RAG 中台同时跑两条主链路——**索引**（把文档写进向量库和 ES）和**检索**（把 query 变成召回结果）。两条链都依赖外部组件；本地演示时它们大多稳定，上线之后"某个依赖抖一下"才是常态。

## 效果和鲁棒性，解决的不是一类问题

之前的工作主要在回答：**怎么搜得更准、搜得更全**。鲁棒性回答的是：**依赖出问题时，还能不能给出尽量有用、且诚实的回应**。

| | 效果优化 | 鲁棒性 |
|--|---------|--------|
| 典型症状 | 库里有，但 top1 不对 | ES / Embedding 抖一下，整单 500 |
| 目标 | 提高 recall / precision | 能降级则降级，不能则明确拒绝 |
| 验收 | RAGAS、调试台对比 | 停 ES、单库失败，仍 200 或清晰报错 |

继续堆效果增强，不如先把"挂了怎么办"定清楚。

## 两条链路，一条已兜住，一条还要补

### 索引链路：已经兜住了

上传文档后，走异步索引：

```
upload → PROCESSING → 分块 → Embedding → pgvector → ES → SUCCESS
```

这条路上，失败后的行为已经合理：

- Embedding 超时 → Celery 重试，耗尽后文档 FAILED，调试台可 reindex
- ES 写入失败 → 与 pgvector 同一事务 rollback，不会出现 SUCCESS 但只写进一半
- 内容为空 → 直接拒绝或 FAILED

索引链路不需要额外处理。

### 检索链路：还有缺口

用户一次 retrieve，大致是：

```
词表扩展 → Query 改写（可选）→ Embedding
  → vector / bm25 / hybrid
  → （多库：各库并行，跨库 RRF）
  → rerank（可选）→ 返回 chunks
```

现有代码里已经有一些兜底：

- 改写失败 → 用原 query 继续搜
- hybrid 下 BM25 失败 → 降级为纯 vector
- rerank 失败 → 退回重排前的顺序

但还不完整：

- BM25 挂了能降 vector，**vector / Embedding 挂了还不能降 BM25**——hybrid 只兜了一半
- 多库并行后，**任一库检索异常会让整单失败**——一个库拖垮全部
- 空 query、空库返回空列表，和系统错误在业务方眼里都是"没结果"，缺少区分

代码工作集中在检索链路上。

## 出问题时，只允许三种结局

先约定一条底线：**不要静默吞掉**——降级了就要在 metadata 里标 `degraded`，失败了就要有明确错误码。

| 结局 | 含义 | 典型场景 |
|------|------|----------|
| **拒绝** | 4xx / 5xx，这次做不了 | 参数不对、两路检索都挂、多库全挂 |
| **降级** | HTTP 200，结果打折 | rewrite 失败、单路检索失败、多库 partial、rerank 失败 |
| **重试** | 稍后再试 | 仅索引异步任务；retrieve 同步接口不重试 |

判断逻辑：

- 必选能力挂了，没有备用路径 → 拒绝
- 必选能力挂了，还有另一条路（hybrid 的另一路、多库的其他库）→ 降级
- 可选增强挂了（rewrite、rerank）→ 降级

## 检索链路各场景的处理策略

| 场景 | 策略 | 当前状态 |
|------|------|---------|
| query 为空或超长 | 拒绝 | 不统一，需补 |
| 改写 LLM 失败 | 降级，用原 query | 已有 |
| BM25 / ES 失败（hybrid） | 降级，仅 vector | 已有 |
| Vector / Embedding 失败（hybrid） | 降级，仅 BM25 | 整单失败，需补 |
| hybrid 两路都失败 | 拒绝 | 已有 |
| 多库：某一库失败 | 降级，其余库 RRF | 整单失败，需补 |
| 多库：全部失败 | 拒绝 | 已有 |
| rerank 失败 | 降级 | 已有 |
| 0 条 chunk | 200 + `empty_reason` | 仅空列表，需补 |
| Langfuse 不可用 | 降级，跳过 trace | 已有 |

降级时，metadata 里写清楚原因：

```json
"retrieval": {
  "degraded": true,
  "degraded_reason": "bm25 search failed",
  "failed_kb_ids": ["某库 id"],
  "partial_kb_success": true,
  "empty_reason": null
}
```

已有的 Langfuse 追踪和 retrieval_log 能观测这些字段，不需要新建观测体系，只在降级时把上述字段写全。
