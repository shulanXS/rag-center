# 健壮性与降级策略

这是工程设计系列的最后一篇。前两篇分别讲了 Provider 抽象（可扩展性）和错误码体系（可维护性），这篇讲可靠性——系统在局部故障时如何保持核心路径畅通。

## 核心路径不能被辅助功能拖垮

rag-center 的核心价值是"把用户的 query 变成有用的检索结果"。整个检索链路里，依赖可以分成两类：

- **核心依赖**：检索本身——向量检索、BM25 关键词检索、混合检索。没有检索就没有结果，这一环不可降级
- **辅助依赖**："锦上添花"的环节——LLM 查询改写、rerank 排序、Langfuse trace 写入

辅助依赖的故障不应该传播到核心路径。如果 LLM 改写超时了，用户应该拿到一个稍差的检索结果，而不是一个报错。如果 Langfuse 写入失败了，用户完全不应该感知到，因为这是系统内部的可观测性工具，和用户没有任何关系。

代码里最自然的写法是"调用 A，成功了再调用 B，成功了再调用 C"，任何一步出错都会中断。要让辅助依赖可降级，就需要在每个辅助调用上主动加容错逻辑。

## 核心依赖：哪些情况可以降级

核心依赖不是铁板一块，具体能不能降级，取决于检索模式：

- **纯向量模式**（`mode=vector`）：只有向量这一条路，向量检索失败就直接报错，没有备选
- **纯 BM25 模式**（`mode=bm25`）：同理，BM25 失败就报错
- **混合检索模式**（`mode=hybrid`）：两路并行，**任意一路失败时可以降级为另一路**；两路都失败才报错

混合检索的降级逻辑在 `_retrieve_candidates_for_kb`（`mode=hybrid` 分支）里：

```python
# rag-center/app/services/rag_service.py — hybrid 分支

try:
    vector_chunks = await self._vector_search(...)
except Exception:
    vector_failed = True
try:
    bm25_chunks = await self._bm25_search(...)
except Exception:
    bm25_failed = True

# 两路都挂 → 唯一失败出口
if vector_failed and bm25_failed:
    raise AppError(ErrorCode.RETRIEVAL_FAILED, ...)

# 向量挂 → 降级纯 BM25
if vector_failed and not bm25_failed:
    chunks = self._mark_bm25_chunks(bm25_chunks)
# ES 挂 → 降级纯向量
elif bm25_failed and not vector_failed:
    chunks = self._mark_vector_chunks(vector_chunks)
# 两路成功 → RRF 融合
else:
    chunks = self.hybrid_search_service.fuse_by_rrf(...)

return chunks, {
    "degraded": vector_failed or bm25_failed,
    "degraded_reason": degraded_reason,
}
```

多知识库在 `_retrieve_multi_kb` 里并行检索，单库失败跳过、其余库继续融合：

```python
# rag-center/app/services/rag_service.py — _retrieve_multi_kb

# 各库并行检索，单库异常不外抛
results = await asyncio.gather(*tasks, return_exceptions=True)

for kb, result in zip(knowledge_bases, results):
    if isinstance(result, BaseException):
        failed_kb_ids.append(kb.id)
        # 跳过失败库，其余库继续
        continue
    chunks_by_kb.append(tag_chunks_with_kb_id(...))

# 全部库失败才报错
if not chunks_by_kb:
    raise AppError(ErrorCode.RETRIEVAL_FAILED, ...)

merged = self.multi_kb_fusion_service.fuse_by_rrf(chunks_by_kb, top_n=top_k)
return merged, {
    # 是否部分库失败
    "partial_kb_success": bool(failed_kb_ids),
    "failed_kb_ids": failed_kb_ids or None,
    "degraded": bool(failed_kb_ids) or per_kb_degraded,
}
```

部分库失败仍返回 `code=0`，`metadata.retrieval` 标注 `partial_kb_success` / `failed_kb_ids` 供监控排查。

## LLM 查询改写的超时降级

LLM 改写超时或失败时，不抛错，而是用原始 query 继续检索：

```python
# rag-center/app/providers/query/llm_rewrite.py

try:
    # 超时由 QUERY_REWRITE_TIMEOUT_MS 控制
    response = await self.llm_provider.chat_json(
        ...,
        timeout_seconds=settings.query_rewrite_timeout_ms / 1000,
    )
    rewritten = self._extract_rewritten_query(response)
    return QueryProcessResult(search_query=rewritten, degraded=False, ...)
except Exception as exc:
    return QueryProcessResult(
        effective_query=raw_query,
        # 降级：不改写，原 query 继续检索
        search_query=raw_query,
        degraded=True,
        degraded_reason=str(exc),
    )
```

原始 query 本身就是用户的真实意图，只是没有经过优化。检索结果可能略差，但不是没有结果。`QueryProcessorPipeline` 在改写之后仍会跑同义词扩展；降级信息体现在 `metadata.query_processing.degraded`。

## Rerank 失败的降级

Rerank 失败时保留 RRF 排序的结果返回，RRF 结果本身已经是合理的排序，只是缺少语义精排这一步：

```python
# rag-center/app/services/rag_service.py — _maybe_rerank

try:
    reranked = await rerank_provider.rerank(query=..., chunks=chunks, top_n=top_n)
    return reranked, RetrieveRerankMetadata(enabled=True, ...)
except Exception as exc:
    fallback = [{**c, "rerank_score": None} for c in chunks[:min(top_n, len(chunks))]]
    # 保留 RRF 顺序，标注 degraded
    return fallback, RetrieveRerankMetadata(degraded=True, error=str(exc))
```

这里和第一篇里的 `NoopRerankProvider` 形成呼应：部署时没有配置 rerank 模型，走 noop 直接透传，不会进入 catch 分支；配置了但运行时出错，才进入 catch 分支降级。两种情况最终行为一致，触发路径不同。

## Langfuse 写入失败的处理

Langfuse 是旁路可观测工具，写入失败对用户零影响，只打 warning：

```python
# rag-center/app/observability/langfuse_client.py — finish() 等写入点同理

try:
    self._trace.update(output={...})
    self._langfuse.flush()
except Exception as exc:
    # 旁路失败，不 raise，retrieve 照常返回
    logger.warning("LANGFUSE_TRACE_FINISH_FAILED | ...")
```

检索结果已经返回给调用方了，Langfuse 的状态和用户完全无关。打 warning 是为了让监控系统能统计 Langfuse 的可用性。

## degraded 标注的工程价值

每种降级发生时，响应的 `metadata` 里各子段会带上 `degraded` 和具体原因：

```json
{
  "code": 0,
  "data": {
    "metadata": {
      "retrieval":       { "degraded": true, "degraded_reason": "bm25 search failed" },
      "rerank":          { "degraded": true, "error": "..." },
      "query_processing": { "degraded": false }
    }
  }
}
```

`code` 仍为 0——系统确实返回了结果，这不是业务错误。各子段的 `degraded` 有两个受众：

- **调用方的业务代码**：可以据此决定是否向用户展示"当前检索质量可能下降"的提示
- **监控系统**：可以统计各类降级的频率，降级率突然上升往往是某个依赖出了持续性问题的信号

没有这个标注，降级就是无声的——系统表现正常，但质量悄悄变差了。

## 区分核心依赖与辅助依赖

| 依赖 | 类型 | 故障处理 | 降级后效果 |
|------|------|---------|-----------|
| 纯向量 / 纯 BM25 检索 | 核心（不可降级） | 直接报错 | 请求失败，用户明确感知 |
| 混合检索（单路失败） | 核心（可降级） | 用另一路结果继续 | 缺少融合增益，仍有结果 |
| 混合检索（双路失败） | 核心（不可降级） | 直接报错 | 请求失败 |
| 多库检索（部分库失败） | 核心（可降级） | 其余库 RRF 融合 | 缺少失败库的内容 |
| LLM 查询改写 | 辅助 | 超时后用原始 query | 结果略差，用户有结果 |
| Rerank | 辅助 | 失败后保留 RRF 排序 | 缺少语义精排 |
| Langfuse | 辅助 | 失败静默，记录 warning | 用户无感知 |

判断能不能降级，看两点：**有没有合理的替代方案**，以及**会不会直接导致用户拿不到结果**。混合检索单路失败有备用（另一路），LLM 改写失败有备用（原始 query），Langfuse 失败根本不影响用户——这些都可以降级。纯向量或纯 BM25 没有备选，只能报错。

## 小结

健壮性不是追求"永不出错"，而是在局部出错时"尽量不让用户感知到"。通过在每个辅助依赖和可降级的核心路径上加超时控制、异常捕获和降级逻辑，rag-center 把多个可能的故障点转化为内部的质量降级，并通过 `degraded` 标注保持透明。

至此，工程设计系列三篇全部完成。第一篇的 Provider 抽象解决了技术选型的灵活性，第二篇的错误码体系让系统和调用方之间有了清晰的契约，第三篇的降级策略保障了核心路径在局部故障下的可用性。三者合在一起，构成了 rag-center 在工程层面的核心设计理念。
