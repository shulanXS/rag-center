# 检索日志与用户反馈

检索系统上线之后，最难回答的问题往往不是"系统能不能跑"，而是"效果好不好"。如果没有日志，你只能凭直觉猜测用户在问什么、系统在返回什么、哪些 query 始终答不好。rag-center 的效果评估体系从最基础的一层做起——把每次检索的过程和结果都记录下来。

## 为什么说检索是黑盒

一次检索调用的链路并不短。原始 query 可能被改写，召回会走向量检索和 BM25 两条路，rerank 会再次调整排名，最终返回的是若干 chunk。用户看到的只是最终结果，但系统内部发生了什么，在没有日志的情况下完全不可见。

问题会以各种方式暴露出来：用户反映"搜出来的不对"，你去排查，发现不知道当时的 query 是什么、用的是哪个 profile、召回了哪些 chunk、耗时多少。没有记录就没有起点，优化无从下手。

## retrieval_logs 表的字段设计

每次 retrieve 调用都会向 `retrieval_logs` 表写入一条记录（Alembic 迁移 `0001_initial` 建表，`0006` / `0007` 补充可观测字段）：

```sql
-- rag-center/migrations/versions/0001_initial.py（节选，经 0006/0007 演进）

CREATE TABLE retrieval_logs (
    id               VARCHAR(36) PRIMARY KEY,   -- log_id，UUID
    tenant_id        VARCHAR(128) NOT NULL,
    kb_id            VARCHAR(36) NOT NULL,    -- 主知识库（多库检索时取 kb_ids[0]）
    kb_ids           JSONB,                   -- 多库检索时的完整 kb 列表（0007）
    user_id          VARCHAR(128) NOT NULL,   -- 调用方传入的业务用户标识
    query            TEXT NOT NULL,           -- 用户原始问题
    search_query     TEXT,                    -- 同义词扩展后最终用于检索的 query（0006）
    effective_query  TEXT,                    -- LLM 改写后的 query（未做同义词扩展）（0006）
    profile          VARCHAR(32),             -- 本次 retrieve profile（0006）
    retrieved_chunks JSONB NOT NULL,        -- 召回 chunk 列表（含 content、score 等）
    top_k            INT NOT NULL,
    vector_store     VARCHAR(64) NOT NULL,
    latency_ms       INT NOT NULL,            -- 检索阶段耗时（不含 query 改写）
    trace_id         VARCHAR(64),             -- Langfuse trace ID（0006）
    created_at       TIMESTAMPTZ NOT NULL
);
```

每个字段都有明确用途：

- **query / search_query / effective_query**：`effective_query` 是 LLM 改写结果，`search_query` 在同义词扩展之后，才是向量/BM25 实际使用的文本；三者差异大的记录值得重点排查
- **profile**：记录本次走的是哪套检索配置，才能事后对比不同配置下的表现
- **latency_ms**：工程侧最直接的健康指标，P99 突然升高往往能在日志里找到具体的慢 query
- **trace_id**：这张表和 Langfuse 之间的桥梁；日志存完整召回结果，trace 存各阶段过程元数据
- **retrieved_chunks**：存为 JSONB，包含 `chunk_id`、`content`、`score`、`retrieval_source` 等字段，便于事后复盘；体积由 `top_k` 上限控制
- **user_id / top_k / vector_store**：记录调用上下文，排查「同一 query 不同用户表现不一致」时有用

日志在 `RagService.retrieve` 收尾阶段写入：检索与 rerank 完成后 `commit`，与 Langfuse `flush` 同批完成，不额外阻塞改写阶段：

```python
# rag-center/app/services/rag_service.py（检索收尾）

log_id = generate_uuid()  # 检索开始前生成，贯穿 trace 与日志

# ... query 改写、召回、rerank 完成后 ...

self.retrieval_log_repository.create(
    RetrievalLog(
        id=log_id,
        tenant_id=tenant_id,
        kb_id=primary_kb_id,           # kb_ids[0]
        kb_ids=kb_ids,
        user_id=resolved_request.user_id,
        query=resolved_request.query,
        retrieved_chunks=chunks,
        top_k=top_k,
        vector_store=retrieval_metadata.get("vector_store", self.vector_store.name),
        latency_ms=latency_ms,
        trace_id=observability.trace_id,  # Langfuse 未启用时为 None
        profile=tenant_policy.retrieve_profile,
        search_query=search_query,
        effective_query=query_result.effective_query,
    )
)
self.db.commit()

# 响应 metadata 中同时返回 log_id / trace_id，供前端提交反馈
return RetrieveData(
  # ...
  metadata=RetrieveMetadata(log_id=log_id, trace_id=observability.trace_id, ...),
)
```

## log_id 的价值

每条日志有一个全局唯一的 `id`（UUID 字符串），也就是 `log_id`。一次 retrieve 结束时，`metadata` 里会同时返回 `log_id` 和 `trace_id`——前者对应 PostgreSQL 里的业务日志，后者对应 Langfuse 里的过程 trace。

调用方在展示检索结果时，应把这两个 ID 一并带回前端或下游系统。用户提交评价时，**`trace_id` 必填**（评分挂在 Langfuse 的对应 trace 上）；**`log_id` 建议一并提交**，服务端会校验这条日志是否属于当前租户，且 `retrieval_logs.trace_id` 与请求一致，避免评价错绑到别的检索。评分写入 Langfuse 的 `user_feedback` score，不单独建反馈表，也不会回写到 `retrieval_logs`。

没有 `log_id` 和 `trace_id` 的交叉校验，反馈只能挂在 trace 上，无法从业务侧确认「评的是哪次检索」；没有 `trace_id`，则根本无法提交反馈。

## 用户反馈接口

反馈走 `POST /api/v1/rag/feedback`，由 `FeedbackService` 写入 Langfuse：

```python
# rag-center/app/schemas/feedback.py

class FeedbackRequest(BaseModel):
    trace_id: str = Field(min_length=1, max_length=64)  # 必填，对应 Langfuse trace
    log_id: str | None = Field(default=None, max_length=36)  # 可选，用于与 retrieval_logs 交叉校验
    score: int                                          # 1～5，服务层校验
    comment: str | None = None

# rag-center/app/api/v1/routes/rag.py

@router.post("/feedback")
def submit_feedback(
    request: FeedbackRequest,
    db: Session = Depends(get_db),
    tenant: TenantContext = Depends(get_current_tenant),
) -> dict:
    data = FeedbackService(db).submit_feedback(tenant.tenant_id, request)
    return success_response(data.model_dump(mode="json"))
```

```python
# rag-center/app/services/feedback_service.py（核心逻辑）

FEEDBACK_SCORE_NAME = "user_feedback"

def submit_feedback(self, tenant_id: str, request: FeedbackRequest) -> FeedbackData:
  # 分数范围 1～5
  if request.score < 1 or request.score > 5:
      raise AppError(ErrorCode.FEEDBACK_INVALID_SCORE, ...)

  # 若传了 log_id，校验记录存在且 trace_id 与日志一致
  if request.log_id:
      retrieval_log = self.retrieval_log_repository.get_by_id_and_tenant(
          request.log_id, tenant_id,
      )
      if retrieval_log is None:
          raise AppError(ErrorCode.NOT_FOUND, msg="检索记录不存在", ...)
      if retrieval_log.trace_id != request.trace_id:
          raise AppError(ErrorCode.FEEDBACK_LOG_MISMATCH, ...)

  # 反馈依赖 Langfuse；未启用时返回 20020，不静默丢弃
  langfuse = get_langfuse_client()
  if langfuse is None:
      raise AppError(ErrorCode.FEEDBACK_FAILED, msg="Langfuse 未启用或不可用")

  feedback_id = generate_uuid()
  langfuse.score(
      name=FEEDBACK_SCORE_NAME,
      value=request.score,
      trace_id=request.trace_id,
      id=feedback_id,
      comment=request.comment,
  )
  langfuse.flush()
  return FeedbackData(feedback_id=feedback_id, trace_id=request.trace_id, ...)
```

接口保持轻量，适合嵌在检索结果页——五星或「是否有帮助」按钮，异步提交 `trace_id` + `log_id` + `score` 即可。`LANGFUSE_ENABLED=false` 时反馈不可用，但 `retrieve` 仍正常返回 `log_id`。

## 低分反馈的数据价值

一旦用户开始提交反馈，1 分和 2 分的记录就是最有价值的信号。这些记录直接指向"系统明显表现不好"的 query，不需要人工猜测哪里有问题。

对这些低分记录做简单的归类，就能发现规律，比如：

- 某类专业术语的同义词没有配置，改写时偏离了原意
- 特定 kb 的 profile 配置偏向精确匹配，但用户习惯用口语提问
- 某些 query 召回的 chunk 都来自同一篇文档，多样性不足

除了指导即时的优化，低分记录还是构建评估集的原材料。把这些 query 加上人工标注的标准答案，就能形成有针对性的测试用例，用于后续的系统性评估。

## 日志是评估体系的起点

检索日志和用户反馈解决了"有没有数据"的问题。但日志记录的是结果，看不出过程。当 score 很低时，你知道这次检索效果差，但不知道是哪一步出了问题：是 query 改写出了偏差，还是向量召回没找到相关内容，还是 rerank 把好的结果排到了后面？

要回答这些问题，需要把检索过程的每一步都记录下来，而不只是最终结果。这正是 Langfuse 链路追踪解决的问题，下一篇会详细展开。
