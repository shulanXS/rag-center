# 多知识库并行检索与跨 KB 融合

前三篇描述的是单个知识库内部的检索流程。实际业务场景往往比这复杂：一个问题可能同时需要从产品文档库、FAQ 库、政策文档库里查。用户不可能自己发三次请求再合并结果，也不应该这样做。

rag-center 支持一次请求跨多个知识库检索，并把结果融合成一个统一的列表返回。这篇文章讲这套多知识库检索的设计思路。

## 业务动机

设想一个客服场景：知识库分了两个，一个存产品使用文档，一个存常见问题解答。用户问"如何申请退款"，答案可能在 FAQ 库里，但退款政策的详细说明可能在产品文档库里。

如果只能检索一个知识库，就需要用户提前知道答案在哪里。这对用户来说是不合理的负担。多知识库检索让系统承担这个判断责任：同时查多个库，把相关结果汇总，让用户看到完整的信息。

## 并行检索的实现

多个知识库的检索在 `RagService._retrieve_multi_kb` 里并行发起。每个 KB 独立跑完整单库管道（向量 / hybrid + 单库 RRF），查询优化在 KB 循环之前只做一次：

```
                  ┌─ KB-1 → 向量或 hybrid → 单库 RRF ─┐
search_query ─────┼─ KB-2 → 向量或 hybrid → 单库 RRF ─┼──→ MultiKbFusionService.fuse_by_rrf
 asyncio.gather   └─ KB-N → 向量或 hybrid → 单库 RRF ─┘
```

```python
# rag-center/app/services/rag_service.py

async def _retrieve_multi_kb(self, ..., knowledge_bases: list[KnowledgeBase], search_query: str, ...):
    # 每个 KB 独立跑单库召回（vector 或 hybrid+RRF）
    tasks = [
        self._retrieve_candidates_for_kb(
            tenant_id=tenant_id,
            kb_id=kb.id,
            search_query=search_query,   # 查询优化只做一次，各库共用
            mode=mode,
            per_kb_top_k=per_kb_top_k,   # 单库候选宽度，通常 ≥ 最终 top_k
        )
        for kb in knowledge_bases
    ]
    results = await asyncio.gather(*tasks, return_exceptions=True)

    for kb, result in zip(knowledge_bases, results, strict=True):
        if isinstance(result, BaseException):
            failed_kb_ids.append(kb.id)   # 单库失败记日志，其余库继续
            continue
        chunks, metadata = result
        # 打上来源标记，供展示与跨库融合后溯源
        chunks_by_kb.append([{**chunk, "kb_id": kb.id, "kb_name": kb.name} for chunk in chunks])

    # 仅 1 个库成功时直接截断；多库时做跨 KB RRF
    if len(chunks_by_kb) > 1:
        merged_chunks = self.multi_kb_fusion_service.fuse_by_rrf(
            chunks_by_kb=chunks_by_kb,
            rrf_k=self._get_rrf_k(request),
            top_n=top_k,
        )
```

并行执行的好处是**整体延迟取决于最慢的那个知识库**，而不是所有知识库延迟的总和。5 个知识库各自需要 200ms，串行执行需要 1000ms，并行执行只需要约 200ms。

`return_exceptions=True` 是单点故障隔离的关键：某个知识库的检索超时或报错，其他库的结果仍然会正常返回，不会因为一个库的问题让整次请求失败。

## 跨 KB 的 RRF 二次融合

每个知识库返回了自己的 chunk 列表，每个列表内部已经经过 RRF 融合排好了序。现在需要把多个列表合并成一个。

这里遇到了和第三篇一样的问题：不同知识库返回的分数不可直接比较。知识库 A 的第一名分数是 0.85，知识库 B 的第一名分数是 0.72，这不代表 A 的第一名比 B 的第一名更相关——它们的分数来自各自库内的相对比较，没有可比性。

跨 KB 融合仍用 RRF 思想，但实现与单库内「按 chunk_id 累加」不同：每个 KB 返回的已排序列表按名次赋分 `1/(k+rank)`，所有候选放入同一池子再全局排序截断：

```python
# rag-center/app/services/multi_kb_fusion_service.py

def fuse_by_rrf(self, *, chunks_by_kb: list[list[dict]], rrf_k: int, top_n: int) -> list[dict]:
    fused: list[dict] = []
    for kb_chunks in chunks_by_kb:
        # 每个 KB 内部已排好序，只取库内名次映射为 RRF 分
        for rank, chunk in enumerate(kb_chunks, start=1):
            fused.append({
                **chunk,
                "score": 1.0 / (rrf_k + rank),
                "kb_rank": rank,   # 该 chunk 在所属 KB 内的名次
            })
    # 全局按 score 排序，取最终 top_n（跨库分数已归一化到同一量级）
    fused.sort(key=lambda item: item["score"], reverse=True)
    return fused[:top_n]
```

不同 KB 的原始分数仍不可比，但「各库内排名第 1」会被映射到同一量级（约 `1/(k+1)`），再在同一排名空间里竞争最终 top_k。

## KB 数量限制与 Plan 约束

允许同时检索的知识库数量有上限，由用户的套餐决定：

| 套餐 | 最多联检知识库数 |
|---|---|
| free | 1 个 |
| standard | 3 个 |
| pro | 5 个 |

超出上限时 `resolve_retrieve_request` 直接抛出 `FEATURE_NOT_ALLOWED`，不会静默截断 `kb_ids`。

这个上限本质上是对计算资源的保护。并行的 5 个知识库，每个知识库内部又是向量检索和 BM25 两路并行，加上查询优化的 LLM 调用，资源消耗是显著的。Plan 约束把高资源消耗的用法限定在付费层级。

## 结果里保留 kb_id 来源

每个返回的 chunk 都带有 `kb_id` 字段，标记它来自哪个知识库。这个字段的意义不只是调试用：

- 调用方可以在展示时标注来源（"来自产品文档"或"来自 FAQ"），让用户知道答案的出处
- 在后续引用时精确定位文档，生成带来源的引用标注
- 排查检索问题时，能直接看出每个 chunk 从哪个库召回的

保留来源信息是一个通用原则：检索引擎在做信息融合时，不应该丢失信息的溯源能力。
