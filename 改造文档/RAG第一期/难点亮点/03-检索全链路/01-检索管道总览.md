# 检索管道总览

rag-center 的检索引擎不是一个黑盒函数。它是一条有明确分工的管道，每个环节都有存在的理由。这篇文章是全链路的地图，帮助你在进入细节之前先建立整体认知。

## 全链路一览

从用户发出一个查询，到拿到最终的 chunk 列表，整条管道长这样：

```
用户 query
    │
    ▼
┌─────────────────────────────┐
│         查询优化             │
│  可选 LLM 改写 → 同义词扩展  │
│  失败降级：用原始 query 继续  │
└──────────────┬──────────────┘
               │ search_query
    ┌──────────┴──────────┐
    ▼                     ▼
pgvector               Elasticsearch
向量检索                BM25 检索
（余弦相似度）           （IK 中文分词）
    │                     │
    └──────────┬──────────┘
               ▼
         RRF 融合
         rank 归一化
               │
               ▼
       可选：LLM 重排
       （pro 计划）
               │
               ▼
        最终 chunk 列表
        （含 kb_id 来源信息）
```

多知识库场景下，整条管道会并行执行多次——每个知识库跑一遍，最后再做一次跨 KB 的 RRF 融合。这个细节在第四篇详细展开。

管道的入口是 `RagService.retrieve()`，按顺序串联各环节，并处理各阶段的降级逻辑：

```python
# rag-center/app/services/rag_service.py

async def retrieve(self, tenant_id: str, request: RetrieveRequest) -> RetrieveData:
    # 从租户记录解析套餐上下文（plan、功能开关、配额上限）
    plan_context = PlanResolver.resolve_plan(tenant)
    # Profile 展开 + Plan 校验 → 实际生效的检索参数
    resolved_request, tenant_policy = resolve_retrieve_request(request, plan_context)

    # 检索频次配额：QPS + 日限额，超限直接拒绝
    get_rate_limit_service().check_retrieve(
        tenant_id,
        qps_limit=plan_context.limits.retrieve_qps,
        daily_limit=plan_context.limits.daily_retrieve_limit,
    )

    # 查询优化：可选 LLM 改写 → 同义词扩展，产出 search_query
    query_result = await self.query_processor.process(
        resolved_request.query,
        kb=self._build_query_context(knowledge_bases),  # 多库时合并主库 settings
        query_options=resolved_request.query_options,
    )
    search_query = query_result.search_query

    # 多 KB 并行召回；单库内 vector/hybrid+RRF，多库时再跨库 RRF
    chunks, retrieval_metadata = await self._retrieve_multi_kb(
        tenant_id=tenant_id,
        request=resolved_request,
        knowledge_bases=knowledge_bases,
        search_query=search_query,
        mode=retrieval_mode,
        top_k=top_k,
        per_kb_top_k=per_kb_top_k,
    )

    # 可选 LLM 重排；失败时 RagService 内部降级为 RRF/向量结果
    chunks, rerank_metadata = await self._maybe_rerank(
        request=resolved_request,
        chunks=chunks,
        top_k=min(top_k, len(chunks)) if chunks else top_k,
    )
    return RetrieveData(...)
```

## 各环节的职责

管道里的每个阶段承担不同职责，也有各自的可选性：

| 阶段 | 核心职责 | 是否必选 |
|---|---|---|
| 查询优化 | 可选 LLM 改写 + 同义词扩展，产出 `search_query` | 改写按 profile/Plan；同义词有词表即生效 |
| 向量检索 | pgvector 余弦相似度，语义模糊匹配 | 必选 |
| BM25 检索 | Elasticsearch 关键词检索，精确词命中 | hybrid 模式下必选 |
| RRF 融合 | 倒数排名融合，统一两路结果的排名空间 | hybrid 模式下必选 |
| LLM 重排 | 对候选 chunk 精排，效果最好、成本最高 | 可选，pro 专属 |

**查询优化**是整条链路的起点。用户原始 query 先经可选 LLM 改写得到 `effective_query`，再经知识库 `settings.synonyms` 扩展得到 `search_query`。改写仅在 quality 等配置下开启；同义词扩展不依赖 profile，只要词表配置了就会执行。

**双路召回**是核心设计。pgvector 做向量检索，擅长捕捉语义相似性；Elasticsearch 做 BM25 检索，擅长关键词精确匹配。两者互补：只用向量会漏掉关键词完全命中的文档，只用 BM25 会漏掉措辞不同但语义相关的文档。两路并行执行，各自返回 top_k 的候选 chunk。

**RRF 融合**解决了一个实际问题：向量检索的分数是余弦相似度（0 到 1），BM25 的分数是 TF-IDF 加权的词频统计量，量纲完全不同，不能直接加权。RRF 只看每路检索的排名，不看原始分数，天然绕过了这个问题。融合之后，两路召回的结果合并成一个统一排名的列表。

**LLM 重排**是可选的精排环节。在 RRF 融合之后，用 LLM 对候选 chunk 逐一打相关性分再重新排序。效果最好，成本也最高，因此只在 pro 计划开放。跳过重排时，RRF 的输出直接作为最终结果。

**Profile 与 Plan** 是控制整条管道行为的两层约束。Profile 是预设策略（`speed` / `balanced` / `quality` / `custom`），一个词代表一套检索参数；Plan 是套餐上限（能否用 hybrid、rerank、哪些 profile）。两者在 `resolve_retrieve_request()` 里合并，决定 `RagService` 里每个环节的实际参数。

## 为什么是这条管道

这条设计的核心思路是**效果和成本的分层**。最基础的 speed profile 只走向量检索，响应快、成本低；quality profile 开启全部优化，效果最好，但调用了 LLM 两次。不同用户按需选择，平台按 plan 兜底，避免资源滥用。

管道里每个环节的降级逻辑也是刻意设计的。LLM 改写超时就用原始 query，LLM 重排失败就用 RRF 结果，任何一个环节的不稳定都不会让整条链路崩溃。这个"可选环节不能成为单点故障"的原则，贯穿整条管道的设计。
