# 提问语义优化测试验收

## 测试准备

提示词对应的代码已完成，`alembic upgrade head` 跑完，`knowledge_bases.settings` 列已存在。已有知识库和文档，`.env` 配好 LLM，后端已启动，检索页能正常召回。

准备两个知识库，KB_A 配有词表，KB_B 不配词表。

给 KB_A 写入词表：

```bash
python scripts/update_kb_settings.py \
  --kb-id KB_A \
  --settings-file kb_settings.json
```

`kb_settings.json`：

```json
{
  "synonyms": [
    {"terms": ["背调"], "expand": ["背景调查", "标准问题清单"]},
    {"terms": ["薪酬", "薪资", "工资"], "expand": ["职级", "薪酬定级", "定级标准"]}
  ]
}
```

预期：终端提示更新成功，打印 kb_id 和 synonyms 组数（2 组）。

## LLM 改写测试

### 1. 默认不改写，行为与改前一致

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/rag/retrieve \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{"kb_id":"KB_A","user_id":"test_user","query":"背调要问啥"}'
```

预期：`code` 为 0，`data.query` 为原话「背调要问啥」，`metadata.query_processing` 为 null 或 enabled=false，召回正常。

### 2. 开启改写，改写句应与原话不同

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/rag/retrieve \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{
    "kb_id": "KB_A",
    "user_id": "test_user",
    "query": "背调要问啥",
    "query_options": {"enabled": true, "strategy": "rewrite"}
  }'
```

预期：

1. `metadata.query_processing.degraded` 为 false
2. `raw_query` 为「背调要问啥」，`effective_query` 为改写后的句子，更贴近文档表述
3. `data.query` 仍为原话「背调要问啥」，不被替换
4. `rewrite_latency_ms` 有值

### 3. LLM 不可用时，检索不挂

临时把 `.env` 里 `LLM_API_KEY` 改成错误值，重启后端，再发带 `query_options` 的请求：

预期：

1. `code` 仍为 0，不报 500
2. `metadata.query_processing.degraded` 为 true
3. `effective_query` 等于 `raw_query`，检索正常返回结果

## 词表扩展测试

### 1. 词表命中，扩展词应追加到检索句

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/rag/retrieve \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{"kb_id":"KB_A","user_id":"test_user","query":"背调要问啥"}'
```

预期：

1. `synonym_applied` 为 true
2. `synonym_expansions` 含「背景调查」「标准问题清单」
3. `search_query` 比 `effective_query` 多出扩展词

### 2. 多组词表同时命中，扩展词去重合并

```bash
-d '{"kb_id":"KB_A","user_id":"test_user","query":"背调和薪酬怎么谈"}'
```

预期：两组 synonyms 均命中，`synonym_expansions` 去重后包含两组的全部 expand 词。

### 3. 未命中词表，行为不变

```bash
-d '{"kb_id":"KB_A","user_id":"test_user","query":"面试官行为规范有哪些"}'
```

预期：`synonym_applied` 为 false，`search_query` 与 `effective_query` 相同。

### 4. 跨库隔离，KB_B 无词表

```bash
-d '{"kb_id":"KB_B","user_id":"test_user","query":"背调要问啥"}'
```

预期：`synonym_applied` 为 false，无扩展词，与 KB_A 的词表完全独立互不影响。

## 调试台测试

### 1. 勾选改写开关，运行摘要展示对比

打开 `/retrieve`，勾选「启用 query 改写」，输入「背调要问啥」点检索：

1. 运行摘要显示原话和实际检索句，两者可不同
2. 若词表命中，展示追加的扩展词列表

### 2. 取消勾选，词表仍独立生效

取消勾选「启用 query 改写」，用同一 query 再检索：

1. 运行摘要无改写相关字段，或实际检索句等于原话
2. 若词表仍命中，最终检索句仍含扩展词。词表扩展不受改写开关控制，只要 kb 有配置就会生效。

### 3. 无词表无改写的 KB_B

切换到 KB_B，关闭改写勾选检索：

1. 运行摘要无 `query_processing`，或该字段为 null
2. 检索结果正常
