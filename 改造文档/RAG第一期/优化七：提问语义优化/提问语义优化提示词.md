# 设计提问语义优化提示词

点击此处可复制本篇提示词

提问语义优化有两层，放在一篇里统一设计，避免第二层上来就要重构第一层刚搭的 pipeline 骨架。思路是先把三步链路的数据结构定好，再逐层填充实现。

## 使用场景

这份提示词用于在当前 RAG 中台工程基础上，增加提问语义优化能力。

当前链路直接用用户原话做检索。口语化的问法和文档里的专业表述往往词汇不重合，比如用户说「背调要问啥」，文档里写的是「背景调查标准问题清单」，导致召回率不高。

需要在检索前插入两层可选处理：

- **LLM 改问**：把口语 query 改成更贴近文档表述的检索句
- **词表扩展**：若 query 包含业务术语，自动追加扩展词

改造后的检索流程：

```
用户原话
  → [可选] LLM 改问法 → 改写句
  → [可选] 词表扩展   → 最终检索句
  → hybrid / vector / bm25 检索
  → 可选 rerank（已有，本篇不动）
```

两层均默认关闭，失败时自动降级，不影响检索主流程。

### 一、功能目标

在 rag-center 项目一步完成提问语义优化：

- 新增 `app/providers/query/` 目录，实现 QueryProcessor 抽象，包含 noop、llm_rewrite、synonym 三种实现
- `knowledge_bases` 表增加 `settings` JSONB 字段，存储词表等 kb 级配置
- `retrieve` 接口支持可选 `query_options`，响应 `metadata` 补充 `query_processing` 链路信息
- `RagService.retrieve` 在检索前调用 QueryPipeline，最终用扩展后的 `search_query` 做检索
- 调试台增加改写开关，并在运行摘要中展示改写和扩展结果
- 新增 `scripts/update_kb_settings.py` 脚本维护词表

### 二、代码结构

在现有工程中新增：

```
app/
  providers/
    query/
      base.py              # QueryProcessResult、抽象接口
      noop.py              # 直通，不做任何处理
      llm_rewrite.py       # LLM 改问法
      synonym_expander.py  # 词表扩展
      pipeline.py          # 串联三步，按 query_options 选择策略
scripts/
  update_kb_settings.py    # 维护 kb 词表配置
```

### 三、QueryProcessResult 数据结构

pipeline 最终返回一个完整结果，覆盖整条链路。三个核心字段代表的是同一 query 的三个阶段：`raw_query` 是用户原话，`effective_query` 是 LLM 改写后的句子，`search_query` 是追加扩展词后实际送入检索的最终句子。若某层未处理，对应字段等于上一层的值，业务代码始终用 `search_query` 检索即可。

| 字段 | 类型 | 说明 |
|---|---|---|
| raw_query | string | 用户原话，全程不变 |
| effective_query | string | LLM 改写后的句子，未改写时等于 raw_query |
| search_query | string | 词表扩展后的最终检索句，无扩展时等于 effective_query |
| strategy | string | noop 或 rewrite |
| rewrite_latency_ms | int | 改写耗时，单独计，不混入检索 latency_ms |
| degraded | bool | LLM 改写是否失败并回退 |
| degraded_reason | string | 失败原因，供调试台展示 |
| synonym_applied | bool | 词表是否命中 |
| synonym_expansions | list[str] | 本次追加的扩展词列表 |

### 四、LLM 改问法

**复用现有 `LLMProvider`**，不新增模型配置。LLM 只需要用户原话加上知识库的名称和领域描述，就能完成改写，不需要读取文档正文，避免 token 膨胀。

输入三项：用户原话、`kb.name`（如「客服退款政策库」）、`kb.description`（如「电商售后、退款、物流时效相关制度」）。

若 `knowledge_bases.settings` 里配了 `rewrite_hint` 字段，将其与 description 拼接后传入 Prompt，格式为 `description + "\n" + rewrite_hint`，需在代码注释里说明此规则。`rewrite_hint` 的用途是让业务方给 LLM 提供更精准的领域说明，比如告知某些缩写的含义。

**给 LLM 的 system prompt：**

```
你是检索 query 改写器，不是问答助手。
输入：用户原话 + 知识库名称 + 知识库领域说明。
输出：一条中文短句，更贴近文档常用表述，不超过 30 字。
不编造事实，不扩展用户没问的内容，不生成答案。
只输出改写后的句子，不输出解释。
```

`temperature=0` 或低值，`max_tokens=128`。

**降级规则：**

LLM 超时、报错、返回空时，将 `effective_query` 回退为 `raw_query`，标记 `degraded=true`，检索照常继续，不能因此 500。改写耗时单独记录，不算进检索 `latency_ms`。

### 五、词表扩展

纯函数逻辑，不调 LLM。词表存在 `kb.settings.synonyms` 里，由运维脚本维护，不进平台代码。

```json
{
  "synonyms": [
    {
      "terms": ["背调"],
      "expand": ["背景调查", "标准问题清单"]
    },
    {
      "terms": ["薪酬", "薪资", "工资"],
      "expand": ["职级", "薪酬定级", "定级标准"]
    }
  ],
  "rewrite_hint": "可选，补充给 LLM 改写 Prompt 的领域说明"
}
```

`synonyms` 和 `rewrite_hint` 是两个独立机制：前者在改写之后追加扩展词，后者在改写时给 LLM 提供额外上下文，互不干扰。

**匹配与扩展规则：**

1. 遍历每组 synonyms，若 `effective_query` 包含任一 term 则命中该组
2. 中文 term 精确子串匹配，英文 term 忽略大小写
3. 命中组的 expand 词追加到 query 末尾，空格分隔
4. 多组同时命中时，expand 去重后追加，得到 `search_query`
5. 未命中任何 term 时，`search_query` 等于 `effective_query`

词表仅对当前 kb 生效，不跨库、不跨租户。

### 六、Pipeline 串联

LLM 改写和词表扩展是两套独立机制，可以单独使用其中一种，也可以组合。按 `query_options` 和全局 `QUERY_REWRITE_ENABLED` 决定是否改写，请求级优先于全局：

```
raw_query
  → [若 enabled] llm_rewrite → effective_query
  → [有 settings.synonyms] synonym_expand → search_query
  → 返回完整 QueryProcessResult
```

词表扩展始终执行，只要 kb 有 settings 就会尝试，不受 `query_options.enabled` 控制。这意味着即使不开 LLM 改写，词表也会生效。

### 七、数据库变化

Alembic 新迁移：`knowledge_bases.settings` JSONB NOT NULL DEFAULT `{}`。

`app/models/knowledge_base.py` 增加 settings 字段。create 知识库时 settings 默认 `{}`。`KnowledgeBaseRepository` 增加读写 settings 的方法。

### 八、Schema 变化

**请求：RetrieveRequest 增加可选 query_options**

```json
{
  "query_options": {
    "enabled": true,
    "strategy": "rewrite"
  }
}
```

**响应：RetrieveMetadata 增加 query_processing**

`query_processing` 的作用是让调试台和日志清晰看到改写前后的完整链路，不是给业务方的核心字段，仅供诊断用。

```json
{
  "query_processing": {
    "raw_query": "背调要问啥",
    "effective_query": "背景调查标准问题有哪些",
    "search_query": "背景调查标准问题有哪些 背景调查 标准问题清单",
    "rewrite_latency_ms": 480,
    "degraded": false,
    "synonym_applied": true,
    "synonym_expansions": ["背景调查", "标准问题清单"]
  }
}
```

开了改写、词表命中，或 `search_query` 与 `raw_query` 不同时，返回 `query_processing`；全无处理时返回 null，保持与改前兼容。

`RetrieveData.query` 仍返回用户原始 query，不替换为改写后的句子。rerank 也仍用 `request.query`，不用 `search_query`。

### 九、RagService 接入位置

在 kb 归属校验通过之后、`_retrieve_candidates` 之前调用 QueryPipeline。同一次 knowledge_base 查询取出 name、description、settings 即可，不重复查库。

后续 `_vector_search`、`_bm25_search` 的 query 入参统一改用 `search_query`，hybrid 和 rerank 其余逻辑不动。`retrieval_logs` 可选增加 `effective_query`、`search_query` 字段，便于后续分析改写效果。

### 十、配置项

`.env.example` 补充：

```env
QUERY_REWRITE_ENABLED=false
QUERY_REWRITE_TIMEOUT_MS=2000
```

`QUERY_REWRITE_ENABLED` 全局默认关，避免所有请求被动调 LLM。LLM 模型复用现有 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`，不单独加配置。词表扩展无全局开关，有 settings 即尝试。

### 十一、运维脚本

```bash
python scripts/update_kb_settings.py \
  --kb-id <kb_id> \
  --settings-file kb_settings.json
```

`--kb-id` 和 `--settings-file` 均必填。校验 kb_id 在 DB 是否存在，不存在报错退出。整文件覆盖 `knowledge_bases.settings` 字段，文档与脚本注释写清楚这一点。打印更新后的 kb_id 和 synonyms 组数。

同时在 `examples/` 提供 `kb_settings.example.json`，含 synonyms 和可选 rewrite_hint。

### 十二、调试台

**检索配置区**

增加勾选「启用 query 改写」，勾选时传 `query_options: { enabled: true, strategy: "rewrite" }`，未勾选时不传 `query_options`，行为与改前一致。勾选框旁加 HelpTooltip：「用 AI 把口语问题改成更好搜的说法；更慢、消耗 LLM，可对比开关效果。」

**运行摘要区**

- 原话：用户输入的原始问题
- 实际检索句：LLM 改写后的结果，对应 `effective_query`
- 最终检索句：追加扩展词后的结果，对应 `search_query`，与上一项不同时才突出展示
- 改写耗时，对应 `rewrite_latency_ms`
- 若改写失败降级，提示「改写失败，已用原话检索」
- 若词表命中，展示追加的扩展词列表

`types/api.ts` 和 `ragService` 对齐新字段，不做词表在线编辑 UI。

### 十三、验收标准

- 不传 `query_options` 且 kb 无 settings，与改前完全一致，`query_processing` 为 null
- `query_options.enabled=true` 时，`metadata.query_processing` 有 `effective_query`，可与 `raw_query` 不同
- LLM 不可用时，`degraded=true`，`effective_query` 等于 `raw_query`，code 仍为 0，检索不挂
- 配置 synonyms 且 query 命中 term，`synonym_applied=true`，`search_query` 含扩展词
- 不开改写、仅词表命中，synonym 仍生效，`query_processing` 返回 search 链路
- 改写和词表同时开，`raw → effective → search_query` 完整链路均有值
- 两个 kb 各配不同 synonyms，同一 query 扩展互不影响
- 调试台勾选「启用改写」，运行摘要展示改写前后对比；词表命中时展示扩展词列表
