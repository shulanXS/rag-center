# 00 - 为什么要做语义优化

优化五搭完调试台后，知识库里有哪些 chunk、每条 query 召回了什么，都能直接看到。但真正调试时，还是会反复碰到同一种情况：**问题并不含糊，库里也有相关文档，结果却不对路**——排在第一的「有点沾边，但不是想要的那段」；目标文档有时甚至挤不进前几名。

以招聘知识库为例。用户问「背调要问啥」，库里有《候选人背调通用流程与标准问题清单》。但不做任何处理时，调试台里排第一的往往是其他文档里顺带提到「背调」的零碎片段——招聘流程里的「背调 → Offer」、某份 JD 末尾的「… → 背调 → Offer」。这些片段和问题沾边，却答非所问。

这不是偶发 bug，而是 RAG 里很典型的问题：**人和系统对「同一件事」用的不是同一套说法**。

## 人能理解，系统不会

人看到「背调要问啥」，会直接理解背后的意图——想看标准问题清单。但检索系统不理解意图，只做一件事：在切好的文档块里找出和问句**最像**的几段。

「最像」靠两招：词语有没有重叠（BM25）、整句语义是否接近（向量）。混合检索把两招组合起来用。

但实际上两招都会失手。「背调要问啥」和「标准问题清单」字面重叠少，BM25 容易偏弱；向量有时能靠语义拉近，但问句太短太口语，和制度文档那种条款式写法风格差太远，相似度也不稳定。更常见的是：用户说「背调」，文档关键段落写「背景调查」——对人是同一件事，对机器却是两套字。

问题不在「用户不会问」，而在于：**问句还没有变成文档里真正会出现的那种说法，检索就已经开始了**。

## 在「去搜」之前整理问句

混合检索、重排这些步骤都作用于**已经捞上来的候选 chunk**。问句偏了，捞上来的就大量是「沾边」的内容，后面再怎么精排也只是在这批偏的结果里挑。

想在源头少捞错，就得在**真正检索之前**，把用户的问句往知识库的表述习惯上靠一靠。只改**拿去搜的那句话**，不替用户答题，也不动库里的文档。整理失败就退回原话，检索照常跑——这就是「提问语义优化」要做的事。

```
用户原话
  → 问句整理（语义优化）
  → 向量 / 关键词 / 混合检索
  → （可选）重排
```

这层默认可以不开。文档规范、提问也规范时，直接拿原话搜往往就够。只有从调试台里反复看到「库里有、搜不到或搜偏了」，才值得打开。

## 两类不对齐，两种解法

「把问句往文档那边靠」听起来是一件事，实际会遇到两类缺口，解法不同，所以后面拆成两篇分别实现。

**第一类：问法花样太多。**「背调要问啥」「背调一般问什么」「入职前背调问哪些」——意思相近，写法各异，没法提前穷举。这类情况适合让 LLM 结合知识库名称和描述，把原话改成一条更贴近文档风格的检索句。代价是多一次模型调用，默认关闭。详见 **01 - Query 语义改写**。

**第二类：说法对照是固定的。**「JD」对应文档标题里的「岗位描述」，「背调」对应关键段落里的「背景调查」——这类对照建库的人最清楚，写进词表比每次赌模型更稳，也不花 LLM 调用。详见 **02 - 知识库词表配置**。

两者串起来是一条流水线：**先改句子（可选），再补术语（有词表就走）**，然后用整理后的句子去检索。LLM 不知道内部缩写和制度原文的固定写法；词表也补不了没收录的口语——所以不是二选一，而是各管一段，前后配合。

| | LLM 改问法 | 知识库词表 |
|--|-----------|-----------|
| 典型场景 | 口语、省略、问法花样多 | 缩写、术语、固定说法 |
| 谁维护 | 平台能力 + 知识库描述 | 建库方配置 |
| 成本 | 多一次 LLM 调用 | 几乎为零 |
| 可预期性 | 中等 | 高 |
| 默认 | 关 | 配了词表即生效 |

不是每个库都要全开。规范库、规范问法可以零配置；口语多可以在调试台试 LLM 改写；术语和缩写多，词表往往更划算——招聘库就是「词表打底、按需开改写」的典型组合。
