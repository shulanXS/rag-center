# 02 - 知识库词表配置

背景见 [00-为什么要做语义优化](./00-为什么要做语义优化.md)。01 产出 `effective_query` 后，本篇用 **知识库词表** 做术语扩展，得到 `search_query`。每个知识库单独配一张词表：**query 里出现 A 词，搜索时自动带上 B 词**；不同业务维护各自的词表，不写进平台代码。

**01 + 02 都完成后的处理顺序：**

```
用户原话
  → [01] LLM 改问法（可选）→ effective_query
  → [02] 词表扩展（若命中）→ search_query
  → hybrid / vector / bm25 检索
```

租户默认开不开改写、LLM 配额、快/准档位 → 后续「多租户完整落地」，本篇不做。

## 数据存哪

给 `knowledge_bases` 表增加 `settings` 字段，类型 JSONB，默认 `{}`，新跑一条 Alembic 迁移即可。

词表结构示例：

```json
{
  "synonyms": [
    {
      "terms": ["背调"],
      "expand": ["背景调查", "标准问题清单"]
    },
    {
      "terms": ["薪酬", "薪资", "工资"],
      "expand": ["职级", "薪酬定级", "定级标准"]
    }
  ],
  "rewrite_hint": "可选，补充给 01 改写的领域说明；有则拼进 Prompt，没有则只用 description"
}
```

说明：

- **synonyms**：数组，每组 `terms` 是用户可能说的词，`expand` 是搜索时要追加的词
- **rewrite_hint**：可选。01 的 LLM 改写若读到该字段，会把它与 `description` 一起拼进 Prompt 作为领域提示。实现时选一种方式写定就好，比如 `description + "\n" + rewrite_hint`，然后写进代码注释。
- 词表 **只对当前 kb 生效**，不跨库、不跨租户

## 词表怎么用

在 01 的 `effective_query` 之后、送入检索之前：

1. 读取该 kb 的 `settings.synonyms`
2. 若 `effective_query` **包含** 某一组的任一 `term`，大小写策略实现时定一种，建议中文精确匹配、英文 ignore case
3. 将该组 `expand` 中的词**追加**到 query 字符串末尾，空格分隔，得到 `search_query`
4. 向量和 BM25 **都用** `search_query`，与 01 一致，一条最终 query 进检索
5. 多组可同时命中，expand 去重后追加

未命中任何 term → `search_query = effective_query`，行为与仅开 01 时相同。

**metadata 补充：**

```json
{
  "query_processing": {
    "raw_query": "...",
    "effective_query": "...",
    "search_query": "...",
    "synonym_expansions": ["背景调查", "标准问题清单"],
    "synonym_applied": true
  }
}
```

## 怎么维护词表（MVP）

调试台和中台早期 **不做词表编辑 UI**。用脚本更新即可：

```bash
python scripts/update_kb_settings.py \
  --kb-id <kb_id> \
  --settings-file kb_settings.json
```

`kb_settings.json` 即上面的 JSON。脚本内校验 kb 是否存在，若脚本走 DB 不验 Key，至少校验 kb_id 存在。

**可选（scope 紧就只做脚本）：** 增加 `PATCH /api/v1/knowledge-bases/{kb_id}/settings`，需鉴权，只更新 `settings` 字段。

## 后端模块

在 `app/providers/query/` 增加：

```
synonym_expander.py   # 读 settings.synonyms，输入 effective_query，输出 search_query + expansions
```

在 `pipeline.py` 里串联：`rewrite` → `synonym_expand` → 返回最终 `search_query` 给 RagService。

`KnowledgeBaseRepository` / Model 增加 `settings` 读写；`create` 知识库时 `settings` 默认 `{}`。

## 调试台怎么改

检索页「运行摘要」在 01 基础上增加：

- **最终检索句**：`search_query`，与 `effective_query` 不同时才突出展示
- **词表扩展**：若 `synonym_applied`，列出 `synonym_expansions`

不必做词表在线编辑。可选在摘要脚注只读展示「当前库已配置 N 组同义词」，这需要后端在 tree 或 retrieve 上下文里带 settings 摘要，MVP 可以先省略。

## 这篇做什么、不做什么

本篇在 01 的基础上增加词表扩展：`knowledge_bases.settings` 迁移、`SynonymExpander` 接入 pipeline、`scripts/update_kb_settings.py` 脚本维护词表、调试台展示扩展结果。不做词表 Admin Web UI、ES 索引级 synonym filter、Multi-Query，也不做租户级词表，先做 kb 级。

## 给 AI 的提示词

把下面整段复制给 AI，一步完成开发：

```
在 rag-center 项目完成「提问语义优化 - 02 知识库词表配置」（01 LLM 改问法已完成）。

背景：01 产出 effective_query。本篇在其后按 kb.settings.synonyms 做 query 扩展，得到 search_query 再检索。词表 per-kb、脚本维护，不做 Admin UI 与前端词表上传。背景文档见 V2/优化七：提问语义优化/00-为什么要做语义优化.md。

【1. 数据库：settings 存哪】
- Alembic 迁移：knowledge_bases.settings JSONB NOT NULL DEFAULT '{}'
- app/models/knowledge_base.py 增加 settings 字段（dict / JSONB）
- create 知识库时 settings 默认 {}
- Repository 读写 settings；RagService 取 kb 时一并带出 settings

【2. Provider：词表扩展放哪】
- 新增 app/providers/query/synonym_expander.py，风格对齐 01 的 noop / llm_rewrite
- 纯函数或轻量类即可，不调 LLM
- 输入：effective_query, settings（或 settings.synonyms 列表）
- 规则：
  - 遍历每组 synonyms：若 effective_query **包含** 任一 term 则命中该组
  - 中文 term **精确** 子串匹配；英文 term **ignore case**
  - 命中组的 expand 词 **追加** 到 query 末尾（空格分隔）；多组命中 expand **去重** 后追加
  - 未命中任何 term → search_query = effective_query，synonym_applied = false
- 输出：search_query, synonym_expansions（list[str]）, synonym_applied（bool）

【3. pipeline 串联 + QueryProcessResult 扩展】
- KnowledgeBaseQueryContext 增加 settings: dict（或 TypedDict），RagService 传入 kb.settings
- QueryProcessResult 增加：
  - search_query：最终拿去检索的句子（无扩展时等于 effective_query）
  - synonym_expansions：本次追加的 expand 词列表
  - synonym_applied：是否命中词表
- pipeline.process 流程：raw → rewrite(01，可选) → synonym_expand(02，有 settings 即尝试) → 返回完整 QueryProcessResult
- synonym_expand **始终执行**（只要有 kb settings），不受 query_options.enabled 控制

【4. Schema：响应怎么回显】
- app/schemas/rag.py 的 QueryProcessingMetadata 增加：
  - search_query
  - synonym_expansions: list[str] = []
  - synonym_applied: bool = false
- 回显规则：
  - 开了改写 **或** 词表命中 **或** search_query ≠ raw_query 时，应返回 query_processing（含 raw → effective → search 链路）
  - 全无处理时可为 null（与改前兼容）
- RetrieveData.query **仍返回用户原始 query**；重排仍用 request.query，不用 search_query

【5. RagService：检索用哪句】
- process 之后：search_query = query_result.search_query（勿再用 effective_query 直接检索）
- _vector_search / _bm25_search / hybrid 的 query 入参统一 search_query
- hybrid / rerank 其余逻辑不动

【6. 01 衔接 rewrite_hint】
- llm_rewrite 读 kb.settings.rewrite_hint：有则与 description 拼接传入 Prompt（实现定一种：如 description + "\n" + rewrite_hint，写进代码注释）
- rewrite_hint 只影响 01 改写，不参与词表匹配

【7. 脚本 scripts/update_kb_settings.py】
- --kb-id 必填，--settings-file 必填（JSON 路径）
- 校验 kb_id 在 DB 存在
- **整文件覆盖** knowledge_bases.settings 字段（实现简单，文档与脚本注释写清楚）
- 打印更新后的 kb_id 与 synonyms 组数

【8. 前端 RetrievePage（仅展示，不做词表编辑）】
- 运行摘要展示 search_query（与 effective_query 不同时突出）
- synonym_applied 为 true 时展示 synonym_expansions
- types/api.ts 对齐 QueryProcessingMetadata 新字段
- **不做**词表上传、在线编辑 UI

【9. 文档与示例】
- examples/kb_settings.example.json（含 synonyms + 可选 rewrite_hint）
- README：词表 per-kb、脚本维护方式、与文档 upload 的区别

【边界】
- 不做 PATCH settings API（除非顺手且简单）；不做词表 Admin Web UI
- 词表 **不能** 共用 POST /documents/upload（词表是 kb 配置，不是检索正文）
- 不改 ES analyzer；不做 Multi-Query、租户配额

【验收】
- 无 synonyms 的 kb：search_query 等于 effective_query，synonym_applied=false
- 配置 synonyms 且 query 命中 term：metadata 有 expansions，search_query 含扩展词，BM25/vector 均用 search_query
- 未开 rewrite、仅词表：synonym 仍生效，query_processing 有 search 链路
- 01+02 同时开：metadata 链路 raw → effective → search 完整
- 两个 kb 各配不同 synonyms，同一 query 扩展互不影响
- 调试台仅展示扩展结果，无词表编辑入口
```

## 做完怎么验

前置：01 已完成，`alembic upgrade head` 跑完，`knowledge_bases.settings` 列已存在。

### 1. 写入词表

准备 `kb_settings.json`：

```json
{
  "synonyms": [
    {"terms": ["背调"], "expand": ["背景调查", "标准问题清单"]},
    {"terms": ["薪酬", "薪资", "工资"], "expand": ["职级", "薪酬定级", "定级标准"]}
  ]
}
```

```bash
python scripts/update_kb_settings.py \
  --kb-id <kb_id> \
  --settings-file kb_settings.json
```

预期：终端提示更新成功，打印 kb_id 和 synonyms 组数。

### 2. 词表命中（扩展应生效）

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/rag/retrieve \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{"kb_id":"<kb_id>","user_id":"test_user","query":"背调要问啥"}'
```

预期：`metadata.query_processing.synonym_applied` 为 true；`synonym_expansions` 含「背景调查」「标准问题清单」；`search_query` 比 `effective_query` 多出扩展词。

### 3. 未命中词表（行为不变）

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/rag/retrieve \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{"kb_id":"<kb_id>","user_id":"test_user","query":"面试官行为规范有哪些"}'
```

预期：`synonym_applied` 为 false，`search_query` 与 `effective_query` 相同。

### 4. 跨库隔离

对一个**未配词表**的 kb 发同一条 query：

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/rag/retrieve \
  -H "Authorization: Bearer rk_live_你的key" \
  -H "Content-Type: application/json" \
  -d '{"kb_id":"<另一个kb_id>","user_id":"test_user","query":"背调要问啥"}'
```

预期：`synonym_applied` 为 false，无扩展词，两个 kb 的词表完全独立互不影响。
