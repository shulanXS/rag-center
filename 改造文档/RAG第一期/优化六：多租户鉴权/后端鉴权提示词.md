# 设计多租户后端鉴权提示词

点击此处可复制本篇提示词

后端鉴权要分两步走：先把地基打好（表、model、auth 依赖、脚本），再挂到业务接口上。这两步放在一篇里给 AI，可以避免上下文割裂，AI 建完地基后直接接入，不需要再重新理解前半段的实现。

## 使用场景

这份提示词用于在当前 RAG 中台工程基础上，完成多租户鉴权的后端部分。

当前调用方式是把 `tenant_id` 写在请求体里，服务端直接信任。任何人只要猜到别的租户 ID，就能读写对方的数据。作为对外提供能力的 RAG 中台，这不可接受。

改造后的思路：每个租户发一把 API Key，请求头带 Key，服务端自己解析出 `tenant_id`，不再信任客户端传的租户字段。

这份提示词分两阶段完成：

- 第一阶段：搭鉴权地基（建表、model、认证逻辑、脚本、/auth/me），现有四个业务接口暂不动
- 第二阶段：把鉴权挂到四个业务接口，请求体去掉 `tenant_id`，tree 接口按当前租户过滤

### 一、功能目标

在 rag-center 项目一步完成后端多租户鉴权：

- 新增 `tenants`、`api_keys` 两张表及 Alembic 迁移
- 实现 API Key 的创建、校验、hash 存储
- 新增 `get_current_tenant` FastAPI Depends，供所有业务接口复用
- 新增 `GET /api/v1/auth/me` 接口供调用方验证 Key 有效性
- 四个业务接口全部挂上鉴权，请求体去掉 `tenant_id`
- `GET /knowledge-bases/tree` 改为只返回当前租户的数据
- 通过 `AUTH_ENABLED` 环境变量控制是否启用鉴权，本地调试可关闭

### 二、数据库设计

新增 Alembic 迁移 `0002`（在现有 `0001_initial` 之后），建两张表：

**tenants（租户）**

| 字段 | 说明 |
|---|---|
| id | 即 tenant_id，如 `tenant_demo` |
| name | 展示名 |
| status | `active` / `disabled`，禁用后该租户下所有 Key 失效 |
| created_at | |

**api_keys（密钥）**

| 字段 | 说明 |
|---|---|
| id | UUID |
| tenant_id | 外键，指向 tenants.id |
| key_hash | 只存 SHA-256 hash，不存明文 |
| key_prefix | 如 `rk_a1b2`，日志里用来辨认是哪把 Key |
| name | 备注，如「客服系统对接」 |
| status | `active` / `revoked` |
| expires_at | 可选，过期时间 |
| created_at | |

Key 明文格式：`rk_live_` 加 32 位随机 hex。创建时终端打印一次，之后库里只有 hash。

迁移写法和命名风格对齐 `migrations/versions/0001_initial.py`。

### 三、Model 与 Repository

```
app/models/tenant.py
app/models/api_key.py
app/repositories/tenant_repository.py
app/repositories/api_key_repository.py
```

生成 Key 时：明文格式 `rk_live_<32位hex>`，SHA-256 后入库；明文只在创建时打印一次，不落库不落日志。

### 四、鉴权核心

```
app/core/auth.py
app/api/v1/deps.py
```

**TenantContext** — 验证通过后的上下文对象，携带：

- `tenant_id`
- `tenant_name`
- `key_id`
- `key_prefix`

**get_current_tenant**（FastAPI Depends）校验流程：

1. 读取 `Authorization: Bearer rk_live_xxx`
2. 对 Key 做 SHA-256 hash，去 `api_keys` 表查
3. 校验：存在、`status=active`、未过期、对应 tenant `status=active`
4. 通过后返回 `TenantContext`

`AUTH_ENABLED=false` 时跳过验 Key，固定使用内置默认租户 `tenant_demo`（tenant 不存在也可占位通过）。

鉴权失败抛 `AppError UNAUTHORIZED`（`exceptions.py` 新增，建议错误码 `20010`）。

### 五、配置项

`app/core/config.py` 新增：

```
AUTH_ENABLED=true          # 默认开启；本地调试可设 false
```

`.env.example` 补充：

```env
AUTH_ENABLED=true
```

### 六、运维脚本

两个独立脚本，均在项目根目录执行，不要合并成 `cli.py` / `manage.py`：

**scripts/create_tenant.py** — 注册租户：

```bash
python scripts/create_tenant.py --id tenant_demo --name "演示租户"
```

重复相同 `--id` 应报错（租户已存在）。内部复用 `app` 的 config、db session、TenantRepository。

**scripts/create_api_key.py** — 给已有租户发 Key：

```bash
python scripts/create_api_key.py --tenant-id tenant_demo --name "本地开发"
```

生成明文 `rk_live_<32位hex>`，终端打印一次；库里只存 hash。tenant 不存在时报错。

### 七、验证接口

```
GET /api/v1/auth/me
```

走 `get_current_tenant`，返回当前 Key 对应的租户信息：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "tenant_id": "tenant_demo",
    "tenant_name": "演示租户",
    "key_prefix": "rk_a1b2",
    "key_name": "本地开发"
  }
}
```

挂到 `api/v1/router.py`，这是第一阶段唯一需要鉴权的接口。

### 八、业务 API 挂载鉴权

四个业务路由均 `Depends(get_current_tenant)`，复用第一阶段代码，不重复实现：

| 接口 | 改动 |
|---|---|
| `POST /knowledge-bases/create` | 去掉 body `tenant_id`，从 Key 注入 |
| `GET /knowledge-bases/tree` | 必须鉴权，只返回当前租户的数据 |
| `POST /documents/upload` | 去掉 body `tenant_id`，从 Key 注入 |
| `POST /rag/retrieve` | 去掉 body `tenant_id`，从 Key 注入 |

`AUTH_ENABLED=true` 时无 Key 或 Key 无效返回 `UNAUTHORIZED`（code 20010）；`AUTH_ENABLED=false` 时不验 Key，固定 `tenant_demo`。

### 九、请求 Schema 变化

以下请求 Schema 移除 `tenant_id` 字段：

- `CreateKnowledgeBaseRequest`：只留 name、description
- `UploadDocumentRequest`：只留 kb_id、title、content
- `RetrieveRequest`：只留 kb_id、user_id、query、top_k、retrieval_options、rerank_options

响应里的 `tenant_id`（如 `KnowledgeBaseData`）可保留，只读回显。

body 多传 `tenant_id` 时由 Pydantic 忽略，不得以 body 覆盖 Key 对应的租户。

### 十、tree 接口按租户过滤

`GET /knowledge-bases/tree` 接上鉴权后，`get_tree(tenant_id, keyword?)` 只查当前租户：

- 返回结构保持 `TenantTreeItem[]`，但只含一个 tenant
- keyword 若保留：在该租户内按知识库 name 过滤，不再按 tenant_id 搜（避免跨租户）

`retrieval_logs` 写入时继续用注入的 tenant_id，行为与现在一致。

### 十一、验收标准

- `scripts/create_tenant.py` + `create_api_key.py` 建 tenant 和 key，curl `/auth/me` 带 Bearer 成功
- 不带 Key / Key 错误时返回 code 20010（UNAUTHORIZED）
- `AUTH_ENABLED=false` 时不带 Key 也能调 `/auth/me`，`tenant_id` 固定为 `tenant_demo`
- Key A 调 tree 只能看到 tenant_a 的知识库，看不到 tenant_b 的数据
- 用 Key B 携带 Key A 的 `kb_id` 检索，返回知识库不存在
- `AUTH_ENABLED=true` 不带 Key 调任意业务接口返回 code 20010
