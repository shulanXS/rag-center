# 01 - 租户套餐

优化六到八把鉴权、词表、异步索引都搭好了，但所有租户仍共用 `.env` 里的检索默认项——没有套餐，没有配额，谁都能无限建库、随意开 rerank。

这一步只做**租户 plan（套餐）**地基：free / standard / pro 三档，配额与功能上限写死在代码里。检索时怎么选「速度 / 均衡 / 质量 / 自定义」属于单次 retrieve 请求的事，在 02 接入 API；调试台 UI 在 03。

## 先搞清楚两个概念

**plan（套餐）**：挂在租户上，脚本改，决定「能建多少库、能开 hybrid/rerank 吗」。三档：free / standard / pro。

**retrieve profile（检索预设）**：不进租户表，每次 retrieve 请求传，决定「这次检索要快还是要准」。本篇只定义四个 preset 展开成什么参数，02 才接入 API。

词表 `settings.synonyms` 还是挂在知识库上，跟 plan 无关，不动。

## Plan 三档

| plan | 定位 | 典型场景 |
|------|------|----------|
| `free` | 体验 / PoC，能力最窄 | 新建租户默认档 |
| `standard` | 生产可用 | 已有租户迁移档 |
| `pro` | 全功能 + 高配额 | 核心生产、`tenant_demo` |

### 功能上限（写死）

| 项 | free | standard | pro |
|----|------|----------|-----|
| 允许的 retrieve profile | 仅 `speed` | `speed`、`balanced`、`custom` | 全部，含 `quality` |
| hybrid | ❌ | ✅ | ✅ |
| rerank | ❌ | ❌ | ✅ |
| query_rewrite | ❌ | ❌ | ✅ |

> `profile=quality` 在 02 校验：standard 传 `quality` → `FEATURE_NOT_ALLOWED`。

### 配额（写死）

| 项 | free | standard | pro |
|----|------|----------|-----|
| 检索 QPS | 3 | 10 | 50 |
| 日检索量 | 500 | 5,000 | 100,000 |
| 最大知识库数 | 1 | 5 | 50 |
| 单库最大文档数 | 30 | 200 | 5,000 |
| 最大并发 PROCESSING | 1 | 2 | 10 |

数值放在 `app/tenant/plan_presets.py`。改配额就改代码发版，不支持对单个租户写 JSON 覆盖。

## Retrieve Profile 预设（代码表）

本篇只定义四档展开成什么参数，不接入 API：

| profile | 调试台文案 | 展开概要 |
|---------|-----------|---------|
| `speed` | 追求速度 | `mode=vector`，`top_k=3`；关 rerank、rewrite |
| `balanced` | 均衡 | `mode=hybrid`，top_k=5；关 rerank、rewrite |
| `quality` | 追求质量 | `mode=hybrid`，`top_k=8`；**开** rerank、rewrite |
| `custom` | 自定义 | 不展开，以请求里的 options 为准，仍受 plan 约束 |

未传 `profile` 时，服务端默认 `balanced`，02 写死常量 `DEFAULT_RETRIEVE_PROFILE=balanced`。调试台应始终显式传 profile。

## 数据怎么存

Alembic 迁移 `0005_tenant_plan`，`tenants` 表新增一列：

```
plan   VARCHAR(32)  NOT NULL  DEFAULT 'free'
```

就这一列，不加 `profile`，不加 `policy`。

现有租户的迁移策略：

| 租户 | plan |
|------|------|
| 升级前已存在的全部 tenant | `standard`，避免老用户突然变 free |
| `tenant_demo` | `pro` |
| 此后 `create_tenant` 新建 | `free` |

改 plan 不需要 reindex，只影响后续配额与 retrieve 能力边界。

## 代码结构

```
app/tenant/
  plan_presets.py          # PLAN_PRESETS：三档 features + limits
  retrieve_presets.py      # RETRIEVE_PROFILE_PRESETS：四档 options bundle
  plan_resolver.py         # 由 tenant.plan 得到 PlanContext
scripts/
  update_tenant_plan.py    # --tenant-id --plan
```

`PlanResolver.resolve_plan(tenant)` 查 `plan_presets`，返回包含 plan、features、limits 的 `PlanContext`，不涉及 Redis，不改业务 API。

```bash
python scripts/update_tenant_plan.py --tenant-id tenant_a --plan pro
```

脚本校验 plan 必须是 `free` | `standard` | `pro`；tenant 不存在提示先 `create_tenant`。

本篇只搭地基：迁移、presets 代码表、PlanResolver、改 plan 脚本。不改任何路由行为，不改前端，不做 Redis 限流，不做 Admin API。限流 enforcement 在 02 接入。

## 做完怎么验

前置：PostgreSQL 已启动，`.env` 配好 `DATABASE_URL`；优化六 tenants 表已存在；后端可启动。本篇尚未做 enforcement，retrieve 行为应与改前一致。

### 1. 跑数据库迁移

```bash
alembic upgrade head
```

预期：迁移 `0005_tenant_plan` 成功；`tenants` 表新增 `plan` 列。可选确认：

```bash
psql $DATABASE_URL -c "SELECT id, name, plan FROM tenants;"
```

### 2. 确认旧租户迁移结果

预期：升级前已存在的 tenant 为 `standard`，`tenant_demo` 为 `pro`。

若库里尚无 tenant，先创建：

```bash
python scripts/create_tenant.py --id tenant_demo --name "演示租户"
python scripts/create_api_key.py --tenant-id tenant_demo --name "本地开发"
```

再跑迁移或手动确认 `tenant_demo.plan = pro`。

### 3. update_tenant_plan.py

```bash
# 正常改 plan
python scripts/update_tenant_plan.py --tenant-id tenant_demo --plan pro

# 非法 plan 应报错
python scripts/update_tenant_plan.py --tenant-id tenant_demo --plan invalid_plan
```

预期：第一条提示成功；第二条报错，提示 plan 必须是 free / standard / pro。

### 4. PlanResolver smoke 测试

```python
from app.db.session import SessionLocal
from app.repositories.tenant_repository import TenantRepository
from app.tenant.plan_resolver import PlanResolver

db = SessionLocal()
tenant = TenantRepository(db).get_by_id("tenant_demo")
ctx = PlanResolver.resolve_plan(tenant)
assert ctx.plan == "pro"
assert ctx.features.rerank_allowed is True
assert ctx.limits.max_kb == 50
print("ok")
```

预期：断言通过，无异常。
