# 设计知识库列表页与检索调试页提示词

点击此处可复制本篇提示词

用提示词驱动 UI 开发，核心思路和后端一样：把 AI 当初级工程师，我们来设计，AI 来落地。这两个页面一起交付，可以共用顶栏组件，减少来回修改。

## 使用场景

这份提示词用于在当前 RAG 中台工程基础上，新增知识库列表页与检索调试页。

当前调试台只有首页上传页（`/`），用户上传文档后有两个明显痛点：关掉浏览器就找不回建好的知识库；也无法直观验证某条 query 能召回哪些 chunk、分数如何。

需要新增两个页面解决这两个问题：

- `/knowledge-bases`：知识库列表页，按租户 → 知识库 → 文档三级展示已有数据
- `/retrieve`：检索调试页，输入 query 直接看召回结果和评分明细

同时把顶栏抽成公共组件 `AppHeader`，供三个页面共用，后续再加页面不需要重复写导航逻辑。

### 一、功能目标

在 rag-center 项目一步完成「知识库列表页 + 检索调试页 + 顶部导航」：

- 新增 GET `/api/v1/knowledge-bases/tree` 接口，返回租户 → 知识库 → 文档三级树形数据
- 小改 POST `/api/v1/rag/retrieve` 响应，在 `metadata` 中增加 `latency_ms` 服务端耗时字段
- 前端新增 `/knowledge-bases` 路由和 `/retrieve` 路由，复用公共顶栏 `AppHeader`
- 调试台不做鉴权、分页、删除

### 二、公共组件 AppHeader

把三个页面的顶栏抽成公共组件 `AppHeader`，左侧固定显示「RAG 知识文件管理」。右侧根据当前路由显示其他页的入口：

| 当前页 | 右侧显示 |
|---|---|
| `/`（上传页） | 知识库列表（`/knowledge-bases`）、检索调试（`/retrieve`，占位） |
| `/knowledge-bases`（列表页） | 知识库上传（`/`）、检索调试（`/retrieve`） |
| `/retrieve`（检索页） | 知识库上传（`/`）、知识库列表（`/knowledge-bases`） |

### 三、知识库列表页（`/knowledge-bases`）

**页面布局**

顶部搜索框，输入关键字模糊匹配 `tenant_id`（比如输入 `tech` 可筛出 `tech_position`），不做分页。搜索框下方是三级可展开表格：

```
▶ tech_position                          [展开/收起]
    ▶ 技术岗位知识库  kb_id: 939a5baf…   [展开/收起]
        backend_engineer.md    document_id  chunk_count
        frontend_engineer.md   …
    ▶ 面试题库  kb_id: …
▶ tenant_demo
    …
```

知识库行提供两个操作：复制 `kb_id`、跳转到上传页或检索页（URL 自动携带 `tenant_id` 和 `kb_id`，无需手填）。

文档层只展示 `status=SUCCESS` 的记录，失败或处理中的文档不在列表出现。

**前端实现要点**

- 路由 `/knowledge-bases` 新增 `KnowledgeFileTreePage`
- 顶部 `keyword` 搜索过滤 `tenant_id`，调用 `knowledgeBaseService.fetchTree(keyword?)`
- 三级展开收起用本地 state 实现，不引额外 UI 库
- 知识库行：复制 `kb_id`、跳转上传页或检索页时 query 带上 `tenant_id` `kb_id`
- 不使用 localStorage
- UI 沿用现有 shadcn/ui，Table 组件按需补装

### 四、检索调试页（`/retrieve`）

**页面布局**

从列表页点「去检索」跳转时，URL 带上 `tenant_id` `kb_id`，表单自动预填。页面分三块 Card，自上而下：

```
┌─ 检索配置（可折叠，默认展开）──────────────────┐
│ ┌ 检索范围（浅底框）────────────────────────┐  │
│ │ tenant_id [____]    kb_id [____________]  │  │
│ └───────────────────────────────────────────┘  │
│ ── 检索参数 ──────────────────────────────── │
│ top_k              [5]                          │
│ 检索模式           [vector] [bm25] [hybrid]     │
│ vector_top_k [20]  bm25_top_k [20]  rrf_k [60] │  ← 仅 hybrid，单独一行
│ rerank             [☑ 启用]  rerank top_n [5]   │
└─────────────────────────────────────────────────┘

┌─ 检索与召回 ────────────────────────────────────┐
│ query              [多行输入框]                  │
│ [检索]                                          │
│ ── 召回结果 ────────────────────────────────── │
│ #1 score=0.82  vector=0.79  bm25=—  rerank=0.91│
│    title / document_id / chunk_id               │
│    content（可折叠）                             │
└─────────────────────────────────────────────────┘

┌─ 运行摘要（只读，来自 metadata）───────────────┐
│ mode=hybrid | top_k=5 | 服务端耗时 320ms         │
│ vector:12 bm25:8 fused:15                        │
│ rerank: llm / deepseek-chat | ⚠ hybrid degraded  │
└─────────────────────────────────────────────────┘
```

**前端实现要点**

- 路由 `/retrieve` 新增 `RetrievePage`，复用 `AppHeader`
- `tenant_id`、`kb_id`、`query` 必填，`user_id` 固定传 `debug_user`，不在界面展示
- 表单默认值：`top_k=5`、`mode=hybrid`、`vector_top_k=20`、`bm25_top_k=20`、`rrf_k=60`
- 检索模式切换到 hybrid 时，才在检索模式下方显示三个 hybrid 子参数（同一行）
- 未启用 rerank 时不传 `rerank_options` 字段
- chunk 展示：score、vector/bm25/rerank 分数与 rank、title、document_id、chunk_id、content 可折叠
- 运行摘要展示 `latency_ms`（标注服务端耗时）、mode、count、degraded、rerank 模型名
- 布局：选项名宽 100px 右对齐，标签与控件同一行
- 不使用 localStorage，UI 沿用 shadcn/ui，新增 `ragService.retrieve` 与对应 types

### 五、后端接口变化

**新增接口：知识库树形查询**

```
GET /api/v1/knowledge-bases/tree?keyword=
```

`keyword` 可选，模糊匹配 `tenant_id`。不分页，返回全部符合条件数据。响应结构：

```json
{
  "code": 0,
  "msg": "success",
  "data": [
    {
      "tenant_id": "tech_position",
      "knowledge_bases": [
        {
          "kb_id": "939a5baf-...",
          "name": "技术岗位知识库",
          "description": "...",
          "created_at": "2024-01-01T00:00:00Z",
          "documents": [
            {
              "document_id": "doc_001",
              "title": "backend_engineer.md",
              "status": "SUCCESS",
              "chunk_count": 12,
              "created_at": "2024-01-01T00:00:00Z"
            }
          ]
        }
      ]
    }
  ]
}
```

排序规则：按 `tenant_id` 分组，知识库按 `created_at` 倒序，文档按 `created_at` 倒序。文档层只返回 `status=SUCCESS` 的记录。Repository/Service 实现查询与组装，风格与现有 API 一致，不做鉴权。

**小改接口：检索响应增加耗时**

```
POST /api/v1/rag/retrieve
```

`RetrieveMetadata` 增加 `latency_ms`（int，毫秒）字段。`RagService.retrieve` 里已有耗时计算，把结果写入响应 `metadata` 即可。其他主体逻辑、参数、chunk 分数字段均不需要动。

### 六、验收标准

- 多租户多库多文档能在列表页正确树形展示
- 文档层只显示上传成功的文件，失败和处理中的不出现
- 搜索框按 `tenant_id` 模糊过滤有效
- 从列表页点「去上传」跳转后，`tenant_id` 和 `kb_id` 已自动带入表单
- 从列表页点「去检索」跳转后，`tenant_id` 和 `kb_id` 已自动预填
- 检索页输入 query 点检索后，召回 chunk 列表正常展示
- 切换检索模式时，hybrid 子参数仅在 hybrid 模式下显示，且在检索模式控件下方同一行
- 开关 rerank 后参数区域随之变化，禁用时不传 `rerank_options`
- 运行摘要展示服务端耗时 `latency_ms`（非前端计时）
- `AppHeader` 在三个页面均正常渲染，且右侧导航入口按当前路由正确切换
- 首页 `/` 的上传逻辑保持不变
