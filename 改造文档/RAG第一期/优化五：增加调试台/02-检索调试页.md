# 02 - 检索调试页

列表页解决了「库和文档在哪」的问题，检索调试页解决的是：**这条 query 在某个知识库里召回了哪些 chunk、分数怎么来的**。

页面走 `POST /api/v1/rag/retrieve`（纯检索），不生成最终答案。形态是**输入框 + 检索按钮 + 结果区**，不做 Chat 气泡，避免让人误以为在「对话」或支持多轮追问。

## 界面长什么样

打开 `/retrieve`，顶部是公共顶栏 `AppHeader`。从列表页点「去检索」跳转时，URL 会带上 `tenant_id`、`kb_id`，表单自动预填。

页面分**三块**，自上而下：

```
┌─ 检索配置（可折叠，默认展开）──────────────────┐
│ ┌ 检索范围（浅底框，租户/知识库级）────────────┐ │
│ │ tenant_id [____]    kb_id [____________]    │ │
│ └─────────────────────────────────────────────┘ │
│ ── 检索参数 ────────────────────────────────── │
│ top_k              [5]                          │
│ 检索模式           [vector] [bm25] [hybrid]     │
│ vector_top_k [20]  bm25_top_k [20]  rrf_k [60]  │  ← 仅 hybrid，单独一行
│ rerank             [☑ 启用]  rerank top_n [5]   │
└─────────────────────────────────────────────────┘

┌─ 检索与召回 ────────────────────────────────────┐
│ query              [多行输入框________________] │
│ [检索]                                          │
│ ── 召回结果 ───────────────────────────────── │
│ #1 score=0.82  vector=0.79  bm25=—  rerank=0.91│
│    title / document_id / chunk_id               │
│    content（可展开）                             │
│ #2 …                                            │
└─────────────────────────────────────────────────┘

┌─ 运行摘要（只读，来自 metadata）───────────────┐
│ mode=hybrid | top_k=5 | 服务端耗时 320ms        │
│ vector:12 bm25:8 fused:15                       │
│ rerank: llm / deepseek-chat | ⚠ hybrid degraded │
└─────────────────────────────────────────────────┘
```

## 前后端各要做什么

**后端** 改动很小：`RetrieveMetadata` 增加 `latency_ms`（int，毫秒）字段，`RagService.retrieve` 里已有耗时计算，把结果写入响应即可。检索接口主体逻辑、参数、chunk 分数明细均不需要动。

**前端** 新增 `/retrieve` 路由，实现 `RetrievePage`，复用 `AppHeader`。页面包含三块 Card：检索配置（`tenant_id`/`kb_id` 与检索参数分区）、检索与召回（query 输入框 + chunk 列表）、运行摘要（只读展示 metadata）。新增 `ragService.retrieve()` 和对应 types，`user_id` 固定传 `debug_user` 不在界面展示，参数改动只影响本次请求不写 localStorage。

## 开发提示词

```
在 rag-center 项目一步完成「检索调试页」（RAG 调试台）：

【后端】
- 小改 POST /api/v1/rag/retrieve 响应：RetrieveMetadata 增加 latency_ms（int，毫秒）
- RagService.retrieve 里已有 latency_ms 计算，写入返回的 metadata 即可

【前端】
- 路由：/retrieve 实现 RetrievePage；复用 AppHeader；URL query 预填 tenant_id、kb_id
- 交互：输入框 +「检索」按钮，不做 chat 形式
- 页面三块 Card：
  1. 检索配置（可折叠）
     - 检索范围（浅底框）：tenant_id、kb_id 同一行
     - 检索参数（分隔线下方）：top_k、检索模式、hybrid 子参数、rerank
  2. 检索与召回：query + 检索按钮 + chunk 列表（同 Card）
  3. 运行摘要：metadata 只读（在召回结果 Card 下方）
- 布局：选项名宽 100px 右对齐，标签与控件同一行；hybrid 三参数在检索模式下一行
- 表单：
  - tenant_id、kb_id、query（必填）；user_id 固定 "debug_user"
  - top_k、rerank top_n：数字输入，默认 5，范围 1–50
  - mode：vector / bm25 / hybrid（默认 hybrid）
  - hybrid：vector_top_k、bm25_top_k、rrf_k 默认 20/20/60
  - rerank：勾选启用；启用时显示 rerank top_n
- 未启用 rerank 时不传 rerank_options
- chunk 展示：score、vector/bm25/rerank 分数与 rank、title、document_id、chunk_id、content（可折叠）
- 运行摘要：latency_ms（标注服务端耗时）、mode、count、degraded、rerank model
- 不使用 localStorage；UI 沿用 shadcn/ui；新增 ragService.retrieve 与 types

验收：列表页跳转预填；query 检索出 chunk；hybrid 子参数在模式下一行；检索范围与检索参数分区清晰；latency_ms 为服务端耗时。
```

## 验收方式

1. 从列表页点「去检索」，`tenant_id`、`kb_id` 自动预填进表单。
2. 输入 query 点「检索」，召回 chunk 列表正常展示，运行摘要显示服务端耗时。
3. 切换检索模式（vector / bm25 / hybrid）、开关 rerank，参数变化与结果符合预期。
