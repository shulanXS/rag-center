# 检索篇：召回、策略、性能优化

> 适用场景：混合召回、检索策略档位、精排与性能优化类面试  
> 关联简历：检索主链路、检索全链路优化、核心链路多层降级

## 1. 一次检索的主流程大致是什么？

可以按这条链路讲：先解析租户套餐和本次检索策略，检查 QPS 与日配额；再处理问题（可选查询改写、词表扩展）；确定检索作用域后做向量路和/或关键词路召回；关系候选注入，再全局 RRF 融合；可选精排，再做上下文恢复；判断空结果原因，写检索日志，成功则日计数加一，最后返回片段和策略元信息。

普通检索走完整条链路一次；受控 Agentic Research 在外层做规划与补证，但每一轮子查询仍进同一套检索内核。证据包如何整理属于进阶篇，不在这条主流程里默认展开。

**高频追问**：主流程里哪些步骤是可选的？失败了会怎样？

**追问回答**：按档位或套餐真正可开可关的，主要是查询改写和精排；词表扩展也按配置启用。改写、精排失败，或关系增强、上下文恢复异常时，**应降级继续返回可用结果，而不是整单失败**。**配额或作用域校验过不了，则在检索开始前直接拒绝，那不属于降级**。

## 2. 向量检索是怎么工作的？

用户问题先通过向量化模型转成向量，再到向量库中查找**余弦距离最近的若干片段**。距离越小越相似，返回时会转成 0 到 1 左右的相似度分数，便于阅读和调试。它擅长语义相近的匹配，例如「退钱多久到账」和「退款到账时间」能对上。

**高频追问**：为什么不直接在数据库里存数组自己算相似度？

**追问回答**：**专用向量扩展提供了向量类型和近似最近邻索引**，比逐行算余弦快几个数量级。片段元数据和向量还可同库管理，适合当前中台的规模与运维成本。

## 3. 关键词这一路里，BM25 是怎么工作的？中文分词怎么做？

关键词路走 Elasticsearch。入库时把片段写成可检索文档，查询时先按租户、知识库等条件过滤，再对查询句做全文匹配，**默认相关性算法就是 BM25**。

可以把它理解成「倒排索引 + 词项打分」：文档被拆成一个个词，每个词记下出现在哪些文档里；检索时看查询词命中了哪些文档，再按词频、稀有程度和文档长度打分——某个词在这篇里出现得多、在全库里又比较少见，通常分更高；文档特别长时，同样命中会被适当压一压。**分数没有 0～1 那种固定上限**，所以后面才需要和向量分用 RRF 融合，而不是直接加权相加。

中文没有空格，必须靠分词器把「退款到账时间」切开。项目用的是 IK 分词：**索引时用 `ik_max_word`，尽量切细，提高召回；查询时用 `ik_smart`，切得更整、更接近用户说法，降低噪声**。当前检索主要打在检索用文本上，里面已经拼好了文档名、章节路径和正文，这样章节标题里的关键词也更容易命中。错误码、型号、条款名、专有名词这类精确匹配，往往比纯向量更稳。

**高频追问1**：为什么索引切细、查询切粗，而不是两边一样？

**追问回答**：索引切细是为了「库里尽量能对上」；查询切粗是为了「一次查询别拆成太多碎词，避免被常用字带跑」。两边都用最细或都用最粗，要么噪声大，要么该召回的召不回。这是中文检索里比较常见的组合。

**高频追问2**：BM25 分高就一定最相关吗？

**追问回答**：不一定。它强在字面和术语命中，弱在同义改写和语义相近。所以单独一路不够，要和向量路一起召回，再用 RRF 按排名融合；需要更准时，后面还有精排。

## 4. BM25 和向量分数为什么用 RRF 融合？两路各召回多少再取最终结果？

两路分数量纲不同：BM25 受词频、文档长度影响，没有固定上限；向量相似度大约在 0 到 1。直接加权相加不稳定，权重也难泛化。**RRF 只看各路排名**，排名越靠前贡献越大，**不依赖原始分数归一化**。融合分是各路「1 / (k + 排名)」之和，**k 默认 60**。接口里顺带返回的向量分、关键词分只供调试，**最终排序看 RRF**。

两路通常各召回比最终条数更多的候选，再融合筛到最终 Top。例如质量档两路各约 20，再精排到 5。这样「一路很强、另一路一般」的好结果也有机会冒出来。窗口不是越大越好：过大则融合和精排变慢，噪声也会进来。

**高频追问**：k 取 60 是什么意思？一路召回很少、另一路很多时怎么融？

**追问回答**：k 是平滑常数，排在第 r 名大约贡献 `1/(k+r)`。k 越大，前几名和后面名次的分差越小，融合更「温和」。一路结果很少也不影响：有命中的路正常按排名加分，没命中的文档在那一路就没有贡献；最终仍按各路贡献之和排序。所以 **RRF 不要求两路候选一样多，也不要求原始分数可比**。

## 5. 检索有哪些模式？速度、均衡、质量、自定义四档有什么区别？

模式上：纯向量最快，适合延迟敏感、语义接近的问题；纯关键词适合错误码、型号、条款名；混合两路召回再 RRF，召回更全，但依赖搜索引擎，延迟略高。

产品上常用四档策略，而不是每次手填全部参数。**速度档追求快：纯向量，不做改写和精排**。**均衡档默认混合召回，不开精排和改写**。**质量档追求效果：混合召回加改写和专业精排**，延迟更高。自定义档可显式传参数，但仍受套餐能力上限约束。三档命名策略**统一最终返回 5 条**，内部候选不同：速度档向量约 10；均衡档两路各约 10；质量档两路各约 20 再精排。统一最终条数是为了对齐下游上下文预算，也便于公平对比。

**高频追问1**：不同档位之间测过延迟吗？大概差多少？

**追问回答**：测过。固定评测集上，速度档 P95 大约 1 秒上下；均衡档多了关键词一路，大约 1～2 秒；质量档多了改写和精排，大约 3 秒上下，每题还会多两次模型调用。整体是速度最快，均衡略慢一点，质量明显更重，具体会随模型和索引规模波动。

**高频追问2**：准确率和召回率又有什么差距？

**追问回答**：统一最终 Top5 对比时，从精确率看：速度档和均衡档基本持平，差不到 1 个百分点；质量档大约再高 1～2 个百分点，是三档最高。再看召回率：均衡档大约高出速度档 5～7 个百分点，是三档最高；质量档大约比速度档高 5 个百分点左右，比均衡档低 1～2 个百分点。可以记成：**均衡偏召全，质量偏排准，速度用更轻链路换低延迟**。

## 6. 检索链路是怎么从最初的向量 TopK，想到做成现在这么长一条的？当时有测过每个环节大概提升多少准确率吗？

不是一开始就按完整蓝图设计出来的。公司之前已经在部分业务里用过 RAG，也踩过实际问题：用户提问很口语化，文档表述却正式，就加上 Query 改写；专业术语、错误码需要精准匹配，纯向量不稳，就引入 BM25；两路融合后核心内容有时排不准，就再加精排。这些能力在具体业务里验证过有效，建设检索中台时主要是**把已有经验统一沉淀下来**，做成可配置、可套餐约束的标准链路。

因此当时没有重新做「每加一步单独测一次提升」的拆解实验，主要做整体回归，确认主链路可用。**后来做效果闭环时才补上统一质量门禁**：固定测试集、单变量对照，逐轮记录优化对召回率、精确率和延迟的影响，后续改造才有可归因的数据。

## 7. 查询改写和词表扩展有什么区别？

改写用大模型，把口语问题整理成更完整、更接近文档表述的句子，有成本和延迟，通常在质量档或专业版开启。词表是知识库配置的同义词组，例如「背调」扩成「背景调查」，规则匹配、不耗模型，各套餐都能用。两者可叠加时**固定先改写后词表**：先整理口语，再补业务术语；顺序颠倒，扩展词容易对不上。词表只改查询句，不改文档向量，**改词表不用重索引**。

**高频追问1**：改写失败会怎样？

**追问回答**：不阻断检索。超时、异常或输出不合规时，**降级用用户原问题继续召回**，响应里标明发生了降级。业务方仍能拿到结果，只是没用上改写。

**高频追问2**：改写会不会把语义改偏，反而把检索结果拉低？

**追问回答**：理论上有这个风险，所以不能只靠体感。固定评测集上做过关闭 vs 开启的单变量对照：开启后**精确率大约提升 8 个百分点，召回大约提升 3 个百分点**，整体质量收益成立，才保留为质量档能力。个别题可能有波动，但不是整体变差；一旦改写失败还会回退原问题，避免坏改写硬伤主链路。代价是多一次模型调用、延迟更高，所以按档位和套餐按需开，**不默认全开**。

## 8. 你们的精排是怎么实现的？

精排接在召回和 RRF 融合之后：两路先把候选找全、融合成一小批（质量档大约 Top 20），再对这批候选按「和问题是否真正相关」重新打分，取出最终 Top 5。它**不替代召回，全库精排成本和延迟都不可接受**。

最初用通用大模型做生成式重排：把问题和候选拼进提示词，让模型输出带分数和理由的 JSON，再解析重排。效果上能改善排序，但慢、贵、还依赖格式正确——P95 可到数十秒，偶发超时或 JSON 不合规就要降级。后来改成专业精排：接入 Qwen3 Rerank（Cross-Encoder），一次请求传入问题和候选列表，直接返回候选下标和相关性分数，不再生成长文本。**延迟压到秒级**，更适合在线。给模型看的是拼好的检索文本（文档名、章节路径、正文），返回给调用方的仍是原始正文。首次只换模型时质量曾掉过，对齐查询句、候选格式和排序指令后才稳定可用。

**高频追问1**：当时看过哪些精排方式和模型，为什么最后选 Qwen3？

**追问回答**：方式上主要就三类：不做精排，直接用 RRF 顺序；通用大模型生成式重排，让模型写 JSON 分数和理由；专用精排（Cross-Encoder），一次吃进问题和候选，直接出相关分。部署上还可以选本地模型或远程 API。选型时用固定候选集做了对照：相对不精排，专用精排能把更有用的证据往前排、召回也有提升；相对旧的 LLM 重排，质量有取舍，但 P95 能从几十秒压到大约 3 秒，格式也更稳，更适合在线。具体模型选百炼上的 `qwen3-rerank`，一是知识库以中文为主、适配更好，二是支持 instruct 说清「什么算有效证据」，三是 Embedding 已在同一平台，鉴权费用省事，不必再接一套供应商。旧 LLM 重排留作离线对照，线上默认走 Qwen3。

**高频追问2**：精排失败会怎样？

**追问回答**：不会整单失败。超时、HTTP 异常、响应非法或下标/分数不合规时，降级为融合后的原始顺序取前若干条，响应标明降级。**精排改善顺序，但不能成为基础检索的单点故障**。

## 9. 检索链路有没有做过性能优化？具体做了哪些？

有，主要三条线，对应延迟瓶颈不同。

**精排换型。** 原先用通用大模型做生成式重排，P95 可到数十秒，还不稳。换成 Qwen3 专业精排后，**延迟压到秒级**（大约 3 秒量级），更适合在线。实现和选型细节上一题展开；这里强调它首先是性能与稳定性改造，不是只换个模型名。

**混合召回并行和连接复用。** 早期向量路和关键词路串行，总耗时接近两段之和；两路其实无依赖，后来并行执行，总耗时接近较慢一路。同时给向量化、改写、精排、ES 做应用级连接复用和独立连接池。固定评测下质量无退化，**P50 大约降 45%，P95 大约降 35%**；只改执行时序，不靠缩小候选换速度。

**多知识库全局融合。** 早期每个库各跑一遍完整检索再二次融合，会重复算查询向量，引擎访问随库数线性涨，还容易变成「每库先占几个名额」。后来**多个授权库组成统一作用域**：一次问题处理、一次向量化、一次全局向量查询、一次全局关键词查询、一次全局 RRF。库越多，省下的重复计算越明显。工程已落地，但部分双库题质量仍不理想，**不宣称多库质量已全面提升**。

**高频追问1**：多库全局融合后，某个库失败或没权限会怎样？

**追问回答**：作用域在服务端统一解析，权限或索引未就绪的库会前置拦住，不会悄悄少查还当成功。旧的分库并行下，单库失败可跳过其余库继续、响应标明部分成功，全部失败才检索失败；全局融合更强调先把可查范围校干净，再一次检索。

**高频追问2**：连接池会不会无限涨？

**追问回答**：会配最大连接数、Keep-Alive 数量和存活时间。ES 客户端还会关掉环境代理继承，避免内部检索流量被误送到外部代理。

## 10. 现有检索链路有没有用 Redis 做结果缓存？还需要加吗？

**有用到 Redis，但不是拿来缓存检索结果**。当前主要两件事：Celery 的任务队列和结果后端，支撑异步索引；检索侧的 QPS 限流和日配额计数。连接复用也只复用 HTTP 连接，不缓存查询文本、候选或最终 Top 结果。

**检索结果缓存目前没做，也不是当前优先项**。原因很直接：同一问题在不同租户、知识库、档位、改写开关、索引版本下结果都可能不同，缓存键很容易做错；文档一更新还要处理失效，漏了就会返回过期片段。中台更看重「这一次策略可复现、可降级、可观测」，而不是用缓存把某次结果冻住。性能上我们已经先做了并行召回、连接复用和精排换型，把在线延迟压下来。

什么时候才考虑加：观测到大量完全相同的重复查询、索引变更不频繁，且能接受严格按租户/库/策略/索引版本构造缓存键并在重索引时主动失效。即便加，也更适合短 TTL 的热点查询，而不是把整条质量档链路默认缓存掉。

**高频追问**：如果业务坚持要加，你会怎么做？

**追问回答**：**更适合做成「热点且固定的 FAQ 缓存」**，而不是把任意自然语言检索都缓存。比如运营整理一批高频标准问，或做成「猜你想问」入口：用户点选预设问题，直接返回已校验过的片段或答案材料，键按租户、知识库、问题 ID 和索引版本管理，文档更新时失效重刷。这和开放式检索不同——开放问题表述多变，缓存命中率低、脏读风险高；FAQ / 猜你想问问题集合小、问法固定，命中稳、也好维护。普通自由提问仍走现有检索链路，不默认整链缓存。

## 11. 关系补进来的片段怎么参与排序？上下文恢复会不会把整章都拼上？

关系只说明结构上有关，不等于和问题更相关。若继承种子高分，父章节或引用目标可能靠关系压过真正匹配的片段。因此**注入候选先不带高分、排在原召回之后**；开精排时再按问题与正文重打分；不开精排时它们通常进不了最终命中，价值主要留给上下文恢复。关系负责带进池子，相关性仍由精排或原召回决定。注入有种子数、每种子条数和候选池上限，并去重、跳过指路句和低信息片段。

上下文恢复也有约束：**不会无条件拼整章**。只有当前片段层级较深，且正文出现「本节」「上述」「前述」「该规则」「适用范围」这类依赖上文的说法时，才尝试补父章节；相邻段和明确引用同样有条数和字符预算。表格缺表头时，也会尽量沿相邻或父级把表头类上下文补回来。小块负责命中，关系负责补阅读语境——入库侧怎么建关系，在入库篇展开。

**高频追问**：这和 Evidence Pack 是一回事吗？

**追问回答**：不是。这里是检索链路上的候选增强与上下文补齐；Evidence Pack 是在结果之上整理要点和可信引用，属于进阶篇的可选证据层。

## 12. 核心检索链路有哪些多层降级设计？

原则是：**旁路能力和单路召回可以失败，主链路仍尽量返回可用结果**。混合模式下一路失败退到另一路，两路都失败才检索失败；改写、精排超时或异常旁路降级，沿用原查询或融合顺序；关系增强、上下文恢复、可观测上报失败都不阻断返回。配额没过、作用域校验失败则在开始前直接拒绝，那不属于降级。

降级不会当成一次完全正常的成功：**响应里标明是否降级及原因**，便于监控和排查。纯向量模式下向量化失败、混合模式下两路同时失败，仍然会检索失败，因为已经没有可用召回。

**高频追问**：业务方怎么感知降级？

**追问回答**：看响应里的降级标记和原因说明，调试台也可展示。生产上可以重试、提示换问法，或记日志给运维。

## 13. 如果空结果，怎么区分「库里没数据」和「有数据但没搜到」？

空结果不一定是系统错误。**返回成功加空列表，同时在响应里说明空结果原因**：一种是作用域内没有可检索的成功索引内容，一种是有内容但没有匹配上。业务方据此决定是去补文档，还是换问法、换档位。

**高频追问**：用户问题特别长怎么处理？

**追问回答**：请求校验有最大长度限制，默认约 2000 字符，超过直接参数错误，避免超长文本打爆向量化或模型。正常问题远小于这个长度。

## 14. 如果面试官问检索链路你负责的核心贡献，你怎么答？

我会从三条线说。第一，把单向量 TopK 做成完整的混合召回、融合、精排链路，支持多档策略与套餐双层约束，并把档位收口成可复现的产品契约。第二，抽出检索内核，让普通检索和受控 Agentic Research 共用同一套召回与降级逻辑。第三，针对在线成本做了并行召回、连接复用、全局多库融合和精排升级，在固定评测下能拿出延迟与质量数据；同时主动说明多库质量边界、精排取舍和按需开启的能力，体现工程权衡。

**高频追问**：检索链路里你认为最难的一点是什么？

**追问回答**：难的不是单点技术，而是**效果、延迟、可复现、可降级要同时满足**。每加一项优化都要固定评测集做对照，效果回退就不能上。比如精排从通用大模型换成 Qwen3，一开始延迟下来了，但精确率和召回一起掉，说明还不能当升级成功。后来做了三个优化：第一，把排序指令从「主题相关就行」收紧成优先能直接回答的规则、条件、期限类片段；第二，精排改用 Query 改写后的查询句，和召回保持一致，改写失败再回退原问题；第三，候选从标题加正文，改成带文档名和章节路径的检索文本。对齐后再测，质量回到可用，才真正换成线上默认。
