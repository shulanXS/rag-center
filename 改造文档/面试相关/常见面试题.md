## 1. 用一两句话介绍一下这个项目是做什么的？
这是一个 RAG 检索中台：业务方把文档交给我们建库、建索引；用户提问时，把问题传过来，我们返回最相关的文档片段和分数。最终答案怎么组织、怎么展示，由业务方自己的应用去完成，中台不负责「生成回答」。

**高频追问**：那和直接做一个问答机器人有什么区别？
**追问回答**：问答机器人通常服务一个具体场景，比如客服页面；中台是把「从知识库里找相关片段」做成通用能力，多条业务线都能接，不用各自重复搭向量库、搜索引擎和排序逻辑。

## 2. 为什么把它定位成「中台」，而不是普通的 RAG 应用？
普通 RAG 应用通常绑定一个业务页面，比如内部知识库问答；我这个项目不替业务方生成最终答案，也不绑具体 UI，而是把建库、索引、检索、排序封装成统一 API，多个租户、多个业务系统可以共用同一套能力。

**高频追问**：中台特征具体体现在哪？
**追问回答**：多租户隔离、统一接口、统一索引流程、统一检索返回格式、Provider 可插拔、统一日志和错误码，以及按套餐控制功能上限和配额。

## 3. 能简单说一下核心业务链路吗？
业务方先用 API Key 鉴权，创建知识库，再上传文档；上传后系统立刻返回「处理中」，后台异步完成切片、向量化，并同时写入向量库和搜索引擎。检索时传入问题和知识库 ID，中台返回结构化片段、分数和来源信息，不生成最终答案。

**高频追问**：租户身份怎么传？
**追问回答**：请求头带 Bearer API Key，后端解析出是哪个租户，请求体里不用再传租户 ID，避免业务方伪造身份。

## 4. 为什么中台只做到检索，不直接生成最终答案？
因为不同业务对 prompt、语气、是否带引用、是否流式输出要求差很多。中台只负责把「和问题相关的证据片段」找准、找全；怎么组织成用户看得懂的回答，应该留在离业务最近的应用层，这样职责清晰，也方便各业务独立迭代。

**高频追问**：那业务方怎么接？
**追问回答**：业务方调 retrieve 拿到 chunks，自己拼上下文调大模型生成答案；中台保证检索质量，应用层保证交互体验和 prompt 策略。

## 5. 技术栈是怎么选的？为什么用这些组件？
后端用 FastAPI，向量存 PostgreSQL 加 pgvector，关键词检索用 Elasticsearch，异步索引用 Celery 加 Redis，Embedding 和大模型走 OpenAI 兼容 API，前端调试台用 React。选型原则是：部署运维成本可控、组件成熟、各层职责清晰，方便排查和扩展。

**高频追问**：为什么向量库当前用 pgvector 而不是 Milvus？
**追问回答**：pgvector 是 PostgreSQL 的向量扩展，支持向量类型和 HNSW/IVFFlat 索引，本身就能做生产级相似度检索；和业务表同库，文档、chunk、向量一次事务写入，部署运维比再单独起一套 Milvus 集群轻。Milvus、Qdrant 这类**独立向量引擎**更适合向量规模特别大、检索 QPS 极高、需要专用集群扩展的场景。当前规模 pgvector 够用；若以后成为瓶颈，通过 VectorStore 接口换实现即可，RagService 不用大改。

## 6. 代码整体是怎么分层的？
最外层是 API 路由，负责鉴权和参数校验；中间是 Service 做业务编排，比如检索、上传、配额检查；再往下 Repository 访问数据库；对外部依赖像向量库、搜索引擎、Embedding、大模型，都通过 Provider 适配层接入，避免业务代码和具体厂商绑死。

**高频追问**：为什么要单独抽 Repository？
**追问回答**：把 SQL 和数据访问细节收口，Service 只关心业务逻辑，测试时可以 mock 数据层，后面换存储方案时改动面更小。

## 7. 接口响应为什么统一成 code、msg、data？
这样业务方无论调建库、上传还是检索，处理成功失败的方式都一样：看 code 是否为 0，msg 读人类可读说明，data 拿业务数据。排查问题时还可以用 request_id 去日志里对齐一次完整调用链。

**高频追问**：业务报错时 HTTP 状态码是多少？
**追问回答**：多数业务错误仍然返回 HTTP 200，用 body 里的 code 区分，比如未授权 20010、配额用尽 20014；真正未捕获的服务器异常才走 HTTP 500，避免前端要同时处理 HTTP 层和业务层两套错误语义。

## 8. request_id 有什么用？
每次请求进来到出链路都会带上同一个 request_id 写进日志，从 API 入口、检索、Embedding 调用到异常栈都能串起来。线上用户说「刚才检索不对」，拿 request_id 就能快速定位那一次到底发生了什么。

**高频追问**：request_id 谁生成？
**追问回答**：HTTP 中间件在请求进入时生成或透传，后续 Service 和 Provider 打日志时都带上，不需要业务方自己传。

## 9. 为什么要抽象 VectorStore 接口？
当前底层是 pgvector，但检索服务不应该写死 pgvector 语法。抽象成 VectorStore 之后，RagService 只关心「按向量找相似片段」，以后换 Milvus、Qdrant 只需新增一个实现类，核心业务编排不用动。

**高频追问**：VectorStore 接口大概有哪些方法？
**追问回答**：核心是写入向量片段和按 query 向量做相似度检索，再加按文档删除等维护能力；具体 SQL 或 SDK 调用都藏在实现类里。

## 10. 为什么要抽象 EmbeddingProvider？
Embedding 可能来自 OpenAI、DeepSeek、Ollama 等不同服务，输入是一批文本，输出是向量。抽象之后索引和检索都只调 embed_texts、embed_query，换模型或换供应商只改配置和 Provider 实现。

**高频追问**：换 Embedding 模型要注意什么？
**追问回答**：新模型的向量维度必须和配置一致，而且和旧向量不在同一语义空间，所以换模型后必须清空旧索引、全量重建，不能新旧向量混用。

## 11. 为什么要抽象 LLMProvider，而不是在 rerank 里直接调某个模型？
大模型不只会用于 rerank，后面 query 改写、评测辅助等也会用到。如果每个地方各自写 HTTP 请求，超时、重试、日志、换模型都会重复且容易不一致。统一走 LLMProvider，调用方式、异常处理和日志格式都是一套。

**高频追问**：实际收益是什么？
**追问回答**：模型供应商可替换，业务层只依赖统一接口；切模型改环境变量或换一个 Provider 实现就行，不用改 RagService 等业务代码。

## 12. 关键词检索为什么也做成 Provider？
和向量库一样，今天用 Elasticsearch，以后可能接 OpenSearch 或其他搜索引擎。KeywordSearchProvider 把「写入片段、按关键词检索、按文档删除」封装起来，RagService 不关心底层是 ES 还是别的引擎。

**高频追问**：如果关掉关键词检索会怎样？
**追问回答**：配置里可以不初始化 KeywordSearchProvider，此时只能走纯向量检索（vector 模式）；hybrid 和 bm25 模式依赖关键词检索，没有 Provider 就不能用这两种模式。

## 13. Query 处理为什么单独做 Pipeline，而不是写在 RagService 里？
Query 处理包含改写、词表扩展等多个步骤，以后还可能加 Multi-Query 等策略。抽成 Pipeline 后，RagService 只负责「先处理 query、再检索」，每个步骤是可插拔的 Processor，顺序固定、职责单一，测试和扩展都更方便。

**高频追问**：Pipeline 里步骤顺序是什么？
**追问回答**：先走可选的 LLM 改写，再走词表同义词扩展；改写失败会降级用原问题，词表扩展始终执行，不消耗 LLM。

## 14. 日志和错误码是怎么设计的？
日志带时间、级别、模块、request_id 和业务关键节点标记，接口请求响应、Embedding 调用、LLM 调用、检索成功失败都会打。错误码按类别分段，比如 2 万段是 API 和参数，3 万段是存储，4 万段是模型，5 万段是系统；返回给调用方的是简洁 code 和 msg，详细堆栈只在服务端日志里。

**高频追问**：为什么要单独有 error.log？
**追问回答**：app.log 是全量日志，排查严重问题时噪声多；error.log 只收 ERROR 及以上，打开就能看异常堆栈和上下文，不用在海量 INFO 里翻。

## 15. 20013 和 20014 这两个错误码怎么区分？
20013 是「当前套餐不支持这个功能」，比如免费版用了 hybrid 或开了 rerank；20014 是「配额用完了」，比如知识库数量超限、单库文档数超限、日检索次数用尽。一个是能力天花板问题，一个是用量累计到顶的问题。

**高频追问**：秒级 QPS 超限算哪种？
**追问回答**：算 20005 接口调用超限，和日配额 20014 是两套；QPS 管瞬时并发，日配额管一天总共能检索多少次。

## 16. 50002 检索失败一般在什么情况下返回？
通常是检索链路已经没法给出有意义结果的时候，比如 hybrid 模式下向量路和关键词路同时失败，或者多库检索时所有库都失败了。部分依赖失败会尽量降级继续返回，只有「完全没有可用召回」才报 50002。

**高频追问**：和 20014 日配额用尽有什么区别？
**追问回答**：20014 是检索还没开始就被配额拦住了；50002 是检索过程中依赖异常导致失败，属于服务执行问题，不是用量问题。

## 17. 文档索引为什么做成异步，而不是上传时同步做完？
切片、批量 Embedding、写向量库和搜索引擎，一篇稍长的文档可能要几秒甚至几十秒。同步做会让 HTTP 请求长时间阻塞，容易超时，也没法水平扩展处理能力。改成 Celery 异步后，上传立刻返回「处理中」，Worker 在后台慢慢做，API 和索引解耦。

**高频追问**：Worker 没启动会怎样？
**追问回答**：上传仍然成功，文档状态一直是处理中，永远不会变成成功或失败；所以部署上 API 和 Celery Worker 必须一起起，README 里也强调了这一点。

## 18. 文档有哪几种状态？分别代表什么？
三种：成功表示索引完成可以检索；失败表示索引过程出错，会记录具体失败原因；处理中表示正在索引，此时不能重索引也不能删，避免和后台任务打架。

**高频追问**：业务方怎么知道索引完成了？
**追问回答**：轮询文档详情看状态，或者在前端调试台看状态徽章；生产环境也可以自己做 webhook 或消息通知，中台目前提供的是轮询能力。

## 19. 重索引和重新上传有什么区别？
重索引是用库里已经存好的正文重新切片、向量化、写索引，适合切块策略升级后让老文档也用新规则。重新上传是传一份新内容或新文件，会生成新的文档记录。文件上传的文档还可以选「重新解析原文件再索引」：适合解析逻辑升级后，从磁盘上的原文件重新提取正文，而不只是重切旧正文。

**高频追问**：reindex 时旧 chunk 怎么处理？
**追问回答**：会先 purge 该文档在向量库和 ES 里的旧片段，文档状态置为处理中，重新入队 Celery；避免新旧 chunk 混在一起。

## 20. 为什么处理中的文档不能 reindex 或删除？
因为后台 Celery 任务可能正在写向量库和搜索引擎，这时如果又 purge 又入队新任务，容易出现两个任务抢同一文档、状态不一致或部分写入的问题。等当前任务结束变成成功或失败后，才允许 reindex 或删除。

**高频追问**：用户急着想改内容怎么办？
**追问回答**：只能等当前索引结束；如果必须立刻换内容，需要先等失败或成功，再删除后重新上传，或者后续产品上加「取消索引」能力，当前版本没有。

## 21. Celery 索引任务失败会重试吗？
会。网络超时、Embedding 接口失败等可重试错误，默认最多重试 2 次，间隔 10 秒。重试耗尽后文档标记为失败，失败说明里会提示重试已用尽，业务方可以手动触发重索引再试。

**高频追问**：哪些错误不会重试？
**追问回答**：明确的业务错误，比如文档内容为空，会直接失败不重试；不可恢复的配置错误也不会无限重试，避免任务一直卡住队列。

## 22. 向量库和搜索引擎为什么要双写？一致性怎么保证？
向量检索擅长语义相似，关键词检索擅长专有名词和精确匹配，两路互补。索引时先写 pgvector，再写 ES；如果 ES 写入失败会 rollback，避免只有向量没有关键词或反过来。删除和 reindex 时两边的旧片段也会一起 purge。

**高频追问**：ES 挂了但 pgvector 正常，检索会怎样？
**追问回答**：纯向量模式还能工作；混合或纯关键词模式下关键词一路会失败，混合检索会降级成纯向量并标明发生了降级，不会悄悄返回错误结果。

## 23. 为什么改文档内容不支持直接局部修改，而要删了再传？
因为内容变了意味着切片边界、向量、关键词索引都要重建，不是改几个字段能解决的。先删除清掉旧索引，再上传新内容走完整索引流程，逻辑简单、不会留下脏片段。

**高频追问**：这样会不会丢历史？
**追问回答**：会生成新的文档记录，旧文档删除后其片段也没了；如果业务需要版本历史，应该在中台之上自己做版本管理，中台目前只管「当前有效版本」。

## 24. 切块策略升级后，老文档怎么让新规则生效？
只改代码或配置，新上传的文档会用新规则，老文档片段还是旧的。需要跑全量重索引脚本，按知识库或单篇文档重建索引，从已存的正文重新切、重新向量化，不用业务方重新上传文件。

**高频追问**：reindex 期间能检索吗？
**追问回答**：正在重索引的那篇文档处于处理中，旧片段已被清除，这篇暂时检索不到；其他已成功的文档不受影响。所以重索引适合低峰批量做。

## 25. 上传为什么同一个接口要支持 JSON 和表单两种传法？
Markdown 和纯文本可以在前端读成字符串后，用 JSON 把正文传上来，和以前完全兼容。Word 和 PDF 是二进制，不能塞进 JSON，必须走表单上传文件。共用一个上传地址，后端根据请求类型分流处理。

**高频追问**：为什么不单独做一个文件上传接口？
**追问回答**：少一个接口、少一份文档和鉴权逻辑；两种方式本质都是「建文档 + 触发索引」，只是正文来源不同，合并更干净。

## 26. 文档解析插件和 EmbeddingProvider 是不是同一套思路？
是，都是可插拔设计：解析层按扩展名选解析器，输出统一的解析结果（正文、来源类型、元信息）。新增格式只加实现并注册，索引和检索服务里不用写一堆 if-else 判断文件类型。

**高频追问**：解析出来的正文是什么形态？
**追问回答**：Markdown 风格的纯字符串，不是另存一个 .md 文件；Word 标题 ideally 变成 #/##，表格 ideally 变成 | | |，好让结构化切块接上。

## 27. 为什么解析入口要收敛成一个统一函数？
避免在上传接口、异步任务、索引服务里到处写「如果是 PDF 就……」。全项目只保留一个入口：已有正文就直接用，只有原文件就去读盘、选解析器、提取正文；解析失败走解析失败错误码，文档标失败。之后切块层只当普通 Markdown 字符串处理。

**高频追问**：JSON 上传的 md 还会进解析器吗？
**追问回答**：有正文时直接透传（可选做换行归一化），不读磁盘；和改前行为一致，零破坏。

## 28. Word（docx）具体怎么解析？表格为什么容易出问题？
Word 用 mammoth 先转 HTML，再用 markdownify 转 Markdown——因为 mammoth 自带的转 Markdown **不会**可靠输出 GFM 表格。表格转成功后是 `| 列1 | 列2 |` 格式，切块器会标成表格类型并保留表头。Word 另存 docx 时可能带标题书签，解析时会去掉，避免前端显示成裸 HTML 标签。

**高频追问**：表格和前面那句「可获得以下奖励：」为什么在两个 chunk？
**追问回答**：切块规则里表格单独成块，不和前面的说明文字粘在一起；检索时 Top1 可能是引言句，含数字的表格在相邻块，这是设计取舍，不是解析丢了内容。

## 29. PDF 解析和 docx 有什么本质差别？还要优化吗？
PDF 用 PyMuPDF 按页抽文本，每页加「第 N 页」当伪标题，**不识别** Word 式标题、列表、表格结构。文字版单栏制度 PDF 够用；扫描件抽不出字会标失败；复杂表格、双栏论文顺序可能乱。制度类文档建议优先 docx；PDF 当「能搜到字就行」的兜底，OCR 和版式增强可以以后单独做解析插件。

**高频追问**：扫描件 PDF 怎么处理？
**追问回答**：解析结果为空就标失败，失败原因提示疑似扫描件；当前未接入 OCR，避免悄悄建出空库。

## 30. 解析失败和索引失败怎么区分？
不支持的格式（比如 zip）在上传阶段就直接报参数错误，文档记录都不会创建。解析器报错或抽出空正文 → 文档标失败，失败原因写清楚（比如「解析结果为空」）。解析成功但向量化或写搜索引擎失败 → 同样标失败，但原因在索引阶段。业务方看状态和失败说明，能分清是「文件不对」还是「模型/存储挂了」。

**高频追问**：有单独错误码吗？
**追问回答**：有，解析失败用 20023；上传参数问题在 20001 段。

## 31. 原文件存在哪里？生产怎么扩展？
本地按「存储目录 / 租户 / 文档 / 文件名」分层存放，数据库里记下原文件路径和展示用的文件名。纯文本 JSON 上传没有原文件，这两项为空。上生产可以换成对象存储，解析器只要求「能读到文件字节」，换存储后端不用改解析接口。

**高频追问**：「重新解析」依赖原文件吗？
**追问回答**：依赖。只有当初是文件上传、原文件还在磁盘或对象存储上才有意义；纯文本上传没有原文件，重索引时这个选项会被忽略。

## 32. 前端上传 Word/PDF 和 Markdown 路径有什么不同？
Markdown/纯文本：前端读成文字，JSON 传知识库 ID、标题和正文。Word/PDF：必须用表单上传文件和知识库 ID，不能 base64 塞进 JSON。上传页支持四种扩展名，选文件后自动走不同分支。检索结果用 Markdown 渲染，表格能正常显示。

**高频追问**：上传后为什么要等 Worker？
**追问回答**：解析和索引都在后台 Worker 里；Worker 没起就一直显示处理中。Word/PDF 还要等解析完成才有正文可切。

## 33. 为什么不用固定 800 字滑动切块？
固定字符切会把标题拦腰切断、表格拆成上下两半，用户问表格里某一行时，召回的片段可能缺表头或混进上一节内容。改成按文档结构切，比如按一级二级标题分节、表格整表或按行组切，块本身语义更完整，后面 hybrid 和 rerank 才有好材料。

**高频追问**：结构化切块会不会切太碎？
**追问回答**：会，短文档多标题多表格时 chunk 数会变多，这是用块数换边界正确性；某一节特别长时，节内仍会用 chunk_size 做二次切，不会无限长。

## 34. 标题切块为什么只在一级和二级标题处分节，三级以下不单独拆？
一级二级通常对应章和节，是用户问问题时最常对齐的粒度；三级及以下再拆容易过碎，一个知识点被拆成很多小块，向量语义反而不完整。所以三级标题会留在当前节正文里，不额外开新节。

**高频追问**：标题路径是什么？
**追问回答**：每条片段会带上所属的标题层级路径，比如「退款政策 > 退款时效」，调试和检索结果展示时能看出片段来自哪一节，也方便后续做引用溯源。

## 35. 表格为什么要单独切块？
用户问「满减和优惠券能否叠加」这类问题，答案往往在表格某一行。如果表格被固定字符切拦腰砍断，可能只剩半张表、没有表头，向量语义不完整，召回率会明显下降。表格单独成块，必要时还带表头摘要，检索时更容易命中整行语义。

**高频追问**：大表格怎么处理？
**追问回答**：默认按行分组切，比如每 10 行一块，每块都注入表头摘要「【表头】列1 | 列2」，保证任意一块都能看懂在说什么。

## 36. chunk_size 和 chunk_overlap 分别起什么作用？
chunk_size 控制单块最大字符数，防止一块过长超过 Embedding 或 LLM 上下文限制；overlap 是相邻块之间重叠一小段，避免一句话正好卡在边界上被切断后两边都搜不到。默认 800 字一块、重叠 100 字，是在召回粒度和索引成本之间的折中。

**高频追问**：overlap 越大越好吗？
**追问回答**：不是，overlap 越大 chunk 数越多、索引和 embedding 成本越高，重复内容也越多；100 字左右对中文制度文档通常够用。

## 37. 解析层和切块层为什么要分开设计？
解析层负责「各种格式 → 统一 Markdown 风格文本」：`.md`/`.txt` 做归一化，Word 用 mammoth 转 Markdown，PDF 用 PyMuPDF 按页抽文本；切块层只认字符串，负责按标题分节、表格整表切，和文件格式无关。以后加 HTML、Excel 等新格式，主要换 Parser 插件，切块和检索流程不用推倒重来。

**高频追问**：现在支持哪些上传格式？
**追问回答**：Markdown 和纯文本可以 JSON 直接传正文；Word 和 PDF 要用表单上传原文件，后台 Worker 解析后再写入正文。不支持 zip 等格式，上传时直接报参数错误。

## 38. 向量检索是怎么工作的？
用户问题先通过 Embedding 模型变成向量，再到 pgvector 里找余弦距离最近的若干 chunk 向量，距离越小越相似，返回时会转成 0 到 1 左右的相似度分数方便阅读和调试。

**高频追问**：为什么不直接在 PostgreSQL 里存 JSON 数组自己算？
**追问回答**：pgvector 提供了专用向量类型和 ANN 索引（HNSW、IVFFlat），相似度检索比逐行算余弦快几个数量级；同时 chunk 元数据和向量在同一库里，join 和事务都方便。

## 39. 为什么要引入 Elasticsearch 做 BM25 关键词检索？
向量检索擅长语义相似，比如「退钱多久到账」和「退款到账时间」能匹配；但对错误码、SKU、法规条款名、产品型号这类需要精确命中的场景不够稳。BM25 基于倒排索引做关键词匹配，正好补上向量检索的短板。

**高频追问**：哪些 query BM25 往往比向量更稳？
**追问回答**：错误码、订单状态、接口字段名、产品型号、专有名词、很短的 keyword 查询，这些场景关键词命中比语义相似更可靠。

## 40. BM25 和向量分数为什么用 RRF 融合，而不是直接加权相加？
两路分数量纲完全不同：BM25 的 score 受词频、文档长度等影响，没有固定上限；向量相似度是 0 到 1 左右的值。直接加权相加很不稳定，调权重也很难泛化。RRF 只看每一路里的排名，排名越靠前贡献越大，不依赖原始分数归一化。

**高频追问**：RRF 公式是什么？
**追问回答**：每个 chunk 的融合分是各路人马排名贡献之和，每一项是 1 除以（k 加排名），k 默认 60；一条结果在向量路和关键词路都排得靠前，融合分就高。

## 41. Elasticsearch 的相关性分数是什么？为什么不能直接和向量分数相加？
ES 在查询时动态算出的相关性分数，默认基于 BM25，只用于同一次查询结果内部排序，不是百分制也不是概率。接口里返回的关键词分数主要用于调试和分析，混合检索最终排序用的是 RRF 融合分，不是两路原始分直接相加。

**高频追问**：title 字段为什么权重更高？
**追问回答**：检索时对 title 做了平方加权，标题里命中关键词比正文里命中更重要，因为标题往往概括整篇文档主题。

## 42. 中文检索为什么要配 IK 分词？
BM25 是基于「词」算相关性的，英文有空格天然分词，中文没有。如果不分词，「退款申请」可能被当成一整块或拆错，关键词召回会明显下降。IK 分词器把中文切成有意义的词，BM25 才能稳定工作。

**高频追问**：ik_max_word 和 ik_smart 有什么区别？
**追问回答**：索引时用 max_word 切得更细，提高召回；查询时用 smart 切得更准，减少过度拆分带来的噪声，这是中文 ES 里很常见的组合。

## 43. 检索有哪三种模式？分别什么时候用？
vector 纯向量，最快，适合对延迟敏感、问题表述和文档语义接近的场景；bm25 纯关键词，适合错误码、型号、条款名等精确匹配；hybrid 两路一起召回再 RRF 融合，召回最全，但依赖 ES，延迟也略高。

**高频追问**：默认配置是哪种？
**追问回答**：环境变量默认是纯向量，但 API 未传 profile 时默认走均衡预设，实际是混合检索，所以接口行为和纯环境变量默认可能不同，以 profile 解析后实际生效的参数为准。

## 44. speed、balanced、quality、custom 四档 profile 有什么区别？
speed 追求快，纯向量、少返回几条；balanced 默认均衡，hybrid、不开 rerank 和改写；quality 追求质量，hybrid 加 rerank 加 query 改写，适合 pro 档；custom 允许业务方自己传检索参数，但仍受套餐能力上限约束。

**高频追问**：不传 profile 默认哪档？
**追问回答**：默认 balanced，但 free 套餐只允许 speed，free 租户不传 profile 会报 20013，需要显式传 speed。

## 45. plan 和 retrieve profile 为什么要分两层？
plan 是租户长期的能力套餐，管能不能用 hybrid、rerank、改写，以及 QPS、日检索量、最多几个库等上限；profile 是单次检索请求选用的策略，比如这次要速度还是要质量。分开后，同一个 pro 租户有时可以走 quality，有时可以走 speed，不用改账号配置。

**高频追问**：profile 会写进租户表吗？
**追问回答**：不会，每次 retrieve 请求里指定；租户表只存 plan，不存默认 profile，这样更灵活。

## 46. 三档 plan 的核心差异怎么记？
free 适合体验和 PoC，只能 speed、单库、hybrid 和 rerank 都不能开；standard 适合生产，能 hybrid 和多库，但不能 rerank 和改写；pro 全功能，quality profile、高 QPS、高日检索量、多库上限也最高。

**高频追问**：免费版日检索量大概多少？
**追问回答**：500 次，QPS 3；standard 是 5000 次和 QPS 10；pro 是 10 万次和 QPS 50，具体数字以 plan 配置为准。

## 47. QPS 限流和日检索量配额有什么区别？
QPS 管瞬时并发，比如一秒内不能超过 10 次检索，超限立刻 20005；日检索量管一天总共成功检索多少次，用 Redis 按 UTC 日期计数，成功落库后才加一，用尽报 20014。一个是防瞬时打爆，一个是防总量超套餐。

**高频追问**：多库一次 retrieve 算几次？
**追问回答**：算 1 次，无论联查几个库，只对租户日计数加一，避免多库场景下配额消耗过快。

## 48. 上传文档有哪些配额限制？
除了套餐对应的单库最大文档数，还有租户级别的「同时正在索引的文档数」上限，比如免费档只能有 1 篇在处理中，防止大量上传把 Worker 队列打满。建知识库也有总数上限，免费档只能 1 个库。

**高频追问**：超限返回什么码？
**追问回答**：20014 配额已用尽，错误说明里会写清是文档数、并发索引还是知识库数量哪种触顶。

## 49. API Key 鉴权是怎么工作的？
业务方在 Header 里带 Authorization Bearer，后面是 rk_live 开头的密钥；后端对密钥做 hash 和数据库比对，找到对应租户和套餐，注入请求上下文，后续所有操作都按这个租户隔离，调用方不能伪造别的租户。

**高频追问**：Key 明文存数据库吗？
**追问回答**：不存，只存 hash；创建 Key 时终端只显示一次明文，丢了只能吊销重发，这是常规 API Key 做法。

## 50. 为什么用 API Key 而不是 JWT 做中台鉴权？
中台是服务端对服务端调用，业务方后端持有一个长期有效的 Key 调 retrieve 就行，不需要用户登录态和过期刷新那套。API Key 实现简单、权限和租户绑定清晰，也便于按 Key 做用量统计和吊销。

**高频追问**：本地开发怎么免 Key 调试？
**追问回答**：后端关闭鉴权开关后，会自动用演示租户；前端 Key 留空即可，方便本地跑通，但生产必须开鉴权。

## 51. 租户之间数据怎么隔离？
知识库、文档、片段、检索日志都绑在租户下，数据访问层会校验「这个资源是否属于当前租户」，跨租户访问别人的库或文档会报不存在，从底层保证隔离，而不是只靠前端不传别人的 ID。

**高频追问**：向量检索会不会搜到别的租户文档？
**追问回答**：不会，向量检索和关键词检索都会按租户和知识库过滤，只在本租户本库范围内召回。

## 52. query rewrite 是干什么的？
用户口语化提问，比如「背调要问啥」，直接检索可能匹配不好；rewrite 用 LLM 把问题改写成更完整、更像文档里的表述，再用改写后的话去检索，提高召回质量。只在 quality 等高档策略或 pro 套餐下开启。

**高频追问**：rewrite 失败会怎样？
**追问回答**：不会阻断检索，自动降级用用户原话检索，响应里会标明发生了降级，业务方仍能得到结果，只是没用上改写。

## 53. 词表扩展和 query rewrite 有什么区别？
rewrite 用 LLM，有调用成本和延迟，适合口语化、复杂问法；词表是知识库配置里的同义词组，比如「背调」扩展成「背景调查」，规则匹配、不耗 LLM，各套餐都能用。两者可以叠加：先改写，再词表扩展。

**高频追问**：词表谁维护？
**追问回答**：按知识库维护，运营或业务方通过脚本或修改知识库配置写入；不同领域库可以有不同的词表，互不影响。

## 54. rewrite 和词表扩展的执行顺序是什么？
固定先改写后词表扩展。因为改写可能已经把口语整理成更规范的词，词表再在上面的基础上补业务术语；顺序反了可能导致扩展词和改写结果配合不好。

**高频追问**：只开词表不开 rewrite 可以吗？
**追问回答**：可以，均衡档默认就是只用词表不用改写；词表始终会跑，只要知识库配了同义词且命中。

## 55. LLM rerank 在检索链路里处于什么位置？
在召回和融合之后。完整顺序是：处理 query → 向量路和/或关键词路召回 → RRF 融合得到候选集 → 可选 LLM rerank 精排 → 返回 top_n。rerank 不替代召回，只对已经筛出来的一小批候选重新打分排序。

**高频追问**：为什么 rerank 不直接扫全库？
**追问回答**：全库 rerank 成本太高、延迟不可接受；召回负责从海量 chunk 里快速找候选，rerank 负责在小候选集里做细判断，分工不同。

## 56. LLM rerank 是怎么打分的？
把用户问题和每个候选片段发给大模型，让模型按 JSON 格式给每个片段打 0 到 1 的相关性分，再按分数重排取 top_n。片段正文会截断到一定长度，避免 prompt 过长。

**高频追问**：rerank 失败怎么办？
**追问回答**：降级为精排前的融合顺序，取前若干条返回，响应里标明发生了降级，不会整单失败。

## 57. 多知识库联合检索是怎么做的？
请求里可以传多个知识库 ID，后端对每个库并行做召回，每个库各自走向量或混合检索，得到多路候选后做跨库 RRF 融合，全局排序取 top_k，返回的每条片段会标明来自哪个库。

**高频追问**：单库和多库在融合上有什么区别？
**追问回答**：单库时 hybrid 只在库内做向量加关键词 RRF；多库时在每库已有候选基础上再做一层跨库 RRF，避免某个库 chunk 特别多垄断最终结果。

## 58. 多库检索时部分库失败怎么处理？
并行召回时某个库失败就跳过，其余成功的库继续跨库融合；响应里会标明部分成功、哪些库失败了。只有全部库都失败才返回 50002。

**高频追问**：业务方怎么感知降级？
**追问回答**：看响应里的降级标记、失败的知识库列表和原因说明；调试台也可以展示，生产业务方可选择重试或提示用户换问法。

## 59. hybrid 模式下向量路或关键词路单独失败怎么办？
如果只有一路失败，会降级成另一路的结果继续返回，并标明降级及原因，比如向量路失败或关键词路失败。只有两路同时失败才报 50002。纯向量或纯关键词模式没有这种互为备份，那一路挂了就直接失败。

**高频追问**：Embedding 失败算哪一路失败？
**追问回答**：Embedding 在向量路里，向量路失败且当前是 hybrid 时会降级为纯关键词；如果是纯 vector 模式，Embedding 失败就没有备份，检索会失败。

## 60. 检索 0 条结果为什么还返回 200 成功？
空结果不一定是系统错误，可能库里的确没有相关内容，或问题和文档不匹配。返回 200 加空列表，同时在响应里说明空结果原因：一种是库里根本没有建好索引，一种是有内容但没匹配上，方便业务方区分「没数据」和「没搜到」。

**高频追问**：空结果原因有哪几种？
**追问回答**：主要就是「库里没有可检索内容」和「有索引但没匹配上」两种；有正常结果时不带这个说明。

## 61. 用户 query 过长怎么处理？
请求校验里有最大长度限制，默认 2000 字符，超过直接参数错误拒绝，避免超长文本打爆 Embedding 或 LLM。正常用户问题远小于这个长度，限制主要是防误用和恶意请求。

**高频追问**：2000 字符大概多少中文？
**追问回答**：大约一千字左右，远超典型搜索问句；客服或知识库场景足够用。

## 62. Langfuse 在这个项目里起什么作用？
Langfuse 是可观测平台，可选开启。每次检索会记完整链路和各步骤耗时，比如问题处理、召回、精排，方便线上对比哪一步慢、哪次改写效果不好。链路 ID 也会写入检索日志，和数据库记录对齐。

**高频追问**：Langfuse 挂了会影响检索吗？
**追问回答**：不会，上报失败只打 warning，主检索链路照常返回；可观测是旁路，不能拖垮核心功能。

## 63. 检索日志记什么？有什么用？
记每次检索的租户、知识库、原始问题、实际检索句、检索档位、返回片段摘要、耗时、链路 ID 等。用于运营排查、效果分析和对接反馈；不是给业务方实时查的历史搜索界面，而是中台侧审计和调优数据。

**高频追问**：和 Langfuse 重复吗？
**追问回答**：有重叠但互补；检索日志在自有数据库，不依赖外部服务，长期留存和 SQL 分析方便；Langfuse 可视化更好，适合开发调链路。

## 64. 检索反馈 API 是怎么闭环的？
业务方或调试台对某次检索结果打 1 到 5 分，带上检索记录 ID 和链路 ID，后端校验一致后写入 Langfuse 评分。低分记录可以导出成评测 case，补标准答案后进 RAGAS 离线回归，形成「线上反馈 → 评测集 → 改配置 → 再评测」的闭环。

**高频追问**：Langfuse 没开会怎样？
**追问回答**：反馈接口会报 20020 反馈提交失败，因为分数要写 Langfuse；所以要做反馈闭环，需要同时开 Langfuse。

## 65. RAGAS 离线测评在这个项目里测什么？
只测检索质量，不测生成答案好不好。主要指标是上下文精确率和上下文召回率，用固定评测集批量调检索，改词表、检索档位或切块策略前后跑同一数据集，对比报告分数变化。

**高频追问**：为什么不测 answer faithfulness？
**追问回答**：中台不生成答案，没有 answer 可评；评测聚焦「该召的 chunk 有没有召回来」，和项目边界一致。

## 66. 前端调试台主要解决什么问题？
让运营和开发不用写 curl 也能建库、上传、看文档状态、调检索、切换 profile、多库勾选、看分数明细和打反馈。上传页支持 Markdown/纯文本（读文本走 JSON）和 Word/PDF（走表单上传）；检索结果用 Markdown 渲染，表格能正常显示。还展示当前租户套餐、今日用量，方便验证套餐和配额。

**高频追问**：调试台是生产必须的吗？
**追问回答**：不是，中台能力全在 API；调试台是开发和运营效率工具，业务方可以只用 API 接入自己的后台。

## 67. 查询当前租户信息的接口有什么用？
用当前 API Key 换取租户套餐、可用功能、配额上限、今日已用检索量等。前端靠它决定哪些检索档位置灰、展示套餐标签；业务方接入前也可以自检 Key 是否有效、套餐是否够用。

**高频追问**：和单次检索返回里的策略信息有什么区别？
**追问回答**：前者是租户级静态能力和用量；后者是这一次请求实际走了什么模式、什么 profile、联查了几个库，相当于当次策略快照。

## 68. 知识库同义词表怎么生效？
检索前会读该库配置的同义词组：用户问题命中某一组触发词，就把对应扩展词追加到检索句后面，扩大关键词命中面。不修改文档、不重新上传，也不消耗大模型，改词表后下次检索立刻生效。

**高频追问**：词表配置错了会怎样？
**追问回答**：可能引入噪声词，召回偏宽；可以用离线测评对比改前改后，或在调试台看词表是否真的命中。

## 69. Celery 和 Redis 在这个项目里分别干什么？
Redis 是 Celery 的消息 broker 和结果后端，上传后任务丢进队列，Worker 从 Redis 取任务执行索引。同一个 Redis 也用于检索 QPS 限流和日配额计数，部署简单，但生产上要注意 Redis 高可用。

**高频追问**：索引任务和 retrieve 限流共用 Redis 有问题吗？
**追问回答**：当前架构下为了省组件可以共用；规模大以后可以把 Celery broker 和限流 Redis 拆开，避免互相影响。

## 70. Embedding 批量大小 batch_size 有什么讲究？
默认一批 10 条文本调一次 Embedding API，在请求次数和单次 payload 大小之间折中。太大可能超 API 限制或超时，太小则请求次数多、总延迟高，可在配置里按模型供应商限制调整。

**高频追问**：索引一篇长文档会调多少次 Embedding？
**追问回答**：取决于切出多少 chunk，按 batch_size 分批；比如 25 个 chunk、batch 10，大约 3 次 API 调用。

## 71. 代码块和表格在 Markdown 切块里怎么处理？
围栏代码块单独识别，不会和正文混切；表格按行识别，超长按每块最大行数分组。水平线会过滤，避免产生空块。

**高频追问**：代码块会带上标题路径吗？
**追问回答**：会，代码块属于当前章节正文，片段类型会标成代码，和正文、表格区分开。

## 72. Word 和 PDF 上传是怎么接进现有链路的？（优化十二）
加了文档解析插件层：上传接口同时支持「JSON 传正文」和「表单传文件」两种方式。文件先落到本地存储目录，正文暂空，只记下原文件在哪；后台 Worker 走统一的「准备正文」入口，按格式选对应解析器，转成 Markdown 风格文本后再走原来的切块、向量化、双写索引。检索链路完全不用改。

**高频追问**：为什么不在上传接口里同步解析？
**追问回答**：大 PDF、复杂 Word 可能要几秒到几十秒，放 API 里会阻塞、易超时；和索引一样放 Worker 异步做，上传立刻返回「处理中」，也方便水平扩展 Worker。

## 73. Provider 模式换 Embedding 模型要改几处？
改环境变量里的模型名、API 地址、维度和 Provider 实现（如果新模型不兼容 OpenAI 格式）；然后全量 reindex 所有文档，因为旧向量不能和新向量混用。RagService 和 IndexingService 本身不用改。

**高频追问**：只改模型名不改维度会怎样？
**追问回答**：写入 pgvector 时维度不匹配会报错，索引失败；所以换模型必须确认 dimensions 配置和模型输出一致。

## 74. 为什么检索结果里同时返回向量分数和关键词分数？
方便调试和分析，看某条结果主要靠语义还是主要靠关键词命中；但在 hybrid 模式下最终排序看的是 RRF 融合分，不是简单相加两路原始分。

**高频追问**：纯向量模式下关键词分数有值吗？
**追问回答**：没有，纯向量模式只走向量路，返回向量相似度；关键词分数只在走过关键词路时有意义。

## 75. 同时索引中的文档数上限是为了什么？
防止租户一次性上传几百篇把 Celery 队列塞满，影响其他租户或拖垮 Embedding API。超过并发上限会报 20014，等前面几篇索引完成后再传。

**高频追问**：和 Celery Worker 数量什么关系？
**追问回答**：Worker 数量决定全局吞吐；租户并发上限是公平性隔离，避免单租户占满所有 Worker。

## 76. 删除知识库会发生什么？
级联删除该库下所有文档和 chunk，向量库和 ES 里对应片段也会 purge。操作不可逆，生产上要确认后再删，或者业务方自己做软删除策略。

**高频追问**：删库后 retrieve 还可用吗？
**追问回答**：对该知识库的检索会报知识库不存在；如果业务方缓存了旧的知识库 ID，需要更新配置。

## 77. 为什么 hybrid 默认 vector_top_k 和 bm25_top_k 比最终 top_k 大？
两路各召回较多候选，再 RRF 融合筛到 top_n，比每路只取 top_k 再融合更有机会让「一路排名靠前另一路一般」的好结果冒出来。默认各 20 路，融合后再取最终 5 到 8 条。

**高频追问**：rrf_k 设 60 是什么意思？
**追问回答**：RRF 公式里的 k，越大排名靠后的 chunk 贡献越小，融合越「看重前几名」；60 是常用经验值，有评测集后可以再调。

## 78. 项目里 Docker Compose 起了哪些依赖？
PostgreSQL 加 pgvector、Elasticsearch、Redis，可选 Langfuse 相关服务。API 和 Celery Worker 通常本地或单独容器跑，README 里有完整启动顺序和迁移说明。

**高频追问**：ES 为什么要自建镜像装 IK？
**追问回答**：官方 ES 镜像不带中文 IK 插件，BM25 中文效果会很差；项目用 Dockerfile.elasticsearch 自建镜像并预装 IK，实际部署里验证过中文召回效果明显更好。

## 79. 业务错误为什么大多不返回 HTTP 4xx？
统一 HTTP 200 加 body code，业务方 SDK 可以只解析一种格式；401、403、404 在 HTTP 层和业务 code 层混用容易搞混。未授权在我们这是 20010，不是 HTTP 401，这是项目约定，接入文档里会写清楚。

**高频追问**：那网关层怎么做鉴权拦截？
**追问回答**：可以在网关再加一层，但中台自身用 code 20010 表示 Key 无效；业务方按文档处理 body code 即可。

## 80. quality profile 适合什么场景？
对延迟不太敏感、但希望尽量召准召全的场景，比如 pro 租户的内部知识库深度问答前置检索。它会开 hybrid、rerank 和 rewrite，单次检索耗时会比 speed 明显增加。

**高频追问**：standard 租户能用 quality 吗？
**追问回答**：不能，追求质量档只在专业套餐允许的检索档位里；标准套餐用均衡或自定义，但不能开精排和改写。

## 81. 自定义 profile 和直接传检索参数有什么关系？
自定义表示「这次检索参数由请求里显式指定」，比如检索模式、返回条数、是否精排等，但仍受套餐校验，免费档想开混合检索照样 20013。非自定义的速度/均衡/质量档则用预设好的参数组合。

**高频追问**：预设 profile 还能覆盖返回条数吗？
**追问回答**：可以，请求里传 top_k 会覆盖预设默认值，其他如模式、精排仍跟 profile 走，除非 profile 是自定义。

## 82. 索引时存的正文是什么？和原文件什么关系？
JSON 上传时，存的就是前端传来的全文，没有原文件。文件上传时，原文件落在磁盘，正文一开始为空，Worker 解析后再把 Markdown 风格文本写进去；切块和重索引都读这份正文，不会每次都重新读磁盘上的 Word/PDF。所以普通重索引只要正文还在就行；如果解析器升级了，可以选「从原文件重新解析再索引」，那才需要原文件还在。

**高频追问**：正文会返回给检索调用方吗？
**追问回答**：不会，检索返回的是切片片段；正文是索引和重索引用的内部数据。文档详情里会展示来源类型和原始文件名，方便调试。

## 83. 检索日志里的记录 ID 和链路 ID 有什么区别？
记录 ID 是我们库里每条检索的主键，反馈时用来关联某次检索；链路 ID 是可观测平台里的 trace 标识，用来查各步骤耗时。反馈时要两者对得上，防止给别人家的检索乱打分。

**高频追问**：没开 Langfuse 时链路 ID 还有吗？
**追问回答**：可能为空或不上报，但记录 ID 仍然有；只是反馈功能依赖 Langfuse，没开就无法走反馈闭环。

## 84. 为什么 free 档新建租户默认，而不是 standard？
free 用于体验和 PoC，成本低、限制多，避免未付费租户占满资源；老租户迁移可以脚本升到 standard，新注册默认 free 是 SaaS 常见做法，要生产能力再升档。

**高频追问**：怎么升 plan？
**追问回答**：运维用改套餐脚本更新租户档位，没有自助升档页面，偏 B 端人工开通。

## 85. RagService retrieve 方法的大致步骤是什么？
解析 plan 和 profile → 检查 QPS 和日配额 → 处理问题 → 多库并行召回 → 判断空结果原因 → 可选精排 → 写检索日志 → 成功则日计数加一 → 返回片段和附加信息。

**高频追问**：日计数什么时候加？
**追问回答**：检索成功并且检索日志落库之后才加一，失败或中途报错不计入日配额，避免失败请求白占额度。

## 86. 词表、改写和精排哪些受套餐限制，哪些不受？
混合检索、精排、问题改写受套餐限制；词表扩展不受套餐限制，各档都能用，只要知识库配了词表。这样免费档也能通过词表做轻量问题优化。

**高频追问**：free 能用 balanced 吗？
**追问回答**：不能，balanced 需要 hybrid，free 不允许 hybrid，只能 speed；这是 20013 的典型场景。

## 87. 你怎么证明检索效果不是拍脑袋，而是可验证、可迭代的？
有三层：调试台单次检索看召回片段是否合理；Langfuse 看线上链路和反馈低分 case；RAGAS 用固定评测集离线跑上下文精确率和召回率，改词表或检索档位前后对比报告数字。形成「线上反馈 + 离线回归」闭环。

**高频追问**：golden set 从哪来？
**追问回答**：冷启动用评测数据集里的种子数据；运行后可从 Langfuse 导出低分反馈 case，人工补标准答案再并入主集。

## 88. 如果用三个亮点概括这个项目，你会怎么说？
第一，定位清晰：做的是检索中台不是问答应用，多租户、套餐、API Key 齐全。第二，检索链路完整：向量加 BM25 hybrid、RRF、改写、词表、rerank、多库联查、多层降级，是完整可落地的 retrieve 链路。第三，工程闭环：异步索引、结构化切块、多格式文档解析（Word/PDF）、Langfuse 可观测、RAGAS 离线测评、统一错误码和 Provider 可插拔，能讲架构也能讲效果和鲁棒性。

**高频追问**：最大的不足是什么？
**追问回答**：中台有意不做答案生成；PDF 目前只做文字版、不做 OCR 和复杂版式；套餐写死在代码里、没有运营后台。这些是边界或后续扩展点，面试里主动说反而显得清楚。
