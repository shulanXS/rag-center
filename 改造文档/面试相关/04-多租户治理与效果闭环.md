# 治理篇：多租户、可观测、效果闭环

> 适用场景：鉴权配额、可观测、离线评测、效果验证类面试  
> 关联简历：多租户与商业化配额、可观测与效果闭环、检索效果可度量可回归

## 1. API Key 鉴权是怎么工作的？为什么不用用户登录那套 Token？

业务方在请求头携带密钥，后端**对密钥做哈希后与数据库比对**，找到对应租户和套餐，注入请求上下文。后续建库、上传、检索都按该租户做隔离和配额检查。调用方不必在请求体再传租户标识，避免伪造他人身份。密钥创建时终端只展示一次明文，**库里只存哈希，遗失后只能吊销重发**。

中台**面向服务端之间的调用**：业务方后端持有长期密钥即可，不需要终端用户登录、刷新 Token、过期续期。API Key 实现简洁，与租户和套餐绑定清晰，也便于按密钥统计用量和吊销，适合 B 端 API 型产品。

**高频追问**：本地开发如何免密钥调试？密钥泄露怎么办？

**追问回答**：可关闭鉴权开关，系统自动用演示租户，前端密钥留空即可跑通；生产必须开鉴权。泄露则立即吊销并签发新密钥——库中无明文，无法「找回」原密钥，只能作废重发；也可再加网关 IP 白名单等防护。

## 2. 租户之间的数据如何隔离？多租户共用向量库和搜索引擎会不会串数据？

当前是**「共享存储 + 行级/文档级租户字段」隔离**，**不是每个租户单独一套库**。

存储上：PostgreSQL 里知识库、文档、片段（含向量）、文档关系、检索日志等表都带 `tenant_id`；向量和业务元数据同库，查片段时条件里必须带当前租户。Elasticsearch 也是多租户共用索引，每条关键词文档写入时带上 `tenant_id`、知识库等字段，检索用 filter 先收窄到本租户、本库，再算 BM25。Redis 里的限流和日配额按租户键计数，用量也不串。访问层拿资源时还会校验「是否属于当前租户」，跨租户访问直接当不存在，不是先查出再过滤。

所以会共用向量库和搜索引擎，但不会串数据：**隔离写在数据模型和查询条件里**，关系查询、证据从库加载原文、Research 补证也都卡在同一租户和授权知识库范围内。这是查询与校验链路上的硬约束。租户规模很大、合规要求物理隔离时，可以再演进到分库或分索引，当前规模用行级隔离更省运维。

**高频追问**：查询条件漏带租户，或者改成别的租户 ID，能查到别人的数据吗？

**追问回答**：正常业务请求查不到。**租户身份只从 API Key 在服务端解析注入**，请求体里不能自报或改成别人的租户。即便知道别人的知识库 ID，访问层也是「ID + 当前租户」一起查，对不上就当不存在。向量和 ES 检索同样强制带当前租户 filter。若某段代码漏写租户条件，行级隔离确实会失效，那是实现缺陷而不是产品设计允许跨租户——所以仓储和 Provider 接口把 `tenant_id` 做成必参，评审和测试也要盯住漏过滤。物理分库能降低这类失误面，当前用行级隔离就要靠约束写全。

## 3. 一个公司内部为什么还要做成多租户？

中台往往服务同一公司下的多条业务线或多个团队，多租户首先是数据隔离：各业务的知识库、文档、检索日志互不串。但不止于此——还要**通过套餐区分能力与限额**：能不能开混合检索、精排、改写、Research，以及 QPS、日检索量、知识库数量、并发索引数等上限。

这样做是为了**按业务重要性分配资源**：核心生产业务给更高套餐，体验、试验、低频业务用免费或标准档收紧用量，避免少数请求把模型调用、向量检索、ES 和索引队列打满，把公共资源浪费在低价值流量上。

**高频追问**：会出现多租户互相争抢资源的情况吗？

**追问回答**：设计目标就是避免无序争抢。**每个租户有独立的 QPS、日检索、并发索引和库/文档上限**，触顶就拒绝或报配额用尽，而不是大家去抢同一池子直到拖垮服务。全局 Worker 决定索引总吞吐，租户并发索引上限做公平隔离，避免一个业务占满所有 Worker。数据隔离解决「看不见别人的库」，限额解决「用不完别人的配额」。

## 4. 限流和配额具体怎么做的？当前限额会不会太少、不够用？

检索入口在真正召回前先检查用量，按租户隔离。瞬时有 QPS 上限，一天有成功检索次数上限；上传侧还有知识库数、单库文档数、同时处理中的文档数等，防止索引队列被塞满。**日配额通常检索成功并落日志后才加一，失败不扣**；多库联查一次只计一次。和「功能不支持」要分开：开不了精排是能力天花板，日检索用尽是用量触顶，QPS 超了是瞬时过载。

限额是分级的，不是一刀切「太少」。免费档大约 3 QPS、日检索约 500，故意收紧；标准档大约 10 QPS、日约 5000；专业档大约 50 QPS、日约 10 万。经常触顶应升档或调配置，并评估是否扩 Worker、模型配额——而不是取消限额。

**高频追问1**：限流具体怎么做的？用的什么算法？以后怎么升级？

**追问回答**：当前瞬时限流是 **Redis 上的固定窗口**：键为「租户 + 当前秒」，`INCR` 计数，首次数设置过期；超过套餐 QPS 就拒绝。实现简单，秒级对齐，但**窗口边界可能出现约两倍突发**。日配额是按自然日的计数器，属于配额而不是平滑限流。升级可以换成滑动窗口或令牌桶/漏桶，限流更平滑；也可以把限流前移到网关，和应用内校验叠加。日配额若要更严，可再补分钟级或租户级并发在途请求上限。

**高频追问2**：租户有限额，那全局有限额吗？多个租户同时涌入怎么办？

**追问回答**：**当前主要是租户级限额，没有单独的「全站总 QPS」硬闸**。若多个租户同时打满各自配额，汇总流量仍可能压到数据库、ES、模型或 Worker。租户限额防的是单个业务失控，不等于基础设施无限。后续可加全局限流或网关总阈值、按依赖的熔断降载，并和扩容配合；索引侧则继续用租户并发上限做公平隔离。

## 5. 线上检索出问题，怎么留下现场并排查？Langfuse 和日志是什么关系？

服务端请求日志带请求 ID，记录接口进出、关键步骤和异常；开启 Langfuse 后，还能看改写、召回、精排等分阶段耗时，响应里带回 Trace ID。排查时：**查服务端日志用请求 ID；看检索质量链路用 Trace ID**。**两者不是同一个字段**——请求 ID 管日志串联，Trace ID 管可观测链路和反馈关联。架构篇也会提这组概念，治理侧更关心怎么闭环用起来。

**Langfuse 是可选旁路：上报失败只记警告，不拖垮检索**。它和日志有重叠但互补——日志不依赖外部服务，适合保底排查；Langfuse 可视化更好，适合看单条分阶段耗时，并把反馈评分挂到 Trace 上。

业务方或调试台可对某次检索打 1～5 分，带上检索记录编号和链路编号，写入可观测平台。低分可导出为评测用例，人工补标准答案后并入 Golden Set，形成**「线上反馈 → 评测集 → 改配置 → 再评测」**。未开 Langfuse 时反馈链路当前不可用，要做完整闭环需开启或后续改自有存储。

**高频追问**：Langfuse 挂了会影响检索吗？

**追问回答**：不会。可观测失败不能阻断主链路，这是设计原则。

## 6. 你们测试集怎么构建的？每次回归都要全跑吗？

来源大致三块：一是冷启动的种子题，按知识库原文人工出题并核对标准答案，例如人事库上的一批基础事实、口语改写、跨章节题；二是线上低分反馈导出的 bad case，补全标准答案后并入新版本；三是按能力专题补的题，测复杂检索和受控 Agentic Research 时，要单独准备多要点、依赖型或跨文档的复杂题，不能只用简单事实题代表全部。

**基础题和复杂题要分开管**：基础集看切块、混合召回、精排；复杂集看规划、补证和证据完整性。混在一起分数涨了，也分不清是哪类能力变好。题目或标准答案变更就升版本、不覆盖旧集，保证历史实验可复现。

**不是每次改动都要把所有集合、所有专题全跑一遍**。日常小改可以跑与改动相关的子集做冒烟；正式验收或发版前再跑完整相关集，并固定版本号写进报告。改 Research 就重点跑复杂题，改基础召回就重点跑基础集，避免无关题拖慢反馈、也避免结论被噪声稀释。

## 7. 离线评测具体怎么做？统一看哪四个指标？

用固定版本的 Golden Set 批量调检索接口，在同一索引、同一参数口径下对比改造前后。正式实验统一输出四项核心指标：**上下文精确率、上下文召回率、P95 延迟、平均应用模型调用数**。前两项看检索质量——返回里有多少真有用、标准答案需要的信息有没有找回来；后两项看在线代价。RAGAS 打分用的裁判模型不算进应用调用数，否则对照组也会变「更贵」；精排和 Research 里真实发生的调用要算。

**高频追问1**：为什么不测答案忠实度这类生成指标？

**追问回答**：**中台不生成最终答案，没有答案文本可评**，边界是检索质量。若业务方需要端到端问答效果，应在其应用层单独评测。

**高频追问2**：是不是所有实验都只用这四个指标？

**追问回答**：上线决策看这四项核心指标，但不是每个实验只有这四个数字。精排类可加 nDCG 等排序诊断，解释关键证据有没有排得更前；图谱、证据包、Research 等专题还可看注入条数、引用回溯率、补证轮数等，用来确认机制按设计在跑。诊断和专题指标解释原因，不单独当默认全开的门槛；引用类还有硬条件，例如证据包和 Research 的引用回溯率须达 100%。召回升了但延迟不可接受，或精确率升了召回掉太多，也不能默认全开。

## 8. 怎么保证改动能归因？统一评测和消融实验怎么做？

早期已有 RAGAS 脚本和日志，但不同专题的数据集、运行入口、指标和报告格式不统一。一次实验若同时改索引、改写和精排，分数变了也无法归因。能力越多，越需要固定口径：同一批题、同一索引、同一参数，**baseline 与 candidate 只改一个变量**。

消融每次只比两组：baseline 是改造前或关闭某能力，candidate 是改造后或开启该能力。配置必须声明允许变化的字段；**评测程序发现未声明差异会拒绝执行**。同一次实验还要冻结评测集版本、标准答案、知识库文档、索引版本、最终返回条数、候选宽度、并发和超时等。报告和逐题原始结果按固定目录保存，出现退化时可追溯。

**高频追问**：精排升级、并行召回这类优化，评测时怎么避免误判？

**追问回答**：性能测试最容易被参数变化干扰。若改造后同时把候选从 20 缩成 5，延迟下降也不能证明是并行或连接复用的功劳。**应固定候选宽度和返回条数**，关闭无关能力，只改执行方式或实现类；质量无退化前提下看 P50、P95，才能归因。

## 9. 指标有取舍时怎么决定上不上线？有没有改了反而变差的例子？

**不追求所有指标同时上涨**。例如专业精排大幅降延迟，精确率可能略有取舍；证据包大幅提升精确率并压缩材料，但召回略降、延迟显著上升，则按需开启而非默认全开。工程上由统一报告和启用规则支撑，产品侧结合场景取舍：高价值问答开证据包，复杂问答显式开 Research，普通检索保持轻量。**技术是数据说话，产品是场景取舍**。

有改了反而变差、不能宣称成功的例子。专业精排首次接入时延迟大降但质量退化，后来对齐查询句、候选格式和排序指令才可用。多库全局融合工程已落地，但部分双库题质量仍不理想，不会宣称多库质量已全面提升。**诚实讲边界，比只报涨幅更可信**。

## 10. 前端调试台主要解决什么问题？怎么看套餐和今日用量？

让运营和开发不必写命令行也能建库、上传、看文档状态、调检索、切换策略、多库勾选、看分数明细、观察 Research 与证据包、打反馈。还展示当前租户套餐和今日用量，方便验证套餐与配额是否生效。**调试台不是生产必组件**，**中台能力全在 API**，调试台是效率工具；业务方可只用 API 在自己的后台集成。

调试台展示当前密钥对应的套餐、可用功能、配额上限和今日已用检索量，用来决定哪些档位置灰、核对配额是否生效。这是租户级能力和用量快照，与单次检索返回里「这一次实际走了什么策略」不同。套餐当前偏配置和脚本调整，尚无完整运营后台，面试可主动说明这是已知边界。

## 11. Redis 在项目里承担哪些角色？

一是 Celery 的消息代理和结果后端，上传后任务入队，Worker 取任务执行索引。二是检索 QPS 限流和日配额计数。部署简单、组件少，生产需注意高可用。规模更大时，**可把任务队列用的 Redis 和限流用的 Redis 拆开**，避免索引高峰影响限流准确性。检索结果缓存不是当前用法——要不要对 FAQ 做缓存，在检索篇讨论。

**高频追问**：索引任务和检索限流共用 Redis 有风险吗？

**追问回答**：当前为省组件可以共用；流量上来后建议拆分。这是容量规划时的演进方向。

## 12. 知识库同义词表谁来维护？配错了怎么发现？

按知识库由运营或业务方配置，不同领域库互不影响。**改词表不改文档、不重索引、不耗大模型**，下次检索即可生效。配错会引入噪声、召回偏宽。发现方式是离线评测对比改前改后，或在调试台确认是否命中。改写与词表的执行顺序属于检索策略；治理侧关心配置责任和效果验证。当前各档都能用，因为它几乎没有模型成本；真正受套餐限制的是混合检索、精排和改写。

## 13. 业务线提出定制化需求，中台怎么处理？

先分清是「配置可消化」还是「要改公共内核」。词表、知识库范围、检索档位、是否开证据包/Research、返回条数等，**优先用现有多租户与策略能力解决**，按业务线落在不同租户或不同库上，而不是为每条业务线复制一套服务。定制提示词、领域规则、FAQ 猜你想问等，能放在业务侧或配置层的，就不上沉到中台主链路。

只有多条业务反复碰到、且确属检索公共能力的需求，才考虑纳入中台——还要评估是否破坏统一契约、能否用 Provider/开关做成可插拔。单一业务的特殊生成逻辑、页面交互、行业强绑定规则，应留在业务应用，中台继续只交证据片段和结构化结果。面试里强调：中台价值是复用与边界清晰，**不是把所有定制都接进来**。

**高频追问**：业务说「就我们特殊，必须改主流程」怎么办？

**追问回答**：先问清是效果问题还是流程问题。效果问题用评测集复现，看是切块、词表还是策略档位能解决；流程问题看能否用自定义档或独立入口（如 Research）表达。若仍要改内核，需要明确收益、影响面和回归成本，并排进统一迭代，而不是私下给单业务打补丁导致多租户行为漂移。

## 14. 怎么判断一个新的优化要不要做？

**不看「技术上能不能做」，而看「值不值得做」**。先确认问题是否真实：线上低分反馈、可观测耗时、还是业务口头感觉。再估计收益面：影响多少租户和请求、是质量、延迟还是成本。然后看方案成本：开发量、是否要重索引、会不会拖慢默认链路、评测能不能单变量验证。

优先做高频、可度量、不破坏主链路降级的事；低收益高成本、或只能服务极窄场景的，可配置化或放到业务侧。动手前就要能说清：用哪套题回归、看哪几项指标、什么结果算成功、什么情况回滚或不默认开启。做完仍走统一报告拍板——和第 9 题的「上不上线」衔接：这里决定「排不排期」，评测后决定「开不开默认」。

**高频追问**：和「指标有取舍时是否上线」有什么区别？

**追问回答**：**前者是立项前的优先级判断；后者是实验跑完后的发布判断**。没有评测口径的优化，不该轻易排期；评测没过线的能力，不该默认全开。

## 15. 如果面试官问「你如何保证中台可持续迭代」，你怎么答？日常运维工作流是什么？

靠三件事：多租户和套餐把能力和用量管住；检索日志、可观测和反馈把线上问题显性化；Golden Set、单变量消融和统一报告把离线回归固定下来。每次改检索、切块或证据能力，都先冻结条件跑 baseline/candidate，再看四项核心指标和专题门槛。调试台降低验证成本，API 保持稳定。这样迭代有节奏、有效果、有回退依据。

日常工作流大致是：接入方用密钥自检套餐和余量；检索异常时用请求编号串日志，必要时看可观测分阶段耗时；效果质疑时用相同索引和档位在 Golden Set 上复现；升档走脚本改套餐；低分反馈定期导出，评审是否并入评测集。生产最常被问的三类：配额或功能不支持；检索结果不理想；文档长期处理中——分别对应套餐参数、日志链路评测集、Worker 与任务失败原因。

**高频追问**：团队只有一个人维护，这套体系会不会太重？

**追问回答**：早期可以简化题目数量和报告形式，但**「固定数据集、单变量对比、质量与延迟一起看」的原则不能省**。否则第三次优化开始就说不清谁导致了变化。自动化运行器和模板化报告，正是为了一个人也能做规范回归。
