# 架构篇—定位、选型、架构

> 适用场景：项目开场、中台定位、技术选型与分层架构类面试  
> 关联简历：整体架构与模块划分、中台定位、Provider 可插拔设计

## 1. 这个项目是做什么的？为什么定位成「中台」，而不是普通 RAG 应用或问答机器人？

我做的是一个**企业级的 RAG 检索中台**。业务方把文档交给我们建知识库、建索引；用户提问时，把问题传过来，我们负责从知识库里找出最相关的文档片段，连同分数和来源一起返回。

之所以叫中台，而不是普通 RAG 应用：普通应用往往是「一个产品服务一个场景」，界面、Prompt、答案风格都写死在项目里。我这个项目**不绑具体页面，也不替业务方生成最终答案**，而是把建库、上传、索引、检索、排序封装成一套**标准 API**，多个租户、多个业务系统可以同时接入。套餐、配额、可插拔依赖，是按**「被多个系统调用的服务」**来设计的，而不是按「一个问答产品」来设计的。

**高频追问1**：那和直接做一个问答机器人有什么区别？

**追问回答**：问答机器人通常绑定在单一具体场景，比如客服页面或内部知识库网站，检索、生成、展示往往一体化封装。我这个项目是**把「从知识库里找相关片段」抽成通用能力**，做成**统一接口，供多条业务线接入**。各业务线共用同一套向量检索、关键词检索和排序逻辑，无需各自重复建设基础设施，也更便于统一管控和持续迭代。

**高频追问2**：中台特征具体体现在哪？

**追问回答**：主要体现在几个方面：一是**多租户隔离**，不同客户的数据和配额互不影响；二是接口和返回格式统一，接入成本较低；三是索引和检索流程标准化，各业务无需单独维护；四是**底层依赖可插拔**，更换模型或存储不必改动核心业务代码；五是有统一的日志、错误码和套餐管控，便于运维和商业化。

**高频追问3**：还要不要做调试台？

**追问回答**：要做，但**不是给终端用户的产品界面**，而是给接入方和运维验证能力用的；正式业务的问答页面仍由各业务自己做。

## 2. 能简单说一下这个系统的核心业务链路吗？

可以分成**「入库」和「检索」两条链路**。入库侧：业务方先凭密钥完成身份认证，创建知识库并上传文档；**上传后接口立即返回「处理中」**，后台异步完成解析、切块、向量化，并同时写入向量库和搜索引擎。检索侧：业务方传入问题和目标知识库，中台返回结构化的文档片段、相关分数和来源信息，**不生成最终答案**。

**高频追问**：租户身份是怎么识别的？会不会被伪造？

**追问回答**：业务方在请求头中携带密钥，后端校验后即可识别对应租户，后续操作均按该身份做隔离与配额检查。**租户身份由服务端从密钥解析**，无需业务方在请求体中重复传递租户编号，从而**避免调用方伪造他人身份**。

## 3. 为什么中台只做到检索，不直接生成最终答案？

因为不同业务对答案的要求差异很大：语气风格、引用标注、流式输出、业务规则二次校验等各不相同。中台若同时承担生成职责，容易与业务层边界重叠，每接入一个新客户都可能需要调整 Prompt 和交互逻辑。因此**中台专注于把与问题相关的证据片段找准、找全**；答案如何组织与呈现，**交由离业务最近的应用层负责**，职责清晰，便于双方独立迭代。

**高频追问**：那业务方具体怎么接？

**追问回答**：业务方调用检索接口获取片段列表，自行拼接上下文并调用大模型生成答案；中台负责检索质量与结构化返回，应用层负责用户体验与 Prompt 策略。后续还迭代了可选的「证据包」和「受控 Agentic Research」能力，但本质上仍是返回可信材料，最终表述仍由上游应用决定。

## 4. 这个项目后来做了哪些重要的架构演进？

最初版本解决的是「能否作为多租户检索服务稳定运行」：异步入库、混合检索、多档策略、基础可观测。上线运行后，暴露出三类问题：一是能力持续增加，但缺少统一标准衡量优化是否带来可验证的提升；二是能召回相关片段，却不一定能组织出完整、可信的证据；三是简单问题一次检索即可，复杂问题需要拆解和多轮补证，但又不能做成不受控 Agent 的无约束反复检索。于是沿三条主线迭代：先把检索链路做准、做稳、做快；再在检索结果之上叠加可信证据层；最后引入受控 Agentic Research。整个过程未推翻重建，而是在原有底座上逐层扩展。

**高频追问**：演进之后，整体架构长什么样？

**追问回答**：可以概括成**「一个检索底座、两个产品入口、三层递进能力」**。底座是统一的检索内核，负责召回、融合、精排和降级；两个入口分别是普通检索和受控 Agentic Research，共用同一套内核；三层能力依次是专业检索、可信证据编排、受控 Agentic Research。**每层都复用下一层的结果**，没有做成三套互不相干的系统，这是后期架构上最重要的设计原则。

## 5. 技术栈是怎么选的？为什么用这些组件？

中台要同时满足几件事：对外是稳定 API、入库可以异步扛住长文档、检索要语义加关键词、业务元数据和索引能一起管、底层模型与存储还得能换。围绕这些约束选型：API 层用 FastAPI，因为异步友好、依赖注入和 OpenAPI 文档适合做多租户接入；业务数据与向量先落在同一套 PostgreSQL，用 pgvector 做相似度检索，避免一上来就多运维一套向量集群，也方便片段与元数据同事务写入；关键词检索需要成熟倒排和中文分词生态，所以单独接入 Elasticsearch，而不是硬塞进向量库；索引链路耗时长，用 Celery 加 Redis 把上传和解析向量化解耦；模型和 Embedding 走 OpenAI 兼容接口，再配合 Provider 抽象，换供应商主要改配置。调试台用 React，只服务接入验证，不承担终端产品 UI。整体原则是：**成熟可控、职责清晰、当前规模够用**，并且**关键依赖都留了替换口**。

**高频追问1**：为什么向量库用 pgvector，而不是 Milvus 这类专用向量数据库？

**追问回答**：pgvector 是 PostgreSQL 的向量扩展，可支撑生产级相似度检索，并支持常见的近似最近邻索引。对当前规模已能满足需求，且文档、切片、向量与业务元数据可存于同一数据库，一次事务即可完成写入，**运维成本明显低于单独部署 Milvus 集群**。Milvus、Qdrant 等独立向量引擎更适合向量规模特别大、检索并发极高、需要专用集群横向扩展的场景。若后续确实成为性能瓶颈，**可通过向量存储抽象接口替换实现**，上层检索编排无需大改。

**高频追问2**：技术栈里为什么要有 Elasticsearch，而不是只靠向量库？

**追问回答**：**向量库解决语义相似**，但对错误码、型号、条款名这类要精确命中的查询不够稳。Elasticsearch 提供成熟的关键词倒排检索，**和向量路互补，才能组成混合召回**。它和 PostgreSQL、Redis 一样是可替换的基础设施，换引擎时走搜索 Provider，不必改检索主流程。

## 6. 代码整体是怎么分层的？模块又是怎么拆的？

最外层是 API 路由，负责鉴权、参数校验和统一响应格式；中间是 Service 层做业务编排，例如检索流程、文档上传、配额检查、证据编排；再往下是 Repository 层访问数据库；对外部依赖——向量库、搜索引擎、Embedding 服务、大模型、精排模型、文档解析——**均通过 Provider 适配层接入**，避免业务代码与具体厂商强绑定。后期又抽出了检索内核服务，使普通检索与受控 Agentic Research 共用同一套召回逻辑。

按职责拆成几大块：知识库管理、异步索引、检索编排、证据编排、受控 Agentic Research、多租户与配额、效果评估。**检索内核被普通检索和 Research 共同复用**，**证据层可选挂载，不污染核心检索链路**。

**高频追问1**：为什么要单独抽 Repository 层？

**追问回答**：主要是将 SQL 与数据访问细节集中封装。Service 层只关注业务流程，避免大量编写查询语句；单元测试时可 mock 数据层；后续更换存储方案时，改动范围也更可控。这是较常规的分层方式，但对持续演进的中台而言，可显著降低维护成本。

**高频追问2**：模块拆这么细，会不会过度设计？

**追问回答**：初期并未如此细分，是随能力叠加逐步拆分出来的。例如证据编排和受控 Agentic Research 属于后续新增，若与检索耦合在一起，局部改动容易牵动全局。拆分模块不是为了堆复杂度，而是让「快速检索」「可信证据」「受控 Agentic Research」各自演进，同时共享同一底座。

## 7. 配额用尽或功能不支持时怎么报错？日志和错误码怎么设计？

对外统一用业务状态码加可读说明，再带上业务数据字段。未授权、功能不支持、配额用尽等分属不同错误码段，调用方按码处理即可，不必为每个接口学一套规则。**多数业务错误仍返回 HTTP 200**，**用响应体里的业务码区分**；未捕获的服务器异常才走 HTTP 500。详细堆栈只留在服务端日志。

日志带时间、级别、模块、请求 ID 和关键业务节点，接口进出、向量化、模型调用、检索成败都会记。错误码按类别分段，方便看出问题落在接口参数、存储、模型还是系统。对外是简洁状态码和说明，堆栈留在服务端。另有一份只收 ERROR 及以上的错误日志，打开即可看异常上下文，通常配合请求 ID 排查。

**高频追问1**：网关还要不要拦一层鉴权？

**追问回答**：可以。网关拦截与中台用业务码表示密钥无效并不冲突，按部署架构选择。接入方按文档解析响应体中的状态码即可。

**高频追问2**：为什么要单独有错误日志？

**追问回答**：全量日志 INFO 较多，排障时噪音大。错误日志只收 ERROR 及以上，能更快定位异常，再拿请求 ID 回全量日志补上下文。

## 8. 业务方反馈「刚才那次检索不对」，你怎么快速排查？

先分清要查的是哪一层。**看服务端日志、HTTP 进出、异常堆栈时，用请求 ID**：中间件给每次请求分配，写进日志并从响应头 `X-Request-ID` 回给调用方，API 到模型调用都能按它串起来。**看检索质量、改写精排各阶段、证据编排时，优先用响应里的 Trace ID**：它对应 Langfuse 上的那条观测链路，调试台反馈评分也认这个。**两者不是同一个字段**；Langfuse 未启用时可能没有 Trace ID，这时仍可靠请求 ID 查日志。

**高频追问1**：这两个 ID 谁生成？业务方要自己维护吗？

**追问回答**：请求 ID 由 HTTP 中间件自动生成，也可透传上游已有编号。Trace ID 在开启链路观测时由 Langfuse 创建，并写进检索或受控 Agentic Research 的响应元数据。业务方排查时从响应里取出即可，不必自己实现编号体系。

**高频追问2**：如果两个 ID 对不上，你优先信哪个？

**追问回答**：看问题类型。接口超时、500、配额拒绝，优先请求 ID 查服务端日志；「召回不准、改写怪、精排没生效」这类效果问题，优先 Trace ID 看观测链路。两边对不上时，先确认业务方给的是不是同一次请求的响应头和响应体。

## 9. 为什么要做 Provider 可插拔？六类分别覆盖什么，换模型或换存储怎么做？

中台要对接 Embedding、向量库、搜索引擎、大模型、精排、文档解析等外部能力，而且都可能更换。若业务代码硬编码具体实现，每次替换改动面都很大。做法是**上层只依赖统一接口，实现细节放在 Provider 里**，经工厂和配置切换。套餐不支持某项能力时，还可注入空实现，主流程形状不变。

六类分别是：向量化把文本变成向量；向量存储负责写入和相似检索；关键词搜索负责倒排召回；大模型负责改写、证据编排、Research 等生成式步骤；精排负责对小候选集重打分；文档解析负责 Word、PDF 等变成统一正文。线上切换时改配置或替换实现类，检索主流程仍调同一接口。例如向量库今天是 pgvector，以后接 Milvus 只需新实现；精排从生成式模型换成 Qwen3，编排层仍调用「对候选重新打分」。

**高频追问1**：换 Embedding 模型要注意什么？

**追问回答**：新模型维度须与配置一致，否则写入失败；新旧向量不在同一语义空间，不能混用。**换模型后要清空旧索引并全量重建**。

**高频追问2**：项目里哪些地方用到了大模型，都走 LLM Provider 吗？

**追问回答**：走大模型 Provider 的主要是查询改写、证据编排，以及受控 Agentic Research 的规划、判断和收口；早期生成式精排也曾走它。默认接 DeepSeek：快模型 deepseek-v4-flash 做改写、规划和判断，强模型 deepseek-v4-pro 做 Research 收口。Qwen3 精排和 Embedding 各自有独立抽象，不和聊天补全揉在一套协议里。

## 10. 检索编排为什么自己做，而不是直接用 LangChain 或 LlamaIndex？

这类框架适合快速把切块、向量化、检索、生成串成原型，但中台要管多租户、套餐、降级、统一错误码和可复现的检索契约。核心编排若交给框架，权限边界、档位收口、空实现降级很难按我们的方式收住，出问题也不好区分是框架行为还是业务逻辑。因此**索引、检索内核、证据层和受控 Agentic Research 编排自己写**，外部模型与存储通过 Provider 接入。

**高频追问**：会不会重复造轮子？

**追问回答**：轮子造在编排和治理上，不是重复实现向量检索或 HTTP 客户端。向量库、搜索引擎、模型调用仍用成熟组件；换模型或换存储只换适配层。

## 11. 套餐不支持精排或混合检索时，代码里怎么表达，避免到处写判断？

**用空实现 Provider**：接口还在，实现类不跑真实能力或直接返回不支持，上层流程照常走到这一步再平滑跳过。这样**「能不能用」和「流程怎么编排」分开**，比在业务代码里写满套餐分支清晰。

**高频追问**：能举个例子吗？

**追问回答**：某档不允许精排时注入空的精排 Provider，主流程仍走到精排步骤，但直接返回召回顺序、不调模型。响应里标明精排未启用，结果仍然合法。

## 12. 为什么产品上要拆成两个入口？普通检索和受控 Agentic Research 怎么共用同一套召回？

简单查询要低延迟、行为可预期；复杂问题需要规划、多轮补证和预算控制。若全部塞进同一个接口，参数会膨胀，普通请求也会背上高成本路径。因此分为普通检索和受控 Agentic Research 两个入口，按场景选用。

两边都需要「针对一个查询跑一轮确定的检索」。若各自实现，召回、融合、精排和降级容易漂移。因此**抽出共用的检索内核**：输入查询与参数，输出一轮 Top 结果。普通检索调用一次；Research 把拆解后的多个子查询交给同一内核。**Research 的规划与补证在内核之外**，不另起一套检索引擎。

**高频追问1**：这样做最大的好处是什么？

**追问回答**：**同名策略在不同入口下行为一致**，评测和线上不会各跑一套。后续改召回或精排，两边同时受益。

**高频追问2**：两个入口会不会变成两套系统？

**追问回答**：不会。Research 不绕过内核直接查库，只是在内核之上加编排层。索引、召回、精排、降级完全共用。

## 13. 受控 Agentic Research 入口会生成带引用的答案，这和「中台不生成答案」矛盾吗？

不矛盾，边界不同。普通检索仍然只返回证据片段，答案怎么写由业务方决定。Research 面向多要点、多跳问题，需要在证据约束下给出可检查的结论。**即便生成答案，也只能引用已校验原文**，**材料不足必须说明无法确认**，引用不合法则答案为空、只保留证据包。这是受控的证据整理，不是把中台改成问答机器人。

**高频追问**：能不能只要证据、不要生成的答案？

**追问回答**：可以。响应里证据包与答案分开；答案校验失败时证据包仍会返回。

## 14. 证据包为什么做成可选挂载，而不是写进每次检索的主流程？

检索回答「哪些片段相关」，证据层回答「材料够不够支撑分要点回答、引用能否回溯」。层次不同。做成可选挂载，**失败时仍返回原始检索结果**，避免所有请求都承担额外模型和延迟。简历里写的不修改原始检索结果，指的就是这条原则。

**高频追问**：证据层失败了怎么办？

**追问回答**：主链路仍返回原始片段。增强能力可以失败，召回相关片段不能丢。

## 15. API Key 鉴权挂在哪里？业务里会不会再信请求体里的租户编号？

挂在 API 入口：请求进来先识别租户，再进业务编排。**身份只由服务端从密钥解析，不信任请求体里的租户编号**。后续配额、数据隔离、套餐校验都用这次注入的上下文。密钥存储、为何不用登录态，属于治理篇。

**高频追问**：业务代码还要不要再传一遍租户身份？

**追问回答**：不用。上下文在入口注入后向下传递，数据访问和检索过滤都用服务端认定的租户，避免伪造或漏传。

## 16. 向量量和检索并发上来后，系统怎么扩展？

先分清瓶颈在哪一层，而不是一上来换整套架构。API 层本身无状态，检索入口可以多实例水平扩展，前面用负载均衡；入库侧解析和向量化耗时长，优先加 Celery Worker，把索引吞吐和在线检索隔开。若压力在限流或任务队列，可以把 Redis 按用途拆开，避免索引堆积拖累 QPS 计数。向量检索若成为主瓶颈——例如向量规模明显变大、单库近似检索延迟或资源占用顶满——再通过已有的向量存储 Provider 换成 Milvus 这类专用引擎，上层编排不用重写。关键词路、模型调用同样走 Provider，按观测结果逐项升级。原则是：**先观测定位，再扩无状态层和 Worker，最后才换有状态的存储引擎**。

**高频追问1**：怎么判断该加机器，还是该换向量库？

**追问回答**：看延迟和资源曲线。若 API 与 Worker CPU/队列堆积明显、向量检索本身还健康，先水平扩展应用和 Worker。若 pgvector 所在库的检索延迟、IO 或连接数已经成为主因，且业务向量量会继续涨，再评估迁专用向量库；迁移成本高于继续扩 PostgreSQL 时，也不必为了「架构好看」提前换。

**高频追问2**：扩展时多租户会不会互相拖垮？

**追问回答**：**靠套餐配额和 QPS 限流把单租户用量挡住**，避免一个客户打满整站。这是治理手段，不能替代扩容；量和并发真上去了，仍要扩实例或换存储，两者一起用。

## 17. 现在模块都在一个服务里，什么情况下才会拆成独立服务？

当前更像模块化单体：知识库、索引、检索内核、证据层、Research 在同一套服务里，通过分层和模块边界协作，部署和联调成本低，也适合中台早期把契约跑稳。拆服务不是为了「看起来分布式」，而是出现明确的容量或故障边界时再拆。典型信号包括：大批量索引长时间占满资源，拖慢在线检索；受控 Agentic Research 耗时长、占模型配额，影响普通检索的稳定性；离线评测或重索引任务与在线流量抢同一进程资源。这时可以按「在线检索」「异步索引」「离线评测/Research」等部署单元拆开，但检索内核的召回契约仍应共用，避免拆成两套互不相干的检索引擎。

**高频追问1**：你会先拆哪一块？

**追问回答**：通常先拆异步索引 Worker 与在线 API 的部署，因为两者资源画像最不同，且项目里本来就已经是任务队列解耦。Research 若线上占比高、延迟和成本突出，再考虑独立部署，但仍调用同一检索内核。

**高频追问2**：拆开之后最怕什么？

**追问回答**：最怕检索行为漂移——普通检索和 Research、或索引侧与查询侧对同一策略理解不一致。所以**拆的是进程与扩缩容边界，不是重写两套召回**；配置、档位语义和评测基线要对齐。

## 18. 如果只用三个亮点概括这个项目，你会怎么说？边界和不足呢？

三个亮点：第一，定位清晰——**检索中台而非问答应用**，多租户和套餐齐全，检索与生成分离。第二，检索工程完整——从异步入库、混合召回到精排升级、全局融合、多层降级，是能落地的全链路。第三，可信与可控——证据编排、受控 Agentic Research、统一评测和 Provider 可插拔，既能讲架构，也能拿数据讲效果和边界。架构上用「一个底座、两个入口、三层能力」一句话收口即可。

边界上也主动说清楚：中台有意不做默认答案生成；PDF 目前仅支持文字版，未接 OCR 与复杂版式；套餐配置写在代码中，尚无运营后台；受控 Agentic Research 对主指标的提升仍在优化，不会过度宣称已全面改善。面试里主动说边界，反而体现对系统的清醒认识。

**高频追问**：你会先做哪个改进？

**追问回答**：看业务优先级。复杂问答多就先完善 Research 评测与规划质量；并发压力大就先做索引与检索扩展；ToB 客户多可考虑套餐配额可视化配置。**按真实痛点排期，而不是堆功能**。
