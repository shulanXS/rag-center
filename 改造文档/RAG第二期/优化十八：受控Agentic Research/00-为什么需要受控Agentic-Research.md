# 为什么需要受控 Agentic Research

普通 RAG 的在线链路通常只执行一次检索：处理用户问题，召回候选，完成精排和上下文扩展，然后返回结果。这种方式简单、稳定、延迟可控，适合单事实问题。

当问题同时包含多个要点，或者第二步检索必须依赖第一步发现的信息时，一次检索就可能出现明显缺口：系统找到了部分相关材料，却无法判断还缺什么，也不会围绕缺失内容继续搜索。

受控 Agentic Research 要解决的不是“让模型自由使用各种工具”，而是让检索中台在明确边界内完成三件事：

```text
查询分解
    ↓
并行检索
    ↓
证据不足时执行一次定向补证
```

这里的关键词是“受控”。检索范围、执行轮数、子查询数量、模型调用次数、超时和降级策略都由后端限制，模型只能在限定的数据结构中制定查询计划和提出补证建议。

## 单次检索在哪些场景下已经足够

例如：

```text
未发货订单退款多久到账？
```

这个问题只有一个明确要点：

```text
未发货订单的退款到账时间
```

只要检索命中对应规则，一次召回就能够完成任务。把这类问题强制拆成多个查询，通常不会提高质量，反而会增加模型调用、检索次数和等待时间。

因此，现有 `/rag/retrieve` 应继续保留，作为低延迟、确定性的单次检索入口。

## 查询分解解决什么问题

例如：

```text
积分抵扣订单退款后，积分和现金分别怎么退？
```

这道问题包含两个可以独立检索的要点：

```text
积分如何退回
现金如何退回
```

如果只使用原始长问题检索，排序靠前的结果可能集中在“积分退款”，导致“现金退款”证据被挤出最终结果。

查询分解可以生成两个受控子查询：

```text
积分抵扣订单退款后积分如何退回
积分抵扣订单退款后现金如何退回
```

两个子查询并行执行，每个要点都拥有独立的候选空间。最终结果按要点合并，不再由一个全局 TopK 决定所有证据的去留。

这类问题属于并列多要点问题。信息彼此独立，第一轮并行检索就可能全部找齐。

## 查询分解为什么不能覆盖所有多跳问题

查询分解只能根据用户原问题中已经出现的信息生成查询。如果第二步要搜索的对象只有在第一步证据中才会出现，系统无法在开始时一次性拆完。

例如：

```text
退款后退回的积分，有效期按照哪条规则计算？
```

第一轮可能找到：

```text
退款后积分退回会员账户，具体有效期遵循积分有效期规则。
```

这条证据提供了新的检索线索“积分有效期规则”。系统需要根据第一轮发现的线索继续搜索：

```text
退回积分的有效期规则
```

第二轮查询依赖第一轮证据，这才是真正的多跳补证。只在检索前调用一次查询分解模型，无法稳定处理这种依赖关系。

## 受控 Agentic Research 是什么

受控 Agentic Research 是一个有状态的检索控制器。它不会执行无限循环，而是按照固定状态机运行：

```text
接收 Research 请求
        ↓
Planner 生成 1～3 个首轮查询
        ↓
首轮查询并行执行现有检索链路
        ↓
Decider 组织证据并判断缺失要点
        ↓
证据完整 ───────────────→ 生成带引用回答
        │
        └─ 证据不完整
                ↓
          最多生成 2 个补证查询
                ↓
          执行一次补证检索
                ↓
          合并两轮证据并强制停止
                ↓
          生成带引用回答
```

第一版固定限制为：

| 控制项 | 上限 |
|--------|------|
| 首轮查询数 | 3 |
| 补证查询数 | 2 |
| 检索轮数 | 2 |
| LLM 调用数 | 3 |
| 可访问工具 | 当前知识库检索 |
| 可访问范围 | 当前租户、请求知识库和固定索引版本 |

三次模型调用分别用于：

```text
Planner    识别要点并生成首轮查询
Decider    判断证据完整性并决定是否补证
Finalizer  从最终证据生成带引用回答
```

第二轮只是执行检索，不额外调用规划模型。这样即使触发补证，模型调用数也不会随着轮数无限增长。

## 为什么由调用方选择 Research 模式

系统很难只根据问题长度准确判断是否需要多跳。短问题也可能依赖多篇文档，长问题也可能只需要一条规则。如果默认先让模型判断“是否进入 Agent”，每次普通检索都会增加一次模型调用，而且误判后更难解释。

更清晰的接口是：

```text
POST /rag/retrieve
    单次检索，低延迟、结果确定

POST /rag/research
    查询分解、并行检索和受控补证
```

调用方根据业务场景选择入口。例如普通搜索框使用单次检索，复杂问答、研究助手和多文档问答显式使用 Research。

Research 控制器只负责决定实际执行一轮还是两轮。调用方不能要求任意轮数，也不能通过参数突破服务端上限。

## 为什么 Planner 和 Decider 使用快速模型

Planner 和 Decider 都是结构化决策任务：

- Planner 输出要点和子查询
- Decider 输出证据映射、缺失要点和补证查询
- 两者都不需要长篇推理文本
- 两者的输出都要经过后端严格校验

因此可以使用响应更快的模型，并关闭思考模式。Finalizer 负责组织最终回答，对表达完整性和引用准确性要求更高，使用能力更强的模型更合适。

模型角色建议：

| 角色 | 模型 | 工作方式 |
|------|------|----------|
| Planner | `deepseek-v4-flash` | 非思考、JSON 输出 |
| Decider | `deepseek-v4-flash` | 非思考、JSON 输出 |
| Finalizer | `deepseek-v4-pro` | 非思考、JSON 输出 |

环境变量只保留共享连接配置、快速模型和强模型，不为每个阶段增加一套配置：

```env
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_API_KEY=实际APIKey
LLM_MODEL=deepseek-v4-flash
LLM_STRONG_MODEL=deepseek-v4-pro
LLM_TIMEOUT_SECONDS=60
```

Planner、Decider 和 Finalizer 与模型角色的对应关系写在代码中，避免环境配置越来越多。

## 为什么必须保存 Research 状态

单次检索只关心输入和最终结果；多轮检索还需要知道系统是如何走到结果的。

一次 Research 至少要保存：

```text
原始问题
必要要点
首轮查询计划
每轮检索任务和结果
当前已覆盖与缺失要点
已经执行过的查询
最终证据包
检索轮数和 LLM 调用数
Token 与耗时
停止原因和降级信息
```

这些状态不是为了让模型保存记忆，而是为了让后端能够执行去重、预算控制、强制停止、结果回溯和效果评测。

## 完整性不能完全相信模型

模型可以提出“证据已经完整”或者“仍需补证”，但最终状态必须由后端根据有效证据重新计算：

```text
所有必要要点都有 core 证据 → complete
只有部分要点有 core 证据     → partial
没有要点获得 core 证据       → missing
```

如果模型声称 `complete`，但某个要点没有合法的核心证据，后端仍然判定为 `partial`。只有经过候选下标、权限范围、原文回查和引用关系校验的证据，才能参与状态计算。

## 如何避免一个要点挤掉另一个要点

多个子查询的结果不能简单混成一个全局 TopK。否则高频要点仍可能占满最终名额，查询分解的收益会被抵消。

更合适的方式是按要点保留候选：

```text
要点 A 的首选证据
要点 B 的首选证据
要点 C 的首选证据
        ↓
跨查询去重和来源合并
        ↓
在总预算内补充 supporting 证据
```

同一个 Chunk 可以支撑多个要点，只保留一份正文，并记录它命中了哪些查询、来自哪一轮以及原始排名。

## 系统什么时候停止

Research 不能只依赖“达到最大轮数”停止。每次执行后都要记录明确的停止原因：

| 停止原因 | 含义 |
|----------|------|
| `evidence_complete` | 所有要点已有核心证据 |
| `no_new_evidence` | 补证没有找到新的有效 Chunk |
| `max_rounds` | 已达到两轮上限 |
| `duplicate_query` | 补证查询与已执行查询重复 |
| `timeout` | 达到整次请求时间预算 |
| `budget_exhausted` | 查询数、LLM 调用数或 Token 达到上限 |
| `degraded` | 模型或检索阶段异常，返回可用的已有结果 |

停止原因既用于前端解释，也用于判断 Agent 是否真正受控。

## 异常时应该返回什么

Research 是增强能力，不能因为某个模型阶段失败就丢掉已经检索到的材料。

降级原则是：

- Planner 失败：使用原问题执行一次检索
- Decider 失败：返回首轮候选，不执行补证
- 补证检索失败：保留首轮证据
- Finalizer 失败：返回证据包，`answer=null`
- 链路观测失败：不影响 Research 主流程

无论在哪个阶段失败，都不能跨租户、跨未授权知识库搜索，也不能使用模型伪造的证据正文。

## 怎么证明 Research 确实有效

效果验证使用三组相同问题、相同知识库和相同标注：

```text
A：Single Retrieve
   原问题只检索一次，不分解、不补证

B：Decomposition + Parallel Retrieval
   查询分解并行检索，但禁止第二轮补证

C：Controlled Agentic Research
   查询分解并行检索，证据不足时允许一次补证
```

三组对比可以分别回答：

- B 对 A：查询分解和并行检索是否提高多要点覆盖
- C 对 B：第二轮补证是否修复真正的多跳缺口
- C 对 A：完整 Research 链路是否产生总体收益

核心质量指标沿用统一的证据口径：

```text
Required Aspect Coverage
Complete Case Rate
Evidence Precision
Status Accuracy
Citation Traceability
```

Agentic 只增加两个专属指标：

```text
Multi-hop Repair Rate
Unnecessary Supplement Rate
```

延迟、轮数、LLM 调用、Token 和成本用于约束，不再创造新的效果指标。

## 这次改造不做什么

- 不让模型自由选择任意工具
- 不让模型修改租户、知识库和索引范围
- 不自动把所有普通检索升级为 Research
- 不允许调用方设置无限轮数
- 不执行超过两轮的检索循环
- 不为每个子查询重复执行 LLM Query Rewrite
- 不递归遍历文档关系图
- 不让模型直接返回未经校验的 Chunk ID 和证据正文
- 不使用网页搜索或外部数据源
- 不把链路调试信息写入最终答案

## 完成改造后有什么变化

| 场景 | 处理方式 |
|------|----------|
| 单事实、低延迟搜索 | 使用 `/rag/retrieve` 单次检索 |
| 并列多要点问题 | Planner 分解后并行检索 |
| 依赖首轮线索的问题 | Decider 生成一次定向补证查询 |
| 首轮证据已经完整 | 不执行第二轮检索 |
| 模型或补证异常 | 返回已经获得的安全证据 |
| 需要解释执行过程 | 展示计划、轮次、缺失要点和停止原因 |

最终形成两条边界清晰的能力：

```text
Single Retrieve：稳定、快速、一次完成

Controlled Agentic Research：可分解、可补证、有状态、可停止、可回溯
```
