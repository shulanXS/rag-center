# 为什么需要检索链路收口与性能优化

当前检索中台已经具备向量检索、BM25、RRF、Query Rewrite、Qwen3 精排、多知识库检索和多种索引版本。能力本身已经比较完整，但能力越多，越需要把“配置到底代表什么”“多路结果到底怎样合并”“一次请求到底做了多少外部调用”说清楚。

优化二十不增加新的检索算法，主要解决三个问题：

```text
命名档位与真实执行参数不一致
多知识库结果按库平均分配，且重复计算相同 Embedding
混合检索串行执行，外部 HTTP 连接无法复用
```

目标不是让链路变得更复杂，而是让已有能力更稳定、更可解释，也更接近一个专业 RAG 中台应有的运行方式。

## 一、命名档位现在不是稳定契约

当前预设配置是：

| 档位 | 当前最终数量 | 当前主要链路 |
|------|-------------:|--------------|
| speed | Top3 | 向量检索 |
| balanced | Top5 | Hybrid 10+10 |
| quality | 声明 Top8 | Rewrite + Hybrid 20+20 + 精排 |

但精排没有显式 `top_n` 时，服务又会使用默认 Top5。因此 quality 虽然声明返回 8 条，实际可能只返回 5 条。

命名档位还允许调用方传入 `top_k`、检索模式和精排参数覆盖预设。这样会出现同样叫 balanced 的请求，实际却可能使用纯向量、Top20 或开启精排。界面、日志和评测报告虽然都显示同一个档位，真实链路却不一定相同。

档位应该是一份后端固定的产品契约：

| 档位 | 召回与处理 | 最终返回 |
|------|------------|---------:|
| speed | Vector Top10，不改写、不精排 | Top5 |
| balanced | Hybrid 10+10，RRF 融合，不改写、不精排 | Top10 |
| quality | Rewrite，Hybrid 20+20，Qwen3 精排 | Top10 |
| custom | 调用方显式指定允许开放的高级参数 | 由请求决定 |

这里的 5/10/10 是最终返回数量，不是所有内部候选都只能取这么多。quality 仍然保留 20 条共同候选给精排，最后返回 10 条。这个数量既能覆盖普通问答需要的证据，又不会让下游一次接收过多重复片段。

Query Rewrite 已经通过固定 v1 数据集验证，本轮保留现有产品行为；同义词扩展继续默认关闭，不在命名档位中自动开启。

## 二、多知识库融合不应该等于平均分配

当前多知识库检索会先在每个知识库内独立完成一次检索和融合，再把各库结果按“库内名次”重新计算分数：

```text
知识库 A 第 1 名 → 1 / (k + 1)
知识库 B 第 1 名 → 1 / (k + 1)
知识库 A 第 2 名 → 1 / (k + 2)
知识库 B 第 2 名 → 1 / (k + 2)
```

这样会丢掉各知识库结果原本的相关性强弱。两个知识库返回 Top10 时，很容易稳定形成 5+5；即使某一道问题的高相关材料主要集中在一个库，另一个库仍会获得近似相同的结果席位。

冻结基线已经观察到这个现象：两道双库题和 20 次双库性能样本都严格返回 5+5。双库 Context Recall 保持 1.0，但 Context Precision 从单库的 0.7054 降到 0.3431，说明答案材料虽然没有漏掉，结果中却混入了大量低价值片段。

更合理的链路是：

```text
一个查询
   ├─ 在全部已授权知识库范围内执行一次全局向量召回
   └─ 在相同范围内执行一次全局 BM25 召回
                    ↓
             全局执行一次 RRF
                    ↓
              精排或直接截取
                    ↓
                返回 TopK
```

全局排序允许 Top10 全部来自同一个知识库，也允许自然形成 7+3、6+4 等分布。来源数量是相关性排序的结果，不是后端提前规定的配额。

如果某个业务将来确实需要来源覆盖，可以在全局排序后增加明确的“单库最多 N 条”产品规则，但默认检索不能用平均分配代替相关性。

## 三、同一个查询不应该重复计算 Embedding

当前每个知识库都会独立进入向量检索方法，而向量检索方法内部会再次调用 Embedding。选择两个知识库，同一段查询就会计算两次向量；选择更多知识库，调用次数继续线性增加。

Embedding 的结果只由查询文本和模型决定，与知识库无关。正确的生命周期应该是：

```text
一次检索请求
    ↓
查询处理得到 search_query
    ↓
只计算一次 query_vector
    ↓
将同一个 query_vector 用于整个授权知识库范围
```

这不仅减少模型调用和网络开销，也避免不同知识库分支因为某次 Embedding 调用失败而得到不一致结果。

## 四、混合检索的两条召回链路可以并行

当前单库 Hybrid 的执行顺序是：

```text
Embedding + pgvector 查询完成
             ↓
       BM25 查询开始
             ↓
          RRF 融合
```

向量召回和 BM25 召回彼此没有数据依赖。查询处理完成后，两条分支可以同时启动：

```text
                 ┌─ Embedding → pgvector ─┐
search_query ────┤                         ├─ RRF
                 └─ Elasticsearch BM25 ───┘
```

并行后，Hybrid 阶段的等待时间更接近两条分支中较慢的一条，而不是两条耗时相加。任意一路失败时仍沿用现有降级语义：返回另一路结果并标记 degraded；只有两路都失败时才使检索失败。

## 五、外部连接应该在应用生命周期内复用

Embedding、LLM、Qwen3 精排和 Elasticsearch Provider 当前大多在每次调用中创建并关闭 `httpx.AsyncClient`。高频请求下，这会反复建立 TCP/TLS 连接，无法充分利用 keep-alive 和连接池。

改造后由应用生命周期统一创建共享异步客户端：

```text
应用启动 → 创建模型服务连接池和 Elasticsearch 连接池
请求处理 → Provider 借用连接池发起请求
应用关闭 → 统一关闭连接池
```

连接池只复用网络连接，不缓存租户信息、查询、Authorization Header 或业务结果。模型服务与 Elasticsearch 使用独立客户端，分别设置连接上限、空闲连接数和超时，避免一个外部系统占满另一个系统的连接资源。

## 六、本轮明确不做什么

为了保证性能对比可以归因，本轮不同时改变过多变量：

- 不修改 Query Rewrite 的使用方式；
- 不重新开启默认同义词扩展；
- 不更换 RRF 公式，服务端统一使用固定 RRF；
- 不调整 Qwen3 精排模型和精排算法；
- 不修改 v1、v2 的切块内容和索引数据；
- 不修改结构化切块生产逻辑；
- 不把 Langfuse 同步刷新、响应正文日志、图候选策略或 Evidence 编排混入本轮性能结论。

结构化切块中“段落与表格混合章节”的测试分歧继续作为已知问题记录。修复生产切分器会使大量文档的 Chunk 边界变化，并触发重新索引和质量重测，因此不能作为一个顺手修改并入本轮。

## 七、怎样判断改造是否有效

验收只回答三个清晰问题：

1. 单库固定 Hybrid 20+20 Top10 在结果质量不下降的前提下，P50 和 P95 是否降低；
2. 双库检索是否不再强制 5+5，并且一次请求是否只调用一次 Embedding；
3. v2 的 speed、balanced、quality 是否严格执行 5/10/10，并通过完整回归。

改造前基线已经冻结，改造后不能重新调用旧链路生成一个“新基线”。单库和多库性能使用完全相同的题目、索引版本、召回数量、功能开关、预热和重复次数进行对比；v1 与 v2 三档对比用于说明整体能力变化，不把所有差异都归因于本轮性能改造。

最终希望得到的不是“代码使用了并发和连接池”这样的实现结论，而是可验证的运行结果：档位含义稳定、多库排序回归相关性、Embedding 调用不随知识库数量增长，单库与双库接口延迟有明确记录且没有质量回退。
