# 统一指标计算与实验报告改造提示词

点击此处可复制本篇提示词

在当前 rag-center 项目中，统一 RAGAS、ranx 和自定义指标的输入输出，并生成能够直接回答“优化是否有效”的实验报告。

报告不能只有一张指标表。它必须根据预先配置的验收门槛，给出明确结论、实际提升、附带成本和启用建议。逐题明细用于解释结论，不能代替结论。

## 一、建设目标

- 所有检索实验固定输出四个公共指标
- 不把不同含义的指标强行合成总分
- RAGAS、ranx 和自定义指标复用同一批逐题原始结果
- 每个实验只指定一个主指标
- 在运行前声明提升门槛和质量护栏
- 自动计算 `candidate - baseline` 的绝对变化
- 质量变化使用百分点，延迟同时展示绝对值和相对比例
- 报告顶部必须给出唯一、明确的结论
- 原始数据缺失或评分失败时，不生成虚假的有效结论

## 二、四个公共指标

所有检索效果实验统一输出：

| 指标 | 计算方式 | 作用 |
|------|----------|------|
| Context Recall | RAGAS | 标准答案中的必要信息是否被召回 |
| Context Precision | RAGAS | 召回上下文中有用内容是否排在前面 |
| P95 延迟 | 自定义统计 | 95% 的业务请求在多长时间内完成 |
| 平均应用模型调用数 | 自定义统计 | 每道题平均增加多少业务模型调用 |

公共指标保持原始量纲，不计算“综合得分”。例如 Context Recall 从 0.72 提升到 0.78，应写成：

```text
提升 0.06，即提升 6.0 个百分点
```

不要写成“提升 6%”。只有相对于 baseline 的比例变化才使用百分比。

## 三、统一四项正式指标

当前阶段所有检索效果实验只使用 Context Recall、Context Precision、P95 延迟和平均应用模型调用次数。不同专题可以选择 Context Recall 或 Context Precision 作为主要观察指标，但报告不再增加 ranx、nDCG、MRR、HitRate 或其他自定义正式指标。

需要定位问题时，直接查看逐题上下文、召回来源、阶段耗时和错误信息，不再运行另一套评分脚本。

## 四、统一指标输入

所有评分器读取运行器保存的同一份 JSONL，不重新请求知识库：

```text
baseline.raw.jsonl
candidate.raw.jsonl
        ↓
统一 CaseResult
        ↓
RAGAS scorer
ranx scorer
custom scorer
runtime scorer
```

定义稳定的内部数据模型，至少包含：

```python
class CaseResult:
    case_id: str
    question: str
    ground_truth: str
    answer: str | None
    contexts: list[RetrievedContext]
    latency_ms: float | None
    application_model_calls: int | None
    error: CaseError | None
```

所有评分结果使用相同的 `case_id` 对齐。不得让 RAGAS、ranx 和自定义指标各自读取不同的问题文件。

## 五、RAGAS 计算要求

RAGAS 负责计算：

```text
context_recall
context_precision
```

根据项目当前锁定的 RAGAS 版本适配字段名，不为了照搬示例而升级依赖。评分输入至少使用：

- `user_input`：Golden Set 中的问题
- `reference`：标准答案
- `retrieved_contexts`：业务请求实际返回的上下文

如果当前指标实现需要 `response`，使用本次业务请求的真实回答，不额外生成一份回答。

RAGAS 执行配置建议为：

```python
RunConfig(
    max_workers=4,
    timeout=120,
    max_retries=2,
    seed=42
)
```

要求：

- `max_workers` 默认 4，可由评测配置覆盖
- 在初始化 RAGAS 前关闭遥测
- baseline 和 candidate 使用同一个 Judge 模型及相同参数
- Judge 模型、温度、超时和并发数写入 manifest
- 单题评分失败时保存错误，不用 0 分冒充真实结果
- RAGAS 调用不计入应用模型调用数

## 六、ranx 计算要求

当前阶段不接入 ranx，不生成 qrels、run 或人工 relevance 分级数据。Golden Set 中的标准答案、目标文档和目标章节继续用于 RAGAS 评分及逐题排查。

## 七、指标扩展边界

当前阶段不实现通用自定义指标接口。只有四项正式指标不足以回答新的业务问题时，才单独评估是否扩展；在此之前不增加新的指标抽象、依赖和报告栏目。

## 八、运行时指标

P95 使用成功完成的正式业务请求计算：

```python
sorted_latencies = sorted(latencies)
p95 = percentile(sorted_latencies, 95)
```

同时报告：

- 成功请求数
- 失败请求数
- 平均延迟
- P50 延迟
- P95 延迟
- 最大延迟

平均应用模型调用数使用成功请求中有准确计数的题目计算，并展示实际参与计算的数量。只要存在 `null`，报告中注明“部分题目调用数不可用”。

延迟对比必须保证：

- 两组使用相同并发数
- 两组使用相同题目数量
- warm-up 不计入
- Judge 耗时不计入
- baseline 和 candidate 的失败率没有明显不对称

## 九、验收门槛配置

实验配置中增加 `decision`：

```json
{
  "primary_metric": "context_recall",
  "decision": {
    "min_primary_improvement": 0.03,
    "quality_guardrails": {
      "context_precision": {
        "min_delta": -0.02
      }
    },
    "cost_limits": {
      "max_p95_increase_ratio": 0.30,
      "max_model_calls_increase": 1.0
    },
    "max_failed_cases": 0
  }
}
```

含义是：

- 主指标至少提升 3 个百分点，才算出现明确质量收益
- Context Precision 最多下降 2 个百分点
- P95 增幅超过 30% 时需要标记成本较高
- 平均应用模型调用数最多增加 1 次
- 任何正式题失败时，本次报告不能直接判定成功

门槛是实验开始前的判断规则，不允许看到结果后为了宣布成功再临时修改。不同功能可以使用不同门槛，但必须把门槛和理由写入实验配置及报告。

## 十、结论判定

报告结论只允许以下五种：

### 1. 有效，建议启用

同时满足：

- 主指标达到最小提升
- 所有质量护栏通过
- 失败数在允许范围内
- 延迟和模型调用成本没有超过限制

### 2. 有效但成本较高，建议按场景启用

主指标和质量护栏通过，但延迟或调用成本超过限制。报告必须写明适合开启的场景，例如质量优先 Profile 或复杂问题。

### 3. 无明显收益，暂不启用

评测完整，但主指标未达到最小提升，且没有明显回归。不能因为个别题目变好就宣布整体有效。

### 4. 出现负向效果，建议回退

主指标明显下降，或任一质量护栏被突破。

### 5. 评测执行失败，暂时不能下结论

出现关键输入缺失、评分异常、题目执行失败过多、两组运行条件不一致等问题。

结论判定代码要独立测试，避免 Markdown 模板中散落判断逻辑。

## 十一、报告顶部的明确结论

`report.md` 的开头固定使用以下结构：

```markdown
# Query Rewrite 消融实验报告

## 结论

**有效，建议启用。**

在 golden_basic_20 的 20 道电商基础题上，开启 Query Rewrite 后：

- Context Recall 从 0.720 提升到 0.785，提升 6.5 个百分点
- Context Precision 从 0.810 变为 0.802，下降 0.8 个百分点，未突破 2 个百分点护栏
- P95 延迟从 820 ms 增加到 960 ms，增加 140 ms，增幅 17.1%
- 平均应用模型调用数从 1.0 次增加到 2.0 次，增加 1.0 次

主指标达到预设的 3 个百分点提升门槛，质量护栏和成本限制均通过。建议在 balanced 和 quality 场景启用；对极度关注延迟的 speed 场景保持关闭。
```

示例中的数字只说明格式。实际报告必须从本次 `comparison.json` 自动读取真实结果，禁止将示例数字写成正式结论。

如果结论是“无明显收益”，也要直接写明：

```text
Context Recall 仅提升 0.8 个百分点，未达到预设的 3 个百分点门槛，
因此不能证明该功能在当前数据集上有稳定收益，暂不建议默认启用。
```

## 十二、完整报告结构

每份报告保持以下顺序：

1. 实验结论
2. 实验目标
3. baseline 与 candidate 的唯一差异
4. 数据集、知识库、索引和运行条件
5. 公共指标对比
6. 专项指标对比
7. 分题型结果
8. 改善最多和退化最多的题目
9. 失败与异常
10. 成本分析
11. 启用或回退建议
12. 原始结果文件位置

公共指标表使用统一格式：

| 指标 | baseline | candidate | 变化 | 门槛 | 是否通过 |
|------|----------|-----------|------|------|----------|
| Context Recall | 真实值 | 真实值 | 百分点 | 主指标门槛 | 是/否 |
| Context Precision | 真实值 | 真实值 | 百分点 | 质量护栏 | 是/否 |
| P95 延迟 | 真实值 | 真实值 | 毫秒和比例 | 成本限制 | 是/否 |
| 平均应用模型调用数 | 真实值 | 真实值 | 次数 | 成本限制 | 是/否 |

## 十三、分题型分析

按 Golden Set 中已有字段切片，不另建数据集：

```text
case_type：direct_fact / paraphrase / multi_document
tags：refund / logistics / promotion 等
suite：basic / complex / all
kb_alias：ecommerce / hr_travel
```

每个切片至少达到 3 道题才展示聚合分数；样本太少时只列逐题结果，并注明不能据此得出统计结论。

报告重点列出：

- candidate 改善最多的 3 道题
- candidate 退化最多的 3 道题
- baseline 或 candidate 执行失败的题
- 触发质量护栏的题型

逐题说明引用原始上下文摘要，不复制大段文档内容。

## 十四、结构化输出

除 `report.md` 外，同时生成 `comparison.json`，供完整基线报告汇总：

```json
{
  "experiment_id": "query_rewrite",
  "dataset_version": "golden_basic_20",
  "suite": "basic",
  "verdict": "effective",
  "verdict_text": "有效，建议启用",
  "primary_metric": "context_recall",
  "baseline": {},
  "candidate": {},
  "delta": {},
  "thresholds": {},
  "checks": {},
  "failed_cases": {
    "baseline": 0,
    "candidate": 0
  },
  "recommendation": "balanced 和 quality 场景启用"
}
```

结构化字段使用稳定英文枚举，中文结论由报告层生成。

## 十五、测试代码

至少增加以下自动化测试：

- Context Recall 和 Context Precision 能从统一输入计算
- ranx 只计算存在相关性标注的题目
- 自定义指标输入不足时返回不可计算
- P95 不包含 warm-up 和失败请求
- RAGAS Judge 调用不计入应用模型调用数
- 绝对变化和相对变化计算正确
- 主指标达到门槛且护栏通过时判定为有效
- 主指标有效但成本超限时判定为按场景启用
- 主指标未达到门槛时判定为无明显收益
- 质量护栏失败时判定为负向效果
- 正式结果不完整时判定为评测失败
- 报告中的数值全部来自 `comparison.json`
- 报告顶部包含结论、提升、成本和建议

测试可使用固定的小数输入，不调用真实 RAGAS Judge。

## 十六、完成标准

- RAGAS、ranx 和自定义指标读取相同的逐题结果
- 所有检索实验稳定输出四个公共指标
- 专项指标不会被误写成通用总分
- 每个实验在运行前声明主指标、门槛和护栏
- 报告自动计算实际提升与成本变化
- 报告顶部给出五种标准结论之一
- 任何正式数值都能追溯到原始结果和结构化比较文件
- 评测失败时不会生成“优化有效”的错误结论
- 相关自动化测试全部通过
