# 为什么需要统一评测体系与消融实验基线

RAG 项目已经有 Query Rewrite、同义词扩展、Hybrid Search、结构化切块、重排、证据编排和 Agentic Research 等能力。每项能力都可以通过接口、日志或调试页证明“它已经能够运行”，但这并不能证明“它确实让检索效果变得更好”。

统一评测体系要解决的核心问题是：使用同一批问题、同一套运行规则和同一种报告格式，客观比较改造前后的效果、延迟和调用成本。

## 常用的 RAG 评测方式

常用的 RAG 评测方式主要分为三类。当前项目已经具备 RAGAS 基础评测，ranx 和自定义指标可以按实际实验需要接入统一体系。

| 评测方式 | 擅长回答的问题 |
|----------|--------------------|
| RAGAS | 召回内容是否覆盖标准答案，无关内容是否过多 |
| ranx | 人工标注的相关候选是否被排在更靠前的位置 |
| 自定义指标 | 证据要点是否齐全、引用是否可回溯、Research 是否修复了缺失证据 |

这三类方式本身没有冲突，分别解决不同问题。真正需要避免的是接入后各自使用不同的数据文件、运行入口、输出字段和验收门槛，否则不同实验的报告仍然难以比较。

常见的问题包括：

- 这次使用 8 道题，另一次使用 30 道题，分数无法横向比较
- 一份报告只有 Context Recall，另一份只有 nDCG，无法看出整体取舍
- 改造前后同时改了多个开关，无法确定收益来自哪个功能
- 只保存汇总分数，没有保存逐题的原始召回结果
- 报告只展示明细，没有回答“优化是否有效、提升了多少、是否值得启用”

## 统一不等于只使用一种指标

统一评测体系不是将 RAGAS、ranx 和自定义指标合并成一个“总分”，也不是强迫所有功能使用相同指标。

统一的是以下内容：

1. 一个主 Golden Set；
2. 一个对外运行入口；
3. `baseline` 和 `candidate` 两个对比组；
4. 四个检索公共指标；
5. 一种逐题结果和报告格式；
6. 一套必须给出明确结论的验收规则。

当前阶段的正式效果报告固定使用四个公共指标，不再为单项优化增加 ranx 或自定义正式指标。不同专题可以通过逐题上下文、阶段信息和错误记录排查原因，但启用结论始终由同一组四项指标得出。

## 为什么需要固定测试集

如果改造前使用一批问题，改造后使用另一批问题，分数变化可能只是题目难度不同。

因此，同一次实验必须保持：

```text
同一批问题
同一套标准答案
同一个知识库文档集合
同一份知识库索引
同一组 TopK 和候选参数
只改变当前要验证的功能
```

测试集不需要永远不变。它按版本管理：

```text
golden_basic_20：20 道电商基础题
golden_basic_20_hr_10：20 道电商基础题 + 10 道人事复杂题
```

同一版本内不随意改题。增加题目、修正标准答案或更换知识库文档时，升级数据集版本，并在新版本上重新运行基线。

## 为什么只保留 baseline 和 candidate

单功能消融实验只回答一个问题：

> 开启这个功能，比不开启更好吗？

因此每个实验只保留两组：

| 组别 | 含义 |
|------|------|
| `baseline` | 改造前或功能关闭时的基线 |
| `candidate` | 改造后或功能开启时的候选方案 |

例如：

```text
Hybrid Search：Vector vs Vector + BM25 + RRF
精排升级：LLM 重排 vs Qwen3-Rerank
Query Rewrite：关闭 vs 开启
同义词扩展：关闭 vs 开启
```

存在三个候选方案时，拆成两个独立的 baseline/candidate 实验，不在一份消融报告中同时改变多个目标。

现有知识库已经完成结构化切块，旧的固定切块索引无法可靠复现，因此结构化切块只作为本次评测的基础条件，不单独进行效果消融。

## 四个公共指标分别说明什么

检索类实验统一保留四个指标。

| 指标 | 通俗含义 |
|------|----------|
| Context Recall | 标准答案中的重要内容有没有被找到 |
| Context Precision | 排在前面的召回内容是不是真的有用 |
| P95 延迟 | 95% 的请求能在多长时间内完成 |
| 平均应用模型调用数 | 为效果提升增加了多少远程模型调用 |

前两项表示效果，后两项表示代价。一个功能可能明显提高 Recall，但也增加一次 LLM 调用和几百毫秒延迟。报告必须同时说明收益和代价，不能只展示质量分数。

RAGAS 自身为评分而发起的 Judge 调用属于评测成本，不计入应用模型调用数。

## 为什么基础题和复杂题分开

电商知识库适合验证普通检索能力。它覆盖支付、促销、会员、退款、物流、结算和商品合规，能够构建直接事实、口语改写和跨文档查询。

人事差旅知识库的条件关系更密集，城市类别、员工职级、交通标准、住宿上限、审批权限和报销凭证经常需要联合判断，适合验证 Query Decomposition 和 Agentic Research。

两类题可以位于同一个 Golden Set 中，但每道题只路由到自己所属的知识库。“同一次评测包含两个知识库的题”，不等于“每道题同时检索两个知识库”。

## 为什么每道题每组只运行一次

基础回归的目标是快速、可重复地检查功能收益，不是执行专门的稳定性压测。

每个实验对 20 道基础题执行：

```text
baseline：20 次正式请求
candidate：20 次正式请求
```

正式请求前执行少量 warm-up，避免首次建立连接、加载模型或初始化资源影响 P95。只有专门验证模型稳定性时，才对少量难题进行多次重复运行。

检索请求和 RAGAS Judge 都使用有界并发，默认并发数为 4。并发数作为报告运行条件保存，确保 baseline 和 candidate 的延迟可以比较。

## 报告必须回答什么

每份正式报告的第一个部分必须是明确结论，至少回答四个问题：

1. 这次优化是否有效；
2. 主要指标提升了多少；
3. 增加了多少延迟和模型调用；
4. 是否建议启用，适合什么场景。

结论类型统一为：

```text
有效，建议启用
有效但成本较高，建议按场景启用
无明显收益，暂不启用
出现负向效果，建议回退
评测执行失败，暂时不能下结论
```

不允许使用“指标有升有降，详情见明细”代替结论。逐题明细用于解释原因，不能代替对优化价值的判断。

## 工程验收和效果评测不混在一起

不是所有功能都应使用 Context Recall 和 Context Precision 验收。

| 功能类型 | 合适的验收方式 |
|----------|------------------|
| 查询处理、检索、切块、重排 | Golden Set 效果评测 |
| 多租户鉴权、套餐权限 | 接口测试和隔离测试 |
| Word/PDF 解析 | 解析一致性和文档完整性测试 |
| 降级、超时、远程服务异常 | 故障注入和自动化回归 |
| 日志和 Langfuse | 链路完整性和脱敏测试 |

![四项指标、启用结论与工程验收的双轨判定](https://pic.niumianoffer.com/images/fs/metrics-and-dual-track-acceptance.png)

统一评测体系与 `pytest` 工程回归同时存在。前者判断效果和代价，后者判断功能是否正确、权限是否受控、异常时是否能够安全降级。

## 这次建设不做什么

为了保持体系轻量，不扩大为通用评测平台：

- 不建设独立的评测 Web 管理后台
- 不引入新的数据库保存实验
- 不设计复杂的多人标注工作流
- 不将多个指标合成一个无法解释的总分
- 不为每次回归重复运行同一道题多次
- 不强行为没有效果收益的工程能力制造提升结论

完成后的核心链路是：

```text
一个版本化 Golden Set
        +
一个统一评测入口
        +
多个 baseline/candidate 实验配置
        ↓
每个功能一份明确结论报告
        +
一份完整能力基线汇总
```

这套方式既能证明单个功能是否有效，也能为每次修改提供稳定的回归基准。
