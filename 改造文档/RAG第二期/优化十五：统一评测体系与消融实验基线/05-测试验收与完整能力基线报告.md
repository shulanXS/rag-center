# 测试验收与完整能力基线报告

统一评测体系的验收分为两部分：

1. 工程验收，确认数据校验、并发运行、指标计算和报告生成都按规则工作；
2. 真实效果验收，使用冻结的 Golden Set 和知识库运行消融实验，形成可以长期复查的基线报告。

只有单元测试通过，不能证明检索优化有效；只有一份效果分数，也不能证明评测程序可靠。两部分都完成后，结果才能作为项目的正式结论。

## 一、验收范围

需要验收以下内容：

- Golden Set 的结构、题目数量和标准答案
- 实验配置中的唯一变量
- baseline 和 candidate 的运行条件
- warm-up 与正式请求隔离
- 有界并发和单题单次执行
- RAGAS、ranx 和自定义指标
- P95 与应用模型调用数
- RAGAS 遥测和离线 Langfuse 开关
- 逐题原始结果与运行快照
- 自动结论、报告内容和结构化输出
- 完整能力基线汇总

## 二、真实评测前置条件

运行前确认：

- 后端服务、数据库、Redis、向量库和 Elasticsearch 正常
- 电商知识库使用确认过的 10 篇业务文档
- 所有正式实验使用项目当前默认方式构建的知识库
- Golden Set 中的每个 `ground_truth` 都经过原文核对
- 实际知识库 ID 和语料版本已经写入数据集
- 评测租户拥有所需 Profile 和功能权限
- Embedding、生成模型、当前重排服务和 RAGAS Judge 凭据可用
- 运行期间不修改知识库文档、索引和实验配置
- 机器上没有会显著争抢资源的批量任务

密钥只通过环境变量提供，不写进数据集、实验配置、manifest 和报告。

## 三、工程自动化测试

运行统一评测相关测试：

```bash
pytest \
  tests/test_eval_dataset.py \
  tests/test_eval_experiment.py \
  tests/test_eval_runner.py \
  tests/test_eval_metrics.py \
  tests/test_eval_report.py \
  -v
```

至少确认：

- 非法数据集会被拒绝
- 非法实验配置会被拒绝
- 未声明的组间差异会被拒绝
- 一道题在每组中只发起一次正式请求
- 默认并发数不会超过 4
- warm-up 不进入正式统计
- 并发完成顺序不会改变结果顺序
- 单题失败不会被成功重试结果覆盖
- `score` 和 `report` 不会重新调用业务接口
- 指标差值和门槛判断正确
- 五种报告结论都能正确生成
- 遥测开关默认值正确

自动化测试全部使用模拟客户端，不消耗真实模型额度。

## 四、数据集和实验配置校验

校验 Golden Set：

```bash
python scripts/run_eval.py validate-dataset \
  --dataset eval/datasets/golden_basic_20.json
```

预期结果：

```text
schema_version：通过
knowledge_bases：通过
case ID 唯一性：通过
basic suite：20 道
direct_fact：10 道
paraphrase：5 道
multi_document：5 道
ground_truth：全部非空
结果：PASS
```

逐个校验实验配置：

```bash
python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/query_rewrite.json

python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/synonym_expansion.json

python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/hybrid_search.json

python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/rerank_upgrade.json
```

命令输出必须展示：

- 实验 ID
- 数据集版本和 suite
- baseline 与 candidate 标签
- 唯一允许变化的字段
- 主指标
- 提升门槛和质量护栏
- 并发数和 warm-up 数

只输出“配置合法”而不展示关键条件，不足以支持人工复核。

## 五、两题冒烟测试

正式运行前，用 2 道题验证完整链路：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/query_rewrite.json \
  --limit 2 \
  --output-suffix smoke
```

检查运行目录：

- 两组都恰好有 2 条正式结果
- warm-up 没有写入 JSONL
- 每条结果都有 `case_id`、`question`、`ground_truth`
- 检索上下文保留文档、章节、排名和分数
- 最终生效配置与实验声明一致
- 延迟为客户端端到端耗时
- 应用模型调用数来源明确
- RAGAS 可以读取已保存结果完成评分
- `report.md` 和 `comparison.json` 都能生成

冒烟测试只验证链路，不作为正式效果结论，也不写入基线汇总。

## 六、正式运行

基础能力使用 20 道 `basic` 题运行：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/query_rewrite.json

python scripts/run_eval.py run \
  --experiment eval/experiments/synonym_expansion.json

python scripts/run_eval.py run \
  --experiment eval/experiments/hybrid_search.json

python scripts/run_eval.py run \
  --experiment eval/experiments/rerank_upgrade.json
```

完成单功能消融后，运行 Profile 整体验收：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/profile_speed_vs_balanced.json

python scripts/run_eval.py run \
  --experiment eval/experiments/profile_balanced_vs_quality.json
```

每个命令默认完成：

```text
校验
→ warm-up
→ baseline 正式请求
→ candidate 正式请求
→ 指标计算
→ 门槛判断
→ 生成报告
```

一个实验失败不应自动删除已经落盘的结果。修复问题后创建新的运行目录，不覆盖失败记录。

## 七、并发与单次执行验收

对任一 20 题实验核对：

| 项目 | 预期 |
|------|------|
| baseline 正式结果 | 20 条 |
| candidate 正式结果 | 20 条 |
| 每题每组正式次数 | 1 次 |
| 默认业务请求并发 | 4 |
| 默认 RAGAS 并发 | 4 |
| warm-up | 每组 2 次，不计分 |
| 输出顺序 | 与 Golden Set 一致 |

运行器日志需要显示当前活动任务数或提供可测试的并发计数。不能仅因为总耗时变短，就认定并发实现正确。

基础回归不重复运行同一道题。如果模型输出稳定性需要单独验证，建立独立实验和独立报告，不改变这套正式基线的运行规则。

## 八、遥测验收

正式命令启动时输出：

```text
RAGAS telemetry: disabled
Offline Langfuse tracing: disabled
```

同时检查 `manifest.json`：

```json
{
  "telemetry": {
    "ragas_do_not_track": true,
    "offline_langfuse_enabled": false
  }
}
```

不能以关闭全部应用观测的方式完成验收。线上业务请求使用的 Langfuse 配置保持原样，只有统一离线评测批次默认不上报。

## 九、逐份报告验收

打开每个 `report.md`，首先检查结论部分。它必须包含：

1. 标准结论；
2. 主指标从多少变为多少；
3. 提升或下降了多少个百分点；
4. Context Precision 是否触发护栏；
5. P95 增加或减少多少毫秒和百分比；
6. 平均应用模型调用数变化；
7. 是否建议启用，以及适用场景。

合格示例：

```text
有效但成本较高，建议按场景启用。

Context Recall 提升 5.2 个百分点，达到 3 个百分点门槛；
Context Precision 下降 0.7 个百分点，未突破护栏；
P95 增加 46.8%，超过 30% 成本限制；
平均应用模型调用数增加 1.0 次。
建议仅在 quality 场景启用。
```

不合格示例：

```text
各项指标有升有降，详细结果见下表。
```

表格中的每个汇总值都必须能在逐题结果中复算。抽查至少 3 道题，确认问题、上下文、答案、评分和报告一致。

## 十、失败与不可用条件

出现以下任一情况时，本次实验不能写成“有效”：

- baseline 和 candidate 使用了不同题目
- 非目标配置同时变化
- 正式题目存在未允许的失败
- RAGAS 关键指标没有完成
- Judge 模型或参数在两组间不同
- 知识库在运行期间被重新索引
- 两组使用不同并发数
- 重排对比没有冻结候选集
- 报告中的数字无法追溯到原始结果

没有真实 API Key 或外部服务不可用时，输出 `SKIP` 或“评测执行失败，暂时不能下结论”。不能填入模拟分数，也不能将接口接入成功描述成效果提升。

## 十一、完整能力基线报告

所有有效运行完成后，正式结果统一保存在：

```text
eval/results/<run_id>/
```

Markdown 报告供人阅读，结构化结果供自动回归使用。完整报告只引用各实验的 `comparison.json`，不重新计算另一套指标。

报告开头先给整体结论：

```markdown
# rag-center golden_basic_20 完整能力基线报告

## 总结论

本次共完成 N 项消融实验，其中：

- N 项达到质量提升门槛，建议启用
- N 项有效但成本较高，建议按场景启用
- N 项未显示明确收益，暂不默认启用
- N 项出现负向效果，建议回退
- N 项评测未完成，暂时不能下结论

当前推荐的默认检索配置是：填写根据真实实验得出的配置。
选择理由是：填写主要质量收益、P95 和模型调用成本。
```

占位文字只能存在于模板。生成正式报告时必须替换为真实数量和真实结论。

## 十二、基线汇总表

完整报告使用统一汇总表：

| 实验 | 主指标变化 | Precision 变化 | P95 变化 | 模型调用变化 | 结论 | 建议 |
|------|------------|----------------|----------|--------------|------|------|
| Hybrid Search | 真实值 | 真实值 | 真实值 | 真实值 | 标准结论 | 启用范围 |
| 重排 | 真实值 | 真实值 | 真实值 | 真实值 | 标准结论 | 启用范围 |
| Query Rewrite | 真实值 | 真实值 | 真实值 | 真实值 | 标准结论 | 启用范围 |
| 同义词扩展 | 真实值 | 真实值 | 真实值 | 真实值 | 标准结论 | 启用范围 |

不要只列最终分数，要同时列变化量。没有执行的实验写“未执行”和原因，不留空，也不使用 0 代替。

## 十三、回归基线 JSON

回归基线 JSON 至少包含：

```json
{
  "schema_version": "1.0",
  "dataset_version": "golden_basic_20",
  "corpus_versions": {
    "ecommerce": "ecommerce_corpus_base"
  },
  "created_at": "真实时间",
  "source_runs": {
    "query_rewrite": "真实运行ID"
  },
  "recommended_configuration": {},
  "experiments": {
    "query_rewrite": {
      "verdict": "effective",
      "baseline": {},
      "candidate": {},
      "delta": {},
      "thresholds": {}
    }
  }
}
```

只将满足以下条件的运行写入正式基线：

- 运行状态为成功
- 数据集版本、语料版本和实际知识库 ID 明确
- 两组结果完整
- 指标与报告生成成功
- 结论经过人工复核

基线文件更新时保留旧版本，不覆盖不同数据集版本的历史基线。

## 十四、完整报告必须回答的问题

最终基线报告必须明确回答：

- 哪些能力被真实数据证明有效
- 每项有效能力分别提升了多少
- 哪些能力增加了明显延迟或模型调用
- 哪些能力只适合 quality 场景
- 哪些能力没有表现出明确收益
- 哪些题型仍然是薄弱点
- 当前推荐的 speed、balanced、quality 配置是什么
- 当前结论适用于哪个数据集、语料和知识库

“测试全部通过”只能作为工程结论。效果部分必须使用真实指标和门槛得出判断。

## 十五、验收通过标准

满足以下条件后，统一评测体系验收通过：

- 20 道电商 Golden Set 已完成原文核对
- 统一入口能够校验、运行、评分和生成报告
- 每题每组只执行一次正式请求
- 业务请求和 RAGAS 都使用默认并发 4
- RAGAS 遥测和离线 Langfuse 默认关闭
- 所有运行条件和原始结果可追溯
- 按 Hybrid Search、重排、Query Rewrite、同义词扩展的顺序完成四项消融
- 每项实验都有 baseline、candidate 和唯一变量
- 每份报告都有明确结论、提升量、成本和建议
- 完整能力基线报告能够汇总所有实验
- 基线 JSON 可以作为同版本数据集的回归参考
- 没有伪造、补写或用模拟数据替代真实效果结果

验收完成后，任何会影响检索、排序或答案质量的改动，都使用相同入口和对应实验配置重新评测。Golden Set 版本不变时，可以与既有基线直接比较；数据集或语料版本变化时，先在新版本上重新建立基线。
