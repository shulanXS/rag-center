# 统一评测运行器与并发执行改造提示词

点击此处可复制本篇提示词

在当前 rag-center 项目中，将已有的 RAGAS、ranx 和自定义评测脚本收敛到一个统一入口。运行器负责读取同一份 Golden Set，按实验配置分别运行 `baseline` 和 `candidate`，保存逐题结果，并为指标计算和报告生成提供统一输入。

本次改造以简单、可维护为原则。保留已有评测实现和历史报告，不建设 Web 管理后台，不引入评测数据库，也不把全部逻辑堆进一个大文件。

## 一、建设目标

- 对外只保留一个评测入口 `scripts/run_eval.py`
- 每个实验只包含 `baseline` 和 `candidate` 两组
- 同一道题在两组中使用相同的知识库和相同的非实验参数
- 每道题在每组中只执行一次正式请求
- 正式请求支持有界并发，默认并发数为 4
- 运行前执行少量 warm-up，warm-up 不计入正式结果
- 每题保存检索上下文、回答、延迟和应用模型调用数
- 评测失败必须如实记录，不允许静默跳过
- 默认关闭 RAGAS 遥测和 Langfuse 离线评测上报
- 运行目录保存足够信息，使一次实验能够被复查和重跑

## 二、统一运行入口

新增：

```text
scripts/run_eval.py
```

统一入口至少支持以下命令：

```bash
python scripts/run_eval.py validate-dataset \
  --dataset eval/datasets/golden_basic_20.json

python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/query_rewrite.json

python scripts/run_eval.py run \
  --experiment eval/experiments/query_rewrite.json

python scripts/run_eval.py score \
  --run-dir eval/results/具体运行目录

python scripts/run_eval.py report \
  --run-dir eval/results/具体运行目录
```

`run` 默认依次完成数据校验、实验校验、warm-up、两组正式请求、评分和报告生成。`score` 和 `report` 允许对已保存的原始结果重新计算，避免修改报告样式后再次请求业务 LLM。

## 三、实验配置格式

新增目录：

```text
eval/experiments/
```

单个实验配置示例：

```json
{
  "schema_version": "1.0",
  "experiment_id": "query_rewrite",
  "title": "Query Rewrite 消融实验",
  "target": "query_rewrite",
  "changed_fields": [
    "query_options.rewrite_enabled"
  ],
  "dataset": "eval/datasets/golden_basic_20.json",
  "suite": "basic",
  "primary_metric": "context_recall",
  "concurrency": 4,
  "warmup_cases": 0,
  "baseline": {
    "label": "关闭 Query Rewrite",
    "query_options": {
      "rewrite_enabled": false
    }
  },
  "candidate": {
    "label": "开启 Query Rewrite",
    "query_options": {
      "rewrite_enabled": true
    }
  }
}
```

实验根节点只允许存在 `baseline` 和 `candidate`。如果需要比较多个候选方案，建立多个独立实验配置。

基础回归不做预热，也不重复运行同一道题，因此 `warmup_cases` 固定为 `0`。每道题在 baseline 和 candidate 中各执行一次正式请求。

`changed_fields` 声明本次实验允许变化的字段。除这些字段外，两组配置必须完全一致。运行器要在执行前比较有效配置；如果发现 TopK、知识库、模型、切块策略等非目标字段同时发生变化，直接拒绝运行，并说明差异字段。

## 四、补齐可控的查询开关

检查现有查询接口和服务层是否能够通过请求参数覆盖以下能力：

```text
rewrite_enabled
synonym_enabled
retrieval_mode
rerank_mode
profile
top_k
candidate_k
```

如果同义词扩展当前只能跟随 Profile 或全局配置开启，增加独立的可选覆盖字段：

```python
synonym_enabled: bool | None = None
```

字段为 `None` 时沿用现有配置；显式传入 `true` 或 `false` 时只覆盖当前请求。该覆盖能力仅用于调试和评测，不改变普通业务请求的默认行为。

响应元数据中至少返回最终生效的：

```json
{
  "effective_config": {
    "rewrite_enabled": true,
    "synonym_enabled": false,
    "retrieval_mode": "hybrid",
    "rerank_mode": "none",
    "top_k": 5,
    "candidate_k": 20
  }
}
```

运行器以 `effective_config` 为准校验两组差异，不能只相信实验配置文件中的声明。

## 五、按题目路由知识库

运行器读取 Golden Set 根节点的 `knowledge_bases`，将每道题的 `kb_alias` 转换成实际 `kb_id`。

例如：

```text
case.kb_alias = ecommerce
        ↓
dataset.knowledge_bases.ecommerce.kb_id
        ↓
本次请求只检索该知识库
```

如果题目使用 `kb_aliases`，才调用现有的多知识库检索能力。单个评测批次中出现电商题和人事题，只表示题目分别路由，不表示每道题都联合检索两个知识库。

找不到知识库别名时立即终止运行，不允许回退到默认知识库。

## 六、warm-up 与正式请求

默认每组选择前 2 道题进行 warm-up：

```text
baseline warm-up：2 次，不计分
candidate warm-up：2 次，不计分
baseline 正式请求：每题 1 次
candidate 正式请求：每题 1 次
```

warm-up 用于完成连接池、模型客户端和必要资源的初始化。它不能写入正式逐题结果，也不能计入 P95 和平均模型调用数。

正式请求不默认自动重试。发生超时、服务异常或返回结构错误时：

- 保存该题的错误类型和错误信息
- 将该题标记为失败
- 不用另一次成功结果覆盖失败结果
- 报告中展示两组失败数量
- 只要关键结果不完整，报告不能给出“优化有效”的结论

底层 HTTP 客户端为普通网络抖动设置的重试可以保留，但重试次数必须记录在逐题结果中。

## 七、有界并发执行

正式请求使用异步有界并发，默认值为 4：

```python
semaphore = asyncio.Semaphore(concurrency)
```

实现要求：

- `baseline` 和 `candidate` 分别执行，不将两组请求混在同一批任务中
- 同一组内最多同时运行 `concurrency` 道题
- 无论请求完成顺序如何，输出结果按 Golden Set 原始顺序保存
- 单题异常不能取消其他已开始的题目
- 并发数写入 `manifest.json`
- 命令行可通过 `--concurrency` 临时覆盖配置
- 并发数最小为 1，设置过大时输出明确警告

两组采用相同并发数。P95 是在该并发条件下测得的客户端端到端延迟，不将服务端各阶段耗时相加代替。

## 八、延迟与模型调用数

每道正式请求在客户端记录：

```python
started_at = time.perf_counter()
# 发起完整查询请求
latency_ms = (time.perf_counter() - started_at) * 1000
```

逐题结果同时保存服务端返回的阶段耗时，作为诊断信息：

```json
{
  "latency_ms": 842.6,
  "stage_latency_ms": {
    "rewrite": 105.2,
    "retrieval": 118.4,
    "rerank": 0,
    "generation": 571.3
  }
}
```

应用模型调用数只统计业务链路为回答用户而发起的远程模型调用，例如：

- Query Rewrite
- LLM Rerank
- 答案生成
- 证据编排
- Research 中的规划、检索判断和总结

RAGAS Judge、Embedding 索引构建和 warm-up 不计入应用模型调用数。优先复用服务端已有 usage 或调用计数；如果无法准确获取，标记为 `null`，不能通过猜测补值。

## 九、逐题原始结果

每组保存一个 JSONL 文件，每行对应一道题：

```json
{
  "case_id": "refund_unshipped",
  "group": "candidate",
  "kb_alias": "ecommerce",
  "question": "还没发货可以申请退款吗？",
  "ground_truth": "未发货订单申请后2小时内原路退款。",
  "answer": "……",
  "contexts": [
    {
      "rank": 1,
      "text": "……",
      "document": "售后服务与退换货政策.md",
      "heading": "未发货退款",
      "score": 0.87
    }
  ],
  "latency_ms": 842.6,
  "application_model_calls": 2,
  "retry_count": 0,
  "effective_config": {},
  "error": null
}
```

不要只保存最终答案。RAGAS、ranx、自定义指标和失败分析都需要复用同一份原始召回结果。

## 十、运行目录

每次运行创建独立目录：

```text
eval/results/
└── 20260820_143000_query_rewrite/
    ├── manifest.json
    ├── experiment.snapshot.json
    ├── dataset.snapshot.json
    ├── baseline.raw.jsonl
    ├── candidate.raw.jsonl
    ├── baseline.metrics.json
    ├── candidate.metrics.json
    ├── comparison.json
    └── report.md
```

`manifest.json` 至少记录：

- 运行 ID 和开始、结束时间
- Git commit；工作区不干净时记录 `dirty=true`
- 数据集版本、语料版本和实际知识库 ID
- 实验 ID、suite 和主指标
- 两组最终生效配置
- 并发数、warm-up 数和超时
- 应用模型、Embedding 模型和 RAGAS Judge 模型
- 评测环境中的遥测开关
- 成功题数、失败题数和运行状态

快照文件用于防止源配置后来被修改后无法复查历史实验。

## 十一、关闭离线评测遥测

在导入或初始化 RAGAS 前设置：

```python
os.environ.setdefault("RAGAS_DO_NOT_TRACK", "true")
```

统一评测命令默认不向 Langfuse 上报离线批量链路。为运行器增加明确配置，例如：

```text
EVAL_LANGFUSE_ENABLED=false
```

普通线上请求的 Langfuse 配置不受影响。报告的 `manifest.json` 要记录 RAGAS telemetry 和离线 Langfuse 是否关闭，便于复查运行条件。

## 十二、兼容已有评测代码

先检查 `eval/`、`scripts/` 和测试目录下已有的 RAGAS、ranx、自定义指标脚本：

- 可复用的计算函数移动或封装到 `eval/core/`
- 旧命令可以调用新入口并输出迁移提示
- 历史结果文件保留，不批量删除或改写
- 不复制两套同名指标实现
- 统一数据模型与业务查询模型分离

建议的内部结构：

```text
eval/
├── core/
│   ├── dataset.py
│   ├── experiment.py
│   ├── runner.py
│   ├── models.py
│   └── storage.py
├── datasets/
├── experiments/
└── results/
```

这是内部拆分建议，不要求为了目录整齐而重写已经稳定的业务代码。

## 十三、测试代码

至少增加以下自动化测试：

- 实验配置只能包含 `baseline` 和 `candidate`
- 缺少数据集、suite 或主指标时校验失败
- 非目标配置同时变化时拒绝运行
- `kb_alias` 能正确解析为知识库 ID
- warm-up 结果不会写入正式结果
- 单题每组只执行一次正式请求
- 并发任务数不会超过配置上限
- 并发完成顺序不会改变输出题目顺序
- 单题异常会被保存，其他题目仍能完成
- 客户端延迟和应用模型调用数正确写入
- `score` 和 `report` 不会再次调用业务查询接口
- RAGAS 遥测和离线 Langfuse 默认关闭

测试使用假的查询客户端和很小的临时数据集，不连接真实 LLM 和知识库。

## 十四、完成标准

- 所有正式评测都能从 `scripts/run_eval.py` 启动
- 一个实验配置能够完整运行 `baseline` 和 `candidate`
- 20 道题在每组中各执行一次正式请求
- 默认并发数为 4，且不存在无上限并发
- warm-up、失败请求和底层重试都有明确记录
- 每题的上下文、答案、延迟和模型调用数完整保存
- 运行目录包含配置快照、数据集快照、原始结果和 manifest
- RAGAS 遥测及离线 Langfuse 默认关闭
- 已有评测能力得到复用，历史文件没有被破坏
- 相关自动化测试全部通过
