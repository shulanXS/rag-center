# 受控 Agentic Research 测试验收与统一效果报告

本专题需要验证三件事：完整Research是否比单次检索更适合复杂问题、第二轮补证是否真正修复多跳缺口，以及质量收益是否值得增加的延迟和模型调用。

效果测试接入统一评测体系，继续使用同一份Golden Set、同一个运行入口、四项正式指标和标准报告目录。不创建Research专用数据集、A/B/C报告或独立评测脚本。

## 一、测试范围

测试分成三类：

| 类型 | 作用 |
|------|------|
| 自动化测试 | 验证状态机、权限、硬上限、降级和响应契约 |
| 两次A/B效果测试 | 验证完整Research和第二轮补证的实际收益 |
| 手工与链路检查 | 验证调试台、引用定位和Langfuse Trace |

普通检索和Research的公开响应保持清晰边界：

```text
POST /rag/retrieve
    返回chunks
    evidence_pack仍然可选

POST /rag/research
    不返回chunks字段
    固定返回answer和evidence_pack
```

正常Research成功时，`answer`必须是非空的带引用答案，最终选中的原始片段全部位于`evidence_pack.items`。只有Finalizer异常时才允许`answer=null`，同时返回已经校验的证据包并标记降级。

## 二、统一Golden Set

继续使用现有Golden Set文件，在其中增加`research` suite，共10道固定复杂题：

| case_type | 数量 | 目的 |
|-----------|-----:|------|
| `independent_multi_aspect` | 4 | 验证查询分解和并行检索 |
| `dependent_multi_hop` | 4 | 验证第二轮定向补证 |
| `control` | 2 | 验证无答案和证据冲突边界 |

每道题至少保存：

```text
case_id
case_type
question
ground_truth
expected_documents
expected_headings
evidence_points
required_aspects
expected_status
requires_multi_hop
dependency
review_status
```

依赖型题目还要说明首轮线索和补证目标。标注优先使用文档标题、章节和证据要点，可选保存版本化Chunk ID用于精确诊断，但不能只依赖Chunk ID。

4道依赖型题必须满足：原问题单次检索不能直接覆盖全部证据，第一轮材料中存在明确的新线索，围绕该线索继续检索能够找到目标证据。至少2道题应能形成有效的补证修复分母，否则不能得出第二轮补证有效的正式结论。

正式运行前冻结：

- 10道问题及人工标注；
- 知识库和v2索引；
- Embedding、Qwen3-Rerank和LLM版本；
- Planner、Decider和Finalizer Prompt版本；
- 实验配置和数据集哈希。

## 三、统一运行条件

两次实验统一使用：

```text
suite：research
索引：v2
检索：Vector + BM25 + RRF
共同候选：每次检索RRF Top20
精排：Qwen3-Rerank
精排结果：Top10
最终证据：最多10条
Query Rewrite：关闭
同义词扩展：关闭
每题每组：1次
Case并发：2
Research内部子查询：并行
RAGAS并发：4
warm-up：0
RAGAS telemetry：关闭
离线Langfuse：关闭
```

两组都开启Qwen3精排，因为优化十九验证的是查询分解、并行检索和补证，不重新验证精排。Research执行多个子查询时产生的每次Qwen3调用都必须计入模型调用次数和完整链路延迟。

以上也是`/rag/research`的服务端固定配置，不是只在离线测试中临时指定。Research是Pro套餐独立模式，不属于普通检索的四种Profile；请求不能覆盖索引版本、TopK、召回方式、精排方式、Query Rewrite、同义词、证据数量和轮数。普通`/rag/retrieve`仍保留四种Profile及其原有行为。

## 四、实验一：完整Research效果

在全部10道复杂题上比较：

| 项目 | A组：Single Retrieve | B组：Controlled Research |
|------|----------------------|-------------------------|
| 查询 | 原始问题 | Planner生成1～3个首轮查询 |
| 检索 | 单次Hybrid检索 | 多个子查询并行Hybrid检索 |
| 精排 | Qwen3 Top10 | 每个子查询使用相同Qwen3精排 |
| 证据处理 | 开启普通证据编排 | Decider组织Research证据 |
| 第二轮 | 不执行 | 证据不足时最多补证一次 |
| 最终输出 | EvidencePack | answer + EvidencePack |

A组主动开启普通证据包，是为了让两组都用`evidence_pack.items`计算上下文指标。否则A组评价原始Top10、B组评价筛选后的证据包，会把证据编排差异混进Research结论。

B组不再额外调用普通Evidence Orchestrator。Research中的Decider已经承担证据筛选和组织，再调用一次会重复处理并增加不必要的延迟。

A组不生成最终答案，B组固定执行Finalizer。因此P95和平均模型调用次数比较的是两个真实接口从请求到最终响应的端到端成本，其中包含Research生成答案的成本，不应把这部分从B组扣除。Context Precision和Context Recall只评价两组最终证据，不评价答案文风。

这个实验回答：

> 面对复杂问题，完整Research相比当前最强的单次检索与证据编排链路，是否产生值得付出成本的总体收益？

实验配置：

```text
eval/experiments/research_effect_v2.json
```

## 五、实验二：第二轮补证效果

只运行4道`dependent_multi_hop`题：

| 项目 | A组：禁止补证 | B组：允许补证 |
|------|---------------|---------------|
| Planner计划 | 共用 | 同一份 |
| 第一轮检索 | 共用 | 同一份 |
| 第一轮候选 | 共用 | 同一份 |
| 第二轮 | 禁止 | 最多执行一次 |
| 最终证据 | 第一轮证据包 | 合并补证后的证据包 |

两组必须共享Planner输出、首轮检索任务和首轮候选快照，唯一变量是是否允许一次补证。这样才能把结果变化归因到第二轮，而不是Planner随机性或首轮召回波动。

这个实验回答：

> 第二轮补证是否把第一轮不完整的多跳问题修复为完整？

实验配置：

```text
eval/experiments/research_supplement_v2.json
```

## 六、正式指标

两份报告统一使用四项正式指标：

| 指标 | 本专题中的作用 |
|------|----------------|
| Context Precision | 判断最终证据包中的材料是否集中且有用 |
| Context Recall | 判断回答复杂问题所需证据是否被完整找回 |
| P95延迟 | 比较从接收请求到答案和证据包完成的完整耗时 |
| 平均模型调用次数 | 统计Qwen3、Planner、Decider、Finalizer和普通证据编排调用 |

Context Precision和Context Recall都只使用最终`evidence_pack.items`中的原始正文作为contexts。B组内部未选入证据包的候选不进入RAGAS评分。

不增加ranx、nDCG、MRR、HitRate、Answer Relevance等正式指标。

## 七、Agentic诊断指标

只保留一个必要的自定义诊断指标：

```text
Multi-hop Repair Rate
= A组不完整、经过B组第二轮补证后变完整的题数
÷ A组不完整且知识库中存在合法目标证据的题数
```

它只在第二轮补证实验中计算，用来解释补证是否真正修复缺口，不替代四项正式指标。如果分母为0，报告必须写`not_evaluable`并补充测试题，不能写成0%或100%。

以下信息只作为逐题诊断，不进入主效果表：

- required aspect覆盖明细；
- 第二轮新增证据数量；
- 首轮已经完整却触发补证的题数；
- 查询计划、停止原因和降级原因；
- 每阶段Token与耗时。

## 八、工程硬门槛

以下要求必须全部通过，不能用平均分掩盖单题违规：

- 引用回溯率达到100%；
- 首轮查询数不超过3；
- 补证查询数不超过2；
- 检索轮数不超过2；
- Research LLM调用数不超过3；
- 第一轮证据完整时不得执行第二轮；
- 补证查询只能绑定缺失要点；
- 补证查询不能与已执行查询重复；
- 所有轮次保持相同tenant、kb_ids和v2索引；
- 无答案题不能生成无证据的确定结论；
- 冲突题必须说明来源不一致并分别引用；
- 正常成功响应具有非空answer和evidence_pack；
- Research响应中不存在chunks字段；
- answer中的每个`[E编号]`都能映射到唯一EvidenceItem；
- 10道最终答案必须逐题核对，不能出现证据不支持的明确结论；
- 单题不突破服务端总时间预算。

## 九、执行顺序

不要一次运行所有正式调用。

### 1. 配置校验

```bash
python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/research_effect_v2.json

python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/research_supplement_v2.json
```

### 2. 两题冒烟

先从Research suite选择1道并列多要点题和1道依赖型多跳题，只运行完整Research效果实验。检查：

- Planner、Decider和Finalizer调用成功；
- 内部子查询确实并行；
- 最终answer非空且引用可回溯；
- evidence_pack.items包含真实原文；
- 响应没有chunks字段；
- 遥测和离线Langfuse保持关闭；
- 原始结果可以进入RAGAS评分和统一报告。

### 3. 完整Research效果正式测试

冒烟通过后运行全部10题：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/research_effect_v2.json \
  --tenant-id <评测租户ID>
```

生成第一份报告并确认结果完整后，再继续第二项实验。

### 4. 第二轮补证正式测试

先对1道依赖型题冒烟，确认两组共享同一份首轮快照，再运行4道正式题：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/research_supplement_v2.json \
  --tenant-id <评测租户ID>
```

每组运行结束后立即保存checkpoint。进程中断时允许继续未完成题目，不重跑已经成功的模型调用和检索。

## 十一、自动化测试

后端至少覆盖：

- Planner输出校验和失败回退；
- 1～3个首轮查询并发执行；
- 跨查询候选去重和要点绑定；
- Decider状态由后端重新计算；
- complete时不补证；
- 补证查询去重、数量和轮数上限；
- Finalizer只使用合法证据生成答案；
- Finalizer异常时answer为null但EvidencePack仍返回；
- `/rag/research`成功响应没有chunks字段；
- answer引用全部映射EvidenceItem；
- 租户、知识库和索引范围不可被模型改变；
- 超时、429、部分检索失败和Langfuse异常能够安全降级；
- `/rag/retrieve`行为和响应契约保持不变；
- 统一运行器能够执行两份Research实验并生成标准报告。

前端至少覆盖：

- Single和Research模式使用不同接口；
- Single显示四种Profile，Research隐藏Profile与高级参数并展示固定配置；
- Research模式展示最终答案、证据包、查询计划和轮次；
- 不显示空的chunks区域；
- 点击答案引用能够定位EvidenceItem；
- Finalizer降级时仍能查看证据；
- 不提供轮数、模型调用、工具或`generate_answer`配置；
- 无Research套餐权限时不能发起请求。

单元测试使用Fake Provider或mock，不产生真实模型费用。

## 十二、故障降级验收

至少模拟：

| 场景 | 预期 |
|------|------|
| Planner超时或非法JSON | 使用原问题执行首轮检索并标记降级 |
| 一个首轮查询失败 | 保留其他成功任务 |
| Decider失败 | 不执行不可信补证，由后端构造partial或missing证据包 |
| 补证查询重复 | 拒绝执行并记录duplicate_query |
| 补证检索失败 | 保留首轮安全证据 |
| 第二轮无新证据 | 记录no_new_evidence并停止 |
| Finalizer失败 | answer=null，EvidencePack仍返回，标记降级 |
| Finalizer返回非法引用 | 拒绝该答案并按Finalizer失败处理 |
| Langfuse不可用 | 不影响Research主响应 |
| 超出整次时间预算 | 停止创建新任务并返回安全降级结果或标准超时错误 |

任何异常都不能泄露API Key、Authorization Header和完整内部候选池。

## 十三、手工验收

至少检查三类真实请求：

### 并列多要点

- Planner产生合理的1～3个查询；
- 子查询并行执行；
- 每个必要要点都有独立证据；
- 第一轮完整时不显示第二轮；
- 最终答案引用能够定位证据卡片。
- 最终答案覆盖已取得证据支持的必要要点，不添加证据外结论。

### 依赖型多跳

- 第一轮证据暴露新的检索线索；
- Decider只为缺失要点生成补证查询；
- 第二轮命中目标文档或章节；
- 最终证据包合并两轮来源；
- round_count不超过2，LLM调用不超过3。

### 无答案或冲突

- 无答案时明确说明材料不足；
- 冲突时分别引用不同来源；
- 不使用模型常识补全确定结论；
- EvidencePack状态和stop_reason含义一致但不混用。

## 十四、Langfuse验收

正式离线评测关闭Langfuse，链路观测使用单独手工请求检查。

一轮完成的Trace至少包含：

```text
planner
retrieval_round_1
evidence_decider
finalizer
```

两轮完成的Trace增加：

```text
retrieval_round_2
```

检查trace_id、阶段耗时、Token汇总、stop_reason和API响应一致。Trace不能保存API Key、Header和完整候选正文；Langfuse失败不能影响Research主流程。

## 十五、报告结论

完整Research效果报告必须明确写出：

- Context Precision和Context Recall分别变化多少；
- P95增加多少秒；
- 平均模型调用增加多少次；
- 哪类复杂问题改善最多；
- 是否值得作为复杂查询的显式能力启用。

第二轮补证报告必须明确写出：

- 4道依赖型题中有多少道第一轮不完整；
- 有多少道经过第二轮修复；
- Multi-hop Repair Rate；
- 第二轮增加的延迟和模型调用；
- 是否存在不必要补证或越过硬上限。

建议只给出以下三类结论：

```text
有效，建议在复杂查询中启用
有局部收益，建议按场景启用并继续优化
没有证明有效，暂不启用
```

Research不进入普通检索档位，也不自动接管`/rag/retrieve`。只有调用方明确选择`/rag/research`时，系统才执行查询分解、多轮检索、证据组织和最终答案生成。
