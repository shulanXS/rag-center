# 为什么要从 LLM 重排升级到专用精排

检索系统从知识库中找出候选片段后，还需要判断哪些片段最值得交给生成模型。这个过程通常称为重排。本次改造将通用 LLM 重排替换为 `qwen3-rerank` 专用精排，让排序任务由更适合的模型完成。

这里所说的专用精排属于广义的 Cross-Encoder：模型同时读取问题和候选片段，直接计算两者的相关程度。它不会重新搜索知识库，而是从已经召回的候选中选出更有用的结果。

## 当前 LLM 重排是怎么工作的

当前实现位于 `app/providers/rerank/llm.py`，基本流程如下：

```text
query + 候选 Top20
        ↓
组织成 JSON 提示词
        ↓
通用 LLM 生成 chunk_id、score、reason
        ↓
解析 JSON、按分数排序
        ↓
返回 Top10
```

这种方式容易接入，也能复用现有模型接口，但放在稳定的在线检索链路中存在几个问题。

### 1. 排序被转换成了文本生成

排序真正需要的是候选下标和相关性分数，LLM 却要生成 `chunk_id`、`reason` 和完整 JSON。模型把一部分时间和 token 用在了组织输出格式上，这些内容不会直接提高排序质量。

### 2. 结果依赖提示词和 JSON 解析

LLM 必须严格按照约定返回 JSON。一旦出现候选遗漏、重复 ID、字段缺失或格式错误，重排就会失败并回退到原始顺序。即使使用固定温度，模型版本和服务端策略变化仍可能影响结果。

### 3. 候选越多，输入和输出越重

精排前需要保留足够多的候选，避免有效证据过早被截断。通用 LLM 不仅要读取 Top20 候选，还要为候选生成排序结果，耗时会同时受到输入长度和输出长度影响。

### 4. 通用 LLM 不是专门为检索排序训练的

通用 LLM 擅长理解、生成和推理；专用精排模型则专门学习“给定一个问题，哪个片段更相关”。两者都可以完成排序，但专用模型的任务目标和接口形式更适合在线检索链路。

## 专用精排有什么不同

专用精排直接接收一个 query 和一组 documents，为每个 query-document 组合计算相关性：

```text
向量检索 + BM25
        ↓
RRF 融合候选 Top20
        ↓
Qwen3-Rerank 联合判断问题与每个片段
        ↓
按 relevance_score 排序
        ↓
返回 Top10
```

![通用 LLM 生成式重排与 Qwen3 专用精排对比](https://pic.niumianoffer.com/images/fs/rerank-mechanism-comparison.png)

各阶段分工如下：

| 阶段 | 主要目标 | 默认数量 |
|------|----------|----------|
| 向量检索、BM25 | 从大量数据中尽量找全候选 | 分别召回后参与融合 |
| RRF | 融合不同检索方式的排名 | 保留候选 Top20 |
| Qwen3-Rerank | 判断候选是否真正有助于回答问题 | 精排后返回 Top10 |

候选 Top20 和最终 Top10 都是正式检索链路的生产参数，不是测试专用参数。候选池必须大于最终结果数量，否则精排只能调整顺序，无法淘汰无关片段。

## 为什么选择远程精排服务

专用精排既可以本地部署，也可以调用远程 API。

| 对比项 | 本地部署 | 远程 API |
|--------|----------|----------|
| 基础设施 | 需要准备 CPU/GPU、模型服务和容器 | 不需要部署模型服务 |
| 运维责任 | 负责模型加载、升级、容量和监控 | 模型服务由平台维护 |
| 数据安全 | 文本保留在自己的环境中 | 问题和候选文本会发送给平台 |
| 性能特点 | 内网延迟更可控 | 受公网、平台负载和限流影响 |
| 成本特点 | 有固定机器成本 | 按实际调用量计费 |

当前项目已经使用远程模型服务，重点是完善 RAG 检索链路，而不是建设 GPU 推理平台。因此选择远程 API，可以把改造范围集中在精排 Provider、异常降级、统一评测和生产接入上。

## 为什么选择 Qwen3-Rerank

本次使用阿里云百炼提供的 `qwen3-rerank`，主要考虑以下几点：

1. 项目知识库以中文内容为主，模型适合当前语言场景；
2. 支持面向任务的 `instruct`，可以强调优先返回能够支撑答案的证据；
3. Top20 候选远低于接口上限，不需要拆分多次请求；
4. 与项目现有百炼模型使用同一平台，不需要新增供应商账号和费用治理；
5. 接口直接返回候选下标和 `relevance_score`，不再生成和解析排序 JSON。

Embedding 和 Rerank 虽然使用同一个平台，但接口地址不同。Qwen3-Rerank 的地址包含 Workspace ID，因此单独配置 `RERANK_BASE_URL`。API Key 默认复用 `MODEL_API_KEY`，需要独立权限或额度治理时再使用 `RERANK_API_KEY`。

## 怎么证明精排升级有效

模型更专业并不代表在当前知识库中一定更好。这里需要回答两个不同的问题：Qwen3 精排本身是否比不精排更好，以及它是否比原有 LLM 重排更适合作为在线能力。因此使用同一套 Golden Set 做两种递进测试。

| 测试 | A组 | B组 | 回答的问题 |
|------|-----|-----|------------|
| 精排效果测试 | RRF 原始 Top10，不精排 | Qwen3 精排 Top10 | 开启精排是否带来真实收益 |
| 精排选型测试 | 原有 LLM 重排 Top10 | Qwen3 精排 Top10 | 两种精排方式哪一种更适合中台 |

两种测试都从混合检索产生的同一份 RRF Top20 候选开始，最终返回 Top10。每次 A/B 对比只改变精排开关或精排模型，Golden Set、知识库、索引、检索参数、并发数和超时保持一致。每道题每组只执行一次，不通过重复调用测试稳定性。

正式报告只保留四项指标：

| 指标 | 用途 |
|------|------|
| Context Precision | 判断最终上下文中的相关证据是否更集中 |
| Context Recall | 判断精排后是否仍然保留回答所需证据 |
| P95 延迟 | 判断专用精排对检索尾部延迟的影响 |
| 平均应用模型调用次数 | 判断模型调用成本是否增加 |

Context Precision 会综合评价 Top10 的内容质量，但不直接说明正确片段是否被排得更靠前。因此在“不开启精排与 Qwen3 精排”测试中，额外使用 nDCG@10 解释排序变化。它直接复用 Golden Set 中的期望文档和章节，不单独维护 relevance 数据，也不替代四项正式指标或参与统一验收门槛。

RAGAS 和统一运行器直接读取同一套 Golden Set、原始结果和实验配置，生成相同格式的报告。最终结论需要综合两个实验：先确认精排带来的质量与排序变化，再结合 LLM 重排和 Qwen3 精排的质量、延迟、稳定性与调用成本完成在线选型。

20 道题的正式结果表明，Qwen3 相对不精排将 Context Recall 提升 5.0 个百分点、nDCG@10 提升 2.9 个百分点，Context Precision 下降 1.1 个百分点，P95 增加约 0.86 秒。它相对 LLM 重排的 Context Precision 低 5.1 个百分点，但 Recall 高 3.3 个百分点，并将 P95 从 79.7 秒降到 3.3 秒。Qwen3 没有让所有质量指标同时提升，但能够改善证据覆盖和整体排序，且速度、稳定性和规模化成本更适合在线 RAG 中台，因此保留为默认精排能力；LLM 重排只作为离线参照或低频高价值场景的可选能力。

## 完成升级后有什么变化

| 改造前 | 改造后 |
|--------|--------|
| 通用 LLM 根据提示词生成排序 JSON | Qwen3-Rerank 直接返回候选下标和相关性分数 |
| 排序依赖提示词、生成结果和 JSON 解析 | 排序使用专用精排接口和固定响应结构 |
| 输入输出 token 随候选数量共同增长 | 不再生成 reason 和完整排序 JSON |
| 产品链路使用 LLM 重排 | 产品链路固定使用 Qwen3-Rerank |
| 使用独立脚本和独立指标验证效果 | 使用统一 Golden Set、运行入口、四项指标和报告 |

最终检索链路为：

```text
Vector + BM25 → RRF 候选 Top20 → Qwen3-Rerank → 最终 Top10
```

前端继续复用现有精排开关、TopN 配置和分数展示。Qwen3-Rerank 调用失败时，系统返回 RRF 原始顺序的 Top10，避免精排服务异常导致整个检索请求失败。
