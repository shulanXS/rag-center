# 检索精排升级改造提示词

点击此处可复制本篇提示词

在当前 rag-center 项目中，将通用 LLM 重排升级为阿里云百炼 `qwen3-rerank` 专用精排。生产链路采用“混合检索与 RRF 产生候选 Top20，Qwen3-Rerank 精排后返回 Top10”。复用现有 `RerankProvider`、retrieve API、套餐策略、精排开关和调试台，不增加面向用户的模型选择入口。

效果验收必须接入项目已有的统一评测体系。使用同一套 Golden Set、统一运行入口、四项正式指标和统一报告，分别验证“不开启精排与 Qwen3 精排”和“LLM 重排与 Qwen3 精排”，不再创建精排专用数据集或独立对比脚本。

修改前先检查当前代码，以实际目录、类型和调用关系为准，不重复创建已有能力，也不修改与精排无关的功能。

## 一、改造目标

- 新增或完善 `Qwen3RerankProvider`，通过远程 API 调用百炼 `qwen3-rerank`；
- 生产检索链路固定使用 Qwen3-Rerank，不提供 LLM/Qwen3 切换参数；
- 混合检索和 RRF 为精排准备 Top20 候选，精排后返回 Top10；
- 保持 `RerankProvider.rerank(query, chunks, top_n)` 接口不变；
- 保留 `NoopRerankProvider`，用于关闭精排或套餐不支持精排的场景；
- Qwen3-Rerank 调用失败时回退到 RRF 原始顺序 Top10；
- 复用调试台已有的精排开关、TopN、模型信息和分数展示；
- 将 LLM 重排保留为统一离线评测中的 baseline，不再作为产品能力；
- 先通过统一评测判断 Qwen3 精排相对不精排是否有效，再与 LLM 重排比较并完成在线选型。

## 二、Qwen3-Rerank Provider

新增或修改：

```text
app/providers/rerank/qwen3.py
```

实现：

```python
class Qwen3RerankProvider(RerankProvider):
    name = "qwen3"
```

使用项目已有的 `httpx` 调用百炼兼容接口，不额外引入 DashScope SDK。

```text
POST {RERANK_BASE_URL}/reranks
Authorization: Bearer {RERANK_API_KEY}
Content-Type: application/json
```

请求体示例：

```json
{
  "model": "qwen3-rerank",
  "query": "用户问题",
  "documents": [
    "标题：候选标题\n正文：候选正文"
  ],
  "top_n": 10,
  "instruct": "Given a question, retrieve passages that contain evidence needed to answer the question."
}
```

请求处理要求：

- Provider 接收 RRF 排序后的 Top20 候选；
- Provider 内部最多处理 50 条，作为安全保护；
- document 使用“标题 + 正文”，正文最多保留 1024 个字符；
- 不把 vector score、BM25 score、租户信息和内部 ID 拼进 document；
- `top_n = min(10, candidate_count)`；
- candidates 为空时直接返回空列表，不调用远程接口；
- 请求超时使用 `RERANK_TIMEOUT_SECONDS`；
- 日志记录模型、候选数量和耗时，不记录 API Key 和候选正文；
- HTTP 非 2xx、响应非 JSON 或响应结构不合法时抛出异常，由 `RagService` 统一降级。

成功响应示例：

```json
{
  "results": [
    {"index": 0, "relevance_score": 0.93},
    {"index": 2, "relevance_score": 0.34}
  ],
  "model": "qwen3-rerank",
  "usage": {"total_tokens": 79}
}
```

响应映射要求：

- 通过 `index` 找回原 chunk，不通过返回文本匹配；
- index 必须是整数，并且不能越界或重复；
- `relevance_score` 必须能够转换为有限浮点数；
- 按 `relevance_score` 降序返回，同分时保持原候选顺序；
- 返回结果保留 chunk 原有字段，并写入 `rerank_score`；
- 不使用跨请求的绝对分数阈值，分数只用于当前候选集排序。

## 三、配置改造

在 `app/core/config.py` 增加或确认：

```python
rerank_base_url: str
rerank_api_key: str = ""
rerank_model: str = "qwen3-rerank"
rerank_timeout_seconds: int = Field(default=15, ge=1)
```

配置规则：

- `RERANK_ENABLED` 继续作为全局精排开关；
- `RERANK_BASE_URL` 单独配置，因为地址包含百炼 Workspace ID；
- `RERANK_API_KEY` 留空时复用 `MODEL_API_KEY`；
- `RERANK_MODEL` 默认使用 `qwen3-rerank`；
- `RERANK_TIMEOUT_SECONDS` 默认 15 秒；
- instruct、候选安全上限和正文截断长度保留为 Provider 内部常量；
- 精排候选数量固定为 20，最终返回数量默认 10。

`.env.example` 调整为：

```env
# 专用精排：API Key 留空时复用 MODEL_API_KEY
RERANK_ENABLED=false
RERANK_BASE_URL=https://YOUR_WORKSPACE_ID.cn-beijing.maas.aliyuncs.com/compatible-api/v1
RERANK_API_KEY=
RERANK_MODEL=qwen3-rerank
RERANK_TIMEOUT_SECONDS=15
```

删除产品链路中只服务于 LLM 重排的 Provider 类型、提示词、温度和生成参数配置。

## 四、接入生产检索链路

修改 `app/services/rag_service.py` 及实际负责检索数量控制的服务：

1. 未开启精排时，按照当前 Profile 返回结果；
2. 开启精排时，向量检索和 BM25 先参与 RRF 融合；
3. RRF 结果不能在 Top10 提前截断，而要向精排传入 Top20；
4. Qwen3-Rerank 对 Top20 候选排序并返回 Top10；
5. 精排异常时返回 RRF 原始顺序的 Top10；
6. 不修改切块、索引和多知识库融合逻辑。

推荐 Profile 行为：

| Profile | 检索与精排行为 |
|---------|----------------|
| speed | 不启用精排，最终返回 Top5 |
| balanced | 使用混合检索，最终返回 Top10 |
| quality | RRF 候选 Top20，Qwen3-Rerank 精排后返回 Top10 |

`_build_rerank_provider()` 直接构建 `Qwen3RerankProvider`。产品 API 和前端都不增加 Provider 选择器。

Qwen3 调用成功时，metadata 至少包含：

```json
{
  "enabled": true,
  "provider": "qwen3",
  "model": "qwen3-rerank",
  "top_n": 10,
  "candidate_count": 20,
  "returned_count": 10,
  "latency_ms": 320,
  "degraded": false
}
```

降级时 metadata 保持实际的 provider 和 model，设置 `degraded=true`，并保存经过脱敏的错误信息。

## 五、保留离线 LLM Baseline

产品链路不再使用 LLM 重排，但统一评测仍需要比较升级前后的效果。将旧 LLM 实现移动到只供离线评测使用的位置，例如：

```text
eval/providers/llm_rerank_baseline.py
```

约束如下：

- 公共 retrieve API 不能选择该 Provider；
- `RagService` 不能导入该 Provider；
- 只有统一评测运行器能够构建它；
- 使用与产品改造前一致的提示词和解析逻辑；
- 不额外调整提示词来提高 baseline 分数；
- 评测完成后仍可复现相同 A/B 实验。

## 六、统一精排实验配置

使用两份实验配置回答两个不同问题：

```text
eval/experiments/rerank_effect_v2.json
eval/experiments/rerank_upgrade_v2.json
```

两种实验都只保留 A、B 两组：

| 实验 | A组 baseline | B组 candidate | 唯一变量 |
|------|--------------|-----------------|----------|
| 精排效果 | RRF 原始 Top10，不精排 | Qwen3-Rerank Top10 | 精排开关和 Provider |
| 精排选型 | 原有 LLM 重排 Top10 | Qwen3-Rerank Top10 | 精排 Provider |

两种实验的初始候选都是同一份 RRF Top20，每道题每组正式执行 1 次。先运行精排效果测试，确认 Qwen3 相对不精排的变化；再运行精排选型测试，比较两种精排实现。

统一条件：

```text
dataset：eval/datasets/golden_basic_20.json
suite：basic
检索方式：已验收的混合检索
query rewrite：关闭
同义词扩展：关闭
evidence：关闭
业务并发：4
RAGAS 并发：4
warm-up：0
RAGAS telemetry：关闭
离线 Langfuse：关闭
```

`primary_metric` 使用 `context_precision`，Context Recall 作为质量护栏。正式报告统一展示：

- Context Precision；
- Context Recall；
- P95 延迟；
- 平均应用模型调用次数。

精排效果测试额外计算 nDCG@10，用于说明期望文档和章节在 Top10 中是否更靠前。该指标直接复用 Golden Set 标注，只作为诊断信息，不替代四项正式指标，也不作为统一验收门槛。不增加 MRR、HitRate、独立 Recall@K 或平均精排分数。

## 七、统一运行器对精排实验的支持

扩展现有 `scripts/run_eval.py` 和 `eval/core`，不要创建新的精排命令行脚本。

精排效果实验执行顺序：

1. 每道题只执行一次关闭精排的混合检索，保存 RRF Top20；
2. A组按 RRF 原始顺序保留 Top10；
3. B组读取同一份 Top20，调用 Qwen3-Rerank 后保留 Top10；
4. 使用四项正式指标评价两组，并使用 nDCG@10 诊断排序变化；
5. 按统一 raw 结果格式保存上下文、延迟、模型调用次数和错误；
6. 调用已有 RAGAS 评分和统一报告生成器。

精排选型实验复用相同流程和候选冻结机制，只将 A组改为离线 LLM baseline、B组设为 Qwen3-Rerank，两组分别精排并返回 Top10。

P95 使用“共享检索耗时 + 当前精排调用耗时”计算，使报告能够反映完整检索链路。平均应用模型调用次数必须统计精排调用，不能把 Qwen3-Rerank 排除在模型调用之外。

实验中的 Provider 选择只属于本地离线运行器，不能进入公开请求 Schema、前端表单或租户可配置参数。

## 八、自动化测试

新增或修改：

```text
tests/test_qwen3_rerank.py
tests/test_eval_rerank_upgrade.py
```

`tests/test_qwen3_rerank.py` 覆盖：

- 正常响应的 index、Top10 和 score 映射；
- 返回顺序与输入顺序不同；
- index 越界、重复或缺失；
- relevance_score 非数字或非有限值；
- 空 candidates 不发 HTTP 请求；
- 候选不足 10 条时返回实际数量；
- 标题和正文拼接、正文截断；
- 超时、401、429、500 和非 JSON 响应；
- 降级后保持原 RRF 顺序 Top10；
- metadata 中的 provider、model、latency 和 degraded。

`tests/test_eval_rerank_upgrade.py` 覆盖：

- 每道题只生成一份共享 Top20 候选；
- A、B 两组收到完全相同且顺序一致的候选；
- 不精排组保持 RRF 原始顺序且不产生精排模型调用；
- 两组最终最多返回 10 条；
- LLM baseline 不能被公共 retrieve API 选择；
- 原始结果能够进入现有 RAGAS 和报告流程；
- 报告以统一四项指标为正式结果，nDCG@10 只出现在精排效果诊断中；
- 遥测和离线 Langfuse 默认关闭；
- 任一组失败时报告不能虚构有效结论。

HTTP 和 LLM 单元测试全部使用 mock，不消耗真实模型额度。

## 九、清理旧测试方式

- 不新增或继续维护 `scripts/compare_rerankers.py`；
- 不创建 `eval/opt*_rerank` 专用评测目录；
- 不为精排另建人工 relevance 标注集；
- 不执行三轮重复调用和 warm-up；
- 不生成脱离统一评测体系的排序报告；
- 已有历史文件可以保留为开发过程记录，但不再作为正式效果结论。

正式结论只认统一运行器在 `eval/results/<run_id>_rerank_effect_v2/` 和 `eval/results/<run_id>_rerank_upgrade_v2/` 下生成的报告。

## 十、验收标准

- 生产链路使用“RRF Top20 → Qwen3-Rerank → Top10”；
- Qwen3 Provider 单元测试全部通过；
- 精排异常时 retrieve 主请求成功并回退到 RRF Top10；
- 调试台正常展示 Qwen3 模型、Top10 和 `rerank_score`；
- LLM baseline 只存在于离线评测代码中；
- 统一实验分别比较“不精排与 Qwen3 精排”和“LLM 重排与 Qwen3 精排”；
- 两组使用完全相同的 Top20 候选；
- 每道题每组正式执行一次；
- 统一报告使用四项正式指标，精排效果实验允许附带 nDCG@10 排序诊断，并给出明确结论；
- 不使用 Top5 或独立精排效果脚本；
- 原有 retrieve、多知识库、套餐策略和降级测试全部通过。
