# 检索精排升级测试验收

本专题需要验证三件事：Qwen3-Rerank 能否稳定接入生产检索链路、开启精排本身是否有用，以及它和原有 LLM 重排相比是否更适合作为在线能力。功能正确性使用自动化测试验证，效果和成本使用统一评测体系验证，两类结论不能混在一起。

正式效果测试不再使用精排专用脚本、ranx 或人工 relevance 数据。所有结果都来自同一套 Golden Set、统一运行入口、统一四项指标和统一报告。

## 对应测试报告

- [Qwen3精排效果报告](./报告/Qwen3精排效果报告.md)
- [LLM重排与Qwen3精排选型报告](./报告/LLM重排与Qwen3精排选型报告.md)

## 一、测试准备

准备以下环境：

- 后端服务、数据库和 Elasticsearch 正常运行；
- 电商 Golden Set 对应知识库已经完成索引；
- 评测租户可以访问该知识库；
- Embedding、LLM baseline、Qwen3-Rerank 和 RAGAS Judge 凭据可用；
- `eval/datasets/golden_basic_20.json` 已通过数据校验；
- `eval/experiments/rerank_effect_v2.json` 和 `eval/experiments/rerank_upgrade_v2.json` 已通过实验配置校验。

精排配置：

```env
RERANK_ENABLED=true
RERANK_BASE_URL=https://YOUR_WORKSPACE_ID.cn-beijing.maas.aliyuncs.com/compatible-api/v1
RERANK_API_KEY=
RERANK_MODEL=qwen3-rerank
RERANK_TIMEOUT_SECONDS=15
```

`RERANK_API_KEY` 留空时复用 `MODEL_API_KEY`。配置完成后重启后端。

## 二、工程自动化测试

运行精排 Provider 和统一评测接入测试：

```bash
python -m pytest \
  tests/test_qwen3_rerank.py \
  tests/test_eval_rerank_upgrade.py -v
```

需要覆盖：

- Qwen3 响应能够按 index 映射回原 chunk；
- relevance_score 和 Top10 顺序正确；
- 空候选不调用远程 API；
- 候选不足 10 条时返回实际数量；
- 非法 JSON、401、429、500 和超时触发降级；
- 降级后保持 RRF 原顺序 Top10；
- metadata 中的 provider、model、candidate_count、returned_count 和 latency 正确；
- 统一运行器只生成一份共享 Top20 候选；
- A、B 两组收到完全相同的候选；
- LLM baseline 不能通过公共 API 选择；
- 报告只包含统一四项正式指标。

HTTP 和 LLM 单元测试必须使用 mock，不产生真实模型费用。

运行全量回归：

```bash
python -m pytest tests -v
```

预期 retrieve、套餐策略、多知识库融合、权限和降级测试全部通过。

## 三、生产链路检查

开启 quality Profile 或在 custom Profile 中开启精排，发起一次检索。

正确链路应为：

```text
Vector + BM25
        ↓
RRF 候选 Top20
        ↓
Qwen3-Rerank
        ↓
最终 Top10
```

检查返回结果和 metadata：

- 请求成功并返回不超过 10 条结果；
- `metadata.rerank.enabled=true`；
- `metadata.rerank.provider=qwen3`；
- `metadata.rerank.model=qwen3-rerank`；
- `candidate_count=20`，候选不足时为实际数量；
- `returned_count=10`，候选不足时为实际数量；
- `top_n=10`；
- 结果正常展示 `rerank_score`；
- 前端没有新增模型选择项。

关闭精排后再次检索，预期按照当前 Profile 返回 RRF 原始顺序结果，`metadata.rerank.enabled=false`。

## 四、故障降级检查

| 场景 | 预期 |
|------|------|
| 错误 API Key | retrieve 成功，精排降级，错误信息不包含完整 Key |
| 请求超时 | 到达超时后降级，不重复调用 |
| HTTP 429 | 回退到 RRF 原顺序 Top10 |
| HTTP 500 | 回退到 RRF 原顺序 Top10 |
| results 缺失 | 拒绝错误结果并降级 |
| index 越界或重复 | 拒绝错误结果并降级 |
| relevance_score 非数字 | 拒绝错误结果并降级 |
| 非 JSON 响应 | 拒绝错误结果并降级 |

所有降级场景都应满足：

- retrieve 主请求不失败；
- 返回 RRF 原始顺序 Top10；
- `rerank_score=null`；
- `metadata.rerank.degraded=true`；
- metadata 中保留经过脱敏的错误信息。

## 五、统一实验配置检查

正式评测由两个 A/B 实验组成：

| 实验 | A组 baseline | B组 candidate | 目的 |
|------|--------------|-----------------|------|
| 精排效果 | RRF 原始 Top10，不精排 | Qwen3-Rerank Top10 | 判断开启精排是否有用 |
| 精排选型 | 原有 LLM 重排 Top10 | Qwen3-Rerank Top10 | 判断哪种精排更适合在线中台 |

每个实验内部只生成一份 RRF Top20，两组共用完全相同且顺序一致的候选。最终都返回 Top10，每道题每组只执行 1 次。两个实验分别运行和生成报告，不能把不同运行中的指标交叉拼接成一组 A/B 结果。

除当前实验声明的精排开关或 Provider 外，以下条件必须完全一致：

- Golden Set 版本；
- 知识库、文档和索引内容；
- 混合检索参数；
- Embedding 模型；
- 最终 Top10；
- 并发数和超时；
- Query Rewrite、同义词扩展和证据编排均关闭。

运行配置校验：

```bash
python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/rerank_effect_v2.json

python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/rerank_upgrade_v2.json
```

如果两组候选不一致、存在未声明配置差异或所需服务不可用，必须在正式调用前失败。

## 六、正式统一评测

先运行精排效果实验：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/rerank_effect_v2.json \
  --tenant-id <评测租户ID>
```

确认报告完整后，再运行精排选型实验：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/rerank_upgrade_v2.json \
  --tenant-id <评测租户ID>
```

运行要求：

- 使用 `golden_basic_20` 的 20 道题；
- 每道题只生成一次共享 RRF Top20；
- 每道题每组正式调用一次；
- 业务请求并发数为 4；
- RAGAS 并发数为 4；
- 不执行 warm-up 和重复稳定性测试；
- RAGAS telemetry 关闭；
- 离线 Langfuse 关闭；
- 两组原始结果分别保存，报告能够追溯到每一道题。

运行完成后应生成：

```text
eval/results/<run_id>_rerank_effect_v2/
eval/results/<run_id>_rerank_upgrade_v2/
```

每个目录都使用统一结果结构：

```text
<run_dir>/
├── baseline.raw.jsonl
├── candidate.raw.jsonl
├── shared_candidates.raw.jsonl
├── baseline.metrics.json
├── candidate.metrics.json
├── comparison.json
├── manifest.json
└── report.md
```

不再运行 `compare_rerankers.py`，不再生成另一份精排专用报告。

## 七、正式指标和结论

两份报告都以四项指标作为正式结果：

| 指标 | 本专题中的作用 |
|------|----------------|
| Context Precision | 观察最终上下文中的相关证据是否更集中 |
| Context Recall | 确认回答所需证据没有被精排丢失 |
| P95 延迟 | 比较完整检索链路的尾部延迟 |
| 平均应用模型调用次数 | 比较两种精排方式的调用成本 |

精排效果实验额外展示 nDCG@10，用于诊断期望文档和章节是否被排到更靠前的位置。它不替代 Context Precision，也不参与正式验收门槛。无需增加 MRR、HitRate、Recall@K 或平均 `rerank_score`。

判断规则：

1. Context Precision 或 Context Recall 至少一项提升；
2. 另一项质量指标不能下降；
3. P95 延迟不能超过配置中的成本上限；
4. 平均应用模型调用次数不能超过配置中的成本上限；
5. 两组请求和 RAGAS 评分必须完整成功。

报告不能只机械输出“通过”或“未通过”。如果不同质量指标方向不一致，需要结合排序诊断、延迟、调用次数、稳定性和样本规模给出有依据的综合结论，同时明确保留哪些能力、哪些退化仍需继续处理。

## 八、验收记录

两次正式实验均使用 20 道电商题、共享 RRF Top20、最终 Top10，Query Rewrite、同义词扩展和证据编排全部关闭。每个实验的 20 道检索以及 A、B 两组各 20 道 RAGAS 评分均完整成功。

### 精排效果

| 指标 | 不精排 | Qwen3 精排 | 变化 |
|------|-------:|-----------:|-----:|
| Context Precision | 0.891 | 0.880 | -1.1 个百分点 |
| Context Recall | 0.933 | 0.983 | +5.0 个百分点 |
| P95 延迟 | 1.87 秒 | 2.73 秒 | +0.86 秒 |
| 平均应用模型调用次数 | 0 次 | 1 次 | +1 次 |
| nDCG@10（诊断） | 0.835 | 0.864 | +2.9 个百分点 |

Qwen3 精排补回了必要证据，并让期望文档和章节整体排得更靠前；Context Precision 小幅下降，说明少数题存在噪声片段前移。精排有实际价值，但不能宣称所有质量指标都已提升。

### 精排选型

| 指标 | LLM 重排 | Qwen3 精排 | 变化 |
|------|---------:|-----------:|-----:|
| Context Precision | 0.943 | 0.892 | -5.1 个百分点 |
| Context Recall | 0.950 | 0.983 | +3.3 个百分点 |
| P95 延迟 | 79.7 秒 | 3.3 秒 | -76.4 秒（-95.9%） |
| 平均应用模型调用次数 | 1 次 | 1 次 | 0 次 |

LLM 重排在这 20 道题上的 Context Precision 更高，但约 80 秒的 P95、首次超时风险和生成式模型成本不适合作为中台默认在线链路。历史同项目测算中，Qwen3 每 1000 次约 0.97 元，LLM 重排约 17.04 元，该数据只用于说明成本量级，不作为本次运行账单。

综合两种测试，Qwen3 相对不精排改善了召回和整体排序，相对 LLM 重排则拥有数量级更好的速度、稳定性和成本。因此中台默认保留 Qwen3 精排；LLM 重排保留为离线质量参照或少量允许长时间等待的高价值场景。当前需要继续优化 Precision 退化题，并在扩充 Golden Set 后回归验证。

正式报告：

- `eval/results/20260822_040652_720893_rerank_effect_v2/report.md`
- `eval/results/20260821_023143_975360_rerank_upgrade_v2/report.md`

## 九、完成标准

- 工程自动化测试和全量回归通过；
- 生产检索链路使用“候选 Top20 → 精排 → Top10”；
- Qwen3 异常时能够稳定回退；
- A、B 两组使用完全相同的候选 Top20；
- 每道题每组只执行一次；
- 两种正式实验均使用统一四项指标，精排效果实验仅附带 nDCG@10 排序诊断；
- 报告具有明确、可量化的启用结论；
- 不使用 Top5 或独立精排测试脚本。
