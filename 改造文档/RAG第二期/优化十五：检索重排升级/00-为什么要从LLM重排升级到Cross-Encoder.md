# 为什么要从 LLM 重排升级到 Cross-Encoder

这里所说的 Cross-Encoder，是广义上的联合相关性模型：模型同时读取 query 和 document，直接判断两者的相关程度，而不是分别生成向量后再计算相似度。本次使用阿里云百炼提供的 `qwen3-rerank` 作为精排模型，直接替换现有 LLM 重排。

## 当前 LLM 重排是怎么工作的

当前实现位于 `app/providers/rerank/llm.py`：

```text
query + Top20 chunks
        ↓
组织成 JSON 提示词
        ↓
通用 LLM 生成 chunk_id、score、reason
        ↓
解析 JSON、按 score 排序、返回 Top5
```

这种方式实现简单，可以直接复用现有 LLM 接口，但放到稳定的在线检索链路中会出现几个问题。

### 1. 排序任务被转换成了文本生成任务

排序真正需要的只有候选下标和相关性分数，LLM 却还要生成 `chunk_id`、`reason` 和完整 JSON。模型消耗了一部分时间和 token 来生成辅助内容，这些内容并不会直接提升最终排序效果。

### 2. 排序结果依赖提示词和 JSON 解析

LLM 需要严格按照约定返回 JSON。一旦出现候选遗漏、重复 ID、字段缺失或格式错误，重排就会失败并回退到原始顺序。即使设置 `temperature=0`，模型版本和服务端策略变化仍可能影响输出稳定性。

### 3. 候选数量会明显放大输入和输出

当前最多发送 20 个候选，每个候选最多保留 1024 个字符。候选越多，提示词越长；同时 LLM 还需要为每个候选生成结果。重排耗时会同时受到输入长度和生成长度影响。

### 4. 通用 LLM 的训练目标不是检索排序

通用 LLM 擅长理解、生成和推理；精排模型则专门学习“给定一个问题，哪个文档更相关”。两者都能完成排序，但专用精排模型的任务目标、输入输出和在线调用形式与检索链路更加匹配。

## Cross-Encoder 精排有什么不同

精排模型直接接收一个 query 和一组 documents，为每个 query-document 组合计算相关性：

```text
向量检索 + BM25
        ↓
RRF 得到候选 Top20
        ↓
Cross-Encoder 联合判断 query 与每个 chunk
        ↓
按 relevance_score 返回 Top5
```

它与向量检索的分工不同：

| 阶段 | 主要目标 | 特点 |
|------|----------|------|
| 向量检索、BM25 | 从大量数据中快速找出候选 | 速度快，负责尽量找全 |
| RRF | 融合两路候选名次 | 不比较不同检索体系的原始分数 |
| Cross-Encoder 精排 | 判断候选是否真正有助于回答问题 | 计算更细，只处理少量候选 |

精排不会替代召回，而是在召回候选已经缩小到 Top20 后，把更有用的片段排到 Top5。

## 先选择本地部署还是远程调用

确定使用专用精排模型后，首先要决定模型部署方式，而不是直接比较某个具体模型。

| 对比项 | 本地部署 | 远程 API |
|--------|----------|----------|
| 基础设施 | 需要准备 CPU/GPU、模型服务和容器 | 不需要部署模型服务 |
| 上线成本 | 需要处理模型下载、显存、并发和扩缩容 | 配置地址、Key 和模型名即可调用 |
| 运维责任 | 模型加载、监控、升级和容量都由项目负责 | 模型服务由平台维护 |
| 数据安全 | 文本保留在自己的环境中 | query 和候选文本需要发送给平台 |
| 性能特点 | 同内网调用，延迟更可控 | 受公网、平台负载和限流影响 |
| 成本特点 | 有固定机器成本，调用量越大越容易摊薄 | 按量付费，低中调用量更轻量 |
| 可替换性 | 需要自己维护统一服务协议 | Provider 封装后可通过配置切换平台 |

本地部署适合数据不能出域、调用量足够大，或者团队已经具备模型推理平台的场景。当前项目的重点是升级检索效果，而不是建设 GPU 推理平台；Embedding 也已经使用远程模型服务，因此这里选择远程 API：接入成本更低，能够把精力集中在精排链路、降级策略和效果评测上。

## 远程精排方案怎么选

确定远程调用后，再比较可以直接提供精排 API 的方案：

| 远程方案 | 可用精排模型 | 优点 | 对当前项目的影响 |
|----------|--------------|------|------------------|
| 阿里云百炼 | `qwen3-rerank`、`gte-rerank-v2` | 中文和多语言支持；Qwen3 支持面向任务的 `instruct`；与现有百炼 Embedding 同一平台 | 不新增供应商，可复用账号、网络出口和费用治理 |
| 硅基流动 | Qwen3 Reranker、`bge-reranker-v2-m3` 等 | 模型选择较多，提供统一 Rerank API | 需要增加平台账号、Key、计费和故障依赖 |
| Cohere | `rerank-v3.5` | 专用 Rerank API 成熟，支持结构化文档场景 | 需要新增海外供应商，并评估网络和数据合规 |
| Jina AI | Jina Reranker 系列 | 多语言模型和统一 Rerank API | 同样需要新增供应商，并单独治理配额和稳定性 |

这些平台都能提供“query + documents → 排序结果”的能力，区别主要在模型、服务稳定性、网络、计费和现有技术栈的契合程度。没有必要仅为了精排再增加一个模型平台，因此优先选择已经在项目中使用的百炼。

相关接口可以参考[百炼文本排序 API](https://help.aliyun.com/zh/model-studio/text-rerank-api)、[硅基流动 Rerank API](https://docs.siliconflow.cn/cn/api-reference/rerank/create-rerank)、[Cohere Rerank](https://docs.cohere.com/v2/docs/rerank)和[Jina Reranker API](https://jina.ai/en-US/reranker/)。

## 为什么最终选择 Qwen3-Rerank

选择百炼后，还需要在平台提供的精排模型中确定具体模型。

| 对比项 | `qwen3-rerank` | `gte-rerank-v2` |
|--------|-----------------|-----------------|
| 任务定位 | 文本语义检索和 RAG 精排 | 文本语义检索和 RAG 精排 |
| 中文与多语言 | 支持中文及 100 多种语言 | 支持中文及 50 多种语言 |
| 单次候选上限 | 500 | 500 |
| 单文档长度 | 最高 4000 tokens | 最高 4000 tokens |
| 自定义排序指令 | 支持 `instruct` | 不支持 |
| 生命周期 | 当前推荐模型 | 官方已停止服务，不能作为新接入方案 |

最终选择 `qwen3-rerank`，主要有四个原因：

1. 项目知识库以中文内容为主，模型覆盖当前语言场景
2. 支持 `instruct`，可以明确要求优先返回“能够提供回答证据”的片段，而不只是表面语义相似
3. Top20 候选、单片段 1024 字符远低于接口上限，不需要改变当前召回参数
4. `gte-rerank-v2` 已停止服务，新的精排链路应直接采用其替代模型

百炼返回的结果包含候选 `index` 和 `relevance_score`，项目可以通过 index 直接映射回原 chunk，不再生成和解析包含 chunk ID、原因说明的 JSON 文本。

Embedding 和 Rerank 虽然使用同一个百炼平台，但接口地址不同：Qwen3-Rerank 的地址需要包含 Workspace ID，因此单独配置 `RERANK_BASE_URL`。API Key 默认复用 `MODEL_API_KEY`，只有需要独立权限或额度治理时才通过 `RERANK_API_KEY` 覆盖。精排模型通过 `RERANK_MODEL` 配置，instruct 等实现参数固定在 Provider 内部。

## 怎么证明替换是有效的

模型更专业不等于在当前数据上一定更好，因此需要保留现有 LLM 重排结果作为基线，用同一批候选进行对照。

```text
同一个 question
        ↓
关闭 rerank，冻结召回 Top20
        ↓
同一份 query + candidates
     ↙                  ↘
当前 LLM 重排       Qwen3-Rerank
     ↓ Top5             ↓ Top5
     └──── 效果、时延、稳定性对比 ────┘
```

不能让两种方案分别重新召回，否则差异可能来自 Embedding、BM25 或 RRF，而不是重排本身。

对比保留以下指标：

| 指标 | 用途 |
|------|------|
| nDCG@5 | 判断高相关片段的整体排序是否更合理 |
| MRR@5 | 判断第一条核心证据是否更靠前 |
| HitRate@5 | 判断 Top5 是否至少包含一条核心证据 |
| Recall@5 | 判断有效证据是否被保留下来 |
| P50 / P95 | 对比常见时延和尾部慢请求 |
| 成功率 / 降级率 | 对比接口与结果解析的稳定性 |
| 胜 / 平 / 负 | 找出具体提升和退化的问题 |

nDCG、MRR、HitRate 和 Recall 使用人工标注的固定候选集计算；时延只统计重排调用，不混入召回和数据库耗时。测试报告需要同时给出两种方案的真实数据，不能把“专用模型理论上更好”当成测试结论。

## 完成替换后有什么变化

这次改造直接用 Qwen3-Rerank 替换 LLM 重排，不在产品中同时保留两套排序方案。改造前后的变化如下：

| 改造前 | 改造后 |
|--------|--------|
| 通用 LLM 根据提示词生成排序 JSON | Qwen3-Rerank 直接返回候选下标和相关性分数 |
| 排序依赖提示词、生成结果和 JSON 解析 | 排序使用专用精排接口和固定响应契约 |
| LLM 同时承担理解、打分和结果生成 | 精排模型只负责 query-document 相关性判断 |
| 输入输出 token 随候选数共同增长 | 不再生成 reason 和完整排序 JSON |
| 通过配置选择 LLM 重排 | 产品链路固定使用 Qwen3-Rerank |
| 调试台展示 LLM provider 和模型 | 调试台原有位置展示 qwen3 和 qwen3-rerank |

检索主链路最终变为：

```text
Vector + BM25 → RRF Top20 → Qwen3-Rerank Top5 → 返回检索结果
```

前端的 rerank 开关、TopN 配置和结果展示继续复用，主要变化集中在后端 Provider、配置和评测脚本。Qwen3-Rerank 调用失败时，仍然回退到 RRF 原始顺序，避免精排服务异常导致整个检索请求失败。
