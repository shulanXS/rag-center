# 检索重排升级测试验收

测试需要同时验证 Qwen3-Rerank 的功能正确性、异常降级、调试台集成，以及它与 LLM 重排在相同候选集上的效果和时延差异。没有真实 A/B 数据时，只能确认接口接入成功，不能确认重排效果得到提升。

## 测试准备

准备以下环境和数据：

- 后端服务及数据库、Elasticsearch 正常运行
- 至少一个已经索引成功的知识库
- 一个允许使用 quality profile 的 API Key
- 已人工标注 relevance 的固定候选集
- 已保存的 LLM 重排基线
- 可用的百炼 Qwen3-Rerank API Key

安装测试和评测依赖：

```bash
pip install -e ".[dev,eval]"
```

配置 Qwen3-Rerank：

```env
RERANK_ENABLED=true
RERANK_BASE_URL=https://YOUR_WORKSPACE_ID.cn-beijing.maas.aliyuncs.com/compatible-api/v1
RERANK_API_KEY=
RERANK_MODEL=qwen3-rerank
# 高级配置，一般不需要调整
RERANK_TIMEOUT_SECONDS=15
```

`RERANK_API_KEY` 留空时复用 `MODEL_API_KEY`；需要独立权限时再填写单独的百炼 Key。精排模型默认使用 `RERANK_MODEL=qwen3-rerank`；instruct、候选安全上限和正文截断长度使用 Provider 内部默认值；TopN 继续由调试台已有参数控制。配置完成后重启后端。

HTTP 单测必须使用 mock，不产生真实 API 费用。

## 二、固定候选集检查

运行：

```bash
python scripts/compare_rerankers.py validate \
  --dataset eval/opt15_rerank/rerank_comparison.json
```

预期输出：

- 有效 case 数
- relevance 0、1、2、3 的候选数量
- 重复 chunk、空候选和缺失标注数量
- 候选 TopK 和结果 TopN
- 少于 30 条有效 case 时给出样本量警告

检查要求：

- 每个 case 使用固定的 query 和 candidates
- 每个候选保存 chunk_id、document_id、title、content 和原始 score
- 每个候选都有人工复核的 relevance
- 缺失 relevance 的候选不能被静默当成 0 分
- LLM 和 Qwen3 的结果必须引用相同的候选集版本

## 三、LLM 基线检查

检查：

```text
eval/opt15_rerank/rerank_llm_baseline.json
```

文件必须包含：

- 实际 LLM provider 和 model
- 数据集名称和生成时间
- 每个 case 至少 3 轮正式结果
- 每轮 Top5 chunk_id、rerank_score、latency_ms、success 和 error
- P50、P95、最大时延、成功率和降级率
- 不包含 API Key、Authorization Header 和敏感日志

基线不得修改旧提示词、候选文本和输入顺序。缺少真实 LLM 基线时，A/B 对比标记为未完成，不生成虚构数值。

## 四、Qwen3 远程 API 冒烟测试

直接调用精排接口：

```bash
RERANK_EFFECTIVE_API_KEY="${RERANK_API_KEY:-$MODEL_API_KEY}"

curl -s -X POST "${RERANK_BASE_URL}/reranks" \
  -H "Authorization: Bearer ${RERANK_EFFECTIVE_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3-rerank",
    "query": "退款后优惠券是否退回？",
    "documents": [
      "订单完成后可申请电子发票。",
      "使用优惠券的订单全额退款后，优惠券按活动规则退回账户。",
      "会员等级每月更新一次。"
    ],
    "top_n": 2,
    "instruct": "Given a question, retrieve passages that contain evidence needed to answer the question."
  }'
```

预期：

- HTTP 2xx
- `results` 为数组
- 优惠券规则对应的 index 排在第一位
- 每项包含合法 index 和 0～1 的 relevance_score
- 响应中的 model 为 `qwen3-rerank`

异常排查：

| 状态 | 检查项 |
|------|--------|
| 401 | API Key 是否有效 |
| 404 | Workspace ID、地域和 base URL 是否正确 |
| 429 | 是否触发平台限流 |
| 超时 | 网络、平台状态和 `RERANK_TIMEOUT_SECONDS` |

## 五、Qwen3 批量测试

运行：

```bash
python scripts/compare_rerankers.py run \
  --provider qwen3 \
  --dataset eval/opt15_rerank/rerank_comparison.json \
  --repeat 3 \
  --warmup 1 \
  --output eval/opt15_rerank/rerank_qwen3_result.json
```

检查结果：

- 所有 case 读取固定候选，不重新召回
- 每个 case 有 1 次 warm-up 和 3 次正式调用
- warm-up 不计入 P50 和 P95
- 每轮保存 Top5、rerank_score、latency_ms、success 和 error
- 汇总保存成功率、异常率和 Top5 一致率

远程 API 不可用时，脚本明确输出 `SKIP` 或失败原因，不生成假结果。

## 六、A/B 对比测试

生成报告：

```bash
python scripts/compare_rerankers.py compare \
  --dataset eval/opt15_rerank/rerank_comparison.json \
  --baseline eval/opt15_rerank/rerank_llm_baseline.json \
  --candidate eval/opt15_rerank/rerank_qwen3_result.json \
  --output eval/opt15_rerank/rerank_llm_vs_qwen3.md
```

报告必须包含真实数据：

| 指标 | LLM 重排 | Qwen3-Rerank | 绝对变化 | 相对变化 |
|------|----------|---------------|----------|----------|
| nDCG@5 | 实测值 | 实测值 | 实测值 | 实测值 |
| MRR@5 | 实测值 | 实测值 | 实测值 | 实测值 |
| HitRate@5 | 实测值 | 实测值 | 实测值 | 实测值 |
| Recall@5 | 实测值 | 实测值 | 实测值 | 实测值 |
| P50 | 实测值 | 实测值 | 实测值 | 实测值 |
| P95 | 实测值 | 实测值 | 实测值 | 实测值 |
| 成功率 | 实测值 | 实测值 | 实测值 | 实测值 |
| 降级率 | 实测值 | 实测值 | 实测值 | 实测值 |

指标口径：

- nDCG@5 使用 relevance 0～3 的完整等级
- MRR@5 和 HitRate@5 只将 relevance=3 视为核心命中
- Recall@5 将 relevance>=2 视为有效命中
- P50、P95 只统计 Provider 远程调用时间
- 不比较不同请求之间的平均 rerank_score

胜平负按逐题 nDCG@5 计算。报告必须列出所有负向 case，并展示 query、人工标注、LLM Top5、Qwen3 Top5 和逐题指标变化。

## 七、排序指标抽查

至少人工抽查三类固定样例。

### 1. nDCG@5

候选同时包含 relevance 3、2、1、0。把 relevance=3 的候选从第一位移动到第五位，nDCG@5 必须明显下降。

### 2. MRR@5 和 HitRate@5

Top5 只有 relevance=2、没有 relevance=3 时：

- MRR@5 为 0
- HitRate@5 为 0

### 3. Recall@5

一个问题有 3 条 relevance>=2 的候选，Top5 返回其中 2 条时，Recall@5 为 2/3。

## 八、调试台集成测试

1. 选择支持 quality profile 的 API Key
2. 选择一个已索引知识库
3. 使用 quality profile，或者在 custom profile 中开启 rerank
4. 设置 rerank top_n 为 5
5. 发起检索

预期：

- 请求成功并展示 Top5
- `metadata.rerank.enabled=true`
- `metadata.rerank.provider=qwen3`
- `metadata.rerank.model=qwen3-rerank`
- candidate_count、returned_count 和 latency_ms 与实际调用一致
- chunk 正常展示 rerank_score
- 原有 rerank 开关和 TopN 配置正常
- 页面没有新增模型选择项

关闭 rerank 后再次检索，预期使用 RRF/召回原顺序，`metadata.rerank.enabled=false`。

## 九、故障降级测试

| 场景 | 预期 |
|------|------|
| 错误 API Key | retrieve 成功，精排降级，error 不包含完整 Key |
| 请求超时 | 到达 `RERANK_TIMEOUT_SECONDS` 后降级，不自动重试 |
| HTTP 429 | 回退到原候选顺序 |
| HTTP 500 | 回退到原候选顺序 |
| results 缺失 | 拒绝错误排序并降级 |
| index 越界或重复 | 拒绝错误排序并降级 |
| relevance_score 非数字 | 拒绝错误排序并降级 |
| 非 JSON 响应 | 拒绝错误排序并降级 |

所有降级场景都应满足：

- retrieve 主请求不因精排失败而失败
- 返回原候选顺序的 TopN
- `rerank_score=null`
- `metadata.rerank.degraded=true`
- `metadata.rerank.provider=qwen3`
- metadata 中存在可定位问题的 error
