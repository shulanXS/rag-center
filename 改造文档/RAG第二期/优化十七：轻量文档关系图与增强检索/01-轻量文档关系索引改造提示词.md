# 轻量文档关系索引改造提示词

点击此处可复制本篇提示词

在当前 rag-center 项目中，升级结构化切块和索引链路。以文档、章节和 Chunk 为节点，建立父子、前后相邻和明确引用关系，形成轻量文档关系图；同时过滤低信息片段，分离原始正文与检索文本，并使用索引版本实现历史数据的无损重建、切换和回滚。

修改前先检查当前代码，以实际目录、类型和调用关系为准。复用现有 `MarkdownStructuredSplitter`、`IndexingService`、PgVector、Elasticsearch、Celery 和文档重建能力，不重复创建相同功能，不修改与索引建设无关的业务。

## 一、改造目标

- 过滤空正文、分隔符、纯标题和重复内容等低信息 Chunk
- 保留有完整语义的短句，不使用简单字数阈值批量删除
- 使用普通字段和关系表构建轻量文档关系图，不引入图数据库
- 为每个可检索 Chunk 保存章节 ID、父章节和连续顺序，前后片段根据顺序动态查询
- 解析同一知识库内明确的跨章节、跨文档引用
- 原始正文保存为 `content`，检索增强文本保存为 `retrieval_text`
- v2 向量和 BM25 都基于 `retrieval_text` 建立索引
- 旧索引和新索引同时保留，通过 `index_version` 隔离
- 新索引构建完成并验证后才切换活动版本
- 重建失败时继续使用旧索引，不影响线上检索
- 为切块质量、关系完整性和索引版本切换增加自动化测试
- 接入统一评测运行器，以 v1 为 baseline、v2 为 candidate 完成正式 A/B 验收

## 二、数据模型与数据库迁移

新增 Alembic 迁移，版本号使用项目当前最新迁移之后的下一个编号。

### 1. KnowledgeBase 活动索引版本

在 `knowledge_bases` 增加：

```python
active_index_version: str = "v1"
```

它表示普通检索请求未指定版本时使用的默认索引。业务代码不能默认取最新创建的版本，只有显式激活后才能切换；本次验收通过后将 v2 激活为默认版本。

如果 v2 已按旧规则构建且验收未通过，应先删除非活动状态的 v2，再使用修复后的切块和索引逻辑重新 rebuild v2。v1 始终保留，用于优化前后对比和回滚。

### 2. 索引版本记录

新增 `KnowledgeBaseIndexVersion` 模型和表，至少包含：

```text
id
tenant_id
kb_id
version
status
document_count
chunk_count
error_message
created_at
completed_at
activated_at
```

状态限定为：

```text
building
ready
active
failed
archived
```

约束要求：

- `(tenant_id, kb_id, version)` 唯一
- 同一个知识库最多只有一个 `active` 版本
- `ready` 之前不能激活
- `failed` 版本不能参与普通检索
- 所有查询都必须同时校验 `tenant_id` 和 `kb_id`

### 3. Chunk 索引字段

在 `chunks` 增加：

```text
index_version
retrieval_text
section_id
parent_section_id
order_index
```

字段要求：

- 完成历史数据回填后，`index_version` 非空
- 为兼容 v1 历史数据，数据库层允许 `retrieval_text`、`section_id`、`parent_section_id`、`order_index` 为空
- v2 构建时必须生成 `retrieval_text`、`section_id` 和 `order_index`；没有标题的文档使用稳定的文档根章节 ID，`parent_section_id` 允许为空
- 为 `(tenant_id, kb_id, index_version)` 建联合索引
- 为 `(document_id, index_version, order_index)` 建联合索引
- 为 `(document_id, index_version, section_id)` 建联合索引
- 为 `(document_id, index_version, order_index)` 增加唯一约束，保证同一版本内顺序不重复

以下展示、追溯和解析字段继续保存在现有 `metadata` JSONB 中：

```json
{
  "heading_path": "平台交易规则/退款规则/未发货退款",
  "chunk_type": "prose",
  "heading_level": 3,
  "source_page": 12,
  "parser": "markdown",
  "reference_texts": ["参见《促销活动与优惠券使用规则》2.4 节"]
}
```

复用项目现有的 `heading_path`，保持当前以 `/` 连接标题层级的字符串格式，不再增加含义重复的 `section_path`。`reference_texts` 保存原始引用文字。高频用于 `WHERE`、`JOIN` 和 `ORDER BY` 的字段必须是独立列；主要用于展示、调试和解析的字段放在 `metadata`。后续某个 metadata 字段确实成为高频过滤条件时，再通过迁移将它提升为独立列，不在业务代码中散落 JSON 查询表达式。

在线检索、相邻查询和父章节查询不得依赖 metadata 内部字段。第一版不为整个 `metadata` 增加通用 GIN 索引，避免为低频查询增加额外写入和存储成本。

### 4. 明确引用关系

新增 `ChunkRelation` 模型和表，至少包含：

```text
id
tenant_id
kb_id
index_version
source_chunk_id
target_chunk_id
relation_type
metadata
created_at
```

当前只支持：

```text
relation_type=reference
```

父章节通过 `section_id` 和 `parent_section_id` 定位，前后相邻关系通过 `order_index` 动态计算，不重复写入关系表。引用关系必须满足：

- 来源和目标属于同一租户
- 第一版只解析同一知识库内的引用
- 来源和目标属于同一个索引版本
- 来源和目标不能相同
- 相同来源、目标和关系类型不能重复

### 5. 历史数据迁移

历史数据只做维持查询和版本隔离所必需的处理，不把 v1 伪装成具备结构关系的 v2。

必须处理：

- 现有知识库的 `active_index_version` 设置为 `v1`
- 为每个现有知识库创建一条 `status=active` 的 v1 版本记录
- 现有 Chunk 的 `index_version` 设置为 `v1`
- 如果向量记录与 Chunk 分表保存，现有向量记录同样设置 `index_version=v1`
- Elasticsearch 映射增加 `index_version: keyword`，现有文档回填 `index_version=v1`
- 回填后核对知识库数、Chunk 数、向量数和 Elasticsearch 文档数，并抽样确认 v1 仍可查询

历史 v1 不强制补齐：

- `retrieval_text`
- `section_id`、`parent_section_id`、`order_index`
- `heading_path`、`chunk_type` 等 metadata 字段
- `ChunkRelation` 引用关系

历史 v1 不重新解析文档、不重新切块、不重新计算 Embedding，也不重建原有 BM25 内容。v1 精排文本缺少 `retrieval_text` 时回退到原有“标题 + 正文”格式；v1 不执行章节、相邻和引用扩展。

迁移按照以下顺序执行：

```text
增加可空字段和版本表
        ↓
初始化知识库 v1 版本记录
        ↓
回填数据库 Chunk 和向量记录的 index_version
        ↓
通过独立脚本回填 Elasticsearch 的 index_version
        ↓
核对三处数据数量并验证 v1 查询
        ↓
启用带 index_version 的新版查询
        ↓
开始构建 v2
```

不得在完成回填和查询验证前启用 `index_version` 强制过滤，否则历史数据不会报错，而是可能被静默过滤为空结果。Alembic 只处理数据库结构和数据库内回填，不调用远程 Embedding 或 Elasticsearch；Elasticsearch 回填使用独立、可重复执行的后台脚本或任务。

## 三、升级结构化切块

改造 `app/utils/markdown_splitter.py`，继续复用现有标题、代码块和表格识别能力。

### 1. SplitPiece 输出

每个最终 `SplitPiece` 至少包含：

```python
SplitPiece(
    text="原始正文",
    metadata={
        "heading_path": "退款规则/未发货退款",
        "section_id": "稳定的章节ID",
        "parent_section_id": "父章节ID或None",
        "chunk_type": "prose",
        "order_index": 12,
    },
)
```

`SplitPiece.metadata` 是切块器的中间输出，不等于数据库最终全部存入 JSONB。`IndexingService` 落库时，将 `section_id`、`parent_section_id` 和 `order_index` 提升到 Chunk 独立字段，将现有 `heading_path`、`chunk_type` 等描述信息保留在 Chunk 的 `metadata` 中。

`chunk_type` 限定为项目实际支持的类型，例如：

```text
prose
list
table
code
```

切块过程中可以临时标记 `reference_pointer`，但同一章节合并完成后，路标必须并入证据 Chunk，**不得作为独立落库的检索单元**。章节 ID 在同一次索引构建中必须稳定，不能因为并发执行顺序变化而改变。可以根据 `document_id + index_version + heading_path` 生成确定性 ID。

### 2. 低信息过滤

新增独立、可单测的低信息判断函数。以下内容直接过滤：

- `strip()` 后为空
- 只有 Markdown 分隔符，例如 `---`、`***`、`___`
- 只有标点、编号或特殊字符，不包含中文、字母或数字
- 去掉 Markdown 标记后正文与当前章节标题完全相同
- 只有标题，没有实际正文
- 同一文档、同一章节内完全重复的正文

示意逻辑：

```python
def is_low_information_content(content: str, heading: str | None = None) -> bool:
    normalized = normalize_content(content)
    if not normalized:
        return True
    if is_separator_only(normalized):
        return True
    if not contains_letter_number_or_cjk(normalized):
        return True
    if heading and strip_markdown(normalized) == strip_markdown(heading):
        return True
    return False
```

禁止使用 `len(content) < N` 作为直接删除条件。有完整主谓信息、时间、数字或规则结论的短句必须保留。

不完整短片段优先与同一章节的前一个或后一个内容块合并；不能安全合并时保留并标记，不得凭空补写内容。

### 3. 标题、列表和表格

- 切块的主粒度是 **Markdown 章节**，不是每个段落、列表或引用单独成块
- 同一章节内的导语、列表、表格、代码和引用路标，只要合并后不超过 `chunk_size`，必须合成一个 Chunk
- `**准入：**` 这类小标题必须与随后的列表或正文合并，不能单独落库
- 标题继续用于生成现有 `heading_path`，不单独生成可检索 Chunk
- 列表项需要携带所属章节路径
- 仅当整节或单表超过 `chunk_size` 时才继续分片；表格分片必须重复携带表头
- 表格分隔行不能成为独立 Chunk
- 代码块保持完整，超长时才按现有大小限制切分
- 章节切分后不得产生正文只有标题或水平线的片段

### 4. 前后顺序

完成过滤、去重和合并后，再按照文档中的最终顺序分配连续的 `order_index`。不新增或持久化 `prev_chunk_id`、`next_chunk_id`。

要求：

- `order_index` 在同一 `document_id + index_version` 中从固定起点连续递增
- 被过滤、去重或合并的 Chunk 不占用最终顺序号
- 前一个和后一个 Chunk 通过 `order_index - 1`、`order_index + 1` 查询
- 查询必须同时限定 `tenant_id`、`document_id` 和 `index_version`，不能跨文档、跨租户或跨索引版本
- 只允许在同一章节补相邻内容时，同时限定 `section_id`

### 5. 引用路标

正文中的引用说明，例如：

```text
> 关联规则：现金部分的到账路径参见《支付方式与资金安全规范》第 3 节“退款原路退回”。
```

路标的作用是告诉系统“真正证据在哪”，不是直接回答用户问题，也 **不是独立检索 Chunk**。

处理要求：

- 优先并入同一章节中前一条（若无则后一条）真正有证据的 Chunk
- 路标原文保留在该 Chunk 的 `content` 中，并写入 `metadata.reference_texts`
- `ChunkRelation` 的 `source_chunk_id` 必须是这条证据 Chunk，不能指向单独的路标记录
- 由 `ReferenceRelationService` 扫描 Chunk 正文解析引用并建边
- 不得为路标单独计算 Embedding，也不得把路标作为 Hybrid / 精排候选
- 检索过滤仍应丢弃万一漏网的 `chunk_type=reference_pointer`

如果整节合并后仍超过 `chunk_size`，路标跟随它所注释的那一段证据，不要单独切开。

## 四、生成检索文本

新增统一函数生成 `retrieval_text`，向量、BM25 和精排必须复用同一份生成结果：

```text
文档：{document.title}
章节：{heading_path 将 / 转换为 >}
正文：{content}
```

生成要求：

- 只有 `content` 通过低信息检查后才能生成
- 没有章节路径时省略章节行，不输出空占位
- 不拼接租户、知识库 ID、Chunk ID、检索分数和内部状态
- 不调用 LLM 生成摘要
- `content` 保持原文，不能被 `retrieval_text` 覆盖
- 并入证据 Chunk 的路标原文属于 `content` 的一部分，随该 Chunk 一起生成 `retrieval_text`

修改 `IndexingService._index_document_content()`：

```text
文档解析
    ↓
结构化切块、过滤和关系编号
    ↓
生成 retrieval_text
    ↓
对 retrieval_text 计算 Embedding
    ↓
同时写入 PgVector 和 Elasticsearch
```

Embedding 输入由 `piece.text` 改为 `retrieval_text`；保存到 Chunk 的 `content` 仍然是 `piece.text`。引用路标不得单独写入向量库和 BM25 索引。

## 五、适配 PgVector 和 Elasticsearch

### PgVector

修改 `PgVectorStore`：

- 写入新增的索引和关系字段
- 相似度查询必须支持 `index_version`
- v1 继续查询原有向量，不重新计算 Embedding
- v2 使用 `retrieval_text` 生成的新向量
- 普通查询只查询知识库的活动版本
- 评测查询允许显式指定 `ready`、`active` 或短期保留的历史版本
- 不能把多个版本的 Chunk 混在同一次候选集中

### Elasticsearch

索引映射增加：

```text
index_version: keyword
retrieval_text: text
section_id: keyword
parent_section_id: keyword
order_index: integer
metadata: object (enabled: false)
```

`metadata` 中的 `heading_path`、`chunk_type` 等字段保留在 `_source` 并随结果返回，但不建立子字段索引，避免动态字段膨胀。第一版不使用 Elasticsearch 查询 metadata 内部字段。

v1 继续查询原有 BM25 字段，v2 改为检索 `retrieval_text`；两者都返回原始 `content`。所有新增、查询和删除操作必须带上 `tenant_id`、`kb_id` 和 `index_version`。

普通删除文档时清理该文档的全部索引版本；对活动版本执行单文档重建时，只替换活动版本的 Chunk，不得误删观察期内保留的历史版本。

## 六、解析明确引用关系

引用关系在一个索引版本的全部文档完成切块后，通过第二阶段任务统一解析。

第一版只处理可以确定目标的显式形式，例如：

```text
参见“退款规则”章节
参见《促销活动与优惠券使用规则》2.4 节
[优惠券规则](促销活动与优惠券使用规则.md#退款处理)
```

解析步骤：

```text
识别引用文本
    ↓
在同一知识库、同一索引版本中匹配文档标题
    ↓
匹配章节路径或标题
    ↓
定位目标章节的第一个有效 Chunk
    ↓
写入 ChunkRelation
```

要求：

- 只接受唯一、确定的目标
- 多个候选同名时标记为 unresolved，不随意选择
- 找不到目标时记录原始引用和失败原因，不创建错误关系
- 不用语义相似度或 LLM 猜测引用目标
- 不创建跨租户关系
- 不递归解析引用链

## 七、实现版本化索引重建

当前 `queue_document_reindex()` 会先删除旧 Chunk，这种方式不能用于新旧索引对比。新增知识库级版本化重建流程，不替换现有单文档重建接口的用途。

建议增加：

```text
POST /knowledge-bases/{kb_id}/index-versions/rebuild
GET  /knowledge-bases/{kb_id}/index-versions
POST /knowledge-bases/{kb_id}/index-versions/{version}/activate
DELETE /knowledge-bases/{kb_id}/index-versions/{version}
```

处理流程：

```text
创建 building 版本
        ↓
Celery 按知识库现有文档构建新 Chunk、向量和 BM25
        ↓
校验连续顺序并解析明确引用
        ↓
核对文档数、Chunk 数和双索引写入结果
        ↓
成功标记 ready，失败标记 failed
        ↓
人工或验收程序激活 ready 版本
        ↓
事务内切换 active_index_version
```

重建要求：

- 重建期间线上继续查询原活动版本
- 不要求历史文档重新上传，优先使用已保存的 `Document.content`
- 原内容为空时才读取源文件重新解析
- 同一知识库同一时间只能有一个 `building` 版本
- 为避免快照不一致，重建期间阻止该知识库的上传、删除和单文档重建，并返回明确提示
- 任一文档、Embedding、PgVector 或 Elasticsearch 写入失败时，整个版本不能标记 `ready`
- 激活必须使用数据库事务，切换失败时继续保留原活动版本
- 删除版本前确认它不是活动版本
- 旧版本观察期结束后才能清理

普通检索默认读取 `active_index_version`。`RetrieveRequest` 可以通过 `index_version` 显式选择同一知识库的可查询版本，后端必须校验该版本属于当前租户和知识库，且状态为 active、ready 或 archived；一次请求内不得混合版本。

## 八、索引管理与日志

复用现有知识库管理页面展示索引版本和版本内文档，不新增独立前端页面。后端接口补充：

- 当前活动索引版本
- 版本状态和创建时间
- 文档数和 Chunk 数
- 构建失败原因
- 是否允许激活、回滚和清理

知识库展开后按 `v2 → 文档`、`v1 → 文档` 的层级展示。每个版本显示状态、文档数和 Chunk 数，并标明当前默认版本；历史版本文档只读，避免把逻辑文档删除误解为只删除某个版本。

日志至少记录：

```text
tenant_id
kb_id
index_version
document_id
chunk_count
relation_count
cost_ms
status
```

日志不得记录 Embedding API Key、原始授权头和完整敏感文档内容。

## 十、改造约束

- 不引入 Neo4j 或其他图数据库
- 不抽取实体、事件和语义关系
- 不使用 LLM 生成 Chunk 上下文或猜测引用目标
- 不递归遍历引用关系
- 不修改向量、BM25、RRF 和精排算法本身
- 不在新索引 ready 前切换线上流量
- 不原地覆盖或删除仍在使用的旧索引
- 不通过简单最小字数过滤有效短证据
- 不把 `retrieval_text` 当作原文返回给用户
- 不新增大量环境变量，关系规则和安全上限优先使用代码常量

## 十一、验收标准

- 历史知识库、Chunk、向量记录和 Elasticsearch 文档全部正确标记为 v1
- v1 迁移前后数据数量和固定查询结果一致，没有触发重新切块或 Embedding
- v1 的结构关系字段允许为空，并且不会执行上下文扩展
- 低信息内容不会生成可检索 Chunk
- 引用路标不会进入 Vector、BM25 和 TopK 检索结果
- 有效短句、列表、表格和代码块保留正确
- 每个 Chunk 的章节路径和顺序可追溯，前后片段可以由顺序稳定推导
- 明确引用只在目标唯一时建立关系
- v2 Embedding 和 BM25 都使用 `retrieval_text`
- 普通检索严格限定活动索引版本
- v1 和 v2 可以独立查询，不会混合候选
- v2 构建失败不影响 v1 线上检索
- ready 版本可以切换和回滚
- 历史版本在观察期结束前不会被删除
- 两个新增测试文件全部通过
- 原有文档上传、解析、检索和多租户测试全部通过
- v2 能通过统一实验配置显式查询，评测运行器不会把 v1、v2 候选混在一起
- 正式效果报告使用统一 Golden Set、统一运行入口和四项公共指标，不新增索引专项指标体系
- v2 在统一报告给出明确启用结论前保持 ready，不自动替换活动版本
