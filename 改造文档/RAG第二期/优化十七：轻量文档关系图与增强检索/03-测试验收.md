# 轻量文档关系图与增强检索测试验收

本专题需要验证两件事：轻量文档关系图在工程上是否正确、v2 索引是否让最终检索上下文变得更好。工程正确性使用自动化测试和数据抽查验证，效果与成本使用统一评测体系验证，两类结论分别记录。

正式效果测试不再使用轻量图谱专用数据集、独立对比脚本、ranx 或一组新的自定义正式指标。测试继续使用统一 Golden Set、统一运行入口、四项正式指标和统一报告。

## 对应测试报告

- [v1与v2轻量图谱增强检索对比报告](./报告/v1与v2轻量图谱增强检索对比报告.md)

## 一、测试准备

开始验收前确认：

- PostgreSQL、Elasticsearch、Redis 和 Celery Worker正常运行；
- 数据库已经执行最新 Alembic迁移；
- 电商知识库的原始文档保持不变；
- 同一知识库同时保留可查询的v1和ready状态的v2；
- v1、v2使用相同的Embedding模型；
- Embedding和RAGAS Judge凭据可用；Qwen3-Rerank与LLM凭据只在后续精排复测时需要；
- v2尚未通过正式验收时，不提前删除v1；
- RAGAS telemetry关闭，离线评测不写入Langfuse。

如果现有v2是使用旧逻辑构建的，应删除这个未激活版本，再从相同原始文档重新构建v2。不能在旧v2上局部补字段后直接作为正式实验数据。

## 二、工程自动化测试

先运行与本专题直接相关的测试：

```bash
pytest \
  tests/test_contextual_chunking.py \
  tests/test_index_versioning.py \
  tests/test_context_retrieval.py \
  -v
```

### 1. 切块与关系索引

`test_contextual_chunking.py`至少覆盖：

- 空正文、分隔符、纯标点和纯标题不会生成候选；
- 有完整语义的短句不会因为字数少被删除；
- 标题路径、章节ID、父章节和顺序正确；
- 表格分片携带表头，列表项保留所属章节；
- `content`保存原文，`retrieval_text`保存标题、章节和正文；
- v2 Embedding使用`retrieval_text`；
- 明确引用只有目标唯一时才建立关系；
- 引用路标并入证据Chunk，不作为独立检索候选；
- 同一章节内能够容纳的导语、列表和表格不会被无意义拆散。

### 2. 索引版本

`test_index_versioning.py`至少覆盖：

- 历史知识库、Chunk和Elasticsearch文档正确标记为v1；
- v1不重新切块、不重新计算Embedding；
- 构建v2时v1仍然可以查询；
- 普通请求只查询活动版本，显式请求只查询指定版本；
- v1、v2候选不会混合；
- failed版本不能激活，ready版本可以原子切换；
- 切回v1后查询恢复；
- 活动版本不能删除；
- 不同租户和知识库严格隔离。

### 3. 增强检索

`test_context_retrieval.py`至少覆盖：

- v1不执行图谱注入和上下文扩展；
- v2在精排前执行图谱候选注入；
- v2精排使用`retrieval_text`；
- v2精排后执行一跳上下文扩展；
- previous、next、same_section和reference关系正确；
- 图谱不会递归扩展；
- 注入和扩展遵守数量、字符和权限限制；
- 扩展不会改变Anchor的排名和分数；
- 关系查询失败时仍能返回原始Hybrid候选；
- metadata能追溯索引版本、注入数量、扩展来源和耗时。

专题测试通过后运行全量回归：

```bash
pytest tests -v
```

所有外部服务在自动化测试中使用mock，不产生真实模型费用。

## 三、v1兼容性检查

v1是正式A/B实验的baseline，也是v2上线前的回滚版本。迁移后必须确认：

```text
knowledge_bases.active_index_version = v1
数据库历史Chunk的index_version = v1
Elasticsearch历史文档的index_version = v1
v1的原向量和原BM25内容没有重建
```

选取一组固定查询，对比迁移前后的v1结果：

- 返回的Chunk集合保持一致；
- 数据库Chunk数、向量数和Elasticsearch文档数保持一致；
- 没有新增Embedding调用；
- `retrieval_text`、章节和关系字段为空时仍能正常检索；
- v1不执行图谱注入、相邻补充和引用扩展。

如果v1迁移前后结果不一致，应先修复兼容问题，不能继续构建正式效果结论。

## 四、v2数据抽查

从v2随机抽查至少20个Chunk，覆盖正文、列表、表格和代码块。

每个Chunk检查：

```text
index_version
content
retrieval_text
section_id
parent_section_id
order_index
metadata.heading_path
metadata.chunk_type
```

抽查要求：

- `content`是原始证据；
- `retrieval_text`包含文档标题、章节路径和正文；
- `retrieval_text`不包含租户ID、Chunk ID和检索分数；
- 同一文档内的`order_index`唯一且连续；
- 表格和列表离开原始页面后仍能理解；
- 空正文、分隔符、纯标题和独立引用路标数量为0；
- 明确引用的来源和目标属于同一租户、知识库和索引版本。

再抽查至少10条明确引用，确认唯一目标可以解析，同名或缺失目标不会建立错误关系。

## 五、统一A/B实验

正式效果实验比较完整检索链路，不拆成多个专项脚本。

```text
A组：v1索引 + Hybrid + RRF → Top10
B组：v2索引 + Hybrid + RRF + 图谱注入 + 上下文扩展 → Top10
```

两组固定条件如下：

| 条件 | A组 | B组 |
|------|-----|-----|
| 原始知识库文档 | 相同 | 相同 |
| Golden Set | `golden_basic_20_v2` | `golden_basic_20_v2` |
| 索引版本 | v1 | v2 |
| 检索方式 | Hybrid + RRF | Hybrid + RRF |
| RRF初始候选 | Top20 | Top20 |
| 图谱候选注入 | 不执行 | 自动执行 |
| 精排 | 关闭 | 关闭 |
| 最终返回 | Top10 | Top10 |
| 上下文扩展 | 不执行 | 自动执行 |
| Query Rewrite | 关闭 | 关闭 |
| 同义词扩展 | 关闭 | 关闭 |
| 证据编排 | 关闭 | 关闭 |

v1和v2的Chunk边界、向量与BM25内容不同，因此两组必须分别检索，不能冻结共同候选。除了索引版本以及由版本自动触发的轻量图谱能力外，其他配置保持一致。

本实验验证的是整个优化包是否有效，不用于单独归因切块、检索文本、图谱注入或上下文扩展中的某一个步骤。如果正式指标不理想，再根据逐题原始结果和图谱诊断字段定位原因，不在主实验中增加第三组或第四组。

## 七、RAGAS上下文口径

RAGAS评价实际交给下游回答层的证据：

- A组使用最终Top10的原始`content`；
- B组有`context.content`时使用扩展后的上下文；
- B组没有发生扩展时使用原始`content`；
- 不把`retrieval_text`、Chunk ID、关系名称和检索分数作为回答证据；
- 同一补充内容只计算一次，避免重复Chunk人为降低Precision。

这个口径可以同时反映v2是否找到了更多有效证据，以及补充内容是否引入了过多噪声。

## 八、执行顺序

每道题每组只执行一次。检索请求和RAGAS Judge都使用默认并发4，不做warm-up，也不通过重复调用测试稳定性。

先校验实验配置：

```bash
python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/context_graph_upgrade.json
```

校验通过后运行正式实验：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/context_graph_upgrade.json \
  --tenant-id <评测租户ID>
```

`run`会依次完成两组检索、RAGAS评分和报告生成，不需要再重复执行三个命令。只有RAGAS评分中断且原始检索结果完整时，才补充评分：

```bash
python scripts/run_eval.py score \
  --run-dir eval/results/实际运行目录 \
  --missing-only
```

只有修改报告样式或结论生成逻辑时，才基于已有指标重新生成报告：

```bash
python scripts/run_eval.py report \
  --run-dir eval/results/实际运行目录
```

不要同时启动多份实验。报告生成后先检查两组是否各有20道成功结果、索引版本是否正确，再查看结论并决定是否激活v2或继续诊断。

## 九、正式指标

报告只使用四项正式指标：

| 指标 | 本专题中的作用 |
|------|----------------|
| Context Recall | 判断v2是否补回回答所需的条件、结论和关联证据 |
| Context Precision | 判断图谱注入和上下文扩展是否带来过多无关内容 |
| P95延迟 | 判断关系查询和上下文扩展的性能代价 |
| 平均模型调用次数 | 确认轻量图谱没有引入额外模型调用，两组预期均为0 |

不加入ranx、nDCG、MRR、HitRate、独立Recall@K、引用命中率或上下文完整性总分。

逐题结果额外记录以下诊断字段：

```text
graph_injected_count
supplemental_chunk_count
graph_injection_latency_ms
context_expansion_latency_ms
```

报告可以补充“图谱为多少道题新增了候选”，但它只是解释信息。例如图谱注入了很多候选而Recall没有提升，说明新增内容没有转化为有效证据，不能据此宣布优化成功。

## 十、验收门槛

建议使用以下统一门槛：

1. Context Recall至少提升0.1个百分点；
2. Context Precision最多下降2个百分点；
3. P95延迟增幅不超过30%；
4. 两组平均应用模型调用次数都必须为0；
5. 两组检索请求和RAGAS评分全部成功；
6. 不允许出现跨租户、跨未授权知识库或混合索引版本的数据。

如果Recall没有提升，即使图谱成功注入了候选，也不能认定效果优化有效。如果Recall提升但Precision或延迟超过门槛，报告必须说明收益与代价，并给出是否启用的明确建议。

## 十一、统一报告

统一报告至少包含：

1. 一句话结论；
2. A、B两组配置；
3. Golden Set和知识库语料版本；
4. Context Recall、Context Precision、P95延迟和平均模型调用次数；
5. 每项指标的绝对变化和相对变化；
6. 改善最多和退化最多的题目；
7. 图谱影响题目数量等诊断信息；
8. 是否建议激活v2；
9. 原始结果和配置快照位置。

结论不能只写“指标有升有降”。应采用明确表述，例如：

```text
v2将Context Recall从0.82提升到0.90，提升8个百分点；
Context Precision下降1个百分点，处于2个百分点护栏内；
P95延迟增加12%，模型调用次数不变。
综合判断轻量图谱增强有效，建议激活v2并保留v1用于观察期回滚。
```

实际报告必须使用真实结果，不能在测试前预填“优化有效”。

## 十二、Qwen3精排复测

v2主实验完成后，需要单独复测Qwen3-Rerank在v2上的质量表现，用来确认更完整的标题、章节和关系上下文是否缩小了它与LLM重排的差距。

这是一份独立的A/B报告，不与v1、v2主实验混在一起：

```text
A组：v2图谱注入后的共同Top20 → LLM重排 → Top10
B组：同一份共同Top20 → Qwen3-Rerank → Top10
```

独立实验配置为：

```text
eval/experiments/rerank_upgrade_v2.json
```

复测继续使用统一Golden Set、统一运行入口和四项正式指标。两组必须读取同一份v2候选，不能分别重新召回；每道题每组仍然只调用一次。v2复测结果可以和已经保存的v1精排报告并列说明，但不能把两个不同索引上的分数合并成同一组A/B数据。

执行顺序是：先完成并检查v1与v2主报告，确认没有索引或关系错误，再运行v2精排复测。不要一次性启动两份实验。

运行命令：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/rerank_upgrade_v2.json \
  --tenant-id <评测租户ID>
```

## 十三、调试台和异常验收

通过调试台分别查询v1、v2，至少检查：

- 条件和结论位于相邻Chunk；
- 表格数据需要表头才能理解；
- 列表项需要章节标题才能理解；
- 当前Chunk明确引用其他章节或文档；
- 当前Chunk已经完整，不需要额外扩展。

预期结果：

- v1只返回v1 Chunk，v2只返回v2 Chunk；
- 原始命中、图谱注入和上下文补充分开展示；
- 精排后的Anchor排名不被上下文扩展改变；
- 不会加载整个父章节或递归扩展引用；
- 扩展失败时仍能显示原始结果；
- v1缺少新增字段时页面仍能正常展示。

异常场景必须满足：

| 场景 | 预期 |
|------|------|
| v2构建失败 | v1继续提供服务，v2不可激活 |
| Elasticsearch v2写入失败 | v2标记failed，不保留可激活的半成品 |
| 引用目标不存在 | 不注入，记录unresolved |
| 相邻Chunk缺失 | 返回原始候选并标记降级 |
| 关系跨租户 | 拒绝注入并记录安全日志 |
| 上下文超过预算 | 按优先级停止补充，不删除Anchor |
| 激活事务失败 | 活动版本保持不变 |

## 十四、验收完成标准

满足以下条件后，本专题才算验收完成：

- 三个专题自动化测试文件通过；
- 全量回归测试通过；
- v1兼容性检查通过；
- v2结构字段、低信息过滤和明确引用抽查通过；
- 统一运行器能够严格区分v1、v2；
- A、B两组各执行20道题并完成全部RAGAS评分；
- 统一报告生成四项正式指标和明确结论；
- 报告不使用ranx或另一套专项质量指标；
- v2达到门槛后才切换活动版本；
- v1在观察期内继续保留，可以随时回滚；
- v2上的精排复测在主报告确认后单独执行。
