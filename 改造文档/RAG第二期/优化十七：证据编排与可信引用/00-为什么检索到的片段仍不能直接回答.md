# 为什么检索到的片段仍不能直接回答

RAG 检索通常返回按相关性排列的 TopK Chunk。每条结果都有正文、文档来源、检索分数和可选上下文，但它们仍然只是一个片段列表。

当问题只需要一条证据时，直接使用 TopK 往往已经足够；当问题包含多个要点、需要多篇文档共同支撑时，下游还要自行判断：

- 哪些片段能够直接支撑答案
- 哪些片段只是主题相关
- 每个问题要点应该使用哪条证据
- 当前证据是否已经覆盖完整
- 回答中的引用应该指向哪个 Chunk

证据编排要解决的就是这一层问题。

## TopK 列表缺少什么

例如用户提问：

```text
积分抵扣订单退款后，积分和现金分别怎么退？
```

检索候选可能包含：

```text
会员积分退回规则
现金原路退回规则
优惠券退回规则
普通售后规则
支付安全说明
```

这些片段按相关性排序后，下游仍要识别两个必要要点：

```text
积分如何退回
现金如何退回
```

只要其中一个要点对应的证据没有进入最终 TopK，答案就可能不完整。简单扩大 TopK 可以提高覆盖概率，但也会引入更多噪声、重复内容和 Token 成本，仍然不能说明每条证据支撑哪个要点。

## 证据包是什么

证据包是整次检索响应中的一个可选对象。它不替代 `retrieved_chunks`，也不生成最终答案。

```json
{
  "retrieved_chunks": [
    {
      "chunk_id": "chunk-member",
      "title": "会员体系与积分权益说明.md",
      "content": "退款后，已使用积分按规则退回账户。"
    }
  ],
  "evidence_pack": {
    "status": "complete",
    "missing_aspects": [],
    "groups": [
      {
        "aspect": "积分退回",
        "evidence": [
          {"evidence_id": "E1", "role": "core"}
        ],
        "covered": true
      },
      {
        "aspect": "现金退回",
        "evidence": [
          {"evidence_id": "E2", "role": "core"}
        ],
        "covered": true
      }
    ],
    "items": [
      {
        "evidence_id": "E1",
        "chunk_id": "chunk-member",
        "document_id": "document-member",
        "title": "会员体系与积分权益说明.md",
        "heading_path": "退款规则/积分退回",
        "index_version": "v2",
        "content": "退款后，已使用积分按规则退回账户。",
        "source": "hybrid",
        "retrieved_rank": 1
      },
      {
        "evidence_id": "E2",
        "chunk_id": "chunk-payment",
        "document_id": "document-payment",
        "title": "支付方式与资金安全规范.md",
        "heading_path": "退款到账/原路退回",
        "index_version": "v2",
        "content": "现金支付部分按原支付渠道退回。",
        "source": "graph_injection",
        "retrieved_rank": null
      }
    ]
  }
}
```

外层只有一个 `evidence_pack`，内部可以包含多条 EvidenceItem。证据数量不必等于 TopK：无效片段可以不选，必要证据也可以来自最终 TopK 之外的候选池。

## 证据包做哪些事情

### 1. 识别必要要点

把问题拆成回答时必须覆盖的最少要点，不展开成复杂推理步骤。

### 2. 选择证据

只选择能够直接支撑要点，或提供必要条件、范围和补充说明的 Chunk。主题相似但不能支撑答案的内容不进入证据包。

### 3. 建立多对多关系

同一个 Chunk 可能同时支撑多个要点，因此要点和证据不是固定的一对一关系。`role` 保存在要点与证据的关联上：

```text
core        直接回答当前要点
supporting  提供必要条件、范围或补充说明
```

### 4. 判断完整性

```text
complete  所有必要要点都有核心证据
partial   只覆盖部分必要要点
missing   没有足以支撑回答的核心证据
```

缺少的要点写入 `missing_aspects`，由下游决定部分回答、拒答或采用其他处理方式。

### 5. 提供可核验引用

每条证据保留：

```text
evidence_id
chunk_id
document_id
title
heading_path
index_version
content
```

下游可以在回答中使用 `[E1]`、`[E2]`，并通过 `chunk_id` 回查原始证据。最终引用样式仍由业务方决定。

## 为什么不直接返回生成好的答案

rag-center 是检索中台。不同业务对答案风格、Prompt、引用样式、合规要求和拒答策略可能完全不同。

因此证据编排只提供结构化材料：

```text
问题要点
证据编号
原始证据
来源定位
完整性状态
```

它不输出答案正文，不替业务解释规则，也不让模型生成候选中不存在的事实。

## 为什么做成可选能力

搜索列表、检索调试和相似内容推荐只需要原始 Chunk；带引用问答、多文档问答和完整性判断才需要证据包。

请求通过独立参数控制：

```json
{
  "evidence_options": {
    "enabled": true,
    "max_items": 8
  }
}
```

开启证据编排只能新增数据，不能改变原有 `retrieved_chunks` 的数量、顺序、分数和上下文。

## 这次改造不做什么

- 不生成最终答案
- 不自动继续检索
- 不执行多轮或多跳搜索
- 不修改原检索结果
- 不把 TopK 外证据插入 `retrieved_chunks`
- 不判断文档权威性
- 不自动解决不同文档之间的规则冲突
- 不持久化单次请求的 E 编号

## 完成改造后的返回形式

```text
原有返回：
retrieved_chunks + metadata

新增后：
retrieved_chunks + evidence_pack + metadata
```

`retrieved_chunks` 继续服务所有检索场景，`evidence_pack` 为需要结构化证据和可信引用的业务提供额外视图。
