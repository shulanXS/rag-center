# 证据编排与可信引用测试验收

主测试只验证一件事：在候选和排序结果不变的情况下，`evidence_pack` 能否从固定候选池筛出更准确、更精简且可回溯的证据材料。

使用 5 个固定挑战 Case，每题只运行一轮，不做预热和稳定性重复测试，不把最终答案质量混入本专题。

## 测试准备

准备：

- 已保存的 5 个固定挑战问题及候选 Top10
- 已保存的固定 TopK 排序结果
- TopK 已有的 `context.sources`
- 可用的证据编排 LLM
- 每题人工复核的 2～3 个必要要点和可接受证据 Chunk

评测文件：

```text
eval/opt17_evidence/
├── evidence_dataset.json
├── evidence_pack_comparison.json
└── evidence_pack_comparison.md
```

报告必须由真实脚本运行生成。模型不可用、标注未完成或调用失败时记录失败原因，不生成虚构数据。

## 一、自动化测试

运行：

```bash
pytest tests/test_evidence_orchestration.py -v
pytest tests -v
```

至少覆盖：

- evidence 能够独立开启和关闭
- evidence 关闭时不调用 LLM
- 开启 evidence 前后 `retrieved_chunks` 的 ID、顺序、分数和 context 完全一致
- 最终 TopK、context sources 和 TopK 外候选正确进入证据候选
- TopK 外证据可以进入 evidence_pack，但不能插入 `retrieved_chunks`
- 同一个 EvidenceItem 可以支撑多个 aspect
- EvidenceItem 的正文和来源字段来自原始 Chunk
- index 越界、非法 role、重复引用和超出预算时拒绝结果
- 每个 covered aspect 至少有一条 core 证据
- 输出预算裁剪后重新计算 groups、missing_aspects 和 status
- 选中 Chunk 按 tenant、kb 和 index_version 从仓储层重新加载
- LLM 日志不记录问题和候选正文
- LLM 超时、429、500 和非法 JSON 时原 retrieve 正常返回
- 降级时 `evidence_pack=null`，metadata 记录错误和耗时
- profile、全局开关和套餐限制正确

单元测试使用 Fake LLM 或 mock，不产生真实调用费用。

## 二、固定评测数据

新增：

```text
scripts/compare_evidence_packs.py
```

生成 5 题挑战数据集：

```bash
python scripts/compare_evidence_packs.py prepare-challenge \
  --output eval/opt17_evidence/evidence_dataset.json
```

`prepare-challenge` 不重新检索。它从已有冻结候选和 TopK 中固定 5 个多要点问题，并保存：

- question 和 ground_truth
- 冻结候选 Top10
- 固定 TopK Chunk ID
- TopK Anchor 的 context sources
- TopK + context 去重后的基线材料 ID
- 候选正文、来源和 relevance
- 数据来源和生成时间

示例：

```json
{
  "id": "member_points_refund",
  "question": "积分抵扣订单退款后，积分和现金分别怎么退？",
  "ground_truth": "积分按规则退回账户，现金按原支付渠道退回。",
  "baseline_topk_chunk_ids": ["实际TopK ID"],
  "baseline_context_sources": [
    {
      "chunk_id": "实际补充ID",
      "relation": "reference",
      "document_id": "实际Document ID",
      "title": "实际标题",
      "content": "实际正文"
    }
  ],
  "baseline_material_chunk_ids": [
    "TopK与context sources去重后的ID"
  ],
  "candidates": [
    {
      "chunk_id": "实际候选ID",
      "document_id": "实际Document ID",
      "title": "实际标题",
      "content": "实际正文",
      "relevance": 3
    }
  ],
  "required_aspects": [
    {
      "aspect": "积分退回",
      "acceptable_chunk_ids": ["实际证据ID"]
    },
    {
      "aspect": "现金退回",
      "acceptable_chunk_ids": ["实际证据ID"]
    }
  ]
}
```

### 标注要求

`required_aspects` 定义回答必须覆盖的要点，`acceptable_chunk_ids` 定义能够支撑该要点的候选。

不能按 relevance 阈值自动生成要点。每个要点必须对应问题和 ground truth 中实际需要回答的内容；同一个要点存在多条等价证据时，命中任意一条即可。

人工标注时不展示 baseline 排名和 evidence_pack 结果。复核后保存标注 SHA-256，运行阶段不允许修改。

校验：

```bash
python scripts/compare_evidence_packs.py validate \
  --dataset eval/opt17_evidence/evidence_dataset.json
```

检查：

- Case、候选和固定 TopK 完整
- context source 正文完整
- 每题至少有一个 required aspect
- acceptable Chunk 存在于候选或 context sources
- required aspect 没有重复和空值
- 人工复核状态为 `reviewed`

## 三、主效果对比

两组使用完全相同的问题、候选、TopK、context 和人工标注：

```text
baseline_topk_context
    固定 TopK Anchor + 已有 context sources

evidence_pack
    TopK + context sources + TopK 外基础候选
```

正式运行：

```bash
python scripts/compare_evidence_packs.py run \
  --dataset eval/opt17_evidence/evidence_dataset.json \
  --repeat 1 \
  --warmup 0 \
  --output eval/opt17_evidence/evidence_pack_comparison.json
```

本测试共进行 5 次真实 LLM 调用。每题保存：

- Provider 和 model
- Prompt SHA-256 和运行参数
- 模型结构化输出
- EvidenceItem Chunk ID
- groups、status 和 missing_aspects
- latency_ms
- Token usage
- success、degraded 和 error

## 四、指标口径

### Required Aspect Coverage

```text
有核心证据支持的 required aspect 数 / required aspect 总数
```

证据 `chunk_id` 命中该要点任意一个 `acceptable_chunk_id` 即算覆盖。

### Complete Case Rate

```text
全部 required aspects 均覆盖的 Case 数 / 总 Case 数
```

### Evidence Precision

```text
至少支撑一个 required aspect 的 EvidenceItem 数 / EvidenceItem 总数
```

主题相关但不能支撑答案的证据计为无效。

### Status Accuracy

人工标注计算真实状态：

```text
complete  全部要点覆盖
partial   覆盖部分要点
missing   没有要点得到核心证据支持
```

再与 `evidence_pack.status` 比较。

### 工程指标

- average_evidence_count
- average_evidence_chars
- P50 / P95 latency
- success_rate / degraded_rate
- input、output 和 total tokens
- 单次平均理论成本
- citation_traceability_rate

## 五、生成证据包测试报告

```bash
python scripts/compare_evidence_packs.py compare \
  --input eval/opt17_evidence/evidence_pack_comparison.json \
  --output eval/opt17_evidence/evidence_pack_comparison.md
```

报告至少包含：

- 测试时间、Case 数和人工复核状态
- 候选数、TopK、context source 数和证据预算
- Provider、model 和 Prompt SHA-256
- baseline 与 evidence_pack 的主指标
- 时延、Token 和成本观察值
- 逐题结果和所有退化 Case
- TopK 外证据带来的实际增益
- 测试限制和结论

所有汇总值必须能够追溯到 JSON 中的逐题、逐轮结果。

## 六、建议验收门槛

主效果：

- Evidence Precision 达到 80% 以上
- 平均证据字符数低于 baseline
- 每条证据引用回溯率达到 100%
- 5 个 Case 调用成功率达到 100%

工程要求：

- 每条证据都来自固定候选或 context sources
- 开启 evidence 前后 `retrieved_chunks` 完全一致
- 没有跨租户、跨未授权知识库或混入其他索引版本
- 平均证据字符数不高于 baseline 去重材料总字符数
- Required Aspect Coverage、Complete Case Rate、TopK 外缺口修复、时延和 Status Accuracy 如实记录为观察项
- 降级不影响原 retrieve 返回

本轮结论只用于证明证据筛选、材料压缩和可信引用有效；如果没有修复 TopK 外缺口，报告必须明确说明，不能把压缩收益解释为覆盖收益。

## 七、调试台检查

关闭 evidence：

- 只展示原 `retrieved_chunks`
- `evidence_pack=null`
- metadata 显示 disabled

开启 evidence：

- 原 `retrieved_chunks` 不变
- 页面额外展示整次请求的证据包
- 正确展示 status、missing_aspects 和分组
- 每条证据展示 E 编号、角色、文档、章节和正文
- 能区分最终 TopK 与 TopK 外证据
- 降级时仍能查看原检索结果
