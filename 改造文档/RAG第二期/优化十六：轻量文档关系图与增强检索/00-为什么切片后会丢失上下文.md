# 为什么切片后会丢失上下文

RAG 需要先把长文档切成较小的 Chunk，才能进行向量检索、BM25 和精排。Chunk 越小，通常越容易定位具体内容；但切片也会把原本连续的章节、表格、列表和引用关系拆开，导致系统虽然命中了相关片段，却拿不到完整证据。

这类问题不能只靠增加 TopK 或更换精排模型解决。检索系统需要保留文档结构，让小 Chunk 负责准确命中，再根据层级和关系补回必要上下文。

这里所说的轻量文档关系图，是以文档、章节和 Chunk 为节点，以父子、前后相邻和明确引用为关系形成的逻辑图。它使用普通字段和关系表存储，不代表引入 Neo4j，也不等同于 GraphRAG。

## 切片后具体丢失了什么

### 1. 标题和正文被拆开

原文：

```text
## 未发货退款

待发货状态的订单可以申请退款，申请后 2 小时内原路退回。
```

如果标题和正文分别成为两个 Chunk，可能出现：

```text
Chunk A：未发货退款
Chunk B：申请后 2 小时内原路退回
```

Chunk A 只有主题，没有结论；Chunk B 有结论，却丢失了适用对象。单独返回任何一个都不足以完整回答问题。

### 2. 条件和结论被拆开

```text
Chunk A：仅适用于商品未出库且商家尚未发货的订单。
Chunk B：审核通过后 2 小时内原路退款。
```

如果只命中 Chunk B，系统可能把“2 小时退款”错误地应用到所有退款场景。

### 3. 表头和数据行被拆开

```text
表头：订单类型 | 揽收时限
数据：现货普通订单 | 付款后 24 小时
```

数据行离开表头后，“付款后 24 小时”无法确定是在描述发货、揽收还是退款。

### 4. 列表项失去所属章节

```text
## 禁止上架的商品

- 枪支弹药
- 假币、发票
- 无批准文号的药品
```

如果列表项单独切开，“假币、发票”只是两个名词，缺少“禁止上架”这一关键语义。

### 5. 非相邻内容之间的引用消失

```text
退款规则：优惠券是否退回，参见《促销活动与优惠券使用规则》2.4 节。
```

普通相似度检索只能看到当前 Chunk，不知道还需要继续补充被引用章节。跨章节、跨文档的明确引用也就无法参与回答。

文档里常见的引用说明，例如 `> 关联规则：参见《支付方式与资金安全规范》……`，本质上是指路牌，不是答案本身。它应并入同一章节的证据 Chunk 并建立引用边，在检索阶段把目标证据拉进候选池，而不应该单独成块去竞争 TopK。

切块主粒度是章节。同一节里的导语、列表、表格和路标，只要不超过 `chunk_size`，应合成一块；不要按段落或块类型切成「准入：」这种无证据片段。

## 当前切片为什么会产生低信息片段

结构化切块会识别 Markdown 标题、表格和代码块，但如果只按格式边界拆分，仍可能生成：

- 只有 `---`、`***` 的分隔符 Chunk
- 只有章节标题、没有正文的 Chunk
- 标题与正文完全相同的重复 Chunk
- 只有半句话、缺少主语或条件的片段
- 表格数据行没有表头的片段

这些 Chunk 本身没有足够证据，但在检索或精排时又会拼接文档标题。例如正文只有 `---`，文档标题却是“促销活动与优惠券使用规则”，模型仍可能因为标题相关而给出较高分数。

因此，低信息判断必须检查原始正文，不能检查已经拼接标题后的文本。

## 不能简单按照长度过滤

下面这些短句虽然字数少，却是关键证据：

```text
一个订单只能使用一张优惠券。
现货订单须在付款后 24 小时内揽收。
```

如果直接使用 `len(content) < 30` 之类的规则，会把有效证据一起删除。

合理的处理方式是：

| 内容类型 | 处理方式 |
|----------|----------|
| 空白、分隔符、纯标点 | 直接过滤 |
| 纯标题 | 保留为章节路径，不作为独立候选 |
| 有完整语义的短句 | 保留 |
| 不完整的短片段 | 与同一章节的前后内容合并 |
| 表格数据 | 补充表头后保留 |
| 列表项 | 补充所属章节后保留 |

## 轻量文档关系图需要保存哪些信息

每个可检索 Chunk 不只保存正文，还需要记录它在文档中的位置：

```json
{
  "chunk_id": "chunk-101",
  "document_id": "document-001",
  "index_version": "v2",
  "retrieval_text": "文档：平台交易规则\n章节：退款规则 > 未发货退款\n正文：待发货状态的订单可以申请退款。",
  "section_id": "section-refund-unshipped",
  "parent_section_id": "section-refund",
  "order_index": 12,
  "metadata": {
    "heading_path": "平台交易规则/退款规则/未发货退款",
    "chunk_type": "prose",
    "heading_level": 3
  }
}
```

这些字段不必全部平铺在 Chunk 表中，应该按照使用频率分层保存：

| 信息类型 | 保存位置 | 典型字段 |
|----------|----------|----------|
| 高频查询字段 | Chunk 独立字段 | `index_version`、`retrieval_text`、`section_id`、`parent_section_id`、`order_index` |
| 展示和解析字段 | Chunk 的 `metadata` | `heading_path`、`chunk_type`、`heading_level`、`source_page`、`parser`、原始引用文本 |
| 已解析的非相邻关系 | `ChunkRelation` 关系表 | 跨章节、跨文档的明确引用 |

判断标准很简单：经常出现在 `WHERE`、`JOIN` 和 `ORDER BY` 中的字段独立保存；主要用于展示、追溯和解析的字段放入 `metadata`。

`metadata` 里的字段仍然可以查询，只是 JSON 路径表达式和索引维护会更复杂。因此在线检索主链路不依赖 metadata 内部字段；偶尔的调试、抽查和回溯可以直接读取。某个字段以后真的成为高频筛选条件，再将它迁移为独立字段即可。

这些信息可以支持三类确定性关系：

| 关系 | 用途 |
|------|------|
| 章节层级 | 恢复文档标题、父章节和当前小节 |
| 前后相邻 | 补回被切开的条件、结论和连续段落 |
| 明确引用 | 找到“参见某章节、某文档”指向的内容 |

章节和父子关系通过 `section_id`、`parent_section_id` 定位。前后相邻关系不保存两套指针，而是使用同一文档、同一索引版本下连续的 `order_index` 动态计算；需要限制在当前章节时，再增加 `section_id` 条件。非相邻引用使用轻量关系表保存。它们共同构成轻量文档关系图，不需要为了这些确定性关系引入图数据库。

## 为什么要分离原始正文和检索文本

同一个 Chunk 在不同阶段需要不同内容：

```text
content
    原始正文，用于回答、展示和后续引用

retrieval_text
    文档标题 + 章节路径 + 原始正文，用于向量、BM25 和精排
```

例如：

```text
文档：平台交易规则与买家保障
章节：退款规则 > 未发货退款
正文：待发货状态的订单可以申请退款，申请后 2 小时内原路退回。
```

这样既能让检索模型理解片段属于什么文档、什么章节，又不会修改最终展示的原文。只有正文通过低信息检查后，才允许生成 `retrieval_text`。

第一版使用文档标题和章节路径确定性生成上下文，不需要为每个 Chunk 调用 LLM 生成摘要。这样成本更低，重新索引时结果也更加稳定。

## 什么是“小块检索，大块返回”

如果直接把整个章节作为检索单元，内容过长，容易混入多个主题；如果只返回命中的小 Chunk，又可能缺少条件和背景。

更合适的流程是：

```text
小 Chunk 召回
        ↓
低信息过滤（含引用路标不参与 TopK）
        ↓
沿引用和结构关系注入候选
        ↓
（可选）精排小 Chunk
        ↓
（可选）再补充上下文，拼给下游 LLM
        ↓
返回原始命中和补充内容
```

检索和精排阶段使用较小的 `retrieval_text`，保证定位准确。图谱先在检索阶段把引用目标补进候选池，让跨文档证据有机会进入 TopK；精排结束后再围绕高分 Chunk 补充必要内容，给回答层更完整的上下文。

图谱注入和上下文扩展都不能无限进行。它们只沿确定性关系扩展一跳，并受到数量和长度限制：

- 明确引用目标优先
- 父章节和前后相邻片段其次
- 当前命中 Chunk 始终保留
- 已经加入的 Chunk 不重复添加
- 达到上下文预算后停止扩展

## 为什么需要版本化重建索引

这次改造会改变 Chunk 边界、`retrieval_text`、向量、BM25 内容和关系数据。历史索引不能通过补几个字段直接升级成新索引，也不能原地覆盖。

为了让历史数据继续可查，只需要把现有知识库、数据库 Chunk、向量记录和 Elasticsearch 文档统一标记为 `v1`，不需要补齐章节、顺序和引用关系。v1 继续使用原来的向量和 BM25，不执行上下文扩展；需要新能力的数据通过重新构建产生 v2。

安全的处理方式是：

```text
旧索引 v1 继续提供服务
        ↓
根据原始文档构建新索引 v2
        ↓
分别查询 v1 和 v2 完成效果验证
        ↓
将知识库活动版本切换到 v2
        ↓
观察稳定后再清理 v1
```

旧索引在观察期内承担两个作用：新旧效果对比和故障回滚。它不需要重新解析、重新切块或重新计算 Embedding，也不需要永久保留，但在新索引验收完成前不能删除。

## 这次改造不做什么

本次只处理确定性的文档结构和一跳关系，不扩大为通用知识图谱：

- 不抽取实体、事件和语义关系
- 不根据“内容相似”自动建立跨文档边
- 不递归执行多跳关系遍历
- 不判断证据是否足以回答问题
- 不处理来源权威性、版本冲突和引用可信度
- 不使用 LLM 为每个 Chunk 生成上下文摘要

这些边界可以避免关系数量失控，也让索引质量和上下文扩展效果能够被独立测试。

## 完成改造后有什么变化

| 改造前 | 改造后 |
|--------|--------|
| Chunk 主要保存标题、正文和向量 | Chunk 同时保存章节路径、顺序和关系信息 |
| 标题和正文可能成为两个候选 | 纯标题只作为结构，不独立参与检索 |
| 向量和 BM25 直接使用原始正文 | 使用章节路径增强后的 `retrieval_text` |
| 命中后只返回单个 Chunk | 检索阶段可注入引用目标，回答阶段可补充父级、相邻和引用内容 |
| 「参见 xxx」和普通正文一起竞争 TopK | 引用路标只建边、不参与检索；目标证据通过图谱注入进入候选 |
| 重建文档前先删除旧 Chunk | 新旧索引版本并存，验证后再切换 |
| 很难区分命中内容和补充内容 | 调试信息分别展示原始命中、注入来源和关系扩展来源 |

最终检索链路变为：

```text
结构化切块与轻量文档关系索引
        ↓
Vector + BM25 → RRF
        ↓
低信息过滤 → 图谱候选注入
        ↓
（可选）精排
        ↓
（可选）上下文扩展
        ↓
返回检索结果
```
