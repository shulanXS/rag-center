# 轻量文档关系图与增强检索测试验收

测试需要分别证明三件事：结构和关系数据正确、新索引比旧索引更有效、在新索引上精排模型仍然满足质量要求。三类结论必须分开计算，不能把索引、图谱注入、上下文扩展和排序模型的变化混成一个分数。

## 测试准备

准备以下环境和数据：

- PostgreSQL、Elasticsearch、Redis 和 Celery Worker 正常运行
- 数据库已经执行最新 Alembic 迁移
- 一个包含标题、列表、表格、跨段条件和明确引用的知识库
- 该知识库同时保留可查询的 v1 和 ready 状态的 v2
- 若现有 v2 按旧规则构建且验收未通过，先删除非活动状态的 v2，再用修复后的逻辑 rebuild v2；v1 始终保留
- v1 仍是活动版本，或者能够在测试结束后切回 v1
- 12 条核心验收 Case，另保留 30 条完整回归 Case
- 可用的 Embedding、LLM 重排和 Qwen3-Rerank API

评测文件统一放在：

```text
eval/opt16_context/
├── context_retrieval.json
├── index_v1_vs_v2.json
├── index_v1_vs_v2.md
├── rerank_comparison.json
├── rerank_llm_vs_qwen3.json
└── rerank_llm_vs_qwen3.md
```

所有 JSON 和 Markdown 都围绕当前专题放在同一目录，不再拆分 datasets、runs 和 reports。文件中不得保存 API Key、Authorization Header 和用户敏感信息。

```bash
  tests/test_context_retrieval.py \

```

预期全部通过。

### 1. 切块测试

`test_contextual_chunking.py` 至少覆盖：

- 空正文、`---`、`***`、纯标点和纯标题不会生成候选
- “一个订单只能使用一张优惠券”等有效短句可以保留
- 标题路径、章节 ID 和父章节正确
- `order_index` 连续，能够正确推导前后片段且不跨文档
- 表格分片携带表头
- 列表项携带所属章节
- `content` 保存原文，`retrieval_text` 保存检索上下文
- Embedding 输入使用 `retrieval_text`
- 明确引用只有在目标唯一时才建立关系
- 引用路标并入同一章节的证据 Chunk，边的 source 是该证据，而不是独立路标
- 同一章节内能装进 `chunk_size` 的导语、列表和表格应合并，小标题不得单独成块

`test_index_versioning.py` 至少覆盖：

- 数据未完成回填时不能启用版本强制过滤
- 构建 v2 时 v1 继续提供检索
- 普通请求只查询活动版本
- v1 和 v2 候选不会混合
- failed 版本不能激活
- ready 版本可以原子切换
- 切回 v1 后查询恢复
- 活动版本不能删除
- 重建期间禁止修改知识库文档
- 不同租户和知识库严格隔离

### 3. 关系增强检索测试

`test_context_retrieval.py` 至少覆盖：

- 低信息过滤和引用路标过滤在精排前执行
- Qwen3-Rerank 优先读取 `retrieval_text`
- v1 缺少 `retrieval_text` 时使用旧文本构造方式
- v1 结构字段为空时不执行图谱注入和上下文扩展，也不会导致检索报错
- v2 在精排前执行图谱候选注入；关闭精排时注入后直接返回
- v2 在精排后可再执行上下文扩展
- 注入和扩展都使用全部有效引用边
- previous、next、same_section 和 reference 注入与扩展正确
- 引用只扩展一跳
- 注入和扩展结果去重并遵守长度预算
- 未授权知识库和其他租户内容不能被注入或扩展
- 关系查询失败时返回原始 Hybrid 候选
- metadata 能追溯索引版本、过滤数量、注入来源和扩展来源

运行全量回归：

```bash

```

预期原有文档解析、异步入库、Vector、BM25、RRF、精排、多知识库和套餐策略测试全部通过。

## 二、历史数据兼容与 v2 结构抽查

### 1. 历史 v1 数据

选取一个改造前已经完成索引的知识库，迁移前保存一组固定查询及其 TopK 结果，然后执行历史数据迁移。

必须检查：

```text
knowledge_bases.active_index_version = v1
KnowledgeBaseIndexVersion(version=v1, status=active) 存在
数据库 Chunk 的 index_version = v1
独立向量记录的 index_version = v1（如果项目采用分表保存）
Elasticsearch 历史文档的 index_version = v1
```

数量核对：

- 数据库历史 Chunk 数与迁移前一致
- PgVector 可查询向量数与迁移前一致
- Elasticsearch 历史文档数与迁移前一致
- 没有删除、重复或混入其他租户的数据

查询核对：

- 启用 `index_version=v1` 过滤后，固定查询仍能返回历史结果
- TopK Chunk ID 与迁移前一致；如底层检索存在非确定性并列，至少保证候选集合一致
- v1 使用原向量和原 BM25，不产生新的 Embedding 调用和费用
- v1 缺少 `retrieval_text` 时，精排回退到原有“标题 + 正文”格式
- v1 的 `section_id`、`order_index` 和关系数据可以为空
- v1 不执行图谱注入、父章节、相邻片段和明确引用扩展，只返回原始 Hybrid 结果

必须先完成数据库、向量记录和 Elasticsearch 的 v1 回填及查询验证，再开启版本强制过滤。专门构造一批 `index_version` 为空的数据，确认迁移程序能够发现并阻止切换，而不是让它们被静默过滤。

### 2. v2 结构字段

从 v2 随机抽查至少 20 个 Chunk，并覆盖 prose、list、table、code；确认没有独立的 `reference_pointer` 检索 Chunk。

每个 Chunk 检查：

```text
# Chunk 独立字段
index_version
content
retrieval_text
section_id
parent_section_id
order_index

# metadata 字段
heading_path
chunk_type
heading_level
source_page
parser
reference_texts
```

检查要求：

- `content` 是原始证据正文
- `retrieval_text` 包含文档标题、章节路径和正文
- `retrieval_text` 不包含租户 ID、内部 ID 和检索分数
- `section_id`、`parent_section_id` 和 `order_index` 是独立字段，展示与解析信息保存在 `metadata`
- `order_index` 在同一文档、同一版本内唯一且连续，前后片段可通过 `order_index - 1`、`order_index + 1` 查到
- section 和 order 信息与原文顺序一致
- 表格内容能够脱离原始页面理解列含义
- 列表项能够识别所属规则主题

检查低信息内容和引用路标数量：

```text
空正文 = 0
分隔符正文 = 0
纯标题正文 = 0
同章节完全重复正文 = 0
独立 reference_pointer 检索 Chunk = 0
```

抽查至少 10 条明确引用：

- 唯一目标正确解析
- 同名目标不会随意选取
- 找不到目标时没有生成错误关系
- 来源和目标属于同一租户、同一知识库和同一索引版本

## 三、索引重建与回滚测试

若现有 v2 验收未通过，先删除非活动状态的 v2，再发起 rebuild。重建完成后版本号仍为 v2，v1 不受影响。

对测试知识库发起新版本重建，观察完整状态变化：

```text
building → ready → active
```

重建过程中检查：

- v1 检索持续可用
- v2 Chunk 使用新的切块和 `retrieval_text`
- PgVector 与 Elasticsearch 的 v2 Chunk 数量一致
- 任一文档失败时版本状态变成 failed
- failed 版本不会修改 `active_index_version`
- 同一知识库不能同时创建两个 building 版本
- 文档上传、删除和单文档重建被明确阻止

v2 ready 后执行激活，再切回 v1：

```text
查询 v1 → 激活 v2 → 查询 v2 → 切回 v1 → 再次查询 v1
```

预期：

- 每一步只返回指定版本的 Chunk
- 切换过程中没有混合版本
- 回滚不重新计算 Embedding
- v2 激活失败时 v1 继续有效
- 活动版本删除操作被拒绝

## 四、准备索引对比数据集

`context_retrieval.json` 保存问题和标准答案，不保存某个版本专属的 Chunk ID：

```json
{
  "name": "context_retrieval_v1",
  "knowledge_base_id": "实际知识库ID",
  "profile": "balanced",
  "top_k": 10,
  "annotation": {
    "method": "human_reviewed",
    "rubric": "0=无关，1=主题相关，2=有效支撑，3=核心证据"
  },
  "cases": [
    {
      "id": "refund_unshipped",
      "question": "还没发货可以申请退款吗，多久能到账？",
      "ground_truth": "待发货订单可以申请退款，申请后2小时内原路退回。"
    }
  ]
}
```

默认验收使用 `core` 套件的 12 条问题，完整回归使用 `full` 套件的 30 条问题。开发过程和最终报告默认不重复跑完整集。

12 条核心问题覆盖：

- 标题提供主题、正文提供结论
- 前一个片段提供条件、后一个片段提供结果
- 表头和数据行
- 列表标题和列表项
- 相似标题下的不同规则
- 明确的跨章节引用
- 明确的跨文档引用
- 不应该扩展相邻内容的完整短证据
- 数字、期限、否定条件和适用范围
- 多知识库请求中的权限边界

允许模型辅助生成问题和预标注，但最终 relevance 和上下文完整性必须人工复核。完整集用于发布前回归或后续专题复测，不作为每次改代的必跑项。

## 五、旧索引与新索引对比

这组测试不启用 LLM 重排和 Qwen3-Rerank，只比较索引与关系增强能力。

固定：

- 相同问题
- 相同知识库文档
- 相同 Embedding 模型
- 相同 Vector、BM25、RRF 参数
- 相同 profile 和 TopK
- `rerank_options.enabled=false`
- Hybrid 融合后保留足够候选数（建议 Top20），不在 RRF 后用返回 TopK 提前截断

### 主验收（默认，必跑）

只比较两组：

```text
v1        优化前（老索引）
v2_full   优化后（新索引，图谱注入 + 上下文扩展全开）
```

执行：

```bash
python scripts/compare_context_indexes.py capture-v1 --suite core
python scripts/compare_context_indexes.py prepare --suite core
python scripts/compare_context_indexes.py compare
```

`prepare` 默认只采集 `v1` 和 `v2_full`。报告主表只展示这两列，用于判断**整个优化十六**是否优于优化前。

### 诊断模式（可选，主验收未通过时再跑）

只有主门槛未通过、需要定位是切块、图谱注入还是上下文扩展的问题时，才追加：

```bash
python scripts/compare_context_indexes.py prepare --suite core --diagnostic
python scripts/compare_context_indexes.py compare
```

`--diagnostic` 会额外采集：

```text
v2_hybrid   新索引，注入关，扩展关
v2_graph    新索引，注入开，扩展关
v2_full     新索引，注入开，扩展开
```

诊断结果写入报告附录，不作为对外主验收表。

两组数据由评测脚本直接调用检索阶段、注入服务和扩展服务生成，不要求普通 retrieve API 或前端提供关系增强开关。

先冻结 TopK，再分别标注候选。新旧 Chunk 边界和 ID 不同，不能把 v1 的 relevance 标签直接复制给 v2。

结果统一写入：

```text
eval/opt16_context/index_v1_vs_v2.json
eval/opt16_context/index_v1_vs_v2.md
```

JSON 同时保存主验收逐题结果、相关性标注和汇总指标；启用 `--diagnostic` 时再追加诊断分组，不再为每一组生成独立文件。

### 指标口径

| 指标 | 用途 |
|------|------|
| nDCG@10 | 判断高相关证据的整体顺序 |
| MRR@10 | 判断第一条核心证据是否靠前 |
| HitRate@10 | 判断是否找到核心证据 |
| expected_document_recall@10 | 判断是否命中问题所需的全部目标文档 |
| reference_target_hit_rate@10 | 判断引用目标 Chunk 是否进入 TopK |
| keyword_coverage@10 | 判断关键词是否覆盖 |
| low_information_rate@10 | Top10 中低信息 Chunk 的比例 |
| duplicate_rate@10 | Top10 中重复证据的比例 |
| context_completeness | 扩展后是否包含回答所需全部条件和结论 |
| supplemental_precision | 补充 Chunk 中真正有用内容的比例 |
| context_chars | 扩展前后上下文长度变化 |
| graph_injection_p95_ms | 检索阶段图谱注入耗时 |
| P50 / P95 | 检索和扩展耗时 |

nDCG 使用 0～3 完整等级；MRR 和 HitRate 只将 `relevance=3` 视为核心命中。`expected_document_recall@10` 和 `reference_target_hit_rate@10` 是跨文档 Case 的主门槛，不再使用会被截断为 1 的 `effective_recall@10` 作为唯一 Recall 指标。

上下文完整性按 Case 标注：

```text
complete：必要条件和结论全部存在
partial：只有部分证据
missing：缺少核心证据
```

### 如何解释结果

```text
主验收（默认）
  v1 vs v2_full
      回答：整个优化十六是否优于优化前

诊断模式（--diagnostic，仅排查时）
  v2_hybrid vs v2_graph
      回答：图谱注入是否带来跨文档召回提升
  v2_graph vs v2_full
      回答：上下文扩展是否进一步补全回答材料
```

主验收只看 `v1` 与 `v2_full`。诊断分组由评测脚本内部开关控制，不依赖 API 参数。

如果同时开启精排，就无法判断变化来自新索引还是排序模型，因此这组测试必须关闭精排。

## 六、新索引上的排序回归

索引对比完成后，只使用 **v2 Graph 注入后** 的候选重新生成排序数据集：

```text
v2 Hybrid 检索
    ↓
图谱候选注入
    ↓
冻结注入后的 Top10 或 Top20 候选
    ↓
重新标注 relevance 0～3
    ↓
分别交给 LLM 重排和 Qwen3-Rerank
```

候选集保存为：

```text
eval/opt16_context/rerank_comparison.json
```

两种模型必须接收完全相同的 question、候选顺序和 `retrieval_text`。每个 Case 执行 1 次 warm-up 和至少 3 次正式调用。

结果统一保存为：

```text
eval/opt16_context/rerank_llm_vs_qwen3.json
eval/opt16_context/rerank_llm_vs_qwen3.md
```

JSON 同时保存两种模型逐题、逐轮的排序和汇总结果，不再拆分单独的 baseline 和 candidate 文件。

质量指标对每次正式调用分别计算，再汇总平均值和波动范围，不能只使用第一次成功结果。报告包含：

- nDCG@5、MRR@5、HitRate@5、Recall@5
- P50、P95、最大时延
- 成功率、降级率和 Top5 完整顺序一致率
- 逐题胜、平、负
- 负向 Case 的两组 Top5
- 输入、输出和总 Token
- 单次平均成本和每 1000 次预计成本

成本计算要求：

- 保存 API 返回的真实 usage
- LLM 分别记录 input_tokens 和 output_tokens
- Qwen3-Rerank 记录接口返回的计费 Token
- 报告记录单价来源、地区、查询日期和计费单位
- 官方单价作为评测价格快照，不写死进线上业务代码
- 免费额度、抵扣包和活动价格单独说明，不混入标准理论成本

## 七、调试台人工检查

通过后端接口或脚本激活已验收的 v2，然后使用现有检索调试台分别选择 v2 和 v1 查询。前端提供索引版本选择器但不提供上下文增强开关；扩展前的 Anchor 结果从专题评测报告中对照。

至少检查以下问题：

1. 条件和结论位于相邻 Chunk
2. 表格数据需要表头才能理解
3. 列表项需要章节标题才能理解
4. 当前 Chunk 引用了其他章节
5. 当前 Chunk 已经完整，不需要扩展

预期：

- 原始命中、注入内容和扩展内容分别展示
- 知识库列表同时展示 v1、v2 的文档和分块数，并标记当前版本
- 检索页默认选择 v2，切换 v1 后只返回 v1 Chunk
- 精排后上下文扩展不改变 Anchor 排名
- 现有 `metadata.heading_path` 与原文一致
- 注入来源和 previous、next、reference 扩展来源清晰
- 不会无条件加载整个章节
- 不会递归扩展引用
- 扩展失败时页面仍能展示原始结果
- v1 返回的新字段为空时，现有结果卡片仍能正常渲染

## 八、异常与安全测试

| 场景 | 预期 |
|------|------|
| v2 构建失败 | v1 继续提供服务，v2 不可激活 |
| Elasticsearch v2 写入失败 | 版本标记 failed，不只保留 PgVector 半成品 |
| 引用目标不存在 | 不注入，记录 unresolved |
| 相邻 Chunk 已删除 | 返回原始候选，context 标记降级 |
| 关系跨租户 | 拒绝注入或扩展并记录安全日志 |
| 关系指向未请求知识库 | 不扩展目标内容 |
| 上下文超过预算 | 按优先级停止补充，不删除 Anchor |
| 活动版本清理 | 操作被拒绝 |
| 激活事务失败 | active_index_version 保持不变 |

所有异常日志都不能包含 API Key、Authorization Header 和完整敏感正文。

## 九、建议验收门槛

### 结构与迁移

- 历史知识库、Chunk、向量记录和 Elasticsearch 文档全部正确标记为 v1
- v1 迁移前后 Chunk 数、向量数、ES 文档数和固定查询结果一致
- v1 未重新解析、切块或计算 Embedding，结构关系字段允许为空
- 空正文、分隔符和纯标题可检索 Chunk 数量为 0
- 抽查的章节路径、顺序推导相邻片段和明确引用正确率为 100%
- v1、v2 隔离和租户隔离测试全部通过
- v2 失败、切换和回滚不影响 v1 数据

### 索引与关系增强

- v2_full 的 HitRate@10 不低于 v1
- v2_full 的 low_information_rate@10 为 0
- v2_full 的 nDCG@10、MRR@10 和 expected_document_recall@10 不低于 v1
- v2_full 的 context_completeness_rate 达到 90% 以上
