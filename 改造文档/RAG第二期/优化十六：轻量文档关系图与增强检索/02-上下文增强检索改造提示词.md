# 关系增强检索改造提示词

点击此处可复制本篇提示词

在当前 rag-center 项目中，使用轻量文档关系图中保存的章节层级、前后相邻和明确引用关系改造在线检索。Hybrid 召回小 Chunk 后，先在检索阶段沿关系注入候选，再进入精排；精排结束后仍可补充上下文，拼给下游 LLM。现有调试台继续区分原始命中、注入来源和关系扩展内容。

修改前先检查当前代码，以实际目录、类型和调用关系为准。复用现有 `RagService`、PgVector、Elasticsearch、RRF、Qwen3-Rerank、retrieve API 和调试台，不重复创建检索主链路，不修改与检索增强无关的功能。

## 一、改造目标

- 普通检索默认查询当前活动索引版本，也允许显式选择同一知识库的 v1 或 v2
- v1 继续使用原向量和原 BM25，v2 的向量、BM25 和精排统一使用 `retrieval_text`
- 返回结果继续保留原始 `content`
- 候选进入精排前再次过滤低信息片段、引用路标和重复 Chunk
- v2 在精排前沿章节、相邻和明确引用关系注入候选；未开启精排的档位同样执行注入
- v2 精排后可再扩展一跳上下文，拼给下游 LLM；v1 只返回原始命中
- 分离「精排候选数」和「最终返回数」，避免 Hybrid 融合结果被过早截断
- 对注入、扩展的数量、长度和重复内容进行限制
- 注入或扩展失败时返回原始检索结果，不让 retrieve 失败
- 复用现有调试台选择检索版本，并展示实际版本、原始命中、注入来源和扩展来源
- 增加关系增强检索自动化测试

## 二、确定在线检索顺序

检索主链路调整为：

```text
读取请求 index_version；未指定时读取 active_index_version
        ↓
按照版本查询 Vector + BM25
        ↓
RRF 融合候选（保留足够候选数，如 Top20）
        ↓
低信息过滤、引用路标过滤和精确去重
        ↓
判断 index_version
    ├── v1：进入精排或直接返回
    └── v2：沿关系注入候选，再去重和控制总量
        ↓
（可选）Qwen3-Rerank 精排
        ↓
判断 index_version
    ├── v1：保持原样返回
    └── v2：（可选）围绕 TopN 扩展一跳上下文
        ↓
返回检索结果
```

顺序要求：

- 图谱候选注入放在精排之前；未开启精排时，注入后直接返回 TopK
- 只有具备结构关系的 v2 执行注入和上下文扩展，v1 不猜测或临时生成关系
- 引用路标（`reference_pointer`）不得作为独立检索 Chunk；索引阶段应并入证据块。检索过滤仍丢弃漏网路标，它们不参与 Hybrid 召回、注入起点和精排候选
- 注入时使用 source Chunk 的全部有效引用边，不再固定只取 1 条
- 注入优先级：明确引用 > 父章节 > 前后相邻片段
- 精排后的上下文扩展只拼 `context` 字段，不再改变 Anchor 排名
- 多知识库检索时，显式版本必须在所有选中知识库中可查询；未指定时使用各知识库活动版本

## 三、活动索引版本查询

修改 `RagService` 和检索 Provider：

- 加载知识库时同时读取 `active_index_version`
- PgVector 相似度查询必须带 `index_version`
- Elasticsearch BM25 查询必须带 `index_version`
- 同一知识库的一次请求只能使用一个索引版本
- 多知识库请求允许不同知识库使用各自活动版本
- retrieval metadata 返回每个知识库实际使用的版本

普通 retrieve 请求通过 `index_version` 显式选择 v1 或 v2；未传时使用 `active_index_version`。无论来自调试台还是评测脚本，都必须校验版本属于当前租户、知识库且状态可查询。

索引版本不存在、未 ready 或已被清理时返回明确错误，不能自动混查其他版本。

历史数据回填完成前不能启用版本强制过滤。v1 查询必须确认数据库 Chunk、向量记录和 Elasticsearch 文档均已标记为 `index_version=v1`；否则缺失版本的数据可能被静默过滤，表现为检索结果为空。

## 四、按索引版本选择检索数据

### 向量检索

v1 继续查询原有向量，v2 查询由 `retrieval_text` 生成的新向量，不为 v1 重新计算 Embedding。PgVector 返回结果时携带以下字段；v1 没有的新字段允许为空：

```text
content
retrieval_text
section_id
parent_section_id
order_index
index_version
metadata
```

v2 的 `metadata` 继续使用现有 `heading_path`，并保留 `chunk_type`、`heading_level`、`source_page`、`parser` 和原始引用文本，v1 允许缺失新增字段。不要再增加含义重复的 `section_path`。数据库查询仍然使用独立的 `section_id`、`parent_section_id` 和 `order_index`。

### BM25

v1 查询原有 BM25 字段，v2 查询 `retrieval_text`，不要为了兼容而修改 v1 已有的索引内容。返回结果中的 `content` 始终是原始正文。

### Qwen3-Rerank

修改 `Qwen3RerankProvider._build_document()`：

```python
retrieval_text = str(chunk.get("retrieval_text") or "").strip()
if retrieval_text:
    return retrieval_text[: self.chunk_max_chars]
return build_legacy_document(chunk)
```

要求：

- 新索引优先使用 `retrieval_text`
- v1 历史数据没有完整字段时回退到原有“标题 + 正文”格式
- 不重复拼接标题和章节路径
- 不把关系 ID、索引版本、召回分数和租户信息发送给精排模型
- 精排返回后保留 Chunk 的全部结构字段

## 五、精排前安全过滤

复用索引阶段的低信息判断函数，在 RRF 之后、精排之前增加安全过滤，处理历史数据和异常解析结果。

过滤：

- 空正文
- 只有分隔符或标点的正文
- 只有标题、没有证据的正文
- `chunk_type=reference_pointer` 的引用路标
- 同一请求中正文完全相同的重复 Chunk

不按字数直接过滤短句，不过滤合法表格、列表和代码片段。

去重优先使用 `chunk_id`，再使用规范化后的正文哈希。多个版本不能出现在同一候选集，因此去重键不需要跨版本比较。

`retrieval_candidate_k` 和 `top_k` 分离：

- Hybrid 融合后至少保留 `retrieval_candidate_k` 条候选（建议 20）
- 精排和最终返回使用 `top_k` 或 `rerank_options.top_n`（建议 5 或 10）
- 单知识库检索不得在 RRF 之后直接用 `top_k` 截断全部候选

记录：

```text
candidate_count_before_filter
candidate_count_after_filter
filtered_count
filtered_reasons
```

过滤只删除没有可用证据的候选，不能修改剩余候选的 RRF 相对顺序。

## 六、检索阶段图谱候选注入

新增独立服务，或在现有关系查询能力上封装，例如：

```text
app/services/graph_candidate_expansion_service.py
```

接口保持简单：

```python
async def expand_candidates(
    *,
    tenant_id: str,
    kb_ids: list[str],
    seeds: list[dict],
) -> GraphCandidateExpansionResult:
    ...
```

`seeds` 是 Hybrid 过滤后的初始命中，不含引用路标。注入服务通过 PostgreSQL 查询 `chunk_relations`、`order_index` 和章节字段，**不调用 LLM，不调用 Embedding**。

### 1. 注入规则

从每个 seed 出发，按以下顺序收集关联 Chunk：

```text
明确引用目标
    ↓
父章节范围内的必要片段
    ↓
同一章节中紧邻的必要片段
```

要求：

- 只从 Hybrid 前 N 个 seed 出发（建议 N=10），避免对长尾命中无差别扩展
- 每个 source Chunk 使用全部有效 `reference` 边，不再固定只取 1 条
- 引用目标必须属于请求允许的知识库、同一租户和同一索引版本
- 引用只扩展一跳，不递归遍历
- 注入 Chunk 带来源标记，例如 `injection_source=reference`
- 同一个 `chunk_id` 只保留一份；已在 seed 中的 Chunk 不重复注入

### 2. 数量和权限保护

使用代码常量控制第一版行为，不增加大量环境变量，例如：

```text
MAX_GRAPH_SEEDS = 10
MAX_INJECTED_CHUNKS_PER_SEED = 3
MAX_TOTAL_CANDIDATES = 30
```

处理顺序：

- 原有 Hybrid 命中始终保留
- 注入内容按关系优先级加入
- 达到总量上限后停止
- 关系跨越租户或未授权知识库时拒绝注入并记录安全日志

注入失败时回退为只使用 Hybrid 候选，不让 retrieve 失败。

## 七、精排后上下文扩展

新增独立服务，例如：

```text
app/services/context_expansion_service.py
```

接口保持简单：

```python
async def expand(
    *,
    tenant_id: str,
    kb_ids: list[str],
    anchors: list[dict],
) -> ContextExpansionResult:
    ...
```

Anchor 是精排或注入后的最终候选。扩展服务不能改变 Anchor 的数量、顺序、`score` 和 `rerank_score`。

调用扩展服务前先检查 `index_version`。v1 直接返回 Anchor，并将 `context=None` 或记录 `context_expansion=false`；只有具备结构字段和关系数据的 v2 才进入扩展服务。

### 1. 扩展优先级

每个 Anchor 按以下顺序构建上下文：

```text
当前 Anchor
    ↓
章节路径
    ↓
明确引用指向的目标片段
    ↓
父章节范围内的必要片段
    ↓
同一章节中紧邻的必要片段
```

“必要片段”采用确定性规则，不调用 LLM 判断：

- prose 最多补一个前片段和一个后片段
- table 已携带表头时不重复补表头
- list 已携带章节路径时不扩展整个列表
- code 默认不补相邻代码块，除非当前块有明确连续标记
- 相邻片段必须属于同一文档和同一索引版本
- 引用目标必须属于请求允许的知识库范围
- 引用只扩展一跳，不继续沿目标引用递归遍历

不能因为存在 `parent_section_id` 就无条件加载整个父章节。较大的章节只选择与 Anchor 邻近的有效片段。

前后片段不依赖持久化指针。扩展服务根据 Anchor 的 `order_index` 查询同一文档、同一索引版本中的 `order_index - 1` 和 `order_index + 1`；只允许同章节扩展时再限定 `section_id`。所有查询必须同时校验 `tenant_id`、`kb_id`、`document_id` 和 `index_version`。

### 2. 数量和长度保护

使用代码常量控制第一版行为，不增加大量环境变量，例如：

```text
MAX_NEIGHBORS_PER_ANCHOR = 2
MAX_REFERENCE_TARGETS_PER_ANCHOR = 3
MAX_SUPPLEMENTAL_CHUNKS_PER_ANCHOR = 3
MAX_CONTEXT_CHARS_PER_ANCHOR = 4096
```

处理顺序：

- Anchor 原文始终保留
- 补充内容按关系优先级加入
- 同一个 `chunk_id` 只加入一次
- 规范化正文完全相同的内容只加入一次
- 达到数量或字符预算后立即停止
- 不截断到破坏表格行、列表项或代码围栏的位置

### 3. 上下文输出

不要把补充 Chunk 平铺进 `retrieved_chunks`。为每个 `RetrievedChunkData` 增加可选上下文对象，例如：

```json
{
  "chunk_id": "chunk-101",
  "content": "待发货状态的订单可以申请退款。",
  "metadata": {
    "heading_path": "退款规则/未发货退款",
    "chunk_type": "prose"
  },
  "context": {
    "content": "组合后的完整上下文",
    "chunk_ids": ["chunk-100", "chunk-101", "chunk-102"],
    "sources": [
      {"chunk_id": "chunk-101", "relation": "anchor", "content": "待发货状态的订单可以申请退款。"},
      {"chunk_id": "chunk-100", "relation": "previous", "content": "待发货状态适用于商家尚未发出商品的订单。"},
      {"chunk_id": "chunk-102", "relation": "next", "content": "退款申请通过后 2 小时内原路退回。"}
    ]
  }
}
```

关系类型限定为：

```text
anchor
previous
next
same_section
parent_section
reference
```

`context.content` 用于下游回答；`content` 继续表示原始命中正文。不能用组合后的上下文覆盖原文。

## 八、返回 metadata

不增加关系增强开关。后端根据本次实际检索版本自动决定：v1 不注入、不扩展，v2 按固定规则注入和扩展。扩展前后的对比由专题评测脚本分别调用检索阶段、注入服务和扩展服务完成。

新增或扩展 metadata，至少包含：

```text
# 候选过滤
candidate_count_before_filter
candidate_count_after_filter

# 图谱注入
graph_injection_executed
graph_injected_count
graph_injection_latency_ms

# 上下文扩展
executed
anchor_count
expanded_anchor_count
supplemental_chunk_count
deduplicated_count
latency_ms
degraded
error
```

`RetrieveMetadata` 同时返回：

- 实际使用的索引版本
- 过滤前后候选数
- 图谱注入统计
- 上下文扩展统计
- 每个 Anchor 的注入来源和扩展来源

metadata 不返回完整敏感正文，只返回 ID、关系类型、数量、耗时和错误摘要。

## 九、异常降级

图谱注入和上下文扩展都属于增强能力，失败时不能导致整个 retrieve 失败。

以下场景回退为只使用 Hybrid 候选或只返回 Anchor：

- 关系查询超时
- `order_index` 不连续，无法查询到预期相邻 Chunk
- 引用目标已经删除
- 关系跨越租户或未授权知识库
- 组合上下文过程中出现异常

降级要求：

- Anchor 排名和内容保持不变
- `context.content` 至少包含 Anchor 原文，或者 `context=None`
- `metadata.context.degraded=true`
- error 可以定位原因，但不能包含 API Key 和完整文档正文
- 记录异常关系，不能自动改写数据库关系

发现跨租户或跨未授权知识库关系时必须拒绝扩展并记录安全日志，不能作为普通缺失关系静默处理。

## 十、调试台适配

复用现有检索调试页面，增加 v2/v1 索引版本选择器；默认选择当前活动的 v2，不增加上下文增强开关，也不新增独立页面。

现有结果卡片已经展示 Document ID、Chunk ID、Vector/BM25/rerank 分数、排名、`metadata.heading_path` 和 `metadata.chunk_type`，这些内容继续复用，不重复实现。

每条结果只增加一个“上下文补充”折叠区域，展示：

- 原始命中 Chunk，并标记为 `anchor`
- 检索阶段注入的 Chunk ID、关系类型和原文
- 精排后补充 Chunk 的 ID、关系类型和原文
- 关系类型使用易懂文案展示：前一片段、后一片段、同章节、父章节、明确引用
- 组合后的 `context.content`
- 注入耗时、扩展耗时和降级信息

`parent_section_id`、`order_index` 等技术字段放在折叠的调试详情中，不在卡片主区域展示。

扩展前端 `RetrievedChunkData` 类型，新增字段全部可选：

```typescript
interface RetrievedChunkContext {
  content: string;
  chunk_ids: string[];
  sources: Array<{
    chunk_id: string;
    relation: "anchor" | "previous" | "next" | "same_section" | "parent_section" | "reference";
    content?: string;
  }>;
  latency_ms?: number;
  degraded?: boolean;
  error?: string | null;
}

interface RetrievedChunkData {
  section_id?: string | null;
  parent_section_id?: string | null;
  order_index?: number | null;
  context?: RetrievedChunkContext | null;
}
```

原始命中与补充内容使用不同标签，不能让用户误以为所有内容都是检索直接命中的。

前端只扩展现有知识库列表、检索版本选择器、结果卡片和响应类型，不增加模型选择器、增强开关、图谱管理页或新的检索页面。新增 `context` 和结构字段必须定义为可选，确保 v1 结果仍可正常渲染。

## 十一、实现专题评测工具

新增：

```text
scripts/compare_context_indexes.py
```

脚本支持：

- `capture-v1`：采集 v1 baseline
- `prepare`：默认采集 v1 和 v2_full；加 `--diagnostic` 时额外采集 v2_hybrid、v2_graph
- `validate`：检查索引版本、候选数量、人工标注、重复 Chunk 和缺失字段
- `compare`：计算 v1 vs v2_full 主指标；如有诊断分组则写入报告附录
- `refresh-v2`：只重跑 v2 相关分组，支持 `--diagnostic`
- `export-rerank`：导出 v2_graph（或 v2_full）候选，供精排回归使用

索引比较必须显式关闭 rerank，并把主验收与可选诊断结果合并写入：

```text
eval/opt16_context/index_v1_vs_v2.json
eval/opt16_context/index_v1_vs_v2.md
```

扩展 `scripts/compare_rerankers.py`，增加一次完成新索引排序回归的组合命令。它读取 **v2 图谱注入后** 的冻结候选，交替调用 LLM 和 Qwen3-Rerank，并将两边逐题、逐轮结果、usage、质量指标、时延、稳定性和成本合并写入：

```text
eval/opt16_context/rerank_llm_vs_qwen3.json
eval/opt16_context/rerank_llm_vs_qwen3.md
```

组合命令要求：

- 每次正式调用分别计算排序指标，再汇总平均值和波动范围
- 保存 API 返回的 input、output 和 total token usage
- 价格通过评测参数或价格快照文件传入，不写死在线上业务代码
- 不再额外生成单独的 LLM baseline 和 Qwen3 result 文件
- 输出目录不存在时自动创建
- 数据、报告和日志不得包含 API Key
- 远程接口不可用时明确失败，不生成虚构结果

专题评测目录最终只包含：

```text
eval/opt16_context/
├── context_retrieval.json
├── index_v1_vs_v2.json
├── index_v1_vs_v2.md
├── rerank_comparison.json
├── rerank_llm_vs_qwen3.json
└── rerank_llm_vs_qwen3.md
```

## 十二、测试代码

新增：

```text
tests/test_context_retrieval.py
```

覆盖：

- 多知识库使用各自活动版本
- 不同版本候选不会混合
- 新 Chunk 精排优先使用 `retrieval_text`

- v2 在精排前执行图谱候选注入；关闭精排时注入后直接返回
- v2 在精排后可再执行上下文扩展
- 注入和扩展都使用全部有效引用边
- previous、next、same_section 和 reference 注入与扩展正确
- 引用只扩展一跳
- 不扩展未授权知识库和其他租户内容
- 数量、字符预算和去重正确
- 精排后 Anchor 排名和分数不被上下文扩展改变
- 注入或扩展异常时返回原始候选
- metadata 和调试字段正确

关系存储、PgVector、Elasticsearch 和精排 Provider 在单元测试中使用 mock，不调用远程服务。

## 十三、改造约束

- 不在检索阶段递归遍历引用关系
- 不调用 LLM 判断是否需要注入或扩展
- 不根据语义相似度临时创建关系
- 不让引用路标进入 TopK 候选
- 不做来源权威性、时效性和冲突判断
- 不生成回答引用编号
- 不判断证据是否足以回答并自动继续检索
- 不修改 Vector、BM25、RRF 和 Qwen3-Rerank 的算法参数
- 不新增独立前端页面
- 不在前端增加关系增强开关
- 不把组合上下文覆盖原始 `content`

## 十四、验收标准

- 普通检索默认查询活动索引版本，显式选择时只查询指定版本
- v1 继续使用原检索数据，v2 的 Vector、BM25 和 Qwen3-Rerank 使用 `retrieval_text`
- 候选中的低信息片段和引用路标在精排前被安全过滤
- v2 能在检索阶段沿关系注入候选，未开启精排时同样生效
- 精排后的上下文扩展不改变 Anchor 排名
- 注入和扩展内容受到数量、字符和权限范围限制
- 多知识库和多租户关系不会串联
- 注入或扩展失败时 retrieve 仍返回原始结果
- metadata 能追溯原始命中、注入来源、扩展来源、索引版本和耗时
- 调试台能够区分直接命中、注入内容和关系扩展内容
- `tests/test_context_retrieval.py` 全部通过
- 原有检索、精排、套餐策略和多知识库测试全部通过
