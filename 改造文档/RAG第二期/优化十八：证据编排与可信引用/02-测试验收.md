# 证据编排与可信引用测试验收

本专题验证的是：在v2检索和Qwen3精排结果完全相同的情况下，把原始Top10整理成`evidence_pack`，能否减少无关材料，同时保留回答所需证据并保证每条引用可以回查原文。

正式结论使用统一评测体系，不再由独立5题脚本决定。

## 对应测试报告

- [证据编排与可信引用效果报告](./报告/证据编排与可信引用效果报告.md)

## 一、测试目标

主实验回答四个问题：

1. 证据包是否提高Context Precision；
2. 压缩证据时是否损害Context Recall；
3. 证据编排增加多少P95延迟和模型调用；
4. 每条EvidenceItem是否都能通过`chunk_id`回溯原文。

证据包不生成最终答案，因此本实验不评价答案忠实度、答案风格和Markdown引用格式。

## 二、固定上游链路

两组共用同一次上游处理：

```text
统一Golden Set
      ↓
v2 Hybrid + RRF Top20
      ↓
图谱注入与上下文扩展
      ↓
Qwen3-Rerank精排Top10
```

固定条件：

| 条件 | A组 | B组 |
|------|-----|-----|
| 数据集 | `golden_basic_20_v2` | `golden_basic_20_v2` |
| 索引版本 | v2 | v2 |
| 检索方式 | Hybrid + RRF | Hybrid + RRF |
| 初始候选 | Top20 | 与A组共用 |
| 精排 | Qwen3-Rerank | 与A组共用同一次结果 |
| 精排输出 | Top10 | 与A组完全相同 |
| Query Rewrite | 关闭 | 关闭 |
| 同义词扩展 | 关闭 | 关闭 |
| 最终答案生成 | 不执行 | 不执行 |
| 证据编排 | 关闭 | 开启 |

不能让A组不精排、B组开启精排，否则无法判断变化来自精排还是证据编排。也不能分别重新检索或重新精排，否则候选波动会干扰结论。

## 三、A/B评测材料

每道题只发起一次开启证据编排的真实retrieve请求，再从同一个响应拆出两组材料。

### A组：原始Top10

RAGAS评价最终`retrieved_chunks`：

```text
优先使用context.content
没有context时使用原始content
按chunk_id和正文去重
```

这代表未启用证据编排时，回答层直接收到的Top10上下文。

### B组：证据包

RAGAS只评价：

```text
evidence_pack.items[*].content
```

EvidenceItem可以来自Top10、Top10的`context.sources`或同一固定候选池中的Top10外候选，但正文必须是后端重新加载的原始Chunk内容。

以下内容不能作为B组RAGAS上下文：

- 模型生成的aspect名称；
- `missing_aspects`；
- 模型摘要或改写文本；
- Chunk ID、检索分数和role名称；
- A组中未被证据包选中的片段。

B组不是绕过召回，而是评价召回、精排和证据筛选之后真正准备交给回答层的材料。

## 四、统一运行器改造

新增目标类型：

```text
evidence_orchestration
```

统一运行器识别该目标后，每道题执行一次完整B组请求，并生成两份逐题结果：

```text
baseline.raw.jsonl
    contexts = retrieved_chunks Top10

candidate.raw.jsonl
    contexts = evidence_pack.items
```

运行器必须校验：

- 全部`retrieved_chunks`和EvidenceItem都是v2；
- `retrieved_chunks`最终数量为Top10；
- 实际精排Provider为Qwen3；
- Query Rewrite和同义词扩展均关闭；
- evidence执行前后Top10的ID、顺序、分数和context没有变化；
- 每个EvidenceItem都来自本次固定候选或context source；
- EvidenceItem正文与仓储层原始正文一致；
- B组没有重复`chunk_id`或重复正文；
- 任一引用跨租户、跨知识库或混入其他索引版本时整次实验失败。

### 延迟口径

A组延迟不包含证据编排阶段：

```text
baseline_latency = 完整请求耗时 - evidence_latency
```

B组使用完整请求耗时：

```text
candidate_latency = 完整请求耗时
```

如果服务已经返回可靠的分阶段耗时，优先使用阶段字段求和。不得为了得到A组延迟再执行一次检索。

### 模型调用口径

```text
A组：Qwen3精排1次
B组：Qwen3精排1次 + 证据编排LLM 1次
```

两组共用的Embedding请求不计入“应用模型调用次数”。B组正常情况下比A组增加1次。

证据编排服务需要把本次调用的input、output和total tokens写入逐题诊断信息。报告可以计算单次平均成本和每1000次预计成本，但成本只作为选型信息，不增加第五项正式指标。

## 六、正式指标

报告只使用四项正式指标：

| 指标 | 本专题中的含义 |
|------|----------------|
| Context Precision | 证据包是否减少Top10中的无关材料 |
| Context Recall | 证据包是否保留回答所需的全部证据 |
| P95延迟 | 证据编排增加的在线等待时间 |
| 平均模型调用次数 | 启用证据编排增加的应用模型调用 |

正式质量判断以Context Precision为主指标，Context Recall作为质量护栏。Precision提高但Recall明显下降，说明压缩过度，不能宣布证据编排有效。

## 七、专题硬指标与诊断信息

唯一专题硬指标：

```text
citation_traceability_rate =
能够按tenant、kb、index_version和chunk_id回查原文的EvidenceItem数
÷ EvidenceItem总数
```

门槛固定为100%。只要存在一条无法回溯、正文不一致或越权引用，本次实验就不能通过。

以下只作为诊断信息：

- 平均证据数量；
- 平均证据字符数；
- complete、partial和missing数量；
- `missing_aspects`分布；
- Top10外证据数量；
- 证据编排Token和理论成本；
- 降级率；
- 可选的Status Accuracy。

Required Aspect Coverage、Complete Case Rate和旧版Evidence Precision可以保留在历史开发报告中，不再作为正式报告的主指标，避免和统一的Context Recall、Context Precision重复表达同一问题。

## 八、验收门槛

建议门槛：

1. Context Precision至少提升0.1个百分点；
2. Context Recall最多下降2个百分点；
3. B组P95增幅不超过500%，并且没有超过证据编排超时上限；
4. B组平均应用模型调用次数最多增加1次；
5. 引用回溯率必须为100%；
6. 两组20道结果和RAGAS评分全部成功；
7. 不允许跨租户、跨知识库或混入其他索引版本。

P95上限允许证据编排增加一次LLM调用，但报告必须同时给出绝对延迟。例如从3秒增加到15秒，即使处于比例门槛内，也必须明确说明证据包适合按需开启，不适合作为所有检索请求的默认能力。

## 九、自动化测试

运行：

```bash
pytest tests/test_evidence_orchestration.py -v
pytest tests/test_eval_runner.py tests/test_eval_report.py -v
```

至少覆盖：

- evidence能够独立开启和关闭；
- evidence关闭时不调用LLM；
- 开启前后`retrieved_chunks`完全一致；
- 统一运行器只执行一次上游检索和精排；
- A组正确读取Top10上下文；
- B组正确读取EvidenceItem原文；
- 延迟和模型调用次数拆分正确；
- 引用回溯率计算正确；
- Top10外证据可以进入证据包但不能插入`retrieved_chunks`；
- 非法引用、权限错误和混合索引版本导致实验失败；
- evidence降级时A组保留、B组记为失败；
- 报告只展示四项正式指标和引用回溯硬指标。

单元测试使用Fake LLM或mock，不产生真实远程调用费用。

## 十、执行顺序

先校验配置：

```bash
python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/evidence_orchestration.json
```

先运行2题冒烟：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/evidence_orchestration.json \
  --tenant-id <评测租户ID> \
  --limit 2 \
  --output-suffix smoke
```

确认两组材料、索引版本、引用回溯和RAGAS评分都正确后，再运行完整20题：

```bash
python scripts/run_eval.py run \
  --experiment eval/experiments/evidence_orchestration.json \
  --tenant-id <评测租户ID>
```

每道题只执行一次，不做warm-up，不重复调用测试稳定性。业务请求和RAGAS评分默认并发4，关闭RAGAS遥测和离线Langfuse。

## 十一、统一报告

正式输出：

```text
eval/results/<run_id>_evidence_orchestration/
├── manifest.json
├── experiment.snapshot.json
├── dataset.snapshot.json
├── shared_pipeline.raw.jsonl
├── baseline.raw.jsonl
├── candidate.raw.jsonl
├── baseline.metrics.json
├── candidate.metrics.json
├── comparison.json
└── report.md
```

报告至少包含：

1. 一句话明确结论；
2. 两组共用的v2检索和Qwen3精排条件；
3. Context Precision、Context Recall、P95延迟和平均模型调用次数；
4. 引用回溯率及是否达到100%；
5. 平均证据数量和字符数等诊断信息；
6. 改善最多和退化最多的题目；
7. 证据编排Token和成本观察值；
8. 是否建议默认开启、按需开启或暂不启用；
9. 原始结果和配置快照位置。

结论不能只写“Precision上升、Recall下降”。应明确说明收益、损失和使用建议。例如：

```text
证据包将Context Precision从0.82提升到0.91，Context Recall从0.95下降到0.94，
下降处于2个百分点护栏内；P95从3.2秒增加到12.6秒，每题增加1次模型调用，
引用回溯率为100%。综合判断证据编排有效，建议只在多要点问答和可信引用场景按需开启。
```

示例中的数值仅用于说明写法，正式报告必须使用真实结果。
