# 证据编排与可信引用改造提示词

点击此处可复制本篇提示词

在当前 rag-center 项目中，为 retrieve 增加可选的证据编排能力。保留现有 `retrieved_chunks` 契约，从同一次检索已经产生的候选中选择、去重并组织回答所需证据，新增顶层 `evidence_pack` 和对应 metadata。

证据正文只能复制原始 Chunk，必须能够通过 `chunk_id` 回溯来源。不生成最终答案，不自动继续检索，不修改原检索结果。

修改前先检查当前代码，以实际目录、类型和调用关系为准。复用现有 `RagService`、候选过滤、图谱候选注入、上下文扩展、`LLMProvider.chat_json()`、套餐策略和调试台，不重复创建检索主链路。

## 一、改造目标

- 请求新增可选 `evidence_options`
- 响应新增顶层 `evidence_pack`
- `retrieved_chunks` 的字段、数量、顺序、分数和 context 保持不变
- evidence 使用独立开关
- 证据候选包含最终 TopK、TopK 的 context sources 和 TopK 外基础候选
- 使用 LLM 识别必要要点并选择候选下标
- 后端复制原始 Chunk 构造 EvidenceItem
- 输出要点分组、完整性状态和缺失要点
- 编排失败时 `evidence_pack=null`，原 retrieve 正常返回
- 调试台增加证据编排开关和证据包展示
- 接入统一评测运行器，使用固定v2检索和Qwen3精排结果对比Top10与证据包

## 二、请求与响应模型

### 请求参数

在 `app/schemas/rag.py` 增加：

```python
class EvidenceOptions(BaseModel):
    enabled: bool | None = None
    max_items: int | None = Field(default=None, ge=1, le=20)
```

在 `RetrieveRequest` 增加：

```python
evidence_options: EvidenceOptions | None = None
```

请求示例：

```json
{
  "kb_ids": ["实际知识库ID"],
  "user_id": "debug-user",
  "query": "积分抵扣订单退款后，积分和现金分别怎么退？",
  "profile": "custom",
  "top_k": 5,
  "evidence_options": {
    "enabled": true,
    "max_items": 8
  }
}
```

### 响应模型

```python
EvidenceRole = Literal["core", "supporting"]
EvidenceStatus = Literal["complete", "partial", "missing"]


class EvidenceItem(BaseModel):
    evidence_id: str
    chunk_id: str
    kb_id: str
    document_id: str
    title: str
    heading_path: str | None = None
    index_version: str
    content: str
    source: str
    retrieved_rank: int | None = None


class EvidenceGroupItem(BaseModel):
    evidence_id: str
    role: EvidenceRole


class EvidenceGroup(BaseModel):
    aspect: str
    evidence: list[EvidenceGroupItem]
    covered: bool


class EvidencePack(BaseModel):
    status: EvidenceStatus
    missing_aspects: list[str] = Field(default_factory=list)
    groups: list[EvidenceGroup] = Field(default_factory=list)
    items: list[EvidenceItem] = Field(default_factory=list)


class RetrieveEvidenceMetadata(BaseModel):
    enabled: bool = False
    executed: bool = False
    candidate_count: int = 0
    evidence_count: int = 0
    output_chars: int = 0
    budget_exceeded: bool = False
    context_sources_included: bool = False
    status: EvidenceStatus | None = None
    latency_ms: int = 0
    degraded: bool = False
    error: str | None = None
```

在 `RetrieveData` 增加：

```python
evidence_pack: EvidencePack | None = None
```

在 `RetrieveMetadata` 增加：

```python
evidence: RetrieveEvidenceMetadata = Field(
    default_factory=RetrieveEvidenceMetadata
)
```

关闭 evidence 时固定返回：

```text
evidence_pack = null
metadata.evidence.enabled = false
metadata.evidence.executed = false
```

原有 `retrieved_chunks` 不增加证据字段，也不改成新的嵌套结构。

## 三、候选池与检索链路

在候选过滤和图谱注入完成后保存独立的 `candidate_snapshot`。原检索链路正常完成后，按以下顺序构造 evidence 候选：

```text
最终 retrieved_chunks
    ↓
retrieved_chunks 已有的 context.sources
    ↓
candidate_snapshot 中剩余的基础候选
    ↓
按 chunk_id 和规范化正文去重
```

要求：

- 编排服务不能原地修改主链路的 Chunk 列表
- 使用本次请求最终返回的 TopK，同时保留 TopK 外基础候选
- context sources 必须进入证据候选
- 最多向模型发送 20 条候选
- 至少为 TopK 外基础候选预留 6 个名额
- 某类候选不足时，空余名额可以分配给其他候选
- 模型输入优先使用 `retrieval_text`，返回证据使用原始 `content`
- evidence 关闭时不调用 LLM，不增加远程调用成本

候选配额建议：

```text
MAX_EVIDENCE_CANDIDATES = 20
MIN_BASE_POOL_CANDIDATES = 6
DEFAULT_MAX_EVIDENCE_ITEMS = 8
MAX_EVIDENCE_TEXT_CHARS = 2048
MAX_EVIDENCE_OUTPUT_CHARS = 12000
MAX_ASPECT_CHARS = 100
```

证据包达到输出字符预算后停止加入新 EvidenceItem，不截断已经选中的原始 `content`。删除证据后同步删除 group 引用，并重新计算 covered、missing_aspects 和 status。

## 四、证据编排服务

新增：

```text
app/services/evidence_orchestration_service.py
```

接口建议：

```python
@dataclass(slots=True)
class EvidenceOrchestrationResult:
    pack: EvidencePack | None
    metadata: RetrieveEvidenceMetadata


class EvidenceOrchestrationService:
    async def orchestrate(
        self,
        *,
        query: str,
        tenant_id: str,
        kb_ids: list[str],
        index_versions: dict[str, str],
        candidates: list[dict],
        retrieved_chunks: list[dict],
        options: EvidenceOptions,
    ) -> EvidenceOrchestrationResult:
        ...
```

处理顺序：

```text
检查开关和空候选
    ↓
构造并去重 evidence 候选
    ↓
调用 LLM 返回要点和候选下标
    ↓
严格校验 JSON
    ↓
按租户、知识库和索引版本重新加载选中 Chunk
    ↓
生成 E1、E2……
    ↓
构建 groups、missing_aspects 和 status
```

## 五、运行时提示词

系统提示词保存为服务内部常量：

```text
你是 RAG 证据编排器，不负责回答问题。

任务：
1. 将用户问题拆成回答时必须覆盖的最少要点。
2. 只从给定 candidates 中选择能够支撑这些要点的证据。
3. core 表示直接回答要点，supporting 表示提供必要条件、范围或补充说明。
4. 不要因为主题相似就选择候选，不要选择重复证据。
5. 每个必要要点都必须输出；没有核心证据时返回空 evidence 数组。
6. 同一候选可以支撑多个要点。
7. 不生成答案，不改写证据，不输出候选中不存在的事实。

严格返回 JSON：
{
  "aspects": [
    {
      "aspect": "简短的问题要点",
      "evidence": [
        {
          "index": 0,
          "role": "core|supporting"
        }
      ]
    }
  ]
}
```

输入示例：

```json
{
  "question": "积分抵扣订单退款后，积分和现金分别怎么退？",
  "max_evidence_items": 8,
  "candidates": [
    {
      "index": 0,
      "title": "会员体系与积分权益说明.md",
      "heading_path": "退款规则/积分退回",
      "text": "实际检索文本",
      "retrieved_rank": 1,
      "source": "hybrid"
    }
  ]
}
```

模型只返回数组下标，不返回 `chunk_id`、标题和正文。

调用：

```python
await llm_provider.chat_json(
    system_prompt=EVIDENCE_ORCHESTRATION_PROMPT,
    user_payload=payload,
    temperature=0.0,
    timeout_seconds=settings.evidence_timeout_seconds,
    log_payload=False,
)
```

当前 `chat_json()` 会记录完整 payload。给 `LLMProvider.chat_json()` 和实现增加向后兼容的 `log_payload: bool = True` 参数。传 `False` 时只记录模型、候选数、字符数、耗时和 trace，不记录问题和候选正文。

## 六、结果校验与构建

必须校验：

- 顶层是对象，`aspects` 是非空数组
- aspect 去除空白后不能为空，且不能超过长度限制
- evidence index 是整数且不能越界
- 同一 aspect 内不能重复引用同一个 index
- 同一 index 可以出现在不同 aspect
- role 只能是 `core` 或 `supporting`
- 全局去重后的证据数不能超过 `max_items`

模型输出不可信。收集所有选中 `chunk_id` 后，通过 ChunkRepository 按以下范围重新加载：

```text
tenant_id = 当前租户
kb_id IN 本次请求 kb_ids
每个 kb_id 的 index_version = 本次实际版本
chunk_id IN 选中 ID
```

重新加载数量与选中数量不一致时拒绝整个证据包。

EvidenceItem 的 `content`、文档信息和来源字段全部从原始 Chunk 复制。模型输出的同名字段一律忽略。

编号和状态规则：

```text
按候选首次被引用的顺序生成 E1、E2……
同一个 EvidenceItem 可以被多个 EvidenceGroup 引用
每个 aspect 至少有一条 core 才算 covered
只有 supporting 或没有证据都算未覆盖

全部 covered → complete
部分 covered → partial
全部未覆盖 → missing
```

`source` 复用 `retrieval_source`；图谱注入使用 `graph_injection`；context source 使用 `context:<relation>`。

```text

```

套餐不允许时返回现有 `FEATURE_NOT_ALLOWED`。

## 八、异常降级

以下情况降级：

- LLM 超时、429、500 或网络错误
- 非 JSON 或结构不合法
- index 越界、重复或类型错误
- 选择数量超过预算
- 权限范围重新校验失败

降级要求：

- `evidence_pack=null`
- 原 `retrieved_chunks` 正常返回
- `metadata.evidence.degraded=true`
- error 可定位问题，但不包含正文和敏感信息
- 不使用模型返回的半成品证据

## 九、调试台适配

复用现有检索调试页。

请求区域增加：

- 启用证据编排
- 最大证据数

结果区域新增整次请求级别的“证据包”，不要嵌套到每个 Chunk 卡片中。

展示：

- complete、partial 或 missing
- missing_aspects
- 按 aspect 分组的证据
- E 编号和 core/supporting
- 文档标题、章节路径和原始正文
- 是否来自最终 TopK
- 候选数、证据数、字符数、耗时和降级信息

扩展 `frontend/src/types/api.ts` 和请求类型，新增字段保持可选，兼容旧响应。

## 十、统一效果评测

新增统一实验配置：

```text
eval/experiments/evidence_orchestration.json
```

主实验固定同一条上游链路：

```text
v2 Hybrid + RRF Top20
          ↓
Qwen3-Rerank精排Top10
          ↓
A组：关闭证据编排，RAGAS评价Top10的context.content
B组：开启证据编排，RAGAS只评价evidence_pack.items.content
```

每道题只发起一次开启证据编排的真实retrieve请求。统一运行器从同一个响应拆出两组评测材料：

- A组读取原始`retrieved_chunks`，延迟统计到精排完成为止，模型调用次数记为1；
- B组读取`evidence_pack.items`，延迟统计完整请求，模型调用次数记为2；
- 两组共享同一次v2检索、同一次Qwen3精排和完全相同的Top10；
- 证据编排失败时A组仍可保存，B组记为失败，不能生成有效结论；
- EvidenceItem只能使用后端从仓储层重新加载的原始`content`，不能使用模型摘要或改写文本参与RAGAS。

实验配置只允许以下差异：

```text
evidence_options.enabled：false → true
```

两组都关闭Query Rewrite、同义词扩展和最终答案生成，不增加“不精排”第三组。主测试使用统一Golden Set的20道基础题，每题执行一次，业务请求和RAGAS评分并发均为4，warm-up为0，关闭RAGAS遥测和离线Langfuse。

四项正式指标：

```text
context_recall
context_precision
latency_p95_ms
average_application_model_calls
```

专题硬指标只保留：

```text
citation_traceability_rate = 100%
```

以下字段作为诊断信息写入逐题结果，不参与跨专题正式结论：

```text
evidence_count
evidence_chars
evidence_status
missing_aspects
status_accuracy
topk_outside_evidence_count
```

原有`scripts/compare_evidence_packs.py`和`eval/opt17_evidence/`保留为开发过程记录，不删除、不覆盖，也不再作为正式验收结论。正式报告统一写入：

```text
eval/results/<run_id>_evidence_orchestration/
```

## 十二、改造约束

- 不修改原 `retrieved_chunks` 契约
- 不让证据编排改变原检索结果
- 不接受候选中不存在的引用
- 不让模型生成或改写证据正文
- 不生成最终答案
- 不自动继续检索
- 不新增独立前端页面

- 编排失败时原 retrieve 正常返回
