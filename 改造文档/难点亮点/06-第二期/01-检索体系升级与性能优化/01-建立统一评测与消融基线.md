# 建立统一评测与消融基线

第一期已经能够使用 RAGAS 计算 Context Precision 和 Context Recall，也能通过日志查看每道题召回了哪些 Chunk。但这些评测分散在不同脚本和专题中，数据集、参数与报告格式并不完全一致。单独看一份报告没有问题，一旦进入连续优化阶段，就很难直接回答某次改造到底有没有效果。

第二期需要连续验证查询改写、专业精排、轻量图谱、可信证据和 Research。如果每项能力都使用自己的测试集和指标，最终得到的只会是一组无法横向比较的分数。因此，第二期所有优化开始前，首先建立了一套统一评测与消融基线。

## 为什么后续优化必须先统一基线

评测最容易出现的问题，不是没有分数，而是分数之间没有可比性。

例如，第一次测试使用 8 道简单题，第二次使用 20 道复杂题；第一次最终返回 Top5，第二次返回 Top10；第一次只打开精排，第二次同时改了索引、查询改写和精排模型。即使第二次的分数更高，也无法判断提升来自功能改造，还是来自题目和参数变化。

第一期评测还存在几个具体问题：

- 不同专题使用不同入口，运行规则和输出文件不统一
- 有的报告关注召回质量，有的只记录耗时，效果与代价无法一起比较
- 一次实验可能改变多个变量，结果提升后无法准确归因
- 汇总分数与逐题原始结果没有固定保存方式，出现退化后难以追溯
- 报告给出若干数字，却没有明确回答是否应该启用

这些问题在能力较少时尚可通过人工判断解决。第二期的检索链路更长，能力之间也会相互影响。查询改写会改变召回候选，候选内容会影响精排，图谱扩展又会改变最终上下文。如果没有统一基线，后续每一次效果讨论都会重新争论测试口径。

所以统一评测不是第二期完成后的验收补充，而是所有优化能够继续推进的前提。

## 统一基线由三层指标组成

不同指标回答的问题不同。第二期没有把所有数据压缩成一个总分，而是建立三层指标体系：第一层负责判断是否值得启用，第二层负责解释排序为什么变化，第三层负责观察不同能力内部是否按预期工作。

![三层评测指标体系](https://pic.niumianoffer.com/images/fs/eval-three-layer-metrics.png)

### 第一层：四个核心指标决定是否启用

所有检索类实验都必须输出四个核心指标：

| 指标 | 主要回答的问题 |
|---|---|
| Context Precision | 返回内容中有多少是真正有用的证据 |
| Context Recall | 标准答案需要的信息有没有被完整找到 |
| P95 延迟 | 绝大多数请求需要等待多长时间 |
| 平均应用模型调用数 | 本次提升增加了多少在线模型成本 |

Context Precision 和 Context Recall 由 RAGAS 评分。前者观察噪声，后者观察遗漏。P95 延迟和平均应用模型调用数衡量获得质量提升所付出的代价。RAGAS 自己为评分发起的 Judge 调用属于评测成本，不计入应用模型调用数。官网：[docs.ragas.io](https://docs.ragas.io)

这四项指标会进入每一份正式报告，也是统一决策规则的输入。一个方案即使提高了 Recall，如果 Precision 明显下降，或者 P95 超出在线链路能够接受的范围，也不能直接成为默认能力。

### 第二层：排序诊断指标解释结果变化

四个核心指标可以判断整体效果，却不一定能解释关键证据在列表中的位置。为此，精排实验会补充 `nDCG@10` 作为排序诊断指标。

Golden Set 中已经标注期望文档和章节。`nDCG@10` 会根据这些标注判断正确证据是否排在更靠前的位置。如果 Context Recall 没有变化，但 `nDCG@10` 提升，说明系统找到的内容相近，只是把关键证据移动到了更有利的位置。

这层指标只用于定位原因，不替代第一层指标，也不参与统一启用门槛。当前没有继续叠加 MRR、HitRate 和独立 Recall@K，因为更多相似指标并不会自动带来更可靠的结论。

### 第三层：自定义指标观察专题内部行为

图谱、证据编排和 Research 的内部机制不同，仅靠通用质量分数无法确认它们是否按设计运行。因此，第三层允许每个专题增加自定义诊断指标。

| 专题 | 自定义指标举例 | 用途 |
|---|---|---|
| 轻量图谱 | 受图谱影响的题数、注入候选数、补充 Chunk 数 | 判断关系扩展是否真正参与检索 |
| 可信证据 | 平均证据数、证据字符数、证据状态分布、引用回溯率 | 判断证据是否完整且能够回到原文 |
| Research | 补证题数、检索任务数、模型调用数、输入输出 Token、降级题数 | 判断复杂查询是否在预算内完成 |

其中部分自定义指标还可以成为专题硬门槛。例如证据编排和 Research 产生最终答案时，引用回溯率必须达到 100%。但这些指标只约束对应能力，不能用图谱注入了多少候选来证明 Context Precision 已经提升。

三层指标由此形成清晰分工：核心指标做决策，排序指标做解释，自定义指标检查专题行为。

## 指标统一以后，测试流程也必须固定

只有统一指标还不够。如果每次运行的条件和步骤仍然不同，报告依然无法比较。第二期把一次完整实验固定为六个步骤。

![单变量消融实验的六步闭环](https://pic.niumianoffer.com/images/fs/eval-six-step-ablation-loop.png)

### 第一步：冻结数据与运行条件

首先确定 Golden Set 版本、标准答案、知识库文档、索引版本、最终 TopK、候选宽度、并发数和超时时间。同一次实验中，这些条件不能在两组之间变化。

Golden Set 按版本保存。基础检索主要使用 20 道电商题，复杂能力使用 10 道人事题，多跳能力再从中选取对应子集。题目或标准答案发生变化时升级数据集版本，不覆盖旧版本。

```text
同一批问题和标准答案
同一份知识库与索引
同一组 TopK 和候选参数
同一套并发与超时规则
```

### 第二步：定义 baseline 与 candidate

每次消融实验只保留两组。`baseline` 代表改造前或关闭能力，`candidate` 代表改造后或开启能力。

实验配置必须声明 `changed_fields`，明确允许变化的字段。验证精排模型时，只能改变 `rerank_provider`；验证查询改写时，只能改变查询处理开关。评测程序会比较两组配置，发现没有声明的差异就停止执行。

```json
{
  "name": "rerank_upgrade_v2",
  "baseline": {"rerank_provider": "llm"},
  "candidate": {"rerank_provider": "qwen3"},
  "changed_fields": ["rerank_provider"]
}
```

这一步保证结果能够归因。如果需要比较三个候选方案，就拆成两次独立实验，而不是在一份报告中同时改变多个变量。

### 第三步：运行前完成配置校验

统一入口 `scripts/run_eval.py` 会先检查数据集和实验配置。空标准答案、重复测例、非法档位和未声明变量都应该在真实请求前被发现，避免运行到一半才知道实验无效。

```bash
# 校验 Golden Set：检查数据集结构、题目数量、题型和知识库配置
python scripts/run_eval.py validate-dataset \
  --dataset eval/datasets/golden_basic_20.json

# 校验实验配置：检查 baseline、candidate、唯一变量和运行参数
python scripts/run_eval.py validate-experiment \
  --experiment eval/experiments/rerank_upgrade_v2.json
```

### 第四步：执行两组请求并保存原始结果

正式运行时，每道题在 baseline 和 candidate 中各执行一次。请求采用相同的有界并发，必要时先进行明确记录的预热。精排类实验还会冻结共享候选，让两种精排器面对完全相同的 RRF 结果。

```bash
# 运行完整实验：依次执行 baseline、candidate，并将结果写入 eval/results/<run_id>
# 本地传入租户 ID 后，运行器会创建临时评测 Key，并在实验结束后自动删除
python scripts/run_eval.py run \
  --experiment eval/experiments/rerank_upgrade_v2.json \
  --tenant-id <评测租户ID> \
  --base-url http://127.0.0.1:8000
```

`run` 是完整实验入口。它会先执行本步骤中的两组请求，随后继续完成第五步的统一评分和第六步的报告生成。这里将三个阶段拆开讲，是为了说明原始结果、指标和结论分别在什么时候产生。

每道题的召回内容、阶段耗时、模型调用、有效配置和异常都会写入原始 JSONL。即使后面的 RAGAS 评分失败，检索结果也不会丢失，更不需要重新发起整轮请求。

### 第五步：统一评分并生成诊断信息

运行完成后，RAGAS 对两组结果计算 Context Precision 和 Context Recall，运行器汇总 P95 与模型调用数。需要排序诊断的实验继续计算 `nDCG@10`，图谱、证据和 Research 再写入各自的自定义指标。

这一步只负责生成事实数据，不在原始结果不完整时强行给出效果结论。请求失败、评分失败和降级都会被单独记录。

### 第六步：生成可以追溯的结论报告

最终目录同时保存数据快照、实验快照、逐题结果、指标汇总、两组对比和 Markdown 报告：

```text
<run_id>/
├── dataset.snapshot.json      # 本次运行使用的数据集快照，固定问题和标准答案
├── experiment.snapshot.json   # 本次运行使用的实验配置，记录两组参数和唯一变量
├── manifest.json              # 运行清单，记录时间、状态、题目数和成功失败情况
├── shared_candidates.raw.jsonl # 精排实验的共享候选，保证两组面对相同的 RRF 结果
├── baseline.raw.jsonl         # baseline 每道题的原始请求、召回结果、耗时和异常
├── candidate.raw.jsonl        # candidate 每道题的原始请求、召回结果、耗时和异常
├── baseline.metrics.json      # baseline 的四项核心指标与专项诊断指标
├── candidate.metrics.json     # candidate 的四项核心指标与专项诊断指标
├── comparison.json            # 两组指标差异、门槛检查和最终判定依据
└── report.md                  # 面向阅读者的结论报告和逐题改善、退化说明
```

报告必须说明主要指标提升了多少、增加了多少延迟和模型调用、是否出现失败，以及最终是否建议启用。结论固定收敛为建议启用、按场景启用、暂不启用、建议回退或评测失败，不能只写指标有升有降。

## 统一基线最终证明了什么

统一基线首先解决的是测试有没有标准。对于单个功能，可以用 baseline 与 candidate 的单变量消融判断它是否值得启用；对于一期、二期这样的整体改造，也可以在相同数据、TopK 和指标口径下完成系统级回归。每次测试都能从报告反向追溯到指标、原始结果和运行配置，不再依靠个别问题的主观体验判断效果。

例如，第二期改造完成后，我们使用 20 道基础题，对第一期和第二期的 Speed、Balanced、Quality 做了统一 Top5 测试。报告同时展示 Context Precision、Context Recall、P95 延迟和平均应用模型调用数：

| 阶段 | 档位 | Context Precision | Context Recall | P95 延迟 | 应用模型调用/题 |
|---|---|---:|---:|---:|---:|
| 第一期 | Speed | 0.8828 | 0.8042 | 1059.6 ms | 0 |
| 第一期 | Balanced | 0.8717 | 0.8042 | 2453.8 ms* | 0 |
| 第一期 | Quality | 0.9542 | 0.9333 | 62549.9 ms* | 2 |
| 第二期 | Speed | 0.9517 | 0.9333 | 1928.3 ms | 0 |
| 第二期 | Balanced | 0.9500 | 1.0000 | 1150.7 ms* | 0 |
| 第二期 | Quality | 0.9658 | 0.9833 | 3213.2 ms* | 2 |

![统一Top5下的一期与二期三档对比](https://pic.niumianoffer.com/images/fs/eval-phase1-phase2-top5.png)

从检索质量看，三个同名档位的 Precision 和 Recall 全部提升。Speed 的 Precision 提升 6.89 个百分点，Recall 提升 12.91 个百分点；Balanced 的 Precision 提升 7.83 个百分点，Recall 提升 19.58 个百分点；Quality 的 Precision 提升 1.17 个百分点，Recall 提升 5 个百分点。第二期 Balanced 的 Recall 达到 1.0000，Quality 的 Precision 达到 0.9658，三档的定位变得更加清楚。

从性能和调用成本看，链路更复杂的 Balanced 与 Quality 改善最明显。Balanced 的 P95 从约 2.45 秒降到 1.15 秒，Quality 从约 62.55 秒降到 3.21 秒；两档都没有增加应用模型调用数。Speed 没有模型调用，P95 从约 1.06 秒升到 1.93 秒，说明它的质量明显提升，但延迟仍有继续优化空间。

`*` 标记的 Balanced 和 Quality P95 来自原 Top10 正式请求，只用于比较延迟量级，不是最终 Top5 配置的新一轮端到端 P95。Balanced 和 Quality 的 Top5 质量则来自冻结结果的统一离线评分。把这些限制写进报告，可以避免后续引用时把诊断数据误当成精确生产数据。

综合四项指标可以得出更完整的结论：第二期三个档位的检索质量全面提升，Balanced 和 Quality 的长尾延迟显著下降，模型调用成本没有增加。虽然 Speed 的 P95 出现上升，但不改变第二期整体改造有效的判断，也为下一步性能优化留下了明确目标。

这组对比同时包含索引结构、Chunk、检索链路和精排方案等多项变化，因此它证明的是第二期整体改造有效，不能把全部收益归因于某一个功能。要判断某项能力的独立价值，仍然需要回到 baseline 与 candidate 的单变量消融报告。

## 总结

统一评测与消融基线把第二期的测试方式收敛成了一条完整主线：先用三层指标明确判断依据，再冻结数据和运行条件，通过 baseline 与 candidate 隔离变量，保存逐题结果并统一评分，最后生成能够追溯、能够执行的结论报告。

有了这套基线，后续优化不再依靠功能是否已经实现或个别问题是否看起来更好来判断价值。第一期与第二期三档的统一对比也表明，第二期不仅提高了检索质量，还显著改善了复杂档位的长尾延迟，并在没有增加模型调用数的情况下完成了整体能力升级。
