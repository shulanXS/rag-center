# 从串行召回到并行检索与资源复用

第一期已经通过向量检索、BM25 和 RRF 建立了完整的 Hybrid Search。它解决了单一路径容易漏召回的问题，却没有充分优化两路检索的执行方式：向量分支完成后才启动 BM25，外部请求还可能反复创建 HTTP 客户端。检索效果已经具备，用户等待时间却随着每个阶段不断累加。

第二期没有减少候选数量，也没有关闭任何召回分支，而是重新组织执行顺序和资源生命周期。Vector 与 BM25 改为并行，模型服务和 Elasticsearch 连接跟随应用生命周期复用，分支耗时与降级状态也被完整记录。这样得到的性能收益来自执行效率，而不是牺牲检索质量。

## 第一期的性能问题出在哪里

一次 Hybrid 请求至少包含查询向量生成、向量数据库检索、BM25 检索和 RRF 融合。第一期按照顺序执行时，总耗时接近每个阶段的累加：

```text
T_hybrid ≈ T_embedding
         + T_vector_search
         + T_bm25_search
         + T_rrf
```

Embedding 和向量查询存在依赖，必须先拿到查询向量，再访问向量数据库。但 BM25 只依赖文本 Query，与向量分支没有先后关系。如果仍然等向量结果返回后再启动 BM25，这段等待时间就被白白浪费了。

另一个问题来自外部连接。Embedding、查询改写、Qwen3 精排和 Elasticsearch 都需要发起 HTTP 请求。如果每次调用都创建并关闭客户端，就会反复承担 TCP 建连、TLS 握手和连接回收成本。单次请求只增加少量时间，并发升高后却会明显放大 P95，还可能增加本机端口和下游服务的压力。

第一期的日志主要记录整段检索耗时。请求变慢时，很难快速判断问题出在 Embedding、向量数据库、Elasticsearch，还是外部连接。第二期因此不能只把串行改成并行，还需要同时补齐资源复用、分支观测和异常降级。

## 第二期对检索执行链路做了哪些改动

这次性能优化由三项改动组成。三者共同作用，才形成最终的检索执行底座。

![从串行等待到并行检索与连接复用](https://pic.niumianoffer.com/images/fs/parallel-retrieval-and-pooling.png)

### Vector 与 BM25 从串行改为并行

第二期把召回拆成 Vector 和 BM25 两个独立分支。Vector 分支内部仍然按照 Embedding、向量查询的顺序执行，BM25 分支则可以同时开始：

```python
# 两路召回没有先后依赖，同时启动并等待结果
vector_result, bm25_result = await asyncio.gather(
    run_vector_branch(search_query, retrieval_scope),
    run_bm25_branch(search_query, retrieval_scope),
)
```

并行后的时间关系变为：

```text
T_hybrid ≈ max(
    T_embedding + T_vector_search,
    T_bm25_search
) + T_rrf
```

如果向量分支需要 700 毫秒，BM25 需要 500 毫秒，串行至少等待约 1200 毫秒，并行后则接近较慢分支的 700 毫秒，再加很小的 RRF 计算时间。

这项改造只改变执行时序。Vector TopK、BM25 TopK、RRF 参数和最终结果数量保持不变，因此不会通过缩小检索范围换取速度。

### 外部连接从按请求创建改为应用级复用

服务启动时创建两组基于 HTTPX 的异步客户端：一组访问模型服务，另一组访问 Elasticsearch；应用关闭时再统一释放。官网：[python-httpx.org](https://www.python-httpx.org/)

```python
@asynccontextmanager
async def lifespan(app):
    # 应用启动时创建连接池，供后续请求共同复用
    clients = build_external_http_clients()
    app.state.external_http_clients = clients
    try:
        yield
    finally:
        # 应用关闭时统一释放模型服务和 Elasticsearch 连接
        await clients.aclose()
```

模型客户端由 Embedding、Query Rewrite、证据编排和 Qwen3 精排复用，Elasticsearch 使用独立客户端。两组连接池分别设置最大连接数、最大 Keep-Alive 数量和连接存活时间，既减少重复建连，也避免连接无限增长。

两类服务没有共用同一个连接池。模型服务与 Elasticsearch 的地址、代理策略和负载特征不同，拆开后可以避免某类慢请求占满全部连接。Elasticsearch 客户端还会关闭环境代理继承，防止内部检索流量被意外发送到外部代理。

### 召回分支增加独立观测与降级

Vector 分支会分别记录 Embedding 调用次数、Embedding 耗时、向量查询次数和向量数据库耗时；BM25 分支记录请求次数和分支耗时。最终元数据再汇总 Hybrid 总耗时、降级来源和失败原因。

| Vector | BM25 | 系统行为 |
|---|---|---|
| 成功 | 成功 | 执行 RRF 融合 |
| 失败 | 成功 | 返回 BM25 结果并标记降级 |
| 成功 | 失败 | 返回 Vector 结果并标记降级 |
| 失败 | 失败 | 返回统一检索失败错误 |

并行执行并没有削弱原来的可用性。任何一路失败，另一路仍然可以提供候选；只有两路同时失败，主请求才会失败。任务被主动取消时，`CancelledError` 继续向上传播，避免客户端断开后后台任务仍然占用资源。

## 固定条件测试证明了多少性能收益

性能测试最容易被参数变化干扰。如果改造后同时把 Top20 缩成 Top5，即使延迟下降，也无法证明收益来自并行和连接复用。

因此，测试固定使用 v2 索引、20 道基础题、Custom 档、Hybrid 20+20、RRF 60 和最终 Top10，同时关闭 Query Rewrite、同义词扩展、精排和证据编排。改造前后唯一变化是 Hybrid 执行方式和外部连接生命周期。

| 阶段 | Context Precision | Context Recall | P50 | P95 | Embedding/题 | 失败 |
|---|---:|---:|---:|---:|---:|---:|
| 改造前 | 0.9087 | 0.9500 | 1664.8 ms | 2538.9 ms | 1 | 0/20 |
| 改造后 | 0.9212 | 0.9500 | 903.7 ms | 1638.3 ms | 1 | 0/20 |
| 变化 | +0.0125 | 0 | -45.7% | -35.5% | 0 | 0 |

![并行检索的性能收益与降级路径](https://pic.niumianoffer.com/images/fs/parallel-performance-and-degradation-v2.png)

P50 从约 1.66 秒降到 0.90 秒，说明普通请求接近缩短一半；P95 从约 2.54 秒降到 1.64 秒，长尾延迟下降 35.5%。Context Recall 保持不变，Context Precision 没有退化，20 道题也全部成功。

这组结果证明，性能收益来自并行等待和连接复用，而不是减少候选、关闭 BM25 或降低最终上下文数量。它也为后续多知识库全局检索、专业精排和 Research 留出了更稳定的延迟预算。

## 性能优化的边界

并行会缩短等待时间，也会提高某一时刻的资源并发度。串行链路一次只访问一个外部服务，并行链路会同时使用向量侧和 BM25 侧。因此，连接池上限、数据库连接数、下游限流和超时必须一起规划，不能简单地把业务并发不断调高。

连接复用也不代表连接永远有效。Keep-Alive 连接仍会按存活时间回收，远端主动关闭后也需要重新建立。连接池减少的是正常流量下的重复建连，不能替代超时、降级和容量监控。

本次正式数据隔离的是基础 Hybrid 召回。Quality 还包含 Query Rewrite 和 Qwen3 精排，它的端到端延迟自然高于纯 Hybrid；Research 还有查询分解和多轮补证，也需要单独设置预算。不能把基础召回的 P95 直接当成所有档位的响应时间。

## 最后收口检索档位

执行链路稳定以后，第二期将 Speed、Balanced、Quality 三个命名档位统一为服务端固定契约：

| 档位 | 查询处理 | 内部召回 | 精排 | 最终返回 |
|---|---|---|---|---:|
| Speed | 不改写、关闭同义词 | Vector Top10 | 关闭 | Top5 |
| Balanced | 不改写、关闭同义词 | Vector Top10 + BM25 Top10 + RRF 60 | 关闭 | Top5 |
| Quality | Query Rewrite、关闭同义词 | Vector Top20 + BM25 Top20 + RRF 60 | Qwen3 Top5 | Top5 |

三个档位统一返回 Top5，让效果比较建立在相同上下文预算上。Speed 提供最低复杂度的向量检索，Balanced 用并行 Hybrid 提高证据覆盖，Quality 保留更宽候选并通过专业精排控制噪声。

命名档位不能再被客户端覆盖 `top_k`、`rrf_k`、查询处理和精排开关，避免同一个 Balanced 在不同调用方手里表现完全不同。需要调整高级参数时必须使用 Custom，由调用方明确承担配置责任。

档位负责定义检索行为，Plan 负责限制可用能力和资源额度。Research 使用自己的固定检索配置，不会因为普通检索档位调整而被意外改变。

## 总结

第二期性能优化沿着一条清晰主线完成：第一期 Hybrid 已经能够找到结果，但串行等待、重复建连和粗粒度观测拖慢了在线请求；第二期将两路召回并行执行，把外部连接提升到应用级复用，并为每个分支补齐观测与降级。

固定条件测试显示，P50 下降 45.7%，P95 下降 35.5%，检索质量没有退化。在这套稳定执行底座上，Speed、Balanced、Quality 最终收敛为统一 Top5、行为固定的三档能力，为多知识库融合和后续高阶检索提供了清晰边界。
