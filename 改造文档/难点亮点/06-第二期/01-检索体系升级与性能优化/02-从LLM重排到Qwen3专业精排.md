# 从 LLM 重排到 Qwen3 专业精排

第一期已经在混合召回之后加入重排。向量检索和 BM25 负责尽量找全候选，RRF 完成初步融合，再由通用 LLM 判断哪些片段真正有助于回答问题。这套方案明显改善了 Quality 档的检索质量，却也把生成式大模型的长耗时和高成本带进了每一次在线检索。

第二期没有放弃重排，而是将它升级为 Qwen3 专业精排。整个改造经历了四个阶段：先确认旧重排的性能瓶颈，再完成模型选型和工程接入，然后通过统一评测发现首次接入的质量退化，最后收紧精排指令与查询参数，使专业精排真正达到可用标准。

## 第一期已经有重排，为什么还要升级

第一期的重排由通用 LLM 完成。系统把用户问题和 RRF Top20 候选组织成提示词，要求模型为每个 `chunk_id` 生成相关性分数和理由，然后解析 JSON、重新排序并返回 TopK。

```text
问题 + RRF Top20
        ↓
构造排序提示词
        ↓
通用 LLM 生成 chunk_id、score 和 reason
        ↓
解析 JSON 并重新排序
        ↓
返回最终结果
```

![生成式LLM重排与Qwen3专业精排对比](https://pic.niumianoffer.com/images/fs/rerank-llm-vs-qwen3.png)

这套方式容易复用现有模型，也能通过提示词表达复杂要求。但排序本来只需要候选下标和相关性分数，通用 LLM 却需要阅读完整 JSON、理解输出格式，再生成分数、理由和结构化结果。候选越多，输入与输出 Token 越多，延迟和成本都会随之增长。

统一评测将旧 LLM 重排与 Qwen3 精排放在相同的 RRF Top20 候选上比较。使用 v2 索引的正式结果显示，LLM 重排的 P95 达到 79.7 秒，20 道题中还有两道首次运行超时。对于普通在线检索，这个长尾延迟已经超出可接受范围。

历史同项目测算中，LLM 重排每 1000 次预计约 17.04 元。这个数字会随候选长度、模型价格和计费方式变化，不能当作当前精确账单，但足以说明调用量扩大后的成本压力。

除了性能和成本，生成式重排还依赖模型严格输出 JSON。候选遗漏、重复 ID、字段缺失或格式错误都会触发回退。第一期证明了重排有价值，第二期要解决的是如何让这项能力适合稳定在线运行。

## 精排模型如何完成选型

专业精排模型接收一个 Query 和一组 Documents，直接返回每个候选的相关性分数，不需要生成回答和排序理由。相比通用 LLM，它的任务目标和接口形式都更贴近 RAG 排序。

精排既可以本地部署，也可以使用远程服务。本地部署能够把文本留在自己的环境中，延迟也更容易控制，但需要准备 GPU、模型服务、容量规划和监控。当前项目的重点是完善 RAG 链路，不是建设推理平台，因此第二期优先选择远程精排服务。

市面上可以选择不同厂商的 Rerank 模型。项目最终使用阿里云百炼提供的 `qwen3-rerank`，主要基于以下考虑：

- 项目知识库以中文内容为主，Qwen3 更适合当前语言场景
- 支持 `instruct`，可以明确告诉模型什么样的片段才算有效证据
- 接口直接返回候选下标和 `relevance_score`，不再生成排序 JSON
- Top20 候选远低于接口上限，不需要拆成多次请求
- Embedding 等模型能力已经接入同一厂商平台，无需新增供应商账号、鉴权和费用治理

使用同一平台不意味着 Embedding 与精排共用同一个接口。Qwen3 Rerank 使用独立服务地址，但 API Key 可以默认复用现有模型凭据，需要单独配额时再配置专用 Key。官网：[aliyun.com](https://www.aliyun.com/product/bailian)

模型选型由此完成：保留统一 `RerankProvider` 抽象，线上实现切换为 Qwen3，旧 LLM 重排只作为离线基线，不再暴露给普通产品请求。

## 专业精排如何接入检索链路

新的精排链路仍然从混合召回开始：

```text
Vector + BM25
        ↓
RRF 候选 Top20
        ↓
Qwen3 Rerank
        ↓
最终 TopK
```

`Qwen3RerankProvider` 接收 `query`、`documents`、`top_n` 和 `instruct`。候选最多保留 50 条，每条精排文本最多保留 1024 个字符，避免超长输入放大远程调用成本。

优化十六首次接入时，Qwen3 接收 RRF Top20 候选，使用用户原始问题作为 Query，Document 由标题和正文组成，最终返回 Top10。下面使用实际评测题目和候选片段展示当时的请求结构。为了便于阅读，`documents` 只展示前两个候选，真实请求会携带完整候选列表。

```json
{
  "model": "qwen3-rerank",
  "query": "申请七天无理由退货需要满足什么期限和商品条件？",
  "documents": [
    "标题：售后服务与退换货政策.md\n正文：## 2. 七天无理由退货\n### 2.1 适用条件\n- 确认收货后 7 个自然日内发起……",
    "标题：售后服务与退换货政策.md\n正文：# 售后服务与退换货政策\n适用范围：B2C 实物商品售后……"
  ],
  "top_n": 10,
  "instruct": "Given a question, retrieve passages that contain evidence needed to answer the question."
}
```

这份 JSON 中的字段和参数就是优化十六实际采用的方式。此时尚未使用结构化 `retrieval_text`，也没有把 Query Rewrite 的结果传给精排。接口虽然已经从生成式 LLM 切换到专业 Rerank，但输入仍然沿用第一期的组织方式。

接口返回结果后，Provider 会检查 `results` 数量、候选下标和相关性分数。下标不能越界或重复，分数必须是有限数值，再统一限制到 0 到 1。只有响应完整通过校验，结果才会进入最终排序。

如果请求超时、HTTP 状态异常、响应不是合法 JSON，或者字段不符合协议，检索主链路不会失败，而是回退到 RRF 原始顺序，并在元数据中记录降级原因。精排负责改善顺序，但不能成为基础检索的单点故障。

## 第一次接入为什么质量反而下降

模型更专业，不代表直接替换以后一定更好。第一次统一评测使用第一期已有索引，为每道题冻结同一份 RRF Top20，再分别交给旧 LLM 和 Qwen3，最终都返回 Top10。查询改写、同义词扩展和证据编排全部关闭，唯一变化是精排 Provider。

当时 Qwen3 接收的是用户原始问题，候选主要使用旧索引中的标题与正文，排序要求也停留在通用相关性判断。也就是说，接口已经换成专业精排，但 Query、Document 和任务指令还没有围绕当前 RAG 场景完成对齐。

第一次报告的结果如下：

| 指标 | LLM 重排 | 首次 Qwen3 精排 | 变化 |
|---|---:|---:|---:|
| Context Precision | 0.930 | 0.889 | -4.1 个百分点 |
| Context Recall | 0.950 | 0.858 | -9.2 个百分点 |
| P95 延迟 | 50.1 秒 | 4.6 秒 | -90.9% |
| 平均应用模型调用数 | 1.00 | 1.00 | 不变 |

Qwen3 把 P95 从约 50 秒降到 4.6 秒，工程性能优势非常明显，但 Context Precision 和 Context Recall 同时退化。此时只能得出速度和成本方向正确、质量尚未通过的结论，不能因为模型名称更专业就直接宣布升级成功。

后续使用 v2 索引复测时，Qwen3 的 Recall 已经超过 LLM，但 Precision 仍然偏低。这进一步说明问题不只是模型能力，还与输入文本、排序目标和最终结果数量有关。

## 真正的问题是精排目标没有对齐

![第一次接入时的精排目标错位](https://pic.niumianoffer.com/images/fs/rerank-target-misalignment.png)

结合首次退化题和后续 Quality 链路继续检查，最终发现精排存在两个错位。

第一个错位是任务指令过于宽泛。主题相关的背景片段可能获得较高分数，但它们并不能直接回答用户问题。对于条件、期限、金额和多子问题场景，主题相似远远不够。

第二个错位出现在后续 Quality 链路。Quality 档已经通过 Query Rewrite 生成更明确的 `search_query`，召回候选也是围绕它产生的，精排却继续使用用户原始问题。两个阶段对相关性的理解不一致，容易让已经召回的关键证据在精排时再次掉下去。

另外，第一期 Quality 返回 Top10，后半部分容易混入噪声。第二期将三个命名档位统一为 Top5，在相同上下文预算下重新确定 Speed、Balanced 和 Quality 的职责。Quality 仍保留 20+20 的宽候选，只把精排输出收紧到 Top5，不会因为最终结果变少而提前损失召回范围。

## 收紧指令，并让 Query 前后一致

轻量图谱改造先通过 v2 索引补充了结构化 `retrieval_text`，让精排能够看到文档、章节路径和正文。在此基础上，优化二十又对 Qwen3 做了两次递进调整。

第一步把 `instruct` 收紧为面向证据的中文规则：

- 能直接回答问题，或者给出明确规则、条件、时间、金额和结论的片段优先
- 只有主题相似、只提供背景、需要推测才能关联的片段降权
- 多子问题优先覆盖所有子问题
- 内容重复或高度重叠的片段降权

第二步让精排只使用 Query Rewrite 产出的实际 `search_query`。改写失败时自然回退原问题，不再拼接原始问题与改写结果。这样 Query Rewrite、召回和精排围绕同一个问题表达工作。

优化后的请求结构如下。这里继续使用同一道实际评测题，Query Rewrite 将原问题收敛为 `七天无理由退货条件`。Document 改为索引阶段统一生成的 `retrieval_text`，包含文档、完整章节路径和正文；Quality 最终只取 Top5。为了便于阅读，`documents` 仍只展示两个候选。

```json
{
  "model": "qwen3-rerank",
  "query": "七天无理由退货条件",
  "documents": [
    "文档：售后服务与退换货政策.md\n章节：售后服务与退换货政策 > 2. 七天无理由退货 > 2.1 适用条件\n正文：- 确认收货后 7 个自然日内发起；\n- 商品完好，不影响二次销售……",
    "文档：售后服务与退换货政策.md\n章节：售后服务与退换货政策 > 2. 七天无理由退货 > 2.2 不适用类目\n正文：- 鲜活易腐、订制商品、数字化商品、报纸期刊……"
  ],
  "top_n": 5,
  "instruct": "根据用户问题对候选片段进行严格相关性排序。只提高能够直接回答问题、提供明确规则、条件、时间、金额或结论的片段。仅主题相似、只提供背景信息、需要推测才能关联的片段应降低排名。对于包含多个子问题的查询，优先覆盖所有子问题。重复或信息高度重叠的片段应降低排名。"
}
```

前后两份 JSON 的接口字段没有变化，真正变化的是精排看到的内容和任务目标：Query 从用户原问题变成 Rewrite Query，Document 从标题加正文升级为结构化检索文本，`top_n` 从 10 收紧到 5，`instruct` 也从通用相关性描述变成直接证据优先的中文规则。

为了确认每一步是否有效，实验复用同一批 Quality Top10 候选，只改变 `instruct` 和精排 Query：

| 方案 | Context Precision | Context Recall |
|---|---:|---:|
| A：原始 Qwen3 排序截取 Top5 | 0.9300 | 0.9333 |
| B：加入严格中文 instruct | 0.9342 | 0.9833 |
| C：再使用 Rewrite Query 精排 | 0.9658 | 0.9833 |

![Qwen3专业精排的ABC单变量消融](https://pic.niumianoffer.com/images/fs/rerank-abc-ablation.png)

严格中文指令让 Recall 提升 5 个百分点，把遗漏的必要证据重新送回前五；使用 Rewrite Query 后，Precision 又提升 3.17 个百分点。最终 C 相比初始 A，Precision 提升 3.58 个百分点，Recall 提升 5 个百分点，两项核心质量指标都得到改善。

这组结果来自冻结候选上的消融实验，没有重新执行完整的 20+20 端到端检索，因此可以用于确定精排参数，不能把单次 Qwen3 调用耗时当作最终链路 P95。

## 最终 Quality 是否超过第一期

在统一 Top5 口径下，第一期 Quality 使用旧 LLM 重排，第二期 Quality 使用严格中文 instruct、Rewrite Query 和 Qwen3 Top5：

| 阶段 | Context Precision | Context Recall |
|---|---:|---:|
| 第一期 Quality | 0.9542 | 0.9333 |
| 第二期 Quality | 0.9658 | 0.9833 |
| 变化 | +1.17 个百分点 | +5.00 个百分点 |

第二期 Quality 的 Precision 达到三档最高，Recall 也高于 Speed，只比 Recall 为 1.0000 的 Balanced 低 1.67 个百分点。专业精排最终不仅保留了数量级更好的性能和成本优势，也在统一质量口径下超过了第一期 Quality。

这里的提升来自完整链路配合，不应该只归功于更换模型。结构化 `retrieval_text` 改善了 Document，严格 `instruct` 明确了排序目标，Rewrite Query 保证召回与精排一致，Top5 又控制了最终上下文噪声。Qwen3 是核心能力，但正确的输入和边界同样重要。

## 总结

从 LLM 重排升级到 Qwen3 专业精排，不是一次简单的 Provider 替换。

旧 LLM 重排已经证明排序有价值，却带来约 50 到 80 秒的 P95 和更高的规模化成本。Qwen3 因为中文能力、专用排序接口以及与现有模型平台一致而被选中，首次接入也确实把 P95 降低了约 90%。但第一次评测中 Precision 和 Recall 同时下降，说明专业模型不能脱离具体输入直接获得收益。

第二期随后收紧中文排序指令，让精排使用与召回一致的 Rewrite Query，并将最终结果统一为 Top5。优化二十的消融结果显示，两项核心质量指标最终都得到提升；与第一期 Quality 相比，第二期 Quality 的 Precision 和 Recall 也实现了同步增长。至此，Qwen3 才真正从一个速度更快的替代方案，变成适合在线 RAG 中台的专业精排能力。
