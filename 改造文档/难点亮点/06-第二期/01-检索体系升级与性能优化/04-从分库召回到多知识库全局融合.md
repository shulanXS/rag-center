# 从分库召回到多知识库全局融合

第一期已经支持一次查询多个知识库。用户可以同时选择产品规则库、客服 FAQ 库和业务流程库，系统分别检索各个知识库，再把结果合并成一个列表。跨库查询从功能上已经可用，但内部仍然是多个单库检索的叠加，知识库越多，重复计算和二次融合的问题越明显。

第二期没有改变跨库接口的使用方式，而是重新定义它的执行语义：多个被授权的知识库共同组成一个检索作用域，系统在这个范围内只执行一次 Query 处理、一次 Embedding、一次全局 Vector、一次全局 BM25 和一次全局 RRF。跨库检索由多个单库结果拼接，升级为真正的全局检索。

## 已经支持跨库查询，为什么还要改造

第一期收到多个 `kb_id` 后，会让每个知识库独立执行完整检索，再进行第二次跨库融合：

```text
KB-A：Embedding → Vector + BM25 → 单库 RRF → TopK ─┐
                                                     ├→ 跨库二次 RRF → 最终 TopK
KB-B：Embedding → Vector + BM25 → 单库 RRF → TopK ─┘
```

![分库召回与多知识库全局融合对比](https://pic.niumianoffer.com/images/fs/global-fusion-before-after.png)

这套实现便于复用单库能力，却带来三个问题。

首先，同一个 Query 会在每个知识库中重复计算 Embedding。查询两个知识库需要两次，查询五个知识库最多需要五次。向量本身表达的是问题语义，并不会因为知识库不同而改变，这些调用属于重复计算。

其次，每个知识库都会分别访问向量数据库和 Elasticsearch。知识库数量增加后，Vector、BM25 和单库 RRF 的执行次数同步增长。即使多个知识库并发，连接、数据库和下游服务的资源消耗仍然按知识库数量放大。

最后，跨库二次 RRF 只看候选在所属知识库中的局部名次。KB-A 的第一名和 KB-B 的第一名会被映射到相同量级，即使前者能够直接回答问题，后者只是弱相关内容。最终结果容易形成固定的 5 加 5，看起来来源均衡，实际上是在为每个知识库隐式保留名额。

跨库查询真正要回答的问题，不是每个知识库各自返回哪些内容，而是在当前用户有权限访问的所有内容中，哪些证据最相关。因此，召回和排序都应该从一开始就在全局范围内完成。

## 第二期对跨库检索做了哪些优化

第二期没有继续修补二次融合，而是从检索作用域、召回次数和融合层级三个方面重构跨库链路。

### 建立统一检索作用域

系统先把本次请求允许访问的知识库及其生效索引版本整理成一个作用域：

```json
{
  "tenant_id": "tenant-a",
  "index_versions": {
    "kb-product": "v2",
    "kb-faq": "v1",
    "kb-policy": "v3"
  }
}
```

`tenant_id` 限制租户边界，`kb_id` 限制用户本次允许访问的知识库，`index_version` 确保每个知识库只查询当前生效版本。不同知识库可以处于不同索引版本，系统不会为了全局查询把它们错误地压成同一个版本。

作用域由服务端完成权限和状态解析。客户端不能通过增加 `kb_id` 绕过租户隔离或 Plan 上限，索引正在切换时也不会同时召回新旧版本内容。

### Query 与 Embedding 在作用域内只执行一次

Query Rewrite 和同义词处理在进入知识库检索前完成，所有知识库共享同一个 `search_query`。Vector 分支也只对这个 Query 计算一次 Embedding，再用同一份查询向量检索整个授权作用域。

```text
search_query
    ↓
一次 Embedding
    ↓
query_vector
    ↓
tenant_id + 多组 kb_id/index_version 条件
    ↓
一次全局向量查询
```

基于 pgvector 的查询会在数据库层同时带上租户和多知识库版本条件，再对所有满足条件的 Chunk 统一按向量距离排序。官网：[github.com/pgvector](https://github.com/pgvector/pgvector)

```sql
WHERE tenant_id = :tenant_id
  AND (
       (kb_id = :kb_a AND index_version = :version_a)
    OR (kb_id = :kb_b AND index_version = :version_b)
  )
ORDER BY embedding <=> :query_vector
LIMIT :top_k
```

无论查询一个、两个还是五个知识库，一次跨库请求都只需要一次 Embedding 和一次向量数据库查询。

### Vector、BM25 和 RRF 都改为全局执行

BM25 使用与向量分支相同的知识库作用域，在 Elasticsearch 中执行一次全文检索。官网：[elastic.co](https://www.elastic.co/elasticsearch)

Vector 与 BM25 由前一篇建立的并行检索底座同时启动。两路返回的已经是全局候选，系统不再为每个知识库生成局部 TopK，也不再执行跨库二次 RRF。

全局 RRF 使用 `kb_id + chunk_id` 作为候选唯一键，避免不同知识库出现相同 Chunk ID 时被错误合并。一个片段同时出现在 Vector 与 BM25 列表中，就累加两路排名分；只被一路召回，也可以根据该路排名参与最终竞争。

```text
RRF(chunk) = 1 / (60 + vector_rank)
           + 1 / (60 + bm25_rank)
```

最终结果可能来自一个知识库，也可能按照 8 加 2、6 加 4 等比例分布。来源比例由全局相关性决定，不再由每个知识库先获得一份固定候选。

### 融合以后仍然保留完整来源

全局融合不会丢失知识库边界。每个返回结果仍然保留 `kb_id`、`kb_name`、`document_id`、`chunk_id`、`index_version`、两路原始排名和最终 RRF 分数。

检索元数据还会记录本次知识库数量、知识库版本映射、Embedding 请求数、Vector 请求数、BM25 请求数以及最终来源分布。调用方可以展示来源，证据编排可以生成引用，排查性能问题时也能确认一次跨库请求实际调用了多少外部资源。

## 优化后的跨库架构

经过上述改造，跨库检索从多套单库管道加二次融合，收敛成一条全局管道：

![统一检索作用域中的权限版本与来源追溯](https://pic.niumianoffer.com/images/fs/global-scope-and-provenance-v2.png)

这条链路同时消除了按库重复 Embedding、按库重复访问检索后端和跨库二次融合。知识库数量仍会扩大数据库过滤范围，但不会再线性增加模型调用和外部请求次数。

异常处理也从按知识库失败改为按召回分支降级。Vector 失败时可以返回全局 BM25 结果，BM25 失败时可以返回全局 Vector 结果，只有两路同时失败才会终止整个跨库请求。

## 跨库接口性能提升了多少

跨库性能测试固定使用相同的两个知识库、Hybrid 20+20、RRF 60 和最终 Top10，关闭 Query Rewrite、同义词、精排和证据编排。测试包含两道双知识库问题，每道题预热一次后正式运行 10 次，共得到 20 个有效样本，请求并发为 1。

| 阶段 | 平均延迟 | P50 | P95 | 最大延迟 | 成功请求 |
|---|---:|---:|---:|---:|---:|
| 改造前 | 1221.6 ms | 1162.4 ms | 1512.1 ms | 1801.2 ms | 20/20 |
| 改造后 | 727.3 ms | 668.0 ms | 1118.4 ms | 1345.9 ms | 20/20 |
| 变化 | -40.5% | -42.5% | -26.0% | -25.3% | 无失败 |

![双知识库全局融合的调用收敛与性能收益](https://pic.niumianoffer.com/images/fs/global-fusion-performance.png)

改造后，跨库接口的平均延迟从约 1.22 秒降到 0.73 秒，P50 从约 1.16 秒降到 0.67 秒，P95 从约 1.51 秒降到 1.12 秒。普通请求和长尾请求都得到改善，20 个样本没有出现失败。

工程行为测试同时确认，双知识库请求只计算一次 Embedding，只执行一次全局 Vector、一次全局 BM25 和一次全局 RRF。性能数据与调用计数共同说明，跨库检索已经摆脱按知识库重复执行的旧模式。

这组测试只覆盖一个和两个知识库，没有扩展到五库并发压力场景。它能够证明固定条件下的跨库接口性能收益，不能替代更大知识库规模、更高请求并发和真实业务流量下的容量测试。

## 总结

第一期跨库查询解决了能不能同时查多个知识库，第二期解决的是能否把多个知识库当成一个统一检索范围高效处理。

改造后的链路只执行一次 Query 处理、一次 Embedding、一次全局 Vector、一次全局 BM25 和一次全局 RRF，同时保留完整的知识库与文档来源。固定双知识库测试中，平均延迟下降 40.5%，P50 下降 42.5%，P95 下降 26.0%，跨库接口的执行效率得到明确提升。
