# Research 的执行边界与安全降级

Agentic Research 让检索系统具备了规划、判断和继续行动的能力，也带来了新的工程风险。模型可能把一个问题拆成过多查询，第一轮材料不足时可能反复补查，某个外部调用超时又可能拖住整条链路。如果只关注能不能多查几次，Research 很容易变成成本、权限范围和结束时间都无法预测的黑盒。

第二期把受控作为这项能力成立的前提。模型可以提出计划和补证建议，但数据范围、查询数量、检索轮次、模型调用和停止条件全部由后端状态机掌握。即使某个阶段失败，系统也优先保留已经验证的材料，不允许模型绕过边界寻找另一条路径。

## 自由循环为什么不适合检索中台

让模型在每一轮判断是否继续，看起来更加灵活，却会破坏检索中台最重要的确定性。

首先，模型不知道服务端的真实资源预算。它可能认为再查一次会更完整，却不知道请求已经接近超时或调用上限。其次，同一问题在不同运行中可能生成不同数量的 Query，延迟和费用无法预测。最后，如果停止依赖模型文本，非法 JSON、重复查询和错误的完整性判断都可能让流程失去方向。

第二期没有使用开放的 `while` 循环，而是把 Research 固定成一条有限状态路径：

```text
Planner 提出首轮查询
        ↓ 后端校验计划与数据范围
执行首轮检索
        ↓ 后端记录任务和资源消耗
Decider 提出停止或补证
        ↓ 后端重算完整性并校验补证 Query
最多执行一次补证
        ↓ 达到轮数后强制收口
Finalizer 只基于合法候选生成答案
```

模型负责语义判断，后端负责决定这些判断能否执行。受控不是在流程外增加一个超时参数，而是从请求进入到答案返回都存在不能绕过的约束。

## 第二期把控制集中在四层边界中

![Research 的四层不可绕过护栏](https://pic.niumianoffer.com/images/fs/research-four-guardrails.png)

Research 的限制如果散落在各个服务里，很难判断一次请求到底能做什么。第二期把控制收敛为数据、资源、停止和输出四层，每一层解决一种不同风险。

### 第一层：数据与权限边界

Research 使用独立的 `/rag/research` 接口，只接受用户问题和授权知识库范围，多余高级字段会被拒绝。它不是普通检索的 Custom 档，调用方不能传入轮数、工具列表、索引版本或精排参数。

服务端固定使用指定索引、Hybrid 召回和 Qwen3 精排。Planner 与 Decider 只能生成检索文本，不能选择租户、知识库、网页或外部工具。每个子查询都会复用请求开始时解析出的 `tenant_id`、`kb_ids` 和索引映射，第二轮也不会扩大权限范围。

查询文本同样需要校验。包含网址、SQL、Shell 命令或外部工具调用意图的 Query 会在执行前被拒绝。当前 Research 只向 Pro 套餐开放，普通检索的权限和行为不受影响。

### 第二层：资源与时间边界

一次请求能消耗的主要资源在开始前已经确定，调用方无法覆盖：

| 控制项 | 当前上限 | 约束目的 |
|---|---:|---|
| 必要要点 | 5 个 | 防止问题被过度拆解 |
| 首轮查询 | 3 个 | 限制首轮并发与精排调用 |
| 补证查询 | 2 个 | 限制第二轮扩张 |
| 检索轮数 | 2 轮 | 禁止无限补证 |
| Research LLM 调用 | 3 次 | 固定 Planner、Decider、Finalizer |
| 融合候选 | 24 条 | 控制判断模型的输入规模 |
| 最终证据 | 10 条 | 控制引用与答案上下文体积 |
| Query 长度 | 300 个字符 | 拒绝异常长查询 |
| 单候选送模文本 | 1600 个字符 | 防止长文档挤满输入 |
| 模型输入载荷 | 40000 个字符 | 控制 Decider 与 Finalizer 上下文 |
| 总时间预算 | 90 秒 | 达到预算后不再创建后续阶段 |

Research LLM 的 3 次调用只统计 Planner、Decider 和 Finalizer。每个检索任务内部的 Qwen3 精排也会进入评测中的应用模型调用总数，但它不改变 Research 控制器的调用上限。

90 秒属于阶段间预算检查。系统会在补证和 Finalizer 开始前判断是否已经达到预算，超时后不再创建新阶段；它不会强制中断已经发出的单次外部请求。这是当前实现的真实边界，不能把它表述成整条链路一定会在第 90 秒被立即终止。

### 第三层：状态与停止边界

一次 Research 会持续维护结构化状态，后端以它作为控制依据：

```jsonc
{
  "research_id": "research-001",
  "stage": "supplementing",
  "problem_type": "dependent",
  "aspects": ["直播带货权限", "类目额外资质"],
  "visited_queries": [
    "直播带货美妆或医疗器械需要哪些额外资质"
  ],
  "missing_aspect_ids": ["A2"],
  "round_count": 1,
  "retrieval_task_count": 2,
  "llm_call_count": 2,
  "input_tokens": 6200,
  "output_tokens": 310,
  "degraded": false
}
```

已执行 Query 会先经过大小写、空白和末尾标点归一化，再写入 `visited_queries`。系统在补证前检查历史查询、剩余轮次、缺失要点和时间预算，也会保存每轮候选、新增 Chunk 数、模型 Token 与阶段耗时。

每次结束都有明确的 `stop_reason`：

| `stop_reason` | 触发条件 |
|---|---|
| `evidence_complete` | 首轮所有必要要点都已有合法 `core` 证据 |
| `no_new_evidence` | 第二轮没有找到新的有效 Chunk |
| `max_rounds` | 完成第二轮或达到轮数上限 |
| `duplicate_query` | 补证 Query 都与已执行 Query 重复 |
| `timeout` | 创建后续阶段前已经达到时间预算 |
| `budget_exhausted` | Research LLM 调用达到上限 |
| `degraded` | 规划、判断、检索或生成阶段异常 |

![有限状态路径与明确停止原因](https://pic.niumianoffer.com/images/fs/research-bounded-state-machine.png)

`stop_reason` 解释流程为什么结束，Evidence Pack 中的 `complete`、`partial` 和 `missing` 描述证据覆盖程度，两者不能混为一谈。达到 `max_rounds` 时，材料可能已经完整，也可能仍然只覆盖部分要点。

### 第四层：答案与引用边界

Finalizer 不能提交任意 Chunk ID 或自己编写证据正文，只能选择当前候选池中的下标。后端会重新从数据库加载选中 Chunk，检查租户、知识库和索引范围，再生成 E1、E2 等证据编号。

回答内容也有硬性校验：

- 有确定结论的回答块必须至少引用一条 `core` 证据；
- 材料不足的回答块不能伪造引用；
- 答案不能包含未解析的候选编号或内部 Chunk ID；
- 规则冲突时必须分别保留来源，不能替用户判断哪个来源更权威。

任何一项不合法，都按 Finalizer 失败处理。系统返回已经验证的 Evidence Pack，并将 `answer` 设为空，而不是把一段无法回溯的内容交给调用方。

## 失败时不是全部回退，而是分阶段降级

Research 由多个模型与检索任务组成，要求所有环节永不失败并不现实。第二期的降级原则是：失败发生在哪里，就停止那一层的不可信扩张，同时尽量保留之前已经取得的合法结果。

| 失败位置 | 降级行为 |
|---|---|
| Planner 超时或结构非法 | 使用原问题执行一个首轮查询并标记降级 |
| 一个首轮查询失败 | 保留其他成功任务并继续融合 |
| 首轮全部查询失败 | 返回统一检索失败，不伪造材料 |
| Decider 失败 | 不执行不可信补证，保留候选并构造缺失状态 |
| 补证 Query 重复或越界 | 拒绝执行并记录停止原因 |
| 补证检索失败 | 保留第一轮候选与证据 |
| 第二轮没有新 Chunk | 记录 `no_new_evidence` 并停止 |
| Finalizer 失败或引用非法 | `answer=null`，返回已有 Evidence Pack |
| 链路观测失败 | 不影响 Research 主响应 |

![失败停在当前层，合法结果继续保留](https://pic.niumianoffer.com/images/fs/research-staged-degradation.png)

这里没有一个统一的降级答案模板。Planner 失败后仍然可以退回单次检索，Decider 失败后却不能继续猜测补证方向，Finalizer 失败时更不能绕过引用校验返回原始模型文本。不同阶段承担的职责不同，安全退路也必须不同。

## 证据不足也是一种正常结果

受控不仅意味着次数有上限，也意味着系统知道什么时候不应该给出确定结论。

例如知识库只说明积分不能用于充值、虚拟卡密和部分国际站订单，没有提到线下停车费。Research 可以围绕停车费执行一次定向补证，但仍然找不到直接规则时，Finalizer 必须说明当前材料不足，不能根据常识推断停车费能否抵扣。

如果两份文档对同一规则给出不同结论，系统需要分别引用来源并指出冲突，不能自行决定哪个版本更权威。当前 Research 负责检索、补证与引用控制，不承担业务规则仲裁。

无答案、部分答案和冲突答案都不等于链路失败。相比生成一个看似完整却无法验证的结论，明确暴露证据缺口更符合可信检索的目标。

## 完整链路经过了哪些验证

正式实验使用 10 道复杂题，对比单次检索加普通证据编排与 Controlled Research。两组使用相同的 Hybrid 和 Qwen3 检索基础，质量指标只统计双方都能进入 RAGAS 评分的 9 道题。RAGAS 用于计算 Context Precision 和 Context Recall。官网：[docs.ragas.io](https://docs.ragas.io)

| 指标 | 单次检索 | Controlled Research | 变化 |
|---|---:|---:|---:|
| Context Precision | 0.889 | 0.923 | +3.4 个百分点 |
| Context Recall | 0.944 | 0.944 | 0 |
| P95 延迟 | 31.98 秒 | 12.87 秒 | -19.11 秒 |
| 平均应用模型调用数 | 2.00 | 4.90 | +2.90 |

10 道 Research 请求全部成功，答案全部非空，答案引用映射有效率和 EvidenceItem 回溯率均为 100%；没有发生降级，也没有突破查询数、轮数和 Research LLM 调用上限。平均每题执行 1.9 个检索任务，其中 2 道触发第二轮。

这些数据证明受控执行、预算约束和安全引用已经通过完整链路验收，Context Precision 也有所提升。但 Context Recall 没有达到预设的至少提升 1 个百分点门槛，平均应用模型调用又增加 2.90 次，因此当前数据不足以支持默认开启 Research。

本次实验中的 P95 下降也不能理解成 Research 天生比单次检索更快。对照组包含耗时较高的普通证据编排，两组执行结构并不相同。这个数字只能作为本次真实接口实验的观察结果，不能推广到所有场景。

最终策略是保留独立 Research 接口和完整调试状态，由调用方在复杂问答场景显式选择，不把它加入 Speed、Balanced 或 Quality 默认档位。

## 总结

Research 的受控不是一句产品描述，而是四层不能被模型绕过的工程边界：数据与权限决定能查哪里，资源预算决定最多做多少，状态机决定何时停止，答案校验决定什么内容可以返回。

当某个阶段失败时，系统停止这一层的不可信扩张，并保留前面已经验证的材料；当知识库无法支持结论时，系统允许返回材料不足。正式测试证明这套链路能够在既定上限内稳定运行，但也暴露了额外模型调用和质量收益尚未全面达标的代价。因此，当前更合理的定位是把 Research 作为一项显式开启、有硬上限、可解释且可安全降级的复杂问题处理能力。
