# 从查询分解到证据驱动的多跳补证

Agentic Research 能不能真正解决复杂问题，关键不在于多调用几次模型，而在于系统能否把一个问题拆成正确的检索任务，并在第一轮结束后准确判断还缺什么。

查询分解负责把已知目标拆开，多跳补证负责沿新出现的证据继续前进。两者看起来是两个动作，实际上属于同一条证据驱动链路：先让每个答案要点拥有独立的召回机会，再根据真实材料决定是否需要第二轮。

## 复杂问题有两种不同的缺证方式

仍以组合支付退款为例：

```text
组合支付发生部分退款后，银行卡、优惠券和积分分别怎么退？
```

银行卡、优惠券和积分都已经明确写在问题中，三个目标彼此独立。系统可以在检索前直接生成三个查询：

```jsonc
{
  "problem_type": "independent",
  "aspects": [
    "银行卡退款路径",
    "优惠券退回规则",
    "积分退回规则"
  ],
  "prerequisite_aspect_indexes": [],
  "queries": [
    {
      "query": "组合支付部分退款时银行卡退款规则",
      "aspect_indexes": [0]
    },
    {
      "query": "组合支付部分退款时优惠券退款规则",
      "aspect_indexes": [1]
    },
    {
      "query": "组合支付部分退款时积分退款规则",
      "aspect_indexes": [2]
    }
  ]
}
```

另一类问题的检索目标无法提前全部确定。例如用户询问直播带货美妆或医疗器械需要哪些额外资质，第一轮可能只找到：

```text
达人带货需要完成带货权限申请，部分类目需要额外资质。
具体类目资质参见《商品上架与类目合规规范》第 3 节。
```

这段材料确认了直播权限，也给出了文档和章节线索，却没有写出美妆与医疗器械的具体资质。真正的第二跳只有读过这段材料后才能形成：继续检索《商品上架与类目合规规范》第 3 节中的类目要求。

因此，两类问题需要不同的推进方式：

```text
并列问题：目标已知 → 首轮拆开并行查找

依赖问题：目标依赖中间证据 → 首轮确认前置条件
                            ↓
                       再沿证据补查
```

![两种缺证与两种推进方式](https://pic.niumianoffer.com/images/fs/research-two-evidence-gaps.png)

## 第二期把检索过程组织成两阶段关系增强链路

整条链路围绕证据覆盖情况推进，而不是让模型自由决定查几次。第一阶段负责扩大不同要点的有效召回，第二阶段只修复已经确认的证据缺口。

### 第一阶段：查询分解后并行召回

Planner 最多生成 3 个首轮 Query，每个 Query 必须绑定一个或多个必要要点。后端会检查要点下标、查询长度、重复内容和安全边界，确保计划可执行。

计划通过后，多个查询并行进入同一条单次检索内核：

```python
# 每个子查询都复用相同的检索配置，局部失败不会取消其他任务
results = await asyncio.gather(
    *(retrieve_once(query) for query in planned_queries[:3]),
    return_exceptions=True,
)
```

组合支付正式测试中，三个子查询分别耗时约 1.99 秒、1.95 秒和 1.91 秒，整轮耗时约 1.99 秒，而不是串行相加后的 5.85 秒。这是单题诊断数据，只用于证明并行执行已经生效。

并行召回之后，结果不能重新混成一个普通 TopK。如果所有候选只按全局分数排序，相关性更强的银行卡材料仍然可能挤掉优惠券和积分。第二期因此把查询分解产生的关系保留到融合阶段：

```jsonc
{
  "chunk_id": "chunk-points-refund",
  "aspect_ids": ["A3"],       // 对应积分退款要点
  "query_ids": ["Q3"],        // 由第三个查询召回
  "rounds": [1],              // 来自第一轮检索
  "best_rank": 1,
  "source": "hybrid"
}
```

候选先按照知识库、索引版本、Chunk ID 和规范化正文去重，再按下面的顺序控制最多 24 条结果：

```text
先为每个要点保留第 1 条候选
        ↓
再为每个要点保留第 2 条候选
        ↓
优先保留能够覆盖多个要点的候选
        ↓
剩余名额按跨查询融合分数补齐
```

![并行召回与要点公平融合](https://pic.niumianoffer.com/images/fs/research-parallel-fair-fusion.png)

这样做不是平均分配名额，而是先保证每个问题要点至少有机会进入判断阶段，再用全局相关性填满剩余空间。

### 第二阶段：根据证据缺口定向补证

首轮融合完成后，Decider 会把候选映射回必要要点。每条证据有两种角色：

| 角色 | 判断标准 |
|---|---|
| `core` | 能直接回答该要点的条件、步骤、时限或结论 |
| `supporting` | 只提供背景、适用范围、前置条件或引用路径 |

直播规则中参见某文档第 3 节只能算 `supporting`，因为它只是导航信息，不是具体资质。模型完成初步选择后，后端会在当前租户、知识库和索引范围内重新加载 Chunk，并根据合法 `core` 证据重新计算完整性：

- 所有必要要点都有 `core`，状态为 `complete`；
- 只有部分要点拥有 `core`，状态为 `partial`；
- 所有必要要点都没有 `core`，状态为 `missing`。

如果状态不是 `complete`，Decider 最多提出两个补证 Query。它们只能绑定缺失要点，不能重复已执行查询，也不能使用材料尚未确认的中间值。

例如首轮已经出现商品上架与类目合规规范第 3 节这一明确路径，补证可以写成：

```text
商品上架与类目合规规范 第3节 美妆 医疗器械 必备资质
```

如果首轮没有找到文档名、章节或具体类目，模型就不能凭常识编造线索。依赖型问题也是如此。第一轮尚未确认员工职级时，只能继续查询职级，不能猜测等级后直接查差旅上限。

## 第二轮不是重新搜索，而是合并证据链

补证查询仍然复用首轮的检索内核和数据范围，最多并行执行两个任务。系统不会再次调用 Planner，也不会扩大知识库或接入网页搜索。

第二轮完成后，两轮结果重新进入统一融合：

```text
第一轮候选 + 第二轮新增候选
              ↓
按知识库、索引、Chunk ID 和正文去重
              ↓
合并要点、查询、轮次和来源关系
              ↓
再次按要点公平选择
              ↓
形成最终候选池
```

![证据缺口驱动唯一一次定向补证](https://pic.niumianoffer.com/images/fs/research-evidence-driven-supplement.png)

同一个 Chunk 如果两轮都被命中，只保留一份正文，并记录 `rounds: [1, 2]`。第二轮没有找到新 Chunk 时，系统以 `no_new_evidence` 停止，不会为了凑满轮次继续查询。

最终答案必须同时尊重前置证据和末端规则。例如系统查到了某职级的差旅标准，却没有证据证明用户属于该职级，就不能把标准直接套到用户身上。证据不足的要点只能明确说明当前知识库无法确认。

这也是证据驱动与自由推理的区别：系统保存的不是一段不可验证的思维过程，而是一条可复盘的状态链。

```text
首轮状态：partial
缺失要点：美妆与医疗器械的具体资质
补证依据：首轮原文中的文档名和章节
补证查询：围绕缺失要点定向检索
第二轮新增：目标规则原文
最终输出：前置材料 + 末端规则 + 可回溯引用
```

## 当前测试证明了什么

完整 Research 的 10 道正式题中，有 2 道触发第二轮补证。所有请求都成功返回，最终引用映射有效率和证据回溯率达到 100%，说明查询分解、并行召回、证据判断、两轮融合和引用生成已经形成完整工程链路。

第二轮的独立质量收益还不能下定论。专项实验使用 4 道依赖型题，对比禁止补证和允许一次补证：

| 指标 | 禁止补证 | 允许一次补证 | 表面变化 |
|---|---:|---:|---:|
| Context Precision | 0.896 | 0.958 | +6.3 个百分点 |
| Context Recall | 1.000 | 1.000 | 0 |
| P95 延迟 | 13.94 秒 | 15.93 秒 | +1.99 秒 |
| 平均应用模型调用数 | 4.50 | 5.00 | +0.50 |

Precision 虽然有所上升，但这组变化不能直接归因于补证。禁止补证组的首轮证据已经覆盖 4 道题的全部人工标注要点，合法修复分母为 0；两组也只有 2 道题拥有相同的首轮计划和候选快照。因此 Multi-hop Repair Rate 只能记录为 `not_evaluable`。

当前能够确认的是机制已经实现：系统可以识别证据缺口，沿原文线索补查，并把两轮材料合成可回溯证据链。要证明补证本身带来稳定质量收益，还需要补充首轮确实缺证、第二轮能够命中冻结目标材料的题目，并让实验两组复用完全一致的 Planner 输出和首轮候选。

## 总结

查询分解解决的是已知目标之间的召回竞争，多跳补证解决的是下一步目标只有读过首轮材料后才会出现的问题。第二期把它们连接成一条两阶段链路：先围绕必要要点并行检索并公平融合，再根据合法 `core` 证据判断缺口，沿现有材料中的明确线索执行一次定向补证。

整个过程始终保留要点、Query、轮次和 Chunk 之间的关系。系统因此获得了继续行动的能力，但每一步都必须由证据推动，也都能回到知识库原文进行验证。
