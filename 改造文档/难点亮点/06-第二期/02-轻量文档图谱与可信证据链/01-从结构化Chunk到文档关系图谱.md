# 从结构化 Chunk 到文档关系图谱

第一期已经能够按照 Markdown 标题、段落、列表和表格进行结构化切块，相比固定字数切分，Chunk 的语义完整性有了明显改善。但无论切分规则多么精细，只要长文档被拆成独立 Chunk，原文中的章节层级、前后顺序和跨章节引用就可能被削弱。

例如，命中的 Chunk 只有“提交后 3 个工作日内完成审核”，真正的适用对象却写在父章节；命中的表格只有数据行，表头留在相邻 Chunk；正文写着“具体限制参见《售后规则》第三节”，检索系统却把它当作普通文本。单个 Chunk 看起来相关，离能够支撑回答的完整证据仍然差一步。

第二期没有通过继续放大 Chunk 或盲目增加 TopK 来掩盖这个问题，而是在第一期结构化 Chunk 之上补充稳定的位置和关系信息，把原本彼此孤立的片段组织成轻量文档关系图谱。

## 第一期的问题不是不会切，而是切完以后失去了关系

小 Chunk 和完整上下文本身存在一组矛盾：Chunk 越小，向量与关键词越容易准确命中；Chunk 越大，保留的信息越完整，但无关内容也越多。仅仅调整切片大小，只是在定位精度和上下文完整度之间移动，并没有真正解决问题。

第一期切片后的数据主要回答三个问题：它属于哪个文档、正文是什么、向量是什么。第二期需要继续回答：

- 它位于哪个章节，父章节是谁
- 它在文档中的先后位置是什么
- 它与哪些章节或文档存在明确引用
- 哪些文本只负责指路，不应该参与普通召回
- 索引结构变化后，旧数据如何安全重建和切换

这些信息原本都存在于文档中，只是在切片和索引过程中没有被完整保留下来。因此，这次改造的重点不是凭空推断新知识，而是把文档已经明确表达的结构关系保存下来。

## 用一篇文档看改造前后的存储变化

以《售后服务与退换货政策》中的一段内容为例：

```markdown
# 售后服务与退换货政策

## 4. 售后时效

### 4.1 买家寄回

退货申请通过后，买家应在 7 天内将商品交给快递揽收。

### 4.2 质检与退款

商家签收后，应在 48 小时内完成质检。

> 关联规则：退款到账时间参见《支付方式与资金安全规范》第 3 节。
```

第一期切块后，核心存储结构可以抽象成一组彼此独立的记录：

```jsonc
[
  {
    "chunk_id": "chunk-1",
    "document_id": "doc-after-sale",
    "title": "售后服务与退换货政策",
    "content": "退货申请通过后，买家应在 7 天内将商品交给快递揽收。",
    "embedding": [0.12, -0.08, 0.31] // 正文对应的向量，此处仅展示部分数值
  },
  {
    "chunk_id": "chunk-2",
    "document_id": "doc-after-sale",
    "title": "售后服务与退换货政策",
    "content": "商家签收后，应在 48 小时内完成质检。",
    "embedding": [0.06, 0.17, -0.22]
  },
  {
    "chunk_id": "chunk-3",
    "document_id": "doc-after-sale",
    "title": "售后服务与退换货政策",
    "content": "退款到账时间参见《支付方式与资金安全规范》第 3 节。",
    "embedding": [0.25, -0.11, 0.09]
  }
]
```

这些 Chunk 都知道自己属于哪篇文档，但系统无法直接判断 `chunk-1` 和 `chunk-2` 的先后关系，也不知道它们共同属于“售后时效”。`chunk-3` 只是一条普通候选，检索命中它以后还需要重新理解文本，才能找到真正的退款规则。

改造后，正文没有被修改，但每个 Chunk 都有了稳定的章节坐标，明确引用也变成了可以查询的关系：

```jsonc
{
  "document": {
    "document_id": "doc-after-sale",
    "title": "售后服务与退换货政策"
  },
  "chunks": [
    {
      "chunk_id": "chunk-1",
      "section_id": "section-return-send",
      "parent_section_id": "section-after-sale-sla",
      "order_index": 1,
      "metadata": {
        "heading_path": ["4. 售后时效", "4.1 买家寄回"],
        "chunk_type": "prose"
      },
      "content": "退货申请通过后，买家应在 7 天内将商品交给快递揽收。",
      "retrieval_text": "文档：售后服务与退换货政策\n章节：4. 售后时效 > 4.1 买家寄回\n正文：退货申请通过后，买家应在 7 天内将商品交给快递揽收。"
    },
    {
      "chunk_id": "chunk-2",
      "section_id": "section-return-inspection",
      "parent_section_id": "section-after-sale-sla",
      "order_index": 2,
      "metadata": {
        "heading_path": ["4. 售后时效", "4.2 质检与退款"],
        "chunk_type": "prose"
      },
      "content": "商家签收后，应在 48 小时内完成质检。"
    },
    {
      "chunk_id": "chunk-3",
      "metadata": {
        "chunk_type": "reference_pointer" // 只负责建立引用，不参与普通向量和 BM25 召回
      },
      "content": "退款到账时间参见《支付方式与资金安全规范》第 3 节。"
    }
  ],
  "relations": [
    {
      "source_chunk_id": "chunk-3",
      "target_chunk_id": "chunk-payment-refund",
      "relation_type": "reference"
    }
  ]
}
```

这份结构可以直接回答三个问题：`chunk-1` 和 `chunk-2` 在文档中的位置是什么，它们是否属于同一个父章节，以及引用语句真正指向哪个 Chunk。前后关系通过 `order_index` 计算，父子关系通过 Section 字段定位，跨文档引用通过关系表查询，一篇普通文档由此变成了一张可检索的轻量关系图。

## 第二期如何把 Chunk 组织成轻量图谱

这里所说的文档关系图谱，不是抽取人物、公司、产品等实体，也不是通过大模型推断语义关系。它由 Document、Section 和 Chunk 三类逻辑节点组成，只保存父子、前后相邻和明确引用三类确定性关系。

```text
Document：售后服务与退换货政策
└── Section：七天无理由退货
    ├── Chunk 12：适用条件
    ├── Chunk 13：不适用范围
    └── Chunk 14：办理流程
             │
             └── reference → Section：退款到账时间
```

Document 继续复用原有文档表，Section 通过稳定 ID 表达，不额外建立一套重型节点系统；Chunk 保存章节和顺序字段，非相邻引用进入关系表。普通关系型数据库已经足够完成单跳查询，不需要为了确定性关系引入图数据库。

### 先把结构化切片从“按格式拆开”升级为“按章节定位”

第二期的切片器会维护标题栈。每读取一个标题，就更新当前 `heading_path`；生成 Chunk 时，同时写入当前章节、父章节和文档内顺序。

```jsonc
{
  "document_id": "doc-after-sale",
  "section_id": "sec-7d-return-condition",       // 当前章节的稳定标识
  "parent_section_id": "sec-7d-return",         // 父章节的稳定标识
  "order_index": 12,                              // Chunk 在当前文档中的连续位置
  "metadata": {
    "heading_path": ["售后服务", "七天无理由退货", "适用条件"],
    "chunk_type": "prose"
  },
  "content": "商品应保持完好，且不影响二次销售。"
}
```

`section_id` 不是数据库自增编号，而是根据文档、当前索引和标题路径稳定生成。同一份索引重复构建时，相同章节能够得到相同标识；不同索引又不会意外串联，为关系解析和重建隔离提供基础。

切片过程中还会过滤空正文、分隔符、纯标点、只有编号的片段，以及与标题完全重复的正文。过滤规则判断的是信息量，不是简单设置最小字数。像“支持自提”“不可叠加”这类短句虽然字少，却可能是回答问题的关键事实，仍然必须保留。

### 分离原始正文和检索文本

同一个 Chunk 在召回阶段和返回阶段承担的职责不同。召回需要更多上下文帮助模型理解，最终返回则必须忠实保留原文，不能把系统补充的标题当成用户文档正文。

第二期因此把文本拆成两份：

```text
content
商品应保持完好，且不影响二次销售。

retrieval_text
文档：售后服务与退换货政策
章节：售后服务 > 七天无理由退货 > 适用条件
正文：商品应保持完好，且不影响二次销售。
```

改造后的向量和 BM25 都基于 `retrieval_text` 建立索引。即使正文中没有再次出现“七天无理由退货”，标题路径也能帮助它命中正确问题。API 返回、证据引用和最终回答仍使用 `content`，避免把检索增强信息误当成原文。

这种双文本设计解决了一个容易被忽略的问题：增强召回不等于改写证据。系统可以为了找到材料补充检索语义，但交给用户的材料必须保持可回溯。

![同一 Chunk 的三种职责](https://pic.niumianoffer.com/images/fs/graph-chunk-three-responsibilities.png)

### 用字段表达层级和相邻关系，用关系表保存明确引用

父子关系可以通过 `section_id` 与 `parent_section_id` 查询，前后相邻关系可以根据同一文档中的 `order_index` 动态计算。它们都有唯一、确定的来源，没有必要重复写入大量边记录。

只有跨章节、跨文档的明确引用需要进入 `chunk_relations`：

```jsonc
{
  "source_chunk_id": "chunk-return-process",
  "target_chunk_id": "chunk-refund-time",
  "relation_type": "reference",
  "metadata": {
    "reference_text": "具体到账时间参见《退款规则》第二节"
  }
}
```

关系解析只识别文档中真实存在的显式表达，包括“本文件第三节”“《退款规则》第二节”和 Markdown 链接。目标文档或章节存在歧义时不建边，跨租户、跨知识库和跨索引版本也不能关联。

这条约束很重要。轻量图谱的可信度来自关系可验证。如果系统为了提高覆盖率，根据词义相似度自动猜测引用，最终得到的边虽然更多，却可能把错误上下文补进答案。

### 把引用指针和可检索正文分开处理

“具体规则参见《退款规则》第二节”本身通常不能回答业务问题。如果把它和普通正文一起写入向量库与 Elasticsearch，系统可能命中一条只负责指路的句子，把真正答案挤出 TopK。

第二期会把这类内容标记为 `reference_pointer`。它保留在数据库中用于建立引用关系，但不生成有效向量，也不进入 BM25 索引。检索时沿引用边直接找到目标内容，而不是把指针句当作答案。

这一步让文档关系同时服务于两个目标：减少低信息候选，并保留人工写在文档里的导航能力。

## 索引结构变化后如何安全完成重建

这次改造会同时改变 Chunk 边界、检索文本、向量、BM25 索引和引用关系，不能直接在原有数据上逐项覆盖。否则重建中途失败时，可能出现数据库已经保存新 Chunk，Elasticsearch 仍然查询旧文本，关系表又只生成一部分的混合状态。Elasticsearch 继续承担全文检索索引。官网：[elastic.co](https://www.elastic.co/elasticsearch)

第二期采用旁路重建：先在不影响在线查询的情况下生成完整的新索引，确认 PostgreSQL 中的 Chunk 和关系、向量索引以及 Elasticsearch 文档全部一致，再显式切换活动索引。PostgreSQL 负责保存 Chunk 结构和引用关系。官网：[postgresql.org](https://www.postgresql.org/)

```text
线上索引继续提供查询
        ↓
旁路重建 Chunk、向量、BM25 和关系
        ↓
完成数量校验、关系校验和统一效果测试
        ↓
显式切换到新索引
```

![v2 索引的旁路重建与显式切换](https://pic.niumianoffer.com/images/fs/graph-v2-side-build-switch.png)

项目中保留 v1 的主要目的，是让改造前后的方案能够使用同一套 Golden Set 做对比测试，并不是要在业务中长期维护两套检索架构。新结构完成验证并成为正式索引后，旧版本即可结束其对比测试职责。

索引版本在查询时仍然需要参与租户、知识库和关系范围校验，防止测试期间把两套数据拼到同一份结果中。版本号在这里是重建与测试的隔离手段，不是轻量图谱本身需要重点讲解的业务能力。

## 建图完成后，系统获得了什么

轻量文档关系图谱首先是一项索引基础能力，它让每个 Chunk 从一段孤立文本变成一个可定位、可关联、可按版本追溯的文档节点。

| 改造前 | 改造后 |
|---|---|
| Chunk 只知道所属文档 | Chunk 同时知道章节、父章节和文档内顺序 |
| 标题与正文分离后语义变弱 | `retrieval_text` 带上文档名和完整标题路径 |
| 引用语句与普通正文一起召回 | 指针只用于建边，目标正文参与召回 |
| 索引结构原地覆盖 | 旁路完整重建，统一测试通过后再显式切换 |
| 只能返回命中的孤立片段 | 可以沿确定性关系寻找父级、相邻和引用内容 |

这些变化并不直接承诺每道题的最终分数都会提升。它建立的是统一的数据前提：在线检索能够利用关系扩展候选，精排后的结果能够恢复上下文，证据编排也能够保留可靠的章节和版本来源。如果底层节点没有稳定坐标，上层任何“补上下文”都只能依赖模糊文本匹配。

## 轻量图谱的能力边界

当前方案仍然存在明显边界。第二期刻意把关系限制在文档能够直接证明的范围内：

- 不抽取实体、属性和开放语义关系
- 不使用大模型推断两段内容是否存在关联
- 不执行不受限制的多跳图遍历
- 不用图谱生成摘要或修改原始正文
- 不解决不同来源之间的事实冲突和权威性判断
- 不把图数据库作为当前方案的必要依赖

这意味着它不能替代通用知识图谱，也不能自动完成复杂多跳推理。但对于当前架构已经够用：知识库以结构化 Markdown 文档为主，最常见的问题是标题、相邻段落和明确引用被切开；在线检索更需要关系确定、查询有界和延迟可控，而不是构建一张关系来源不明的大图。使用普通字段和关系表，就能覆盖当前最主要的上下文恢复场景。

如果未来接入大量弱结构化资料，需要抽取人物、组织、产品和事件等实体，自动发现隐含的跨文档语义关系，或者支持多跳推理、全局主题总结和大规模关系检索，轻量关系表就会逐渐触及上限。届时可以引入 GraphRAG，把实体与关系抽取、图结构检索和全局信息组织纳入新的架构层。官网：[microsoft.github.io](https://microsoft.github.io/graphrag/)

因此，轻量图谱不是 GraphRAG 的替代品，而是当前阶段更合适的实现。它先用较低成本解决确定性的文档结构问题，等业务真的需要开放关系和复杂图推理时，再承担引入 GraphRAG 的建设与运行成本。

## 总结

第一期结构化切块解决了“如何把文档切得更合理”，第二期轻量文档关系图谱继续解决“切开以后如何不丢关系”。系统为 Chunk 增加稳定章节、父级和顺序坐标，分离原文与检索文本，解析可验证的显式引用，并通过旁路索引完成安全重建和切换。

这套方案没有引入重型图数据库，却保留了文档中最有价值的层级、相邻和引用关系。它足以覆盖当前以结构化文档和单跳关系为主的检索场景；当业务进一步走向开放实体、多跳推理和全局主题分析时，再升级到 GraphRAG。
