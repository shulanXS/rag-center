# 图谱增强检索与上下文恢复

轻量文档关系图谱把章节层级、前后顺序和明确引用保存了下来，但图谱建成不代表问题已经解决。如果在线检索仍然只执行 Vector、BM25、RRF 和精排，新增关系只是躺在数据库里的元数据，最终返回的仍可能是一个缺少条件、表头或引用目标的孤立 Chunk。

第二期真正的难点，是把关系能力接入现有检索链路，同时守住候选规模、响应时间和租户隔离。为此，系统没有在检索后简单拼接一圈相邻内容，而是把关系增强拆成两个阶段：最终排序前注入可能被遗漏的候选，TopK 确定后只为最终命中项恢复必要上下文。

## 单纯增加 TopK 为什么解决不了上下文缺失

面对片段不完整，最直接的做法是把 Top5 扩大到 Top20，希望相关上下文也能被召回。但 TopK 只表示相关性排序，不理解文档关系。相邻段落可能没有重复用户 Query 中的关键词，跨文档引用目标更可能完全使用另一套表述，因此它们不一定会自然进入结果列表。

即使上下文碰巧进入 TopK，也会和真正命中项作为独立结果竞争位置。系统不知道两段内容应该组合使用，最终只能把更多材料一起交给下游模型，噪声和 Token 消耗随之增加。

另一种做法是在 TopK 返回后，无条件为每条结果拼接父章节和前后段落。这样能够补充信息，却来得太晚。假如命中的只是一条“参见退款规则”的引用句，真正目标在最终排序前没有进入候选，它就没有参与精排或后续证据选择的机会；而且无条件扩展容易把无关兄弟章节一起带入上下文。

所以关系必须在两个不同位置发挥作用：最终排序前补充候选，TopK 确定后恢复阅读语境。精排是候选排序的一种可选方式，不是两阶段关系增强能够运行的前提。

## 第二期建立了两阶段关系增强链路

完整检索链路变为：

```text
Query
  ↓
Vector + BM25 → RRF 全局候选
  ↓
过滤低信息 Chunk
  ↓
第一阶段：沿关系注入候选
  ↓
可选：Qwen3 精排
  ├── 开启：关系候选与原候选重新竞争 TopK
  └── 关闭：沿用原召回顺序确定 TopK
  ↓
第二阶段：为最终命中项恢复上下文
  ↓
返回“小 Chunk 命中 + 大上下文阅读”的结果
```

![两阶段关系增强：先竞争，再补全](https://pic.niumianoffer.com/images/fs/graph-two-stage-enhancement.png)

两阶段使用同一套文档关系，却承担不同职责。候选注入回答“哪些材料有资格参与排序”，上下文恢复回答“最终材料怎样才足够完整”。

精排不是关系增强的强制依赖。在自定义档关闭精排后，系统仍然会完成普通召回，并为最终 TopK 恢复父级、相邻和引用上下文。因此，不开启精排并不会让轻量图谱和上下文恢复失效。

区别在于第一阶段的效果。关系注入候选的初始分数为 0，并追加在原召回候选之后。开启精排时，它们可以根据 Query 与正文的相关性重新竞争 TopK；关闭精排时，普通检索会沿用 Vector、BM25 或 RRF 的原有顺序，注入候选通常难以成为最终锚点，关系增强的收益主要来自第二阶段的上下文恢复。

所以系统保留精排开关，但在质量优先、跨章节引用和复杂查询场景中，建议把关系增强与专业精排组合使用。精排可以让关系候选和原始候选重新比较相关性，更充分地发挥第一阶段的作用。对延迟和调用成本更敏感的场景，可以关闭精排，只保留原召回排序与上下文恢复。

### 第一阶段：在最终排序前沿关系补充候选

RRF 结果产生后，系统最多取前 10 个种子 Chunk，批量查询它们的关系。扩展优先级固定为明确引用、父章节、同章节前一项、同章节后一项，每个种子最多注入 3 个候选，整个候选池最多保留 30 个。

```text
原始命中：办理入口位于订单详情页，具体限制参见《售后规则》第三节
                       │
                       └── reference
                              ↓
注入候选：定制商品、已拆封数字商品不适用七天无理由退货
```

被注入的 Chunk 不继承种子分数，也不会因为存在关系就直接排在前面。它的初始分数为 0，来源标记为 `graph_injection`。开启精排时，它会与原始候选一起交给阿里云百炼 Qwen3 精排。官网：[aliyun.com](https://www.aliyun.com/product/bailian)

关系只负责把它带进候选池。开启精排后，是否进入最终 TopK 仍由 Query 与内容的相关性决定；关闭精排后，则继续沿用原召回顺序。

候选注入还会跳过 `reference_pointer` 和低信息片段，并对 Chunk ID 与规范化正文去重。查询关系时严格限定当前租户、允许访问的知识库和当前索引版本，避免沿边越过数据边界。

### 第二阶段：在最终 TopK 确定后恢复必要上下文

精排完成或原召回顺序截取 TopK 后，系统不再改变最终命中项的分数和名次，而是为每个锚点补充回答所需的阅读上下文。关系优先级仍然是明确引用、父章节、前一项和后一项，但会施加更严格的预算：每个锚点最多补 3 个 Chunk，合并后的上下文最多 4096 个字符。

父章节也不会无条件补充。只有当前 Chunk 位于较深层级，并出现“本节”“上述”“前述”“以下”“该规则”“其中”或“适用范围”等依赖上文的信号时，系统才尝试带回父级内容。这样可以补齐省略的主语和适用条件，又不会把每个命中项都扩展成整章。

最终结果会同时保留原始锚点和补充来源：

```jsonc
{
  "chunk_id": "chunk-return-condition",
  "content": "商品应保持完好，且不影响二次销售。",
  "score": 0.93,
  "context": {
    "content": "七天无理由退货适用于……\n商品应保持完好……\n定制商品不适用……",
    "sources": [
      {"chunk_id": "chunk-parent", "relation": "parent_section"},
      {"chunk_id": "chunk-return-condition", "relation": "anchor"},
      {"chunk_id": "chunk-next", "relation": "next"}
    ]
  }
}
```

锚点仍然是检索命中的核心证据，`context.sources` 只说明为了完整阅读补充了哪些原文。下游既可以直接使用合并上下文，也可以根据来源逐条回查。

## 为什么候选增强和上下文恢复必须分开

精排可以关闭，但候选增强和上下文恢复的位置不能随意交换。

开启精排时，关系注入必须发生在精排之前，否则引用目标没有机会参与相关性判断。无论是否开启精排，上下文恢复都应该发生在最终 TopK 确定之后；如果提前拼接大段父级和相邻文本，会改变候选原有语义，如果把补充上下文当成新的结果项，又会挤占最终 TopK。

第二期因此将“用于竞争的内容”和“用于阅读的内容”分开：

| 阶段 | 处理对象 | 是否参与精排 | 是否改变锚点排名 | 主要目标 |
|---|---|---|---|---|
| 图谱候选注入 | 关系目标 Chunk | 精排开启时参与 | 开启精排后可能产生新的最终命中项 | 找回普通召回遗漏的材料 |
| 上下文恢复 | 最终锚点的父级、相邻和引用内容 | 否 | 否 | 补齐条件、范围和连续语义 |

这就是“小 Chunk 负责检索，大上下文负责回答”。系统不需要把所有索引 Chunk 做大，也不需要把整章都塞给模型。

## 关系增强不能突破检索边界

沿关系扩展会主动查找更多数据，因此安全和稳定性约束比普通 TopK 更严格。

首先，每次关系查询都必须带上租户、知识库和索引版本范围。某个 Chunk 即使保存了错误或过期的目标 ID，只要目标不在当前范围内，就不能进入候选或上下文。

其次，当前只允许单跳扩展。系统不会从 A 找到 B 后继续沿 B 找 C，更不会循环遍历整张图。固定的种子数、单种子注入数、总候选数、单锚点补充数和字符预算，共同控制最坏情况下的数据库查询与上下文体积。

最后，关系增强属于可降级能力。关系表查询异常、目标 Chunk 缺失或上下文拼接失败时，系统记录 `degraded` 和错误原因，继续返回原有检索结果。新增能力不能让已经可用的 Vector、BM25 和精排主链路变得不可用。

## 固定条件测试带来了什么收益

正式实验使用统一的 20 道基础题，对比第一期 v1 索引和第二期 v2 完整关系增强链路。两组使用相同文档、Hybrid 配置和最终 Top10，关闭 Query Rewrite、同义词扩展和精排，应用侧都没有额外模型调用。RAGAS 用于计算 Context Precision 和 Context Recall。官网：[docs.ragas.io](https://docs.ragas.io)

| 指标 | v1 基线 | v2 关系增强 | 变化 |
|---|---:|---:|---:|
| Context Precision | 0.840 | 0.889 | +4.9 个百分点 |
| Context Recall | 0.925 | 1.000 | +7.5 个百分点 |
| P95 延迟 | 1536.7 ms | 1397.1 ms | -139.6 ms，下降 9.1% |
| 平均应用模型调用数 | 0 | 0 | 0 |

![关系增强的整体收益](https://pic.niumianoffer.com/images/fs/graph-enhancement-results.png)

20 道题均请求成功，RAGAS 评分也没有失败。诊断数据进一步显示，图谱影响了其中 18 道题，共生成 98 个关系注入候选，并为最终结果补充 82 个上下文 Chunk。

这次实验特意关闭了精排，因此也证明关系增强并不依赖精排才能工作。由于注入候选没有经过重新排序，质量收益主要来自新切片、结构化检索文本和最终 TopK 的上下文恢复；98 个注入候选只能证明关系查询已经执行，不能证明它们都进入了最终结果。

四项核心指标共同表明，第二期在没有增加应用模型调用的情况下，既减少了返回材料中的噪声，又把标准答案需要的信息完整找回，P95 也没有因为关系查询而上升。对于“命中了局部内容，却缺少条件或引用目标”的问题，这次改造是有效的。

不过，这组实验比较的是 v1 与 v2 完整方案。v2 同时包含切片边界、`retrieval_text`、关系候选注入和上下文恢复，结果能够证明整体升级有效，不能把 7.5 个百分点的 Recall 提升全部归因于某一种关系。

## 图谱增强的能力边界

关系增强擅长恢复文档原本存在的结构，不负责创造文档没有表达的逻辑。它适合处理标题与正文分离、条件跨段、表格表头缺失、列表连续项和明确引用；对于需要组合多个独立事实才能推导结论的复杂问题，仍然需要更高层的查询分解和补证机制。

它也不是“返回越多越好”。扩展预算过小可能补不全上下文，过大则会重新引入噪声和延迟。当前限制来自正式实现与评测结果，调整时仍需通过统一基线验证，不能只看某一道问题是否回答得更长。

## 总结

第二期没有把轻量图谱停留在索引字段层面，而是把它接进检索主链路：普通召回先找到精确的小 Chunk，关系候选在最终排序前进入候选池，TopK 确定后再为锚点恢复必要的父级、相邻和引用内容。精排可以按场景关闭，但质量优先、跨章节引用和复杂查询场景建议开启，让关系候选获得重新竞争 TopK 的机会。

统一测试中，Context Precision 提升 4.9 个百分点，Context Recall 提升 7.5 个百分点，P95 下降 9.1%，并且没有增加应用模型调用。这条两阶段链路让系统从“找到相关片段”进一步走向“返回能够完整理解的材料”。
