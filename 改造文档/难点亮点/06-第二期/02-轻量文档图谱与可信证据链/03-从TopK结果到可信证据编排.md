# 从 TopK 结果到可信证据编排

经过 Hybrid 召回、图谱增强和阿里云百炼 Qwen3 精排后，系统已经能够返回一组质量较高的 TopK Chunk。官网：[aliyun.com](https://www.aliyun.com/product/bailian)

但 TopK 本质上仍是一张按相关性排序的材料列表，它没有说明一个问题包含哪些回答要点，也没有说明每个要点是否已经得到直接证据支持。

对于“七天无理由退货需要什么条件”这类单点问题，前几条结果通常已经够用。面对“企业采购支持哪些付款方式、申请月结需要什么条件、发票怎么开”这样的多要点问题，仅靠 TopK 就容易出现两个风险：材料很多，看起来相关，却漏掉其中一个要点；模型生成了完整答案，却无法判断每句话究竟由哪段原文支撑。

第二期因此没有继续扩大 TopK，而是在检索结果之上增加可选的 Evidence Pack。它把问题拆成必要要点，为每个要点选择能够直接支撑结论的原始 Chunk，并给出完整性状态和可回溯引用，让下游在生成答案前先知道证据是否真的够用。

## TopK 解决了相关性，却没有解决证据完整性

TopK 的排序单位是 Chunk，业务问题的判断单位却是回答要点。两者并不总是一一对应。

一条排名很高的 Chunk 可能只说明办理入口，没有说明适用条件；两条内容相似的结果可能都覆盖付款方式，却共同漏掉发票规则；相邻上下文补齐了阅读语义，也不代表它能够直接证明某个结论。

如果把 Top10 原样交给下游模型，下游还要自行完成四件事：

- 从问题中识别必须回答的要点
- 判断每段材料能支持哪个要点
- 区分直接结论和补充条件
- 判断当前材料是否足以生成完整答案

这四件事如果只发生在答案生成的黑盒里，系统就无法提前发现漏证，也很难在答案出错后定位是检索遗漏、证据选择错误，还是生成模型曲解了原文。

Evidence Pack 的价值，就是把这层隐式判断变成结构化、可检查的数据。

## 第二期如何把候选结果编排成证据包

证据编排不会替换原有 `retrieved_chunks`，也不会生成最终答案。它是检索响应中的一份可选结构化视图，完整流程分为候选汇总、要点与证据选择、后端可信构建三个阶段。

```text
最终 TopK + 关系上下文 + 精排前基础候选
                    ↓
         组成有界、去重的候选池
                    ↓
   LLM 识别回答要点，只返回候选序号与角色
                    ↓
 后端重新校验 Chunk 范围并加载数据库原文
                    ↓
Evidence Pack：分组、完整性、引用、原始证据
```

![从 TopK 到结构化 Evidence Pack](https://pic.niumianoffer.com/images/fs/evidence-pack-pipeline.png)

### 候选池不只取最终 TopK

如果只让证据编排查看最终 TopK，它只能重新整理已经保留下来的材料，无法发现精排边界之外仍有价值的证据。第二期会从三处汇总候选：最终 `retrieved_chunks`、它们的 `context.sources`，以及精排前保存的基础候选快照。

候选池最多输入 20 条，并至少为基础召回候选保留 6 个位置。所有内容按 Chunk ID 和规范化正文去重，单条文本最多送入 2048 个字符。这样既能看到最终高相关结果，也能给被精排截断的材料一次参与证据选择的机会。

这一步不会发起新的检索。Evidence Pack 只能从当前请求已经拿到的候选中选择材料，因此它的职责是编排，不是补证。

### LLM 只识别要点和选择序号

模型收到用户 Query 和带编号的候选列表后，需要输出最少必要回答要点，并为每个要点选择候选序号。它不能改写证据、不能生成答案，也不能返回候选列表之外的 Chunk ID。

每条关联证据只能使用两个角色：

| 角色 | 含义 | 例子 |
|---|---|---|
| `core` | 能够直接支撑该要点的结论 | “申请月结需完成企业认证并通过授信审核” |
| `supporting` | 补充适用范围、条件或背景 | “月结账期以合同约定为准” |

系统会严格校验模型输出：要点不能为空或重复，候选序号必须存在，同一要点不能重复选择同一材料，角色只能是 `core` 或 `supporting`，总证据数不能超过 `max_items`。模型输出不是可信数据，只是一份待验证的选择建议。

### 后端用数据库原文构建可信证据

模型选中序号后，后端不会直接把提示词里的文本复制到响应。系统会根据 Chunk ID 重新访问数据库，并同时校验租户、知识库和索引版本。只要目标不存在或越过当前请求范围，本次 Evidence Pack 就不能成立。

通过校验的 Chunk 使用数据库中的原始 `content` 构建 EvidenceItem，并依次分配 `E1`、`E2` 等证据编号：

```jsonc
{
  "status": "partial",
  "missing_aspects": ["发票开具方式"],
  "groups": [
    {
      "aspect": "申请月结的条件",
      "covered": true,
      "evidence": [
        {"evidence_id": "E1", "role": "core"},
        {"evidence_id": "E2", "role": "supporting"}
      ]
    },
    {
      "aspect": "发票开具方式",
      "covered": false,
      "evidence": []
    }
  ],
  "items": [
    {
      "evidence_id": "E1",
      "chunk_id": "chunk-monthly-settlement",
      "kb_id": "kb-enterprise",
      "document_id": "doc-enterprise-payment",
      "heading_path": "企业采购 > 月结申请",
      "index_version": "v2",
      "content": "企业完成认证并通过授信审核后，可以申请月结。",
      "source": "hybrid"
    },
    {
      "evidence_id": "E2",
      "chunk_id": "chunk-monthly-cycle",
      "kb_id": "kb-enterprise",
      "document_id": "doc-enterprise-payment",
      "heading_path": "企业采购 > 月结账期",
      "index_version": "v2",
      "content": "月结账期和结算日以企业合同约定为准。",
      "source": "context:next"
    }
  ]
}
```

EvidenceItem 保留 `chunk_id`、`document_id`、`kb_id`、标题路径、索引版本和原始正文。下游生成“企业完成认证后可申请月结 [E1]”时，用户或审计程序可以沿 E1 精确回到当时使用的文档版本，而不是只看到一个无法验证的网页式角标。

## 完整性不是模型的一句判断，而是由核心证据计算

![完整性由合法 core 证据计算](https://pic.niumianoffer.com/images/fs/evidence-completeness-core.png)

Evidence Pack 使用三种状态：

| 状态 | 判定规则 | 推荐行为 |
|---|---|---|
| `complete` | 每个必要要点至少有一条 `core` 证据 | 可以在证据约束下生成完整答案 |
| `partial` | 至少一个要点有 `core`，但仍存在缺口 | 明确回答已覆盖部分，必要时继续补证 |
| `missing` | 所有要点都缺少 `core` 证据 | 不应根据当前材料强行给出结论 |

模型负责提出要点和证据映射，最终状态由后端根据 `core` 引用重新计算。只有 supporting 证据的要点仍然算未覆盖，因为背景说明不能代替直接结论。

证据总量还受双重预算控制。接口允许设置 1 到 20 条，默认最多 8 条；输出正文总量最多 12000 个字符。达到字符预算后，系统不会截断某条原文制造半条证据，而是跳过放不下的 EvidenceItem，再根据实际保留下来的 `core` 证据重新计算分组和状态。

## 可信证据链如何避免影响原有检索

Evidence Pack 是显式开启的增强能力。关闭时不会发生模型调用，原有 TopK 响应保持不变；开启后，即使模型返回非法 JSON、证据越权、构建失败或超出预算，系统也只把证据状态标记为降级并返回 `evidence_pack: null`，正常检索结果仍然可用。

它还遵循三条不侵入原则：

- 不删除、不重排、不改写 `retrieved_chunks`
- 不把模型生成的摘要保存为原始证据
- 不用 Evidence Pack 的状态冒充最终答案正确性

因此，业务方可以根据场景选择使用方式。普通搜索直接消费 TopK；需要可信引用的问答开启 Evidence Pack；发现 `partial` 或 `missing` 时，再由受控 Research 判断是否发起新一轮检索。

## 统一测试证明了什么，也暴露了什么

正式实验使用 20 道基础题和同一份 v2 Hybrid、RRF、图谱增强、Qwen3 精排 Top10 结果。baseline 直接评价原始 Top10，candidate 只评价 Evidence Pack 选择出的原始正文，唯一变量是是否开启证据编排。

| 指标 | 原始 Top10 | Evidence Pack | 变化 |
|---|---:|---:|---:|
| Context Precision | 0.865 | 1.000 | +13.5 个百分点 |
| Context Recall | 0.983 | 0.958 | -2.5 个百分点 |
| P95 延迟 | 2679.7 ms | 35842.5 ms | +33162.8 ms |
| 平均应用模型调用数 | 1.00 | 2.00 | +1.00 |

![Evidence Pack 的收益与代价](https://pic.niumianoffer.com/images/fs/evidence-pack-benefit-cost.png)

证据编排把平均材料从 10 条、2136 个字符压缩到 1.75 条、364.6 个字符，20 道题中 18 道为 `complete`，2 道为 `partial`，所有证据都能回溯到原始 Chunk，引用回溯率达到 100%。Context Precision 提升到 1.000，说明交给下游的材料更集中，噪声显著减少。

代价同样明显。Context Recall 下降 2.5 个百分点，P95 从约 2.7 秒增加到 35.8 秒，每题多一次模型调用。退化题“企业购客户可以怎么付款，申请月结要什么条件，发票怎么开”中，证据包只选中 2 条材料并标记为 `complete`，却漏掉期望的结算与对账文档。该题没有触发证据数量上限，问题来自要点或证据选择遗漏，而不是 `max_items` 截断。

这组结果说明 Evidence Pack 已经证明了两项价值：它能够大幅压缩材料，并建立 100% 可回溯的引用；但当前模型判断仍可能高估完整性，在线延迟也不适合所有请求。因此它被保留为按需能力，而不是默认加到每次检索中。多要点问答、可信引用、异步 Research 和高价值查询更适合开启，普通在线检索继续直接使用精排结果。

## 证据编排的能力边界

Evidence Pack 只能整理当前候选池里的证据。如果关键文档没有被召回，编排本身无法把它找回来；`partial` 或 `missing` 只是暴露缺口，不会自动进行无限补证。

`complete` 也只表示每个已识别要点存在 core 证据，不等于要点识别绝对正确，更不等于最终答案一定正确。正式测试中的 Recall 退化正说明，完整性状态仍需要通过更严格提示词、规则校验和受控补证继续增强。

最后，证据编排不承担答案生成。它输出的是“回答需要哪些材料、当前材料覆盖到什么程度、每条材料来自哪里”，最终答案仍需在 Evidence Pack 约束下单独生成，并保证引用只指向实际使用的 EvidenceItem。

## 总结

第二期把第一期的 TopK 材料列表升级为一份可选的可信证据包：先汇总有界候选，再识别回答要点和 core、supporting 角色，最后由后端重新校验数据范围、加载数据库原文并计算完整性状态。

统一测试显示，它将 Context Precision 提升 13.5 个百分点，把平均 10 条材料压缩为 1.75 条，并实现 100% 引用回溯；同时也带来了 Recall 下降、P95 上升和额外模型调用。正因为效果与代价都被明确量化，Evidence Pack 最终不是被包装成默认万能能力，而是成为多要点、可信引用和受控 Research 场景中的专业组件。
