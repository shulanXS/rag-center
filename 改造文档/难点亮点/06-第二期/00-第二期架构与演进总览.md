# 第二期架构与演进总览

第一期解决的是如何把一个 RAG 原型做成可交付的检索中台。文档可以异步入库，多个租户可以安全共享服务，查询可以经过 Vector、BM25、RRF 和重排，效果也能够通过日志、反馈和 RAGAS 进行观察。

当这些基础能力真正连成一条生产链路后，新的问题才暴露出来。系统能够返回相关 Chunk，却不一定能提供完整证据；功能越来越多，却缺少统一的评测标准；面对多要点和多跳问题，单个 Query、单轮 TopK 很快触及上限。

第二期没有推翻第一期重新做一套 RAG，而是沿着这三个问题继续演进：先把已有检索体系做准、做稳、做快，再把检索结果升级为可信证据，最后在可信证据之上构建受控的 Agentic Research。

![从检索中台到可信研究系统](https://pic.niumianoffer.com/images/fs/phase2-evolution-overview.png)

## 第一期已经完成了什么

第一期的核心成果，是搭建了一条具备生产基础的 RAG 检索链路。

```text
┌──────────────────────────────────────────────────────┐
│ 平台治理：API Key · Tenant · Plan · Profile · 配额   │
├───────────────────────┬──────────────────────────────┤
│ 索引链路              │ 检索链路                     │
│ 上传 → 解析 → 分块    │ Query → 查询优化             │
│ → Embedding → 写入    │ → Vector/BM25 → RRF          │
│                       │ → LLM重排 → TopK Chunk       │
├───────────────────────┴──────────────────────────────┤
│ 存储：PostgreSQL + pgvector · Elasticsearch · Redis │
├──────────────────────────────────────────────────────┤
│ 观测：检索日志 · 用户反馈 · Langfuse · RAGAS         │
└──────────────────────────────────────────────────────┘
```

这套架构已经解决了许多 RAG 原型没有处理的问题：

- 通过 API Key 和 `tenant_id` 实现租户身份识别与数据隔离；
- 通过 Plan 和 Retrieve Profile 控制功能权限、知识库数量和检索配额；
- 通过异步任务完成文档解析、结构化切块和双路索引；
- 通过 pgvector 向量检索与 Elasticsearch BM25 形成混合召回；
- 通过 RRF 解决向量分数与 BM25 分数量纲不一致的问题；
- 通过 Query Rewrite、重排和降级策略提升复杂查询下的可用性；
- 通过检索日志、用户反馈、Langfuse 和 RAGAS 建立初步效果闭环。

pgvector 是 PostgreSQL 的向量检索扩展，Elasticsearch 负责关键词倒排检索。官网：[github.com/pgvector/pgvector](https://github.com/pgvector/pgvector)，官网：[elastic.co](https://www.elastic.co/elasticsearch)

第一期证明了 rag-center 可以作为统一检索服务运行。第二期要解决的，不再是链路有没有，而是这条链路是否足够准确、完整、可信和可控。

## 第一期暴露出的三个核心问题

第二期包含评测、精排、文档关系、证据编排、Research 和性能优化，看起来涉及很多模块。如果只按功能罗列，很容易把它理解成一次功能堆叠。实际上，这些改造都来自三个更高层的问题。

### 问题一：检索能力越来越多，但缺少稳定的判断标准

第一期已经有 RAGAS 脚本，也能观察检索耗时，但不同专题的数据集、运行入口、指标和报告格式并不统一。调整 Query Rewrite、重排或混合检索后，很难保证比较双方只改变了一个变量。

在线链路也出现了相同问题。Quality 声明返回的数量和重排默认 `top_n` 可能不一致；同一个命名档位允许调用方覆盖关键参数；多知识库检索按库独立召回，再执行二次融合；Vector 和 BM25 串行等待，外部 HTTP Client 还会在每次调用时重新创建。

这类问题不会直接让接口报错，却会慢慢破坏三个重要基础：

```text
同名档位不再代表同一条链路
实验结果难以复现
外部调用随知识库和请求数量不断放大
```

### 问题二：相关 Chunk 不等于完整证据

第一期的 Markdown 感知分块能够保留 `heading_path`，表格也尽量整体切分。但 Chunk 一旦生成，父章节、相邻段落和显式引用关系仍然会丢失。

例如某个 Chunk 只写着审核通过后两小时内原路退回。它和退款问题高度相关，却没有说明这条规则只适用于未发货订单。扩大 TopK 可能碰巧找回条件段落，也可能引入更多无关内容。

即使所有相关片段都已召回，TopK 列表仍然没有回答下面这些问题：

- 当前问题包含哪些必须回答的要点；
- 每个要点由哪条证据直接支撑；
- 哪些片段只是背景信息；
- 当前证据是完整、部分覆盖还是完全缺失；
- 回答中的引用能否回到原始文档和具体章节。

因此，第二期不能只继续调整召回参数，还需要在 Chunk 之上恢复结构，并在检索结果之上增加证据层。

### 问题三：单个Query和单轮TopK难以处理复杂问题

简单事实问题通常一次检索就能解决。复杂问题却可能包含多个并列要点，或者后一项检索依赖前一轮出现的新线索。

以组合支付退款为例，现金、优惠券和积分可能分散在不同文档中。一个 Query 很难同时贴近三种规则的原文表达。即使召回十条结果，系统也不知道其中是否缺少某个支付方式的规则。

完全开放的 Agent 循环也不是合适答案。它可能不断改写查询、重复调用模型、反复检索相同材料，最后仍然无法解释为什么停止。一个多租户中台必须同时控制查询数、轮数、模型调用、证据数量、总超时和权限边界。

第二期需要的不是自由搜索，而是**受控 Research**：先分解问题，再并行检索，根据证据完整性决定是否补证，并在预算范围内结束。

## 第二期要解决什么

三个问题最终对应三项建设目标。

| 建设目标 | 要解决的问题 | 包含的主要能力 |
|---|---|---|
| 建立专业检索体系 | 优化难验证、链路语义不稳定、在线成本偏高 | 统一评测、Qwen3精排、档位收口、全局融合、并行检索、资源复用 |
| 建立可信证据链 | Chunk丢失上下文，TopK无法表达证据完整性 | 版本化Section、轻量文档关系图、上下文恢复、Evidence Pack、引用追溯 |
| 构建受控Agentic Research | 单Query难覆盖复杂问题，自由循环不可控 | 查询分解、并行检索、完整性判断、多跳补证、预算、停止与降级 |

三项目标不是平行堆叠。它们存在清晰的依赖顺序：

```text
专业检索体系
   先保证候选结果可验证、可复现、可在线运行
                  ↓
可信证据链
   再把候选整理成完整、可回溯的证据
                  ↓
受控Agentic Research
   最后根据证据缺口决定是否继续检索
```

这条顺序决定了第二期的架构。Research 不会绕过普通检索直接调用数据库，证据编排也不会替代原始 TopK。每一层都复用并保留下一层能够检查的原始信息。

## 第二期完整架构

第二期完成后，rag-center 由原来的索引链路和单次检索链路，扩展为一个检索底座、两个产品入口和三层递进能力。

```text
┌──────────────────────────────────────────────────────────────┐
│ 接入与治理                                                   │
│ API Key · Tenant · Plan · Profile · QPS · 日配额 · 权限边界 │
├─────────────────────────────┬────────────────────────────────┤
│ 普通检索 /retrieve           │ 受控研究 /research              │
│                             │                                │
│ Query处理                    │ Planner识别要点并查询分解       │
│      ↓                      │      ↓                         │
│ RetrieveOnce单次检索         │ 1～3个查询并行复用RetrieveOnce  │
│      ↓                      │      ↓                         │
│ 原始TopK结果                 │ Evidence Decider判断完整性      │
│      ↓                      │      ↓                         │
│ 可选Evidence Pack            │ 最多2个定向补证查询             │
│                             │      ↓                         │
│                             │ Finalizer生成证据约束答案        │
├─────────────────────────────┴────────────────────────────────┤
│ 可信证据层                                                   │
│ 要点分组 · core/supporting · complete/partial/missing · 引用 │
├──────────────────────────────────────────────────────────────┤
│ 单次检索内核                                                 │
│ 全局召回 → RRF → 关系候选注入 → Qwen3精排 → 上下文恢复       │
├──────────────────────────────────────────────────────────────┤
│ 版本化索引                                                   │
│ 解析 → Section切块 → 关系索引 → v2校验 → 激活与回退          │
├──────────────────────────────────────────────────────────────┤
│ 存储与外部能力                                               │
│ PostgreSQL+pgvector · Elasticsearch · 文件存储 · 模型服务    │
├──────────────────────────────────────────────────────────────┤
│ 评测与观测                                                   │
│ Golden Set · 消融实验 · Langfuse · 四项指标 · 标准报告       │
└──────────────────────────────────────────────────────────────┘
```

这张图里最重要的设计，不是多了多少组件，而是**普通检索、证据编排和 Research 没有被做成三套互相独立的系统**。

`RetrieveOnceService` 把一次确定的检索抽成原子能力。普通 `/retrieve` 调用它一次，Research 则把 Planner 生成的多个查询并行交给它。两条产品链路因此共享相同的索引版本、召回方式、关系增强、精排模型和降级语义。

Evidence Pack 同样保持独立。普通检索可以按需开启，Research 也可以用它判断证据是否完整。它不修改原始 `retrieved_chunks`，不自动继续检索，也不强迫所有普通查询承担额外模型成本。

## 第二期形成的三项核心竞争力

第二期的竞争力不应该拆成十几个彼此孤立的功能点。真正值得讲的是三个大能力，每个能力内部包含一组互相配合的设计。

### 竞争力一：可验证、可收口、可在线的专业检索体系

第一项竞争力不是某个单独算法，而是一套能够持续优化的检索工程体系。

它首先用版本化 Golden Set、统一实验配置和 `baseline/candidate` 单变量消融解决优化结果不可比的问题。所有正式实验统一记录 Context Precision、Context Recall、P95 延迟和平均应用模型调用数。RAGAS 负责上下文质量评分，Langfuse 负责在线阶段追踪。官网：[docs.ragas.io](https://docs.ragas.io)，官网：[langfuse.com](https://langfuse.com)

在此基础上，系统完成四项链路升级：

- 用 Qwen3 专业精排替换在线通用 LLM 重排，避免排序 JSON 解析和生成式长延迟；
- 将 speed、balanced、quality 收口为固定产品契约，只有 `custom` 可以设置开放的高级参数；
- 把多知识库的分库召回和二次融合改为全局召回与一次全局 RRF；
- 通过并行检索、Embedding 复用和连接池复用降低重复计算与网络等待。

当前三个命名档位统一最终返回 5 条，但内部候选范围不同：

| 档位 | 查询处理 | 内部召回 | 精排 | 最终返回 |
|---|---|---|---|---:|
| speed | 不改写，同义词关闭 | Vector Top10 | 关闭 | Top5 |
| balanced | 不改写，同义词关闭 | Vector Top10 + BM25 Top10 | 关闭 | Top5 |
| quality | Query Rewrite，同义词关闭 | Vector Top20 + BM25 Top20 | Qwen3 Top5 | Top5 |

统一 Top5 不是收窄所有内部候选，而是统一交给下游的上下文预算。这样三档质量可以公平比较，相同档位也能在日志和评测中准确复现。

这项竞争力有真实数据支撑。Qwen3 相比原有 LLM 重排将 P95 从 79.7 秒降到 3.3 秒，Recall 提升 3.3 个百分点，但 Precision 下降 5.1 个百分点。因此它是质量、延迟、稳定性和成本的综合选型，不是所有质量指标全面提升。单库固定链路的性能改造则在质量无退化的前提下，将 P50 降低 45.7%，P95 降低 35.5%。

多知识库全局融合的工程语义已经验证，但当前两道双库题的质量结果仍不理想。现阶段可以说明全局召回、一次 RRF 和单次 Embedding 已经实现，不能把它描述成多库质量已经提升。这种明确写出适用边界的做法，本身也是统一评测体系带来的工程价值。

### 竞争力二：从文档结构恢复到可信证据链

第二项竞争力解决的是相关内容已经找到，却仍然无法安全回答的问题。

它不是单独增加一个图功能，而是形成一条连续链路：

![从相关Chunk到可信证据](https://pic.niumianoffer.com/images/fs/chunk-to-trusted-evidence-v2.png)

Evidence Pack 会把问题拆成必要要点，为每个要点关联 `core` 或 `supporting` 证据，并返回 `complete`、`partial` 或 `missing`。每条 EvidenceItem 都保留 `chunk_id`、`document_id`、章节路径、索引版本和原始正文，因此业务方既可以生成 `[E1]` 形式的引用，也可以回查证据是否被模型曲解。

这层能力刻意保持可选。普通检索仍然返回原始 `retrieved_chunks`，Evidence Pack 只新增结构化证据，不改变原始结果的数量、顺序和分数。证据编排失败时，原始检索结果仍然可用。

正式评测中，v2 轻量图谱增强相对 v1 将 Context Precision 提升 4.9 个百分点，Context Recall 提升 7.5 个百分点，P95 下降 9.1%，没有增加模型调用。说明小 Chunk 负责准确命中、关系负责恢复上下文的思路成立。

证据编排将 Precision 提升 13.5 个百分点，平均上下文从 10 条压缩到 1.75 条，引用回溯率达到 100%。代价同样明显：Recall 下降 2.5 个百分点，P95 从 2.7 秒增加到 35.8 秒，每题增加一次模型调用。因此当前结论是保留并按需开启，适合多要点问答、可信引用和高价值查询，不作为所有检索请求的默认步骤。

### 竞争力三：以证据完整性驱动的受控Agentic Research

第三项竞争力不是让 Agent 自由决定调用什么工具，而是让证据状态决定系统是否继续行动。

Planner 先识别问题要点并生成有限数量的查询，多个查询并行复用同一套检索内核。Evidence Decider 将候选映射到要点，判断当前证据是完整、部分覆盖还是缺失。只有存在明确缺口并且仍有预算时，系统才会生成定向补证查询。Finalizer 只能使用最终 Evidence Pack 组织答案，不允许用模型常识补全确定结论。

![证据完整性驱动的受控Research](https://pic.niumianoffer.com/images/fs/controlled-research-state-machine-v2.png)

这项能力包含五层控制：

- **权限控制**：只向 Pro 套餐开放，不混入普通检索档位；
- **执行控制**：限制首轮查询、补证查询和最大轮数；
- **成本控制**：限制模型调用、候选数量、证据数量和总超时；
- **停止控制**：记录证据完整、重复查询、无新证据、预算耗尽等停止原因；
- **降级控制**：任一阶段失败时保留已经取得的安全证据，不生成无依据答案。

当前 Research 已经通过权限、引用、预算、停止和异常降级等工程验收。10 道复杂题全部成功返回答案与 Evidence Pack，引用映射有效率和回溯率均为 100%，没有出现证据外的确定结论。

效果结论需要更谨慎。在双方共同可评价的 9 道题上，Research 相比单次检索的 Recall 持平，Precision 提升 3.4 个百分点，平均应用模型调用增加 2.9 次。主指标 Recall 没有达到预设提升门槛，因此 Research 当前保留为显式能力，不进入 speed、balanced 或 quality 默认档位。第二轮补证实验因为首轮证据已经完整，有效修复分母不足，目前也不能宣称多跳补证已经证明有效。

受控 Research 的竞争力不在于已经解决所有复杂问题，而在于它建立了一套可限制、可解释、可回退的复杂检索框架。后续优化 Planner、补证题集或模型时，不需要重新改变权限、状态机、证据契约和停止边界。

## 第二期最终形成的是分层能力

第二期没有把所有高级能力塞进一条默认链路，而是根据问题难度和成本要求提供不同入口。

| 使用场景 | 推荐入口 | 使用的主要能力 |
|---|---|---|
| 简单事实查询，优先速度 | `/retrieve` + speed | 向量召回，最终Top5 |
| 通用知识库问答 | `/retrieve` + balanced | Hybrid召回与RRF，最终Top5 |
| 质量优先的单次检索 | `/retrieve` + quality | Rewrite、Hybrid、Qwen3精排 |
| 多要点问答与可信引用 | `/retrieve` + Evidence | 要点分组、完整性状态、引用回溯 |
| 复杂并列问题与多跳问题 | `/research` | 查询分解、并行检索、定向补证、证据约束答案 |

这套分层设计把第二期的主线完整串了起来：底层检索负责稳定地找到候选，可信证据层负责判断材料能否支撑回答，Research 只在证据不完整时继续行动。第一期让 rag-center 从 RAG 原型变成多租户检索中台，第二期则让它进一步具备了可验证、可追溯和受控研究的能力。
