# 多格式文档解析：统一接口背后的格式隔离

前三篇从异步任务队列、Markdown 感知分块、重索引策略三个角度拆解了 rag-center 的文档处理流程。但这三篇有一个共同的隐含前提：传入分块器的是干净的文本。现实里，Celery worker 拿到的可能是 `.docx`、PDF 或 `.md` 文件。格式不同，提取方式完全不同。在分块之前，还有更前面的一步没讲——解析层。

## 为什么需要一层专门的解析

如果不抽象解析层，格式处理逻辑会散落各处：PDF 的提取代码可能藏在 `indexing_service.py` 里，Word 的读取逻辑和分块代码混在一起，每次接入新格式都要改核心链路。时间一长，`indexing_service` 变成一个什么都能干、什么都不纯粹的大杂烩。

更深层的问题是复杂度叠加。格式解析有自己的复杂度，语义分块也有自己的复杂度。把两者混在一起，任何一侧的改动都可能意外影响另一侧，测试和维护成本随之翻倍。

rag-center 在分块之前通过 **解析器注册表 + `prepare_document_content`** 把「原始文件 → 结构化文本」单独封装。索引服务看到的始终是 `document.content`，不需要知道这段文本来自哪种格式。

## 解析层和分块层的分离

这是这篇文章最核心的设计决策，值得展开说清楚。

**解析层**的职责是识别文件格式，提取文本内容，尽量还原结构信息——比如 Word 文档里的标题样式、PDF 里的文本块顺序。解析层的输出是带结构的文本字符串，通常是 Markdown 格式，因为 Markdown 可以天然承载标题层级和段落信息。

**分块层**的职责是把结构化文本按语义边界切成合适大小的 chunk。前一篇讲过的 Markdown 感知分块就属于这一层，它依赖标题层级信息来决定切割点。

两层分开之后，边界非常清晰：接入 PDF 时只需要新增一个 PDF Parser，分块逻辑完全不动；想调整分块策略时，不需要碰任何格式相关的代码。解析的复杂度和分块的复杂度各自独立，不会叠加。

## DocumentParser 的抽象接口

分离设计的工程落地依赖一个简洁的抽象接口和注册表分发：

```python
# rag-center/app/providers/parsers/base.py

@dataclass(slots=True)
class ParsedDocument:
    content: str          # 解析后的 Markdown/文本
    source_type: str      # markdown / text / docx / pdf
    metadata: dict = field(default_factory=dict)

class DocumentParser(ABC):
    @abstractmethod
    def supports(self, filename: str, mime_type: str | None = None) -> bool:
        ...

    @abstractmethod
    async def parse(self, file_bytes: bytes, *, filename: str) -> ParsedDocument:
        """解析原始文件字节流，返回结构化文本"""
        ...
```

`registry.py` 按扩展名匹配解析器，上层通过 `get_document_parser()` 获取实现：

```python
# rag-center/app/providers/parsers/registry.py

SUPPORTED_UPLOAD_EXTENSIONS = {".md", ".txt", ".markdown", ".pdf", ".docx"}

def get_document_parser(filename: str, mime_type: str | None = None) -> DocumentParser:
    for parser in _build_parsers():   # DocxParser、PdfParser、MarkdownParser
        if parser.supports(filename, mime_type):
            return parser
    raise AppError(ErrorCode.PARAM_ERROR, msg=f"不支持的文档格式: ...")
```

`document_ingestion.py` 统一编排：有 `content` 则透传，有 `source_file_path` 则读文件并调解析器：

```python
# rag-center/app/services/document_ingestion.py

async def prepare_document_content(
    *,
    content: str | None,
    file_path: str | None,
    filename: str | None,
) -> ParsedDocument:
    if content and content.strip():
        return ParsedDocument(content=normalized, source_type=..., metadata={"parser": "pass-through"})

    file_bytes = read_document_file(file_path)
    parser = get_document_parser(filename or file_path)
    return await parser.parse(file_bytes, filename=filename)
```

新增格式只需实现 `DocumentParser`、注册到 `_build_parsers()`——分块与索引链路完全不动。

## 各格式的处理差异

不同格式的解析难度差异相当大：

| 格式 | 解析难度 | 说明 |
|------|---------|------|
| Markdown / 纯文本（`.md` `.txt`） | 低 | `MarkdownParser` 直接解码 UTF-8，结构天然保留 |
| Word（`.docx`） | 中 | mammoth 转 HTML，再 markdownify 为 GFM Markdown（含表格修复） |
| PDF（文字型） | 中 | PyMuPDF 按页提取，每页加 `## 第 N 页` 标题 |
| 扫描件 PDF | 高 | 整页为图片，需 OCR，当前不在标准链路里 |

当前支持的扩展名见 `SUPPORTED_UPLOAD_EXTENSIONS`：`.md`、`.txt`、`.markdown`、`.pdf`、`.docx`，不含 HTML。

Word 的典型实现路径如下——不是逐段读样式，而是 HTML 中转：

```python
# rag-center/app/providers/parsers/docx.py

class DocxParser(DocumentParser):
    async def parse(self, file_bytes: bytes, *, filename: str) -> ParsedDocument:
        # mammoth 不直接输出 Markdown 表格，先转 HTML 再 markdownify
        html_result = mammoth.convert_to_html(io.BytesIO(file_bytes))
        markdown = docx_html_to_markdown(html_result.value)   # 含表格分隔符修复、书签清理
        return ParsedDocument(
            content=markdown,
            source_type="docx",
            metadata={"parser": self.name, "warnings": [...]},
        )
```

PDF 按页切分，为后续 `MarkdownStructuredSplitter` 提供章节边界：

```python
# rag-center/app/providers/parsers/pdf.py

class PdfParser(DocumentParser):
    async def parse(self, file_bytes: bytes, *, filename: str) -> ParsedDocument:
        doc = fitz.open(stream=file_bytes, filetype="pdf")
        parts: list[str] = []
        for index, page in enumerate(doc):
            text = page.get_text("text").strip()
            if text:
                parts.append(f"## 第 {index + 1} 页\n\n{text}")
        return ParsedDocument(content="\n\n".join(parts).strip(), source_type="pdf", ...)
```

## 解析结果存在哪里

解析完成的结构化文本写入 `document.content` 并持久化；文件上传场景同时保留 `source_file_path`（原文件落盘）。这个设计有两个连锁效果：

- **默认重索引读 `content` 即可**，不必重走解析
- **`--reparse` 时可从 `source_file_path` 重新解析**，适合解析器升级后刷新存量数据

解析在首次索引（或显式 reparse）时执行一次。之后所有分块参数调整都基于已落库的文本，不会重复触发格式解析逻辑。

## 解析质量决定检索上限

把解析层放到整个流程里看，它的位置在最前面，影响却传递到最后：解析质量决定结构化文本的完整度，结构化文本决定分块的语义边界是否准确，分块质量直接影响 embedding 的语义密度，最终到了检索环节，一个向量能召回多精准，追根溯源取决于这段文本在最开始解析时保留了多少结构信息。

格式隔离是手段，让解析质量可预期、可改进，才是解析层存在的真正原因。
