# 重索引策略：让参数变更不留历史包袱

前两篇分别讲了 rag-center 的异步索引架构和 Markdown 感知分块算法。现实运维中，系统上线之后往往不是一劳永逸的——分块参数调整、分块策略升级，这些变化都会让已经入库的旧数据和新代码产生偏差。重索引就是解决这个问题的机制。

## 什么时候需要重索引

最常见的触发场景有两类：

- **修改分块参数**：比如初期把 `chunk_size` 设为 512，跑了一段时间发现检索质量不佳，决定改成 256 来提高语义精度。参数改了之后，新上传的文档会按新参数处理，但已入库的几百篇文档依然是按 512 切的旧 chunk。两批数据用不同粒度，向量空间里的分布不一致，检索结果会出现奇怪的偏差。

- **切换分块策略**：比如把某类文档从朴素切块换成 Markdown 感知切块，已有数据需要重新处理才能获得 heading_path 元数据。

参数改了但不重索引，旧文档的 chunk 就成了历史包袱，拖着整个知识库的检索效果不升反降。

## 重索引的核心挑战

重索引听起来就是"重新跑一遍索引流程"，但实际上是一次破坏性更新。旧 chunk 存在 pgvector 和 Elasticsearch 里，新 chunk 是重新分块的结果，数量和边界都和旧的不同，没有一一对应关系。不能原地更新，只能先删再写。

这带来两个风险：

- **窗口期数据为空**：删完旧 chunk、还没写完新 chunk 的这段时间里，该文档在知识库里查不到任何结果
- **中途失败**：删完之后写入失败，文档会长期处于无 chunk 的状态，直到人工介入重跑

rag-center 的处理策略是接受这个窗口期，但通过状态字段让它可观测，并提供幂等的重跑能力来恢复异常情况。

## 重索引的完整流程

```
queue_document_reindex() 触发
     │
     ▼
purge_document_chunks()：删除 pgvector + ES 中该 document_id 的旧 chunk
     │
     ▼
更新 document 状态 → PROCESSING，清空 error_message
     │
     ▼
index_document_task.delay(document_id, reparse=...)
     │
     ├─ reparse=False：直接读 document.content 重新分块（默认）
     ├─ reparse=True：清空 content，从 source_file_path 重新解析
     │
     ▼
index_existing_document() 复用首次索引逻辑
     ├─ 分块 → 向量化 → 写入 pgvector + ES
     │
     ▼
更新 document 状态
     ├─ 成功 → SUCCESS
     └─ 失败 → FAILED + error_message
```

重索引与首次索引共用同一个 Celery 任务 `index_document_task`，差异在于投递前多了一步清旧数据，由 `reindex_service.py` 编排：

```python
# rag-center/app/services/reindex_service.py

async def queue_document_reindex(db: Session, document: Document, *, reparse: bool = False) -> None:
    if document.status == DocumentStatus.PROCESSING:
        raise ValueError(f"document is processing: {document.id}")

    # 先删旧 chunk（pgvector + ES），再改状态、投递任务——重跑不会产生重复数据
    await purge_document_chunks(db, document.id)
    DocumentRepository(db).update_status(
        document,
        status=DocumentStatus.PROCESSING,
        error_message=None,
    )
    if reparse:
        document.content = ""   # 强制 worker 从 source_file_path 重新解析
        db.flush()
    db.commit()
    index_document_task.delay(document.id, reparse=reparse)
```

清旧逻辑集中在 `chunk_purge_service.py`：

```python
# rag-center/app/services/chunk_purge_service.py

async def purge_document_chunks(db: Session, document_id: str) -> None:
    ChunkRepository(db).delete_by_document_id(document_id)
    if settings.keyword_search_provider == "elasticsearch":
        await ElasticsearchKeywordSearchProvider().delete_by_document_id(document_id)
```

## 为什么通常不需要重新上传文件

重索引能跑起来，依赖一个关键设计：**解析后的文本持久化在 `document.content`**，文件上传场景还保留 `source_file_path` 供 `--reparse` 使用：

```python
# rag-center/app/models/document.py

class Document(Base):
    __tablename__ = "documents"

    id: Mapped[str] = mapped_column(String(36), primary_key=True)
    tenant_id: Mapped[str] = mapped_column(String(128), index=True, nullable=False)
    kb_id: Mapped[str] = mapped_column(String(36), ForeignKey("knowledge_bases.id"), ...)
    title: Mapped[str] = mapped_column(String(255), nullable=False)
    content: Mapped[str] = mapped_column(Text, nullable=False, default="")  # 解析后的结构化文本
    source_file_path: Mapped[str | None] = mapped_column(String(512), nullable=True)   # 原文件路径
    source_filename: Mapped[str | None] = mapped_column(String(255), nullable=True)
    status: Mapped[int] = mapped_column(Integer, nullable=False)
    error_message: Mapped[str | None] = mapped_column(Text, nullable=True)
```

默认重索引（`reparse=False`）直接读 `content` 重新分块，不依赖磁盘上的原文件是否还在。若分块策略或解析器升级，可传 `--reparse` 从 `source_file_path` 重新走解析流程。

值得注意的是，**仅调整分块参数时不需要 reparse**——解析结果已经落库，在文本层面重新切 chunk 即可。`--reparse` 适合解析器本身发生变更的场景。

## 批量重索引脚本

`scripts/reindex_knowledge_base.py` 提供了对整个知识库批量重索引的能力：

```python
# rag-center/scripts/reindex_knowledge_base.py

# 默认选取知识库内所有 SUCCESS 状态的文档
documents = repository.list_by_kb_id_and_status(kb.id, DocumentStatus.SUCCESS)
document_ids = [document.id for document in documents]

for document_id in document_ids:
    document = repository.get_by_id(document_id)
    if document.status == DocumentStatus.PROCESSING:
        continue   # 正在索引中的文档跳过
    if document.status != DocumentStatus.SUCCESS:
        continue   # 仅重索引已成功入库的文档
    try:
        await queue_document_reindex(db, document, reparse=args.reparse)
        stats["queued"] += 1
    except Exception as exc:
        stats["failed"] += 1   # 单文档提交失败不阻断其他文档
```

脚本支持 `--document-id` 指定单篇、`--reparse` 强制重解析、`--wait` 轮询等待完成。跑完之后，可查询 FAILED 状态的文档针对性排查和重跑。先删再写的设计保证了多次重跑不会产生重复 chunk。

## 重索引期间的注意事项

重索引期间，document 状态会临时回到 PROCESSING。前端轮询到这个状态时，应该展示"正在重新处理"，而不是报错。这和首次索引的状态语义完全一致，前端逻辑不需要特殊处理。

中途失败的文档，FAILED 状态和 error_message 会告知是哪一步出了问题，比如 embedding API 超时或者 ES 连接异常。修复底层问题之后，对这些文档重跑脚本即可。先删再写的设计保证了多次重跑不会产生重复 chunk——脚本是幂等的。

前三篇讲完了索引流程的主干：异步架构保证处理不阻塞用户，Markdown 感知分块保证 chunk 语义质量，重索引保证参数调整后存量数据平稳跟进。但这三篇都有一个隐含前提：拿到的是结构化文本。真实场景里，文件格式各异，这是第四篇要讲的内容。
