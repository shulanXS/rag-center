# 项目架构全景

rag-center 是一个多租户 RAG 检索中台。它专注于检索本身，不做答案生成——文档进来，chunk 出去，中间的每一步都是系统要做的事。下图是整体结构，后文沿着这张图逐层讲解。

```
┌────────────────────────────────────────────────┐
│         平台层（多租户 · API Key · Plan 配额）    │
├──────────────────────┬─────────────────────────┤
│      索引链路         │       检索链路            │
│  上传 → 解析 → 分块   │  Query → 查询优化         │
│  → 向量化 → 写入      │  → 双路召回 → RRF 融合    │
│                      │  → 重排 → 返回 chunk      │
├──────────────────────┴─────────────────────────┤
│      存储层（PostgreSQL+pgvector · Elasticsearch）│
├────────────────────────────────────────────────┤
│     观测层（Langfuse · 检索日志 · RAGAS）         │
└────────────────────────────────────────────────┘
```

整个系统由两条链路驱动：文档从索引链路进入，查询从检索链路取出结果。平台层横跨两条链路，负责租户隔离和资源管控。存储层和观测层为两条链路共同服务。

## 平台层

每个请求进入系统，最先经过的是平台层。认证、隔离、资源管控全部在这里完成。

```
Bearer token（API Key）
      │
      ▼
SHA-256 哈希 → 查 api_keys 表 → 读出 tenant_id
      │
      ▼
注入 TenantContext（贯穿整个请求生命周期）
      │
      ▼
查询 Plan 配置（free / standard / pro）
      │
      ├─ 功能开关校验：hybrid / rerank / query rewrite 是否可用
      └─ 配额校验：QPS 限流 + 日检索量上限（Redis 原子计数）
```

所有数据表通过 tenant_id 字段隔离。知识库、文档、chunk、检索日志各表均带这个字段。不同租户的数据在数据库层天然分开，不依赖应用层额外过滤。

## 索引链路

文档上传后，接口立即返回，任务进入 Celery 队列由 Worker 异步执行。进入队列后，依次走四步：

1. **解析**：DocumentParser 识别文件格式，提取结构化文本。标题层级信息在这一步被记录，随后传入 chunk metadata。

2. **分块**：Markdown 感知策略按标题边界切分逻辑段落。同一节内容尽量落在同一 chunk，表格整块保留，不截断行列关系。

3. **向量化**：分块文本批量送入 Embedding API，通过 Provider 抽象层调用，底层模型可随时替换。

4. **写入**：向量写入 pgvector，文本写入 Elasticsearch，两路并行执行。全部成功，document 状态推进到 SUCCESS；任意失败，标记 FAILED 并记录 error_message。

## 检索链路

检索是整个中台最核心的路径。一次 retrieve 请求经历四个阶段：

```
Query
  ↓
① 查询优化（同义词扩展 + LLM 改写，超时自动降级）
  ↓
② 双路并行召回（pgvector 向量 + Elasticsearch BM25）
  ↓
③ RRF 融合排序（多知识库时库内先融、跨库再融）
  ↓
④ 可选 LLM 重排（pro 专属，失败自动降级）
  ↓
返回 TopK chunk + metadata
```

**① 查询优化**先走同义词扩展，再走 LLM 改写。改写目标是让 query 更接近文档的表达方式。这一步设有超时保护，超时后直接用原始 query 进入召回，不阻断主链路。

**② 双路召回**中，pgvector 走向量相似度，Elasticsearch 走 BM25 倒排，两路独立执行互不等待。向量检索擅长语义相近但措辞不同的情况，BM25 擅长关键词精确匹配，两者各有侧重。

**③ RRF 融合**用倒数排名融合算法合并两路结果。算法只看排名，不依赖原始分数的绝对值，解决了两路分数量纲不一致的问题。跨多个知识库时，每个库的结果先各自融合，再做一次跨库的 RRF，产生全局排名。

**④ 可选重排**在 Plan 允许的情况下，把候选 chunk 送入 LLM 或 Reranker 精排。重排失败自动降级回 RRF 结果，不影响检索返回。

## 存储层

存储层包含三个组件，各司其职。

**PostgreSQL + pgvector** 承担两类数据。业务数据，比如租户信息、知识库配置、文档记录，存在普通表里。向量数据存在 pgvector 扩展（官网：[github.com/pgvector/pgvector](https://github.com/pgvector/pgvector)）提供的向量列里，使用 cosine 相似度做检索。业务数据和向量数据同库存放，减少了跨库事务的复杂度。

**Elasticsearch** 专门负责关键词检索。它维护每个 chunk 的倒排索引，配合 IK 分词器处理中文。IK 支持细粒度和智能分词两种模式，系统写入时用细粒度，查询时用智能模式，在召回率和精确率之间取平衡。

**Redis** 同时扮演三个角色：Celery 的消息 broker、QPS 限流的计数窗口、以及日检索配额的计数器。三者共用一个 Redis 实例，用键名前缀区分。

## 观测层

检索链路跑完之后，系统做的最后一件事是记录。

每次 retrieve 完成，系统向 retrieval_logs 表写入一行。记录内容包括：原始 query、使用的检索 Profile、端到端耗时、各阶段耗时拆分、最终返回的 chunk ID 列表，以及关联的 trace_id。这张表是后续分析和评估的原始数据来源。

链路追踪通过 Langfuse（官网：[langfuse.com](https://langfuse.com)）可选接入。启用后，query_processing、retrieval、rerank 三个阶段的中间状态和耗时都可以在 Langfuse 界面可视化查看。没有 Langfuse 时系统照常运行，只是少了这层可视化。

用户可以对返回的检索结果打分，分值从 1 到 5。低分记录可以批量导出，格式兼容 RAGAS（官网：[docs.ragas.io](https://docs.ragas.io)）评估集。RAGAS 离线评估计算 **context_precision** 和 **context_recall** 两个指标，量化检索链路的实际质量。
