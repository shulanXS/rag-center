# 项目竞争力：五大亮点

大多数 RAG 项目停留在跑通流程的阶段：搭一个向量库，加一段 embedding，做个 topK 检索，就算完成了。rag-center 的目标不是这个。它把 RAG 检索做成可以真正交付的基础设施，多租户、分级服务、完整检索管道、效果评估，每一块都是在解决生产环境里真实存在的问题。

下面五个亮点，是这个项目值得认真讲的地方。

## 亮点一：中台定位 + 企业级权限

**中台而非应用**是这个项目的起点。很多 RAG 项目绑定一个具体业务场景，比如给某个产品文档页加问答功能。rag-center 的定位从一开始就不同：它把检索做成统一 API，让多个租户和多个业务系统共用同一套能力。中台不生成最终答案，只负责把最相关的文档片段找准找全。答案如何组织、Prompt 如何设计，全部由业务方自己决定。这个职责划分让各业务可以独立迭代生成策略，而不用动检索层。

**权限体系**是中台定位的配套保障。每个租户持有一个 API Key，格式是 `rk_live_` 前缀加 32 位随机十六进制字符串。数据库只存 SHA-256 哈希，明文只在生成时出现一次，之后不可恢复。请求头带 Bearer token，后端解析出 `tenant_id`，调用方无法伪造其他租户的身份。

**Plan 分级**把能力和资源都按档位管控：

| | free | standard | pro |
|---|---|---|---|
| 混合检索（hybrid） | 不支持 | 支持 | 支持 |
| 查询改写（LLM rewrite） | 不支持 | 支持 | 支持 |
| LLM 重排（rerank） | 不支持 | 不支持 | 支持 |
| 日检索量上限 | 100 次 | 1000 次 | 10000 次 |
| 最大知识库数量 | 3 个 | 20 个 | 100 个 |

不同用户拿到的能力边界从系统层面锁死，不依赖应用层做额外判断。

**数据隔离**前置到检索阶段。不属于当前租户的知识库在数据层就过滤掉，不进入候选上下文，不依赖应用层额外校验。

## 亮点二：生产级检索全链路

大多数 RAG 原型的检索逻辑是 embedding + topK 相似度搜索。向量相似度对口语化查询不友好，也抓不住关键词精确匹配的场景。rag-center 的检索链路是一条完整的管道，每个环节都有明确的设计意图：

```
Query
  ↓
① 查询优化（同义词扩展 → LLM 改写，超时降级为原始 query）
  ↓
② 双路并行召回（pgvector 向量 + Elasticsearch BM25）
  ↓
③ RRF 融合排序（score = Σ 1/(k+rank)，k=60）
  ↓
④ 可选 LLM 重排（pro 专属，失败自动降级）
  ↓
返回 TopK chunk + metadata
```

**查询优化**先走同义词扩展，词表在知识库级别配置，无需重新索引文档。再走 LLM 改写，把口语化问题规范化成更接近文档表述的形式。两步都有超时保护，超时直接用原始 query 降级进入下一阶段，不阻塞检索主链路。

**双路召回**同时启动 pgvector 向量检索和 Elasticsearch BM25 关键词检索。两路在语义上互补。向量检索擅长模糊语义匹配，BM25 擅长精确关键词命中，混合使用比单独任何一路都更鲁棒。

**RRF 融合**解决了两路分数量纲不一致的问题。向量相似度和 BM25 分数无法直接加权，RRF 只看排名，公式是 `score = Σ 1/(k+rank)`，k 默认取 60。候选结果的最终排序只由名次决定，和原始分数的绝对值无关。

**LLM 重排**是 pro 计划专属的可选步骤，对融合后的候选集做精排。重排失败时自动降级回 RRF 结果，不影响检索返回。任意环节出现降级，响应的 metadata 里都会标注 `degraded: true`，调用方可以感知到当次检索走的是哪条路径。

## 亮点三：结构化文档处理引擎

检索效果的上限由入库数据的质量决定。chunk 的语义质量好，向量才有意义；chunk 的边界合理，召回的相关段落才是完整的。rag-center 在文档处理阶段投入了专门的设计：

```
原始文件（Markdown / PDF / Word / HTML）
  ↓
DocumentParser（格式识别 → 提取结构化文本）
  ↓
分块策略选择
  ├─ Markdown 感知分块（按标题层级 + 表格整体保留）
  └─ 朴素字符分块（纯文本文档）
  ↓
批量向量化（Embedding API）
  ↓
写入 pgvector + Elasticsearch
```

**多格式解析**通过 DocumentParser 抽象层完成。系统识别文档格式，提取结构化文本，给后续分块提供干净的输入。Parser 和分块层是分离的，同一套分块逻辑可以处理来自不同格式的解析结果。

**Markdown 感知分块**按标题层级划分逻辑段落。同一节内容优先保持在同一个 chunk 里，表格整体保留不截断。每个 chunk 携带 `heading_path` 元数据，记录自己属于哪个章节层级，检索结果可以带上这个上下文信息返回给调用方。

**异步索引**由 Celery + Redis 驱动。上传接口秒级返回任务 ID，处理在后台完成。文档状态机从 PROCESSING 推进到 SUCCESS 或 FAILED，调用方可以轮询查询，不需要等待上传接口阻塞。

**重索引**是一个实用的工程细节。如果分块参数调整了，不需要重新上传文件。系统从数据库读取已存储的解析文本，用新参数重新分块入库。这个操作是幂等的，可以安全地反复执行。

关键洞察在于：花时间设计入库阶段，是提升检索效果最经济的手段，比调整检索参数的收益更稳定。

## 亮点四：可量化的效果评估闭环

RAG 系统最难的部分往往不是建立初版，而是知道它在哪里出了问题、改了参数有没有用。没有评估闭环，调参就是凭感觉，优化方向无法验证。

```
在线检索
  ↓
写入 retrieval_logs（query / latency / chunk_id 列表 / trace_id）
  ↓
用户对结果打分（1-5，通过 log_id 关联）
  ↓
Langfuse 链路追踪（query_processing / retrieval / rerank 各阶段耗时）
  ↓
低分 trace 导出 → 构建 RAGAS 评估集
  ↓
计算 context_precision + context_recall → 量化检索质量
```

**在线日志**是闭环的起点。每次检索写入 `retrieval_logs`，记录 query、search_query、检索 profile、latency_ms 和 trace_id。`log_id` 关联后续反馈，一次检索的完整上下文可以追溯。

**用户反馈**让调用方可以对某次检索结果打 1 到 5 分，通过 `log_id` 关联到具体的检索记录。低分记录直接指向有问题的 query，是定位问题的第一手数据。

**Langfuse 链路追踪**（官网：[langfuse.com](https://langfuse.com)）可视化每次检索的三个阶段中间状态和耗时。当检索效果差时，可以快速判断是查询优化没发挥作用，还是召回阶段没找到相关内容，还是重排反而把好结果压下去了。

**RAGAS 离线评估**（官网：[docs.ragas.io](https://docs.ragas.io)）从 Langfuse 导出低分 trace，构建评估集，跑 context_precision 和 context_recall 两个指标。调整分块参数或检索 profile 之后，效果变化有数字对比，不依赖主观判断。这套体系让调参结果可验证。

## 亮点五：可插拔的工程架构

系统对所有外部依赖都做了 Provider 抽象，共六类：Embedding、VectorStore、KeywordSearch、LLM、Rerank、DocumentParser。每类都有 ABC 基类，具体实现通过工厂函数加环境变量切换，业务逻辑无需改动。这个设计的价值不只是方便换模型，而是让整个系统的关注点分层更清晰。检索逻辑只知道调 Rerank Provider 拿排序结果，不关心背后是哪个模型在跑，也不关心重排是否真的被启用。

**NoopRerankProvider** 是一个空实现，用于表达当前 plan 不支持 rerank 这个状态。上游代码不需要判断 rerank 是否开启，直接调用 Provider 接口，Noop 实现什么也不做，原样返回输入。这比到处写 `if rerank_enabled` 判断要干净得多。

**统一错误码**覆盖 20000 到 59999 范围，每个错误码的含义确定。比如 20013 是 plan 功能限制，20014 是配额超限。调用方可以根据错误码做精确的错误处理，而不是解析错误消息字符串。

**降级策略**贯穿核心链路：LLM 超时跳过查询优化直接召回，ES 不可用退化为纯向量模式，Langfuse 失败只打 warning 不影响检索返回。辅助依赖的故障不会导致核心链路中断，这是生产系统该有的健壮性。

五大亮点覆盖了定位、检索、数据、评估、工程五个维度，合在一起描述的是一个有完整闭环、有清晰边界、有生产健壮性的检索中台，而不只是一个功能跑通的原型。
