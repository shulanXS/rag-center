# 多租户数据隔离

鉴权解决的是"谁能进来"。进来之后，还需要解决"看到什么"。在一个多租户系统里，不同租户的数据共存于同一套基础设施，隔离设计的好坏直接决定了系统的安全边界。

## 三种隔离策略

多租户数据隔离有三种主流策略，各有权衡：

1. **独立数据库**：每个租户一个独立的数据库实例，连接串、存储、计算全部物理隔开。隔离最彻底，数据泄露风险极低，故障影响域小。代价是运维复杂度随租户数线性增长，资源利用率低，每个空数据库都在消耗内存和连接池。适合高安全要求场景。

2. **独立 Schema**：所有租户共用同一个数据库实例，但每个租户有自己的 Schema，表结构相同但数据物理分开。运维成本比独立数据库低，隔离性比行级过滤强。问题是 Schema 数量增长后，catalog 管理、迁移脚本同步都会变得繁琐，表结构变更时要对每个 Schema 重复执行。

3. **共享表 + 行级过滤**：所有租户的数据存在同一批表里，每条记录带一个 `tenant_id` 字段，所有查询都在 WHERE 条件里加上租户过滤。部署最简单，维护成本最低，表结构变更只需执行一次，资源利用率也最高。

rag-center 的目标场景是中小到中等规模的 SaaS 服务，不需要物理隔离的代价，**行级过滤**是最务实的选择。

确定了策略之后，接下来的问题是如何在工程上把这套策略落实到每一层：从数据模型的字段设计，到数据访问层的强制约束，再到向量和全文两个检索引擎的具体处理。

## tenant_id 贯穿所有核心表

`tenant_id` 是一个字符串类型的标识符，比如 `tenant_demo`。它不只是一个普通字段，而是**所有核心表的主要分区键**。

涉及的表包括：

- `knowledge_bases`：知识库归属于哪个租户
- `documents`：文档隶属于哪个知识库，间接也就隶属于哪个租户
- `chunks`：文档切片，向量和原文都带 `tenant_id`
- `retrieval_logs`：每次检索请求的日志记录

这种设计确保了数据模型层面没有歧义——任何一条业务数据，都能从 `tenant_id` 字段直接追溯到它的归属者。有了字段层面的保证，还需要在访问层确保这个字段被正确使用。

## Repository 层的强制过滤

光有 `tenant_id` 字段不够，还需要确保每次查询都带上了这个过滤条件。rag-center 在 Repository 层做了这个保证。

所有数据库操作都封装在各自的 Repository 类里，方法签名要求调用方传入 `tenant_id`，内部用 SQLAlchemy 查询始终把 `tenant_id` 作为必要条件：

```python
# rag-center/app/repositories/knowledge_base_repository.py

class KnowledgeBaseRepository:
    # id 与 tenant_id 双条件，防止仅凭 kb_id 跨租户读取
    def get_by_id_and_tenant(self, kb_id: str, tenant_id: str) -> KnowledgeBase | None:
        stmt = select(KnowledgeBase).where(
            KnowledgeBase.id == kb_id,
            KnowledgeBase.tenant_id == tenant_id,
        )
        return self.db.scalar(stmt)

    # 列表查询同样强制带 tenant_id 过滤
    def list_for_tree(self, tenant_id: str, keyword: str | None = None) -> list[KnowledgeBase]:
        stmt = (
            select(KnowledgeBase)
            .where(KnowledgeBase.tenant_id == tenant_id)
            .order_by(KnowledgeBase.created_at.desc())
            .options(selectinload(KnowledgeBase.documents))
        )
        if keyword:
            stmt = stmt.where(KnowledgeBase.name.ilike(f"%{keyword}%"))
        return list(self.db.scalars(stmt).all())
```

没有一条对业务数据的查询路径是不带租户过滤的。这意味着即使上层业务逻辑出现了 bug，比如意外地没有正确传入租户信息，Repository 层也会因为参数缺失而报错，而不是悄悄返回其他租户的数据。这是防御性编程的一种体现：**错误应该在边界处暴露，而不是在数据里静默泄露**。

数据库层的隔离做好了，还有检索引擎这一侧——rag-center 同时用了 pgvector 和 Elasticsearch，两个引擎需要用各自的方式实现等效的租户隔离。

## 向量检索和全文检索的隔离

pgvector 的向量检索基于 PostgreSQL，租户过滤在 `PgVectorStore.similarity_search` 里通过 SQLAlchemy WHERE 子句实现：

```python
# rag-center/app/providers/vectorstores/pgvector.py

async def similarity_search(
    self,
    query_vector: list[float],
    *,
    tenant_id: str,
    kb_id: str,
    top_k: int = 5,
) -> list[dict]:
    distance = Chunk.embedding.cosine_distance(query_vector).label("distance")
    stmt = (
        select(Chunk, distance)
        # 向量检索必须在 WHERE 中限定租户与知识库
        .where(Chunk.tenant_id == tenant_id, Chunk.kb_id == kb_id)
        .order_by(distance)
        .limit(top_k)
    )
    rows = self.db.execute(stmt).all()
    # ...
```

Elasticsearch 的隔离方式略有不同。ES 没有行级权限，但 rag-center 通过在每次搜索请求里加 filter 子句来实现等效效果：

```python
# rag-center/app/providers/keyword_search/elasticsearch.py

# filter 不参与评分，只做硬性租户/知识库过滤
payload = {
    "query": {
        "bool": {
            "filter": [
                {"term": {"tenant_id": tenant_id}},
                {"term": {"kb_id": kb_id}},
            ],
            "must": {
                "multi_match": {
                    "query": query,
                    "fields": ["title^2", "content"],
                }
            },
        }
    },
    "size": top_k,
}
```

filter 子句不参与相关性评分，只做精确过滤，性能上比 must 查询更高效，也更适合做租户隔离这类硬性约束。两个引擎的数据写入也是同样逻辑：文档在入库时就带上 `tenant_id`，检索时的过滤只是在查询端验证了写入时已经做好的分类。

## 隔离的边界在哪里

行级过滤的隔离不是物理隔离，它依赖的是代码的正确性。这是它相比独立数据库方案的代价。rag-center 通过把过滤逻辑集中在 Repository 层来控制这个风险——任何新加的查询路径都必须经过这一层，不存在绕过的捷径。

数据隔离解决了"租户看不到彼此的数据"这个基本问题。但在多租户 SaaS 里，不同租户的付费等级不同，享有的服务能力也应该不同。这就引出了下一个设计课题：Plan 体系。
