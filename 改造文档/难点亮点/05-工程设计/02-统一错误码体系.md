# 统一错误码体系

上一篇讲了 Provider 抽象如何解决可扩展性问题，这一篇转向可维护性。一个系统对外暴露的 API 里，错误处理是最容易被低估的部分。rag-center 在这里做了一套统一的错误码体系，值得单独拆开来讲。

## HTTP 状态码不够用

HTTP 状态码描述的是"协议层"的语义，不是业务语义。400 表示"请求格式有问题"，403 表示"没有权限"，404 表示"资源不存在"——这些分类对于 Web 框架来说够用，但对于一个有十几种业务错误的 RAG 系统来说，远远不够。

以鉴权场景为例。用户可能没带 token，可能带了过期的 token，可能带了有效 token 但访问的是别人的 knowledge base，可能账号被封禁。这些情况用 HTTP 来看都是 401 或 403，但业务含义完全不同，调用方要做的处理也不一样。

Plan 相关的错误也存在类似问题。同样是 403，"账号是 free 套餐但调用了 pro 功能"和"今日检索配额已用完"的应对方式截然不同——前者需要引导用户升级套餐，后者只需要提示"今日配额已用完，明天再来"。靠 HTTP 状态码区分不了这两种情况，调用方只能统一弹一个模糊的错误提示。

rag-center 的做法是引入业务错误码，让每一种业务错误都有独立的数字标识，调用方可以针对每种情况做精确处理。

## 统一响应格式

所有接口都遵守同一个响应结构：

```json
{
  "code": 0,
  "msg": "success",
  "data": { ... }
}
```

`code` 是业务状态码，0 表示成功，非 0 表示各种业务错误。`msg` 是面向人的描述，`data` 是实际的业务数据。

**HTTP 状态码和业务 code 是两套体系，各司其职**：

- 业务逻辑产生的错误（权限不足、配额超限），HTTP 状态码统一返回 200，code 字段携带具体错误码
- 服务端内部问题（数据库连接断了、未处理的异常），才返回 5xx

这个策略让调用方的解析逻辑变得清晰：先判断 HTTP 状态码是否 200——不是 200 就是服务器出了问题，记录告警、等待恢复；是 200 再判断 code——0 就处理 data，非 0 走错误处理分支。两层判断，不会把"服务器挂了"和"用户权限不足"混在一起处理。

## 错误码分段设计

业务错误码从 20000 起，按范围划分（定义在 `app/core/exceptions.py`）：

```
20000 – 29999   API / 请求 / 鉴权 / Plan / 资源不存在
30000 – 39999   数据库与存储（DB、索引、向量库、关键词检索）
40000 – 49999   LLM / Embedding / Rerank 调用
50000 – 59999   系统与服务（未捕获异常、检索失败等）
```

注意：`KNOWLEDGE_BASE_NOT_FOUND`（20008）、`DOCUMENT_NOT_FOUND`（20011）在 20000 段，不在 30000 段。

错误码用 `Enum` 集中定义，每个成员携带 `(code, 默认 msg)`：

```python
# rag-center/app/core/exceptions.py

from enum import Enum

class ErrorCode(Enum):
    SUCCESS = (0, "成功")

    # API / 请求 20000-29999
    PARAM_ERROR = (20001, "参数错误")
    REQUEST_VALIDATION_ERROR = (20002, "请求参数校验失败")
    API_RATE_LIMIT = (20005, "接口调用超限")
    UNAUTHORIZED = (20010, "未授权")
    KNOWLEDGE_BASE_NOT_FOUND = (20008, "知识库不存在")
    DOCUMENT_NOT_FOUND = (20011, "文档不存在")
    FEATURE_NOT_ALLOWED = (20013, "当前套餐不支持该功能")
    QUOTA_EXCEEDED = (20014, "配额已用尽")

    # 存储 30000-39999
    DB_ERROR = (30001, "数据库操作失败")
    VECTOR_STORE_ERROR = (30004, "向量存储操作失败")

    # LLM 40000-49999
    LLM_TIMEOUT = (40001, "大模型响应超时")
    RERANK_FAILED = (40009, "大模型重排失败")

    # 系统 50000-59999
    SERVER_ERROR = (50000, "服务器异常")
    RETRIEVAL_FAILED = (50002, "检索服务异常")

    @property
    def code(self) -> int:
        return self.value[0]

    @property
    def msg(self) -> str:
        return self.value[1]
```

几个典型错误码：

| 错误码 | 枚举名 | 触发场景 | 调用方应对 |
|--------|--------|---------|-----------|
| 20010 | UNAUTHORIZED | API Key 无效或缺失 | 检查鉴权配置 |
| 20013 | FEATURE_NOT_ALLOWED | 套餐不支持该功能 | 引导升级套餐 |
| 20014 | QUOTA_EXCEEDED | 当日检索次数达上限 | 提示配额用尽 |
| 20008 | KNOWLEDGE_BASE_NOT_FOUND | 知识库不存在或无权访问 | 检查 kb_id |
| 20002 | REQUEST_VALIDATION_ERROR | Pydantic 校验失败 | 展示字段级错误 |

`20013` 与 `20014` 单独拆分，是因为引导逻辑不同：前者指向升级，后者只需等待配额恢复。

## 开发侧的使用体验

业务层遇到需中断的请求时，抛 `AppError`，传入 `ErrorCode` 枚举：

```python
# rag-center/app/tenant/retrieve_policy.py

from app.core.exceptions import AppError, ErrorCode

if not plan_context.features.hybrid_retrieval and mode == "hybrid":
    raise AppError(
        ErrorCode.FEATURE_NOT_ALLOWED,
        msg="当前套餐不支持混合检索",
        context={"plan": plan_context.plan, "mode": mode},
    )
```

全局异常处理器格式化为统一 JSON（`AppError` 默认 HTTP 200，未捕获异常才 500）：

```python
# rag-center/app/main.py

@app.exception_handler(AppError)
async def app_error_handler(request: Request, exc: AppError) -> JSONResponse:
    return JSONResponse(content=error_response(exc.code, exc.msg, exc.data))

@app.exception_handler(Exception)
async def unhandled_error_handler(request: Request, exc: Exception) -> JSONResponse:
    return JSONResponse(
        status_code=500,
        content=error_response(ErrorCode.SERVER_ERROR, ErrorCode.SERVER_ERROR.msg),
    )
```

`error_response` 定义在 `app/schemas/common.py`。新增错误：在 `ErrorCode` 加枚举项，业务处 `raise AppError(ErrorCode.XXX, ...)` 即可。

## 小结

统一错误码体系本质上是在"系统和调用方之间"建立一套清晰的契约。调用方知道每一种错误码对应什么情况、能做什么处理，不需要靠猜测或反复沟通文档。这种清晰性是可维护性的重要组成部分。
