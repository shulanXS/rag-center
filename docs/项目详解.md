> 一个轻量级、多租户的 RAG（检索增强生成）能力中心。
> 后端 FastAPI + SQLAlchemy + Celery，向量库 PostgreSQL/pgvector，关键词检索 Elasticsearch，
> Embedding / LLM / Rerank 全部走 OpenAI 兼容 HTTP API。
> 后端代码约 13,800 行，评测与脚本约 10,700 行。

## 1. 项目定位与整体架构

### 1.1 它解决什么问题

RAG Center 不是一个「聊天机器人」，而是一个**检索能力中台**。它把企业文档变成可检索的知识，
再通过统一的 HTTP API 提供三种能力：

| 能力 | 接口 | 本质 |
|---|---|---|
| 知识管理 | `/knowledge-bases/*`、`/documents/*` | 建库、传文、查状态、重建索引 |
| 检索 | `/rag/retrieve` | 一次请求返回 Top-K 相关 chunk + 完整元数据 |
| 深度研究 | `/rag/research` | 自动拆解问题 → 多路召回 → 判断证据充分性 → 补检索 → 生成答案 |

关键定位差异：
- **它不生成答案**（除了 Research 的 finalizer 阶段），主链路只负责「找到好证据」；
- **它内置多租户商业化能力**：套餐分级、功能门禁、配额、限流；
- **它把「可观测 + 可回滚 + 可复现」当作一等公民**：每次检索都有 `log_id`/`trace_id`，
  可以导出成评测样本，形成「线上反馈 → 离线回归 → 配置调整」的闭环。

### 2.1 分层依赖规则

```

            ↓

            ↓
         tenant（策略）  core（基础设施）
```

- **路由层极薄**：`app/api/v1/routes/rag.py` 全文只有 ~120 行，
  只做「解析请求 → 调 service → 包 `success_response`」；

## 3. 数据模型

共 10 张表，全部带 `tenant_id` 字段实现租户隔离。

### 3.1 核心表关系

```
tenants
  ├──< api_keys            (一个租户多个 Key，Key 哈希存储)
  ├──< knowledge_bases     (一个租户多个库)
  │      ├──< documents
  │      │      └──< chunks ─── embedding vector(1536)
  │      │            └──< chunk_relations  (chunk → chunk 引用边)
  │      └──< index_versions   (v1/v2 索引版本状态机)
  ├──< research_tasks      (Research 异步任务，存 result JSON)
  └──< feedback            (用户打分反馈)
```

### 3.2 Chunk 表：检索的原子单位

```sql
chunks
├── id                    PK
├── tenant_id             索引（所有查询强制带此条件）
├── kb_id                 FK → knowledge_bases (CASCADE)
├── document_id           FK → documents (CASCADE)
├── title                 文档标题
├── content               原始 chunk 文本（返回给用户的就是它）
├── retrieval_text        ★ v2 索引专有：拼装好的「标题+标题路径+正文」
├── index_version         'v1' | 'v2'
├── section_id            所属章节（uuid5 稳定哈希）
├── parent_section_id     父章节
├── order_index           章节内顺序（用于前后邻查找）
├── metadata (JSONB)      chunk_type / heading_path / heading_level / parser ...
└── embedding             Vector(1536)   ← pgvector
```

**`content` vs `retrieval_text` 是本项目一个很关键的设计**：

| 字段 | 用途 | 说明 |
|---|---|---|
| `content` | **给人看** | 纯正文，干净，直接拼进 LLM 上下文 |
| `retrieval_text` | **给机器检索** | `文档：{title}\n章节：{heading_path}\n\n{content}` |

v1 索引只有 `content`（向量直接对正文算）；v2 索引对 `retrieval_text` 算向量，
这样「章节路径」这类结构信息能参与语义匹配，而返回给用户的仍是干净的 `content`。
切换索引版本时会**全量重建**，不会新旧混存。

### 3.3 索引版本状态机

`app/core/index_versions.py` 只有两行，但含义很重：

```python
DEFAULT_INDEX_VERSION = "v2"
LEGACY_INDEX_VERSION = "v1"
```

- 绝大多数新功能（图扩展、上下文扩展、`retrieval_text` 检索）**只在 v2 生效**；
- 代码里到处出现 `if index_version != LEGACY_INDEX_VERSION` 的守卫，
  这是本项目**渐进式迁移**的核心手法：老库继续跑老逻辑，新库享受新能力。

`index_versions` 表记录 `building / ready / active / archived` 状态，
支持「建新索引 → 验证 → 原子切换 → 保留旧版回滚」。

### 3.4 chunk_relations：轻量知识图谱

```sql
chunk_relations
├── source_chunk_id   引用发起方
├── target_chunk_id   被引用方
├── relation_type     'reference' | ...
├── tenant_id / kb_id / index_version
```

当文档中出现 `> 关联规则：...` 这类引用指针时，系统会：
1. 在 Markdown 中识别出指针，生成一个 `chunk_type=reference_pointer` 的**占位 chunk**；
2. 解析出它指向的正文 chunk，写入 `chunk_relations` 边；
3. 检索时，占位 chunk **不参与向量检索**（`pgvector.py` 里显式过滤），
   但**参与图扩展**——命中的正文 chunk 可以顺边拉出被引用的内容。

这是「轻量图谱」的典型实现：不引入 Neo4j，只用一张关系表 + 一个自建解析器。

### 4.2 结构化分块：为什么不用朴素滑窗

朴素 RAG 用固定长度滑窗切块（如 800 字 + 100 字重叠），问题很明显：
- 一句话被切成两半，语义破碎；
- 表格被拦腰截断，列头和数据分离；
- 章节标题和正文分离，向量丢失结构信息。

本项目实现了 `MarkdownStructuredSplitter`（约 500 行），核心策略：

1. **先按 Markdown 结构切，再按长度兜底**
   - 用 `HEADING_RE` 识别标题，构建 `heading_path`（如 `产品手册 > 退款政策 > 时限`）；
   - `section_id` 用 `uuid5(NAMESPACE_URL, f"rag-center:{doc_id}:{version}:{path}")`
     生成——**确定性哈希**，同一文档同一版本永远得到同一个 ID，重建索引不会漂移。

2. **块类型区分**
   - `prose`（正文）：参与向量检索、上下文扩展
   - `table`（表格）：按行数二次切分，每片带表头
   - `list`（列表）：整块保留，避免打散序号
   - `code`（代码块）：不切分（FENCE_RE 保护）
   - `reference_pointer`（引用指针）：**不向量化**，向量填零，只用于建图

3. **上下文拼接**：v2 下 embedding 用 `retrieval_text`（含标题路径），
   返回给用户的是 `content`（纯正文）。

### 4.3 索引重建（Reindex）

切块策略一改，老 chunk 就过时了。项目提供两种重建路径：

| 方式 | 命令 | 适用 |
|---|---|---|
| 整库重建 | `python scripts/reindex_knowledge_base.py --kb-id <id> --wait` | 切块规则变更后 |
| 单篇重建 | `POST /api/v1/documents/{id}/reindex` | 单篇文档更新 |

**整库重建采用「双版本 + 原子切换」**，避免重建期间服务不可用：

```
1. 创建新版本 v_next，状态 = building
2. 分批投递 Celery 任务 index_kb_batch_task
   （每批一批文档，单文档失败不阻塞整批）
3. 全部完成后 → finalize_index_version_task
   ├─ 重建 chunk_relations（图边）
   ├─ 统计 chunk_count
   └─ 状态 building → ready
4. 切换 kb.active_index_version = v_next，旧版本标记 archived
5. 清理旧版本数据
```

这套机制允许「边重建边服务」，且随时可以回滚到旧版本。

### 4.4 失败重试策略

```python
RETRYABLE_ERROR_CODES = {
    API_TIMEOUT, API_REQUEST_ERROR, EMBEDDING_FAILED, SYSTEM_BUSY
}
```

- **可重试错误**（超时、网络抖动、限流）：Celery 任务 `max_retries=2`，退避 10s；
  耗尽后标记文档 FAILED 并记录原因。
- **不可重试错误**（内容为空、解析失败）：直接标记 FAILED，不浪费重试。

## 5. 检索链路（读路径）

### 5.1 三个检索档位（profile）

`app/tenant/retrieve_presets.py` 定义：

| profile | 检索方式 | Rerank | Query 改写 | 目标 |
|---|---|---|---|---|
| `speed` | vector (vector_top_k=10) | ✗ | ✗ | 最快、最低成本 |
| `balanced` | hybrid (vector+bm25 各 10) | ✗ | ✗ | **默认**，性价比 |
| `quality` | hybrid (vector+bm25 各 20) | ✓ (top_n=5) | ✓ | 最高质量 |
| `custom` | 完全自定义 | 自定义 | 自定义 | 高级用户 |

各档位默认 `top_k` 均为 5（`quality` 也是 5，但其候选池更大、经过精排）。

**关键约束**：命名档位（speed/balanced/quality）**不允许覆盖高级参数**。

```python
# app/tenant/retrieve_policy.py
conflicting_fields = [
    field for field in NAMED_PROFILE_OVERRIDE_FIELDS
    if field in request.model_fields_set
]
if conflicting_fields:
    raise AppError(ErrorCode.PARAM_ERROR, msg="命名检索档位不允许覆盖高级参数，请使用 custom")
```

这是一个很成熟的产品化设计：普通用户用预设，行为可预测、性能可保障；
想要精细调优的用户必须显式声明 `profile="custom"`，从而进入另一条校验路径。
这避免了「用户随手传个 top_k=100 把免费套餐打成 DoS」。

### 5.2 双路召回与 RRF 融合

向量和 BM25 是**互补**的：

- 向量检索懂语义（"退钱" ≈ "退款"），但不懂精确术语（错误码、型号）；
- BM25 懂精确词，但不懂同义表达。

`hybrid` 模式并行发起两路请求，用 **RRF（Reciprocal Rank Fusion）** 融合：

```
score(chunk) = Σ  1 / (k + rank_i)      k = 60 (FIXED_RRF_K)
                 i∈{vector, bm25}
```

RRF 的妙处是**只看排名，不看分数**——向量相似度（0~1）和 BM25 分数（0~∞）
量纲完全不同，无法直接加权；RRF 绕开了这个问题。

代码里 `rrf_k` 被强制固定：

```python
# retrieve_policy.py
if retrieval_options.rrf_k is not None:
    logger.warning("RETRIEVE_RRF_K_DEPRECATED | requested_rrf_k=%s | effective_rrf_k=%s", ...)
retrieval_options = retrieval_options.model_copy(update={"rrf_k": FIXED_RRF_K})
```

用户传的 `rrf_k` 会被忽略并打警告——**参数面收窄到经过验证的组合**。

融合排序还有多级 tiebreak：

```python
fused.sort(key=lambda item: (
    -item["score"],                                    # RRF 分
    -int(item["retrieval_source"] == "hybrid"),        # 两路都命中的优先
    min(rank for rank in (vector_rank, bm25_rank) ...), # 更好的排名优先
    kb_id, chunk_id,                                   # 保证确定性
))
```

最后两级 tiebreak 保证**相同输入永远得到相同顺序**——这对离线评测的可复现性至关重要。

### 5.3 多库联合检索

`kb_ids` 数组支持跨库检索，实现上有三层 RRF：

```
第 1 层：每个 KB 内部 vector vs bm25 融合
   ↓
第 2 层：ES 层按 KB 分组，各组内 RRF（_rrf_fuse_hits）
   ↓
第 3 层：Python 层全局 RRF（HybridSearchService.fuse_by_rrf）
```

设计意图是**防止大库霸屏**：如果直接把 5 个库的 100 条命中丢在一起排序，
内容多的库会天然占优。分层融合让每个库先在内部竞争，再进入全局竞争。

ES 侧的实现印证了这一点——它**不全局排序**，而是每个 KB 单独查、单独算 RRF rank：

```python
kb_ids_sorted = sorted(index_versions.items())  # 确定性顺序
kb_results = await asyncio.gather(*[self._search_single_kb(...) for ...])
# 每条 hit 记录 (kb_id, kb_rank_1based, hit)
fused = _rrf_fuse_hits(all_hits, top_k=top_k)
```

### 5.4 降级策略（Degradation）

系统处处设有降级路径，保证**局部故障不导致整体失败**：

| 故障点 | 行为 |
|---|---|
| vector 检索失败 | 若 bm25 成功 → 用 bm25 结果；两者都失败 → `RETRIEVAL_FAILED` |
| bm25 检索失败 | 同上，反向降级 |
| rerank 失败 | **不降级**，抛 `RERANK_FAILED`（见下方说明） |
| 图扩展失败 | 返回原始候选，`metadata.graph_injection.degraded = true` |
| 上下文扩展失败 | 返回原始 chunk，`metadata.context.degraded = true` |
| 证据编排失败 | 返回 `pack=None`，`metadata.evidence.degraded = true` |
| query 改写失败 | 降级为原话检索，`metadata.query_processing.degraded = true` |

**为什么 rerank 不降级？** 代码注释说得很清楚：

```python
# Rerank is a critical part of retrieval quality. Silent fallback
# to unordered candidates previously produced confusingly bad
# answers; surface the failure explicitly with a dedicated code
# so the client (and operators) can react appropriately.
```

这是一个**从事故中总结出的设计**：静默降级到「未排序的候选」比直接报错更危险，
因为用户会拿到看似正常实则质量崩塌的结果。宁可显式失败。

每一步的降级状态都会汇总到 `metadata` 中：

```python
degraded = bool(
    retrieval_metadata.get("degraded")
    or graph_metadata.degraded
    or rerank_metadata.degraded
    or context_metadata.degraded
)
```

### 5.5 检索后的三道精炼

召回只是第一步，候选还要经过三道加工：

#### ① 候选过滤（`retrieval_candidate_filter.py`）

```
reference_pointer  → 丢弃（占位符，不是真实内容）
low_information    → 丢弃（空行、纯分隔线、纯编号、与标题重复）
duplicate_chunk_id → 丢弃
duplicate_content  → 丢弃（归一化后比对）
```

过滤统计会写进 `metadata.candidate_filter`，可以量化「这次过滤掉了多少噪声」。

#### ② 图扩展（`graph_candidate_expansion_service.py`）

以召回的 chunk 为种子，顺着 `chunk_relations` 边和前后邻关系**注入关联候选**：

```
MAX_GRAPH_SEEDS = 10              最多用 10 个种子
MAX_INJECTED_CHUNKS_PER_SEED = 3  每个种子最多注入 3 个
MAX_TOTAL_CANDIDATES = 30         候选池总量上限
```

注入的候选标记 `retrieval_source = "graph_injection"`，
`score = 0.0`（它不是检索命中的，是图扩展来的）——
这个标记很重要，它让后续 rerank 和评测知道这些候选的来源和可信度不同。

**安全边界**：图扩展严格校验 `kb_id` 和 `index_version` 作用域：

```python
if target.kb_id not in allowed_kb_ids or target.index_version != index_version:
    logger.warning("GRAPH_INJECTION_REJECTED | reason=cross_scope_reference | ...")
    continue
```

防止通过引用边跨越租户/知识库/版本边界，造成数据泄漏。

#### ③ 上下文扩展（`context_expansion_service.py`）

命中的 chunk 往往是半句话，需要补上下文：

```
reference       引用指向的正文（最多 3 个）
parent_section  父章节首块（针对「本节」「上述」「其中」这类指代）
previous / next 同章节前后邻块（prose 类型才做）
```

预算控制：

```python
MAX_NEIGHBORS_PER_ANCHOR = 2
MAX_REFERENCE_TARGETS_PER_ANCHOR = 3
MAX_SUPPLEMENTAL_CHUNKS_PER_ANCHOR = 3
MAX_CONTEXT_CHARS_PER_ANCHOR = 4096
```

**「指代词启发式」**是个很细致的细节：

```python
markers = ("本节", "上述", "前述", "以下", "该规则", "其中", "适用范围")
return any(marker in content for marker in markers)
```

只有当 chunk 里出现「本节」「上述」这类**指代词**，且标题层级 ≥3 时，
才去拉父章节——因为只有这种情况才真正需要上文。

### 5.6 Rerank 精排

召回阶段追求「不漏」（高召回率），rerank 负责「排序准」（高精度）。

```python
class Qwen3RerankProvider:
    # 调用百炼 Workspace 的 Qwen3-Rerank 接口
```

- 候选数上限 `max_candidates`；
- `top_n` 截断；
- 超时 `RERANK_TIMEOUT_SECONDS`（默认 15s）。

`llm.py` 里还提供了一个通用的 LLM-as-rerank 实现，
`noop.py` 是关闭状态下的空实现（保持接口一致）。

### 5.7 证据编排（Evidence Orchestration）

这是 `pro` 套餐的进阶功能：**LLM 不回答问题，只负责「挑证据」**。

系统提示词的核心约束：

```
你是 RAG 证据编排器，不负责回答问题。
1. 将用户问题拆成回答时必须覆盖的最少要点。
2. 只从给定 candidates 中选择能够支撑这些要点的证据。
3. core 表示直接回答要点，supporting 表示提供必要条件、范围或补充说明。
4. 不要因为主题相似就选择候选，不要选择重复证据。
5. 每个必要要点都必须输出；没有核心证据时返回空 evidence 数组。
6. 同一候选可以支撑多个要点。
7. 不生成答案，不改写证据，不输出候选中不存在的事实。
```

输出严格 JSON：

```json
{"aspects": [{"aspect": "退款时限", "evidence": [{"index": 0, "role": "core"}]}]}
```

模型输出经过**严格校验**（`_validate_model_output`）：
- aspect 不能为空、不能重复、长度 ≤100；
- index 必须在候选范围内、同一 aspect 内不能重复；
- role 必须是 `core` 或 `supporting`；
- 选中总数不能超过 `max_items`；
- 任何违规 → 抛异常 → 被捕获 → 标记 degraded。

**为什么校验这么严？** 因为 LLM 幻觉出的 index 会指向不存在的证据，
在 RAG 里这比「少几条证据」危险得多。

候选池构建也有讲究（`build_candidates`）：
- 优先取 Top-K 命中 + 上下文扩展出来的内容；
- **保留至少 6 个基础候选**（`MIN_BASE_POOL_CANDIDATES`），
  防止上下文把真正的答案挤掉；
- 总数上限 20（`MAX_EVIDENCE_CANDIDATES`）。

## 6. Research 深度研究链路

### 6.1 与普通 retrieve 的区别

普通 `retrieve` 是「一问一答一搜」；`research` 是**有状态的多轮自主研究**，
目标是处理需要多角度、多跳、甚至需要先确认前提才能回答的复杂问题。

| 维度 | retrieve | research |
|---|---|---|
| 查询数 | 1 | Planner 生成 N 个（最多 4） |
| 轮次 | 1 | 最多 3 轮（premise + answer + supplement） |
| 检索并行度 | 1 | N 路并发（信号量限流，首轮最多 3 条查询） |
| 证据充分性判断 | ✗ | ✓（Decider） |
| 补检索 | ✗ | ✓（Supplement） |
| 是否生成答案 | ✗ | ✓（Finalizer，用强模型） |
| 模型分工 | 单模型 | fast 做规划/判断，strong 做生成 |
| 执行方式 | 同步 | **异步 Celery** + 轮询 |

### 6.2 Planner → Retrieve → Decider → Supplement → Finalizer

```
                        ┌──────────────┐
                        │   Planner    │  fast 模型
                        │  拆解问题     │
                        │  识别问题类型 │
                        └──────┬───────┘
                               ↓ aspects[] + queries[]
                    ┌──────────┴──────────┐
                    │  problem_type?      │
                    └──┬──────────────┬───┘
              dependent│              │non-dependent
                       ↓              ↓
              ┌────────────────┐  ┌──────────────┐
              │ Premise Round  │  │ Initial Round│
              │  只发前提类查询 │  │  一次覆盖全部 │
              └────────┬───────┘  └──────┬───────┘
                       ↓                 ↓
              ┌────────────────┐  ┌──────────────┐
              │  Decider 判断   │  │  Decider     │
              │  前提是否确认   │  │  证据够不够   │
              └────────┬───────┘  └──────┬───────┘
                 确认 │                   │ 缺证据
                       ↓                   ↓
              ┌────────────────┐  ┌──────────────┐
              │  Answer Round  │  │  Supplement  │ 生成补充查询
              │  依赖前提的值   │  │  再检索一轮    │
              └────────┬───────┘  └──────┬───────┘
                       └────────┬────────┘
                                ↓
                        ┌──────────────┐
                        │  Finalizer   │  strong 模型
                        │  生成答案     │
                        │  附证据包     │
                        └──────────────┘
```

### 6.3 两类问题：dependent vs non-dependent

这是 Research 设计中最精妙的部分。

**non-dependent（独立型）**：问题的各个子问题互不依赖，可以一次并行检索。

例：「公司的年假政策是什么？报销标准是多少？」→ 两个子问题同时搜。

**dependent（依赖型）**：后一个子问题需要前一个的**答案作为输入**。

例：「我们公司员工跳槽，竞业限制补偿怎么算？」
- 前提（premise）：员工签的是什么协议、竞业限制期限多长？
- 答案（answer）：**基于前提的值**去算补偿。

如果直接并行发两个查询，answer 查询会因为不知道前提而检索不到。
所以 dependent 流程**必须两阶段串行**：

```python
# Stage 1: 只发 premise 查询
premise_result = await self._run_premise_round(...)
decider_result = premise_result["decider"]

# Stage 2: 前提全部确认后，才发 answer 查询
if self._all_premises_confirmed(decider_result, state):
    answer_round = await self._run_answer_round(...)
    # 合并所有结果，重新融合，再跑一次 Decider
    final_fusion = self.fusion.fuse(results=all_results, aspects=state.aspects)
    decider_result = await self.decider.decide(state=state, candidates=final_fusion.candidates)
```

`_all_premises_confirmed` 的判定很明确：

```python
for aspect in state.aspects:
    if aspect.aspect_id not in premise_aspect_ids:
        continue
    references = decider_result.selections.get(aspect.aspect_id, [])
    if not any(ref.role == "core" for ref in references):
        return False
```

**每个前提要点都必须有至少一条 `core` 级别的证据**，才算确认。

### 6.4 Decider：证据够不够

Decider 用 fast 模型做两件事：
1. 把候选证据映射到各个 aspect（core / supporting）；
2. 判断还有哪些 aspect **缺核心证据**，并生成补充查询。

`stop_reason` 完整记录了研究为什么停下：

| stop_reason | 含义 |
|---|---|
| `evidence_complete` | 证据已充分 |
| `max_rounds` | 轮次用尽 |
| `timeout` | 超时 |
| `budget_exhausted` | LLM 调用预算耗尽 |
| `duplicate_query` | 补充查询与已有重复 |
| `degraded` | 某环节降级 |

### 6.5 预算与熔断

```python
MAX_RESEARCH_ROUNDS = 3
MAX_RESEARCH_LLM_CALLS = 3
DEFAULT_RESEARCH_TIMEOUT_SECONDS = 90
MAX_INITIAL_QUERIES = 3
MAX_SUPPLEMENT_QUERIES = 2
```

`MAX_RESEARCH_ROUNDS = 3` 的注释说明了它的由来：

```python
# Bumped from 2 to 3 to allow the two-stage dependent flow:
#   round 1 = premise retrieval
#   round 2 = answer retrieval (using confirmed premise values)
#   round 3 = supplement if answer is still missing
```

每次 LLM 调用前都要「预约」：

```python
@staticmethod
def _reserve_llm_call(state: ResearchState) -> None:
    if state.llm_call_count >= MAX_RESEARCH_LLM_CALLS:
        state.stop_reason = "budget_exhausted"
        raise RuntimeError("research LLM call budget exhausted")
    state.llm_call_count += 1
```

这保证 Research **不会因为 LLM 抽风而无限循环烧钱**。

### 6.6 并行检索

```python
semaphore = asyncio.Semaphore(limit)
raw_results = await asyncio.gather(
    *(run_query(query) for query in selected),
    return_exceptions=True,   # ★ 单个查询失败不拖垮整轮
)
```

`return_exceptions=True` 是关键：某个查询失败只标记该 task 为 degraded，
其余查询的结果照常使用。整轮全失败才抛 `RETRIEVAL_FAILED`。

### 6.7 异步执行

```
POST /rag/research  →  创建 research_tasks 记录（status=PENDING）
                    →  投递 Celery 任务
                    →  立即返回 research_id

GET /rag/research/{id}
   ├─ PENDING/RUNNING → { research_id, status, progress }
   ├─ COMPLETED       → 完整 ResearchData
   └─ FAILED          → RESEARCH_FAILED
```

结果以 JSON 存在 `research_tasks.result` 列里。

### 6.8 关键设计：复用同一套检索内核

Research 没有重写检索逻辑，而是复用了 `RetrieveOnceService`：

```python
# retrieve_once_service.py
class RetrieveOnceService:
    """Runs one deterministic retrieval pass without policy, quota, logs, or evidence LLMs."""
```

这个类的设计意图非常清晰——**把「纯检索」和「策略/配额/日志/证据 LLM」解耦**：
- `retrieve` 用它：外面套上套餐策略、限流、可观测、证据编排；
- `research` 用它：外面套上多轮编排、Decider、Finalizer。

好处是**一处修改，两处生效**，且 Research 的每条查询都享受
rerank、图扩展、上下文扩展等全部精炼能力。

### 7.3 鉴权与隔离

```python
# app/core/auth.py

    ...
    if problems:
        raise RuntimeError("production config validation failed: " + "; ".join(problems))
```

**宁可启动失败，也不要带着 `your-api-key` 上生产。**

### 7.4 限流与配额

`rate_limit_service.py` 用 Redis Lua 脚本保证原子性：

```lua
-- QPS 计数
local count = redis.call('INCR', KEYS[1])
if count == 1 then redis.call('EXPIRE', KEYS[1], tonumber(ARGV[2])) end
return count
```

```lua
-- 日配额：超限不递增（避免计数变负）
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
if current >= tonumber(ARGV[1]) then return -1 end
local count = redis.call('INCR', KEYS[1])
if count == 1 then redis.call('EXPIRE', KEYS[1], tonumber(ARGV[2])) end
return count
```

**为什么用 Lua 而不是 `INCR` + `EXPIRE` 两条命令？**
因为 `INCR` 和 `EXPIRE` 之间可能被其他请求插入，导致 key 永不过期。
Lua 脚本在 Redis 中原子执行，无竞态。

同时注释指出了一个易错点：

```python
# The atomic increment in the daily check IS the success counter:
# callers no longer need a separate ``record_retrieve_success`` step.
# Doing both would double-count every quota and let users
# hit their daily limit in half the expected time.
```

## 8. Provider 抽象层

### 8.1 设计动机

所有外部依赖都藏在 `providers/` 下，业务代码只依赖 `base.py` 定义的协议：

```python
app/providers/
├── embedding/base.py          EmbeddingProvider
├── llm/base.py                LLMProvider
├── rerank/base.py             RerankProvider
├── vectorstores/base.py       VectorStore
├── keyword_search/base.py     KeywordSearchProvider
├── parsers/base.py            DocumentParser
└── query/base.py              QueryProcessor
```

好处：
- 换向量库（Milvus / Qdrant）只需实现 `VectorStore`，Service 层不动；
- 关闭 rerank 用 `NoopRerankProvider`，接口一致，无需 `if enabled` 分支；
- 测试可注入 mock provider。

### 8.2 HTTP 连接池管理

```python
# app/core/http_clients.py
clients = build_external_http_clients()   # lifespan 中创建，关闭时 aclose()
app.state.external_http_clients = clients
```

统一的 `httpx.AsyncClient` 池，带 keep-alive 配置：

```python
external_http_max_connections = 100
external_http_max_keepalive_connections = 20
external_http_keepalive_expiry_seconds = 30.0
```

避免每次请求新建 TCP 连接 + TLS 握手——在高 QPS 下这是巨大的性能损耗。

### 8.3 模型角色路由

```python
class LLMRole(StrEnum):
    FAST = "fast"
    STRONG = "strong"

class LLMRoleRouter:
    @staticmethod
    def model_for(role: LLMRole) -> str:
        if role == LLMRole.STRONG:
            return settings.llm_strong_model or settings.llm_model
        return settings.llm_model
```

**快模型做判断，慢模型做生成**——这是成本与质量的关键权衡：
- Planner（拆解）、Decider（判断）用 fast（便宜快）；
- Finalizer（写答案）用 strong（贵但准）。

### 8.4 Query 处理管线

```python
# app/providers/query/pipeline.py
base_result = await rewrite_processor.process(raw_query, kb=kb)   # LLM 改写（可选）
expand_result = expand_synonyms(base_result.effective_query, kb.settings)  # 词表扩展
search_query = expand_result.search_query
```

两个阶段**互补**：

| 阶段 | 手段 | 成本 | 解决什么 |
|---|---|---|---|
| LLM 改写 | fast 模型生成新查询 | 一次 LLM 调用 | 口语化提问 → 正式术语 |
| 词表扩展 | 知识库配置的同义词表 | **零成本** | 业务缩写 → 全称 |

同义词表按知识库维护（`settings.synonyms`），在检索前把业务术语补进 query，
不走 LLM、不消耗额外额度。示例配置见 `examples/kb_settings.example.json`。

## 12. 设计亮点与工程约定

### 12.1 值得学习的十个设计

**① 策略与执行分离：`RetrieveOnceService`**

把「纯检索」从「带策略的检索」中剥离，让普通检索和 Research 复用同一内核。
好设计的最大价值不是代码量，而是**消除重复**。

**② 命名档位禁止覆盖参数**

`profile=balanced` + `top_k=100` 直接报错。要精细调优必须显式 `profile=custom`。
用「显式声明」换取「可预测的性能」和「计费安全」。

**③ RRF 固定 k 值**

用户传的 `rrf_k` 被忽略并打警告。**参数面收窄到经过验证的组合**，
减少调参空间，也减少「调出一个没人测过的组合」的风险。

**④ 全链路降级 + 显式降级标记**

每一步都有降级路径，且降级状态汇总到 `metadata`。
「悄悄变差」是最难排查的问题，这个设计让降级**可观测**。

**⑤ rerank 失败不降级**

从事故中总结的决策：静默返回无序候选比显式报错更危险。

**⑥ dependent 两阶段研究流程**

识别出「后一个问题依赖前一个问题的答案」这类问题，
用 premise → 确认 → answer 的串行流程解决，而不是硬并行。

**⑦ 结构化分块 + 稳定 section_id**

`uuid5` 哈希保证重建索引时 section_id 不漂移；
`retrieval_text` / `content` 分离兼顾「机器检索」和「人读体验」。

**⑧ 渐进式索引版本迁移**

`v1` / `v2` 双版本共存，新功能全部用 `index_version != LEGACY` 守卫，
支持「老库不破坏 + 新库享受新特性 + 随时回滚」。

**⑨ Lua 脚本做原子限流**

避免 `INCR`/`EXPIRE` 竞态；日配额超限不递增，防止计数变负。

**⑩ 评测数据飞轮**

线上低分反馈 → 导出为评测集 → 离线回归 → 改配置 → 再回归。
让「调参」从玄学变成工程。

### 12.2 错误码体系

`app/core/exceptions.py` 定义了分段错误码：

| 段位 | 类别 | 示例 |
|---|---|---|
| 20000-29999 | API / 请求 | 20001 参数错误、20013 套餐不支持、20014 配额耗尽 |
| 30000-39999 | 数据库 / 存储 | 30003 索引失败、30005 关键词检索异常 |
| 40000-49999 | LLM | 40007 向量调用失败、40009 重排失败 |
| 50000-59999 | 系统 / 服务 | 50001 系统繁忙、50002 检索异常、50003 Research 失败 |

全局异常处理器保证**任何异常都返回统一格式**：

```json
{"code": 0, "msg": "success", "data": {...}}
```

`AppError` 还支持 `context` 字段（仅进日志，不进响应），
既方便排查，又不泄漏内部细节。

### 12.3 统一响应格式

```python
# app/schemas/common.py
def success_response(data): return {"code": 0, "msg": "success", "data": data}
def error_response(code, msg, data=None): return {"code": code, "msg": msg, "data": data}
```

注意：**业务错误也返回 HTTP 200**，错误信息在 body 的 `code` 里。
这是很多国内 B 端 API 的惯例，客户端只需判断 `code == 0`。

## 13. 已知局限与改进方向

### 13.1 文档中已明确的

| 问题 | 说明 |
|---|---|
| 无 `/health` 路由 | 探活只能用 `GET /docs` |
| Ollama MRL 截断慢 | 带 `dimensions=1536` 的 embedding 单条约 9.5s，裸调只要 0.16s |
| ES 索引无向量字段 | `rag_chunks` 只存文本做 BM25，向量在 pgvector |
| 前端 bundle 587 kB | 超过 Vite 500 kB 警告阈值，可 code-splitting |

### 13.2 从代码中观察到的

**① 同步 Session 跑异步路由**

`get_db` 提供同步 `Session`，而路由是 `async def`，Service 内部又在跑 `asyncio.gather`。
这意味着**向量/BM25 的数据库查询会阻塞事件循环**。当前规模下没问题，
但 QPS 上来后是首要瓶颈。解法是改用 `AsyncSession` + `asyncio.to_thread`。

**② 索引版本未在检索层完全隔离**

`pgvector.similarity_search_scope` 用 `(kb_id, index_version)` 组合条件过滤，
但 `chunk_relations` 的查询在部分路径下只带 `kb_id`。
虽然代码里有 `allowed_kb_ids` 校验，但缺少强制的 `index_version` 约束——
跨版本串数据的风险存在。

**③ 文档内容存储在明文列**

`documents.content` 明文存全文（只有上传的**源文件**走 Fernet 加密）。
加密的是「文件」不是「解析后的文本」，严格说加密覆盖不完整。

**④ 缺少真正的分页**

检索接口的 `top_k` 上限 50，知识库列表也没有分页。
数据量上来后列表接口会成为瓶颈。

**⑤ Research 的状态机不够通用**

`dependent` / `non-dependent` 是硬编码的二分。
真实问题中还有「三分之依赖」（A→B→C）、「多前提并行」等形态。
现有设计通过 `MAX_RESEARCH_ROUNDS=2` 兜住了复杂度，但表达力有限。

**⑥ 评测框架偏重**

`scripts/compare_agentic_research.py` 有 86,797 字节（约 2100 行），
`eval/core` 3916 行。评测代码本身需要维护，
可以考虑把核心指标计算收敛成一个更小的包。

**⑦ 缺少真正的集成测试**

`tests/` 目录内容有限，主要靠 `scripts/verify_*.py` 手动验证脚本。
异步 Celery 链路、并发检索、限流边界都缺乏自动化回归。

### 13.3 演进建议（优先级排序）

1. **异步化数据库层**——当前最硬的瓶颈，且影响所有链路；
2. **补齐集成测试**——尤其是 Celery 任务链和限流边界；
3. **统一 index_version 约束**——把版本号变成 Repository 层的强制参数；
4. **检索接口加游标分页**——为大数据量做准备；
5. **拆分大脚本**——`compare_agentic_research.py` 等应下沉到 `eval/` 包内；
6. **Research 状态机可配置化**——用声明式描述而非硬编码 if/else。
